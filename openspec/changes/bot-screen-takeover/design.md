# Design

## Context

Server rules (Hermes `tools/bot_desktop/lease.py`, `tui_gateway/methods_display.py`, `hermes_cli/web_routers/display.py`):

- `display.observe` mints viewer ids per gateway connection; it honours a requested id only when that connection minted it. Acquire and release refuse an id the calling connection did not mint (5300, `data.code: "viewer_mismatch"`).
- Acquire always succeeds for a minted id ("last writer wins") and answers `{lease}`; release with a foreign holder is ignored and answers the real lease; `release {force: true}` with no viewer id releases whoever holds.
- The bridge releases the lease when the holder's socket closes with 1000 or 1001. Any other close keeps the person's exclusion. A holder that loses control to another person is closed with 4000.
- `computer_use` raises `HumanHasControl` while a person holds the lease; the agent's step ends with that error and the agent tells the user what it needs.
- Thumbnails are suppressed while a person holds control. RFB watchers are not: Hermes Desktop's live viewers still see the screen.

`bot-screen-live-view` gives `BotScreenViewerController` (observe, stream, close-code table, pause) and the viewer chrome; `bot-screen-rfb-input` gives the client's input methods, `KeysymMapper`, `ScreenGeometry` and `ScreenGestureLayer` (disabled by default). `bot-screen-status` gives `GatewayRpcException.dataCode`. `HermesGatewayTransport.request` always goes over the current connection (`_client()`) and opens a new one when needed; `GatewayConnectionTransport.gatewayConnection` names the current connection. `AppLockController.covered` is true while locked and while the app is inactive (the iOS notification shade, Control Center, the app switcher). The Mac menu bar owns ⌘Q, ⌘W, ⌘H and ⌘M and only sees keys no Flutter widget handled. `accountKeyFor(baseUrl, session)` lives in `lib/src/auth/account_key.dart`.

## Decisions

- **Pinned requests.** `HermesGatewayTransport.requestOn(Object connection, method, params, {timeout})` sends on that connection or throws `GatewayConnectionClosed` without opening another. It and `requestKeepingConnectionOnClient` (which answers with the connection that carried the call) are on `GatewayRequester`, so the app's gateway transport (`HermesGatewayTransport`, which `ChatScreen` reads through the `SessionChatTransport` that forwards both) offers them. `observe` goes through the latter, so `BotScreenObservation.connection` is read in the same microtask the answer completes. `acquire`/`release` use `requestOn` with that connection (a repository without one fails them as closed rather than sending them unpinned). On `GatewayConnectionClosed` or `viewer_mismatch` the controller observes again (new connection, new id) and retries once, logging `outcome: retried`; a second failure is `refused`.
- **Viewer ids.** `BotScreenViewerIds` (one per app session, held by `ChatScreen` next to the controllers) keeps every viewer id minted in this run, their 12-hex hashes and the latest id, which the next observe asks for (the server honours it on the connection that minted it, so a second viewer opened in the same run keeps the same id). "This device holds control" means `holder: human` and `viewer_hash` is one of them. `BotScreenController` (`inControlHere`, `someoneElseInControl`) and the viewer read it; nothing persists it.
- **Hand back across a changed connection.** A release goes over the pinned connection. When that connection is gone (or the server does not know the id, or no answer comes), a viewer with a stream open closes it with 1000, which the bridge takes as the holder's release, reads the status and opens a new stream as a watcher; it does not observe again and take the lease with a new id, because the bridge answers a new holder by closing the old holder's stream with 4000, which would read as lost control. A viewer with no stream observes again (taking the lease over with the new id first, as on any reconnect) and releases. While shutting down the close counts as the hand back without waiting for an answer, since the gateway may be going away too. A forced release is only ever behind the user's confirmation.
- **Stream and lease ids.** `inControl` means the lease names the open stream's own id: the server accepts input only on that stream. A take over whose retry observed a new id reopens the stream with it whatever the acquire answers. The silent re-acquire after a reconnect runs only for a viewer with no stream open and never once shutting down (an acquire still in flight then is released when it answers).
- **Lease state.** `BotScreenControl { watching, acquiring, inControl, lost }`; the question before taking over is state of the widget that asks it, not of the controller. It moves to `inControl` from the acquire answer's lease (hash match), not only from a broadcast, and to `watching` from the release answer. A broadcast or status naming another holder, or Hermes, while `inControl` moves to `lost` and logs `bot_screen.lost_control` (`other_holder`); a 4000 close does the same with `control_taken`, and whichever comes first logs, once. `lost` reads "Someone else took control" and reconnects as a watcher (live-view's table). It lasts until the user dismisses it, takes over again, or the lease turns out to be this device's under the current id.
- **Lifecycle.** While `inControl`:
  - not resumed (background, a hidden Mac window) → close with 4100 at once; the lease stays;
  - covered (App Lock or inactive) → wait 2 s, then close with 4100 if still covered; uncovered within 2 s → keep the stream (the App Lock cover hides the picture meanwhile);
  - return → observe passing the current viewer id (the same connection honours it); if the server minted a new id and the lease hash names an earlier id this app holds, acquire with the new id without asking;
  - sign-out, profile switch, Change Server → `release` (pinned), then close with 1000, before the owner disposes the controller (`shutDown(reason)`, which the owner calls in place of `dispose`); the release has a 2 s budget and the close happens regardless. The reason (`sign_out`, `server`, `profile`, `close`) is told by `ChatScreen`: the viewer is closed with the profile switch's reason, and when the chat screen itself is disposed with the auth state's (`needsServerUrl` is Change Server, `ready` an app that is ending, else sign-out). A `dispose` that still holds control sends the release itself, so no caller can leave a lease behind.
    While watching, every pause closes with 1000 as in live-view.
  - `AppLockController.covered` is true only while locked, or inactive on a phone with App Lock on, and `ChatScreen` gave the viewer `foreground = false` for any inactive phone state, which cannot be debounced. So the viewer's gates are set apart from the card's: `foreground` is false only once the app is paused, hidden or detached (or the chat is not visible, or a Mac has no window), and `unlocked` is false while the lock covers the app or a phone is inactive. A watching viewer therefore closes at once on either, as before; one in control waits the grace period for `unlocked` alone.
- **Closing the viewer** while `inControl` (Close button, ⌘. or F8) calls release first, then closes with 1000; either alone releases, both make the hand-back explicit and logged (`reason: close`).
- **Force hand back.** When `holder: human` and the hash matches no held id, the card and the viewer keep saying "Someone else is in control", which they said already, and add **Hand back to Hermes**. A confirmation (`ForceHandBackDialog`: "Hand control back to Hermes? Whoever is using the screen loses control, which may be you on another device or before the app restarted.") then sends `display.lease.release {profile, force: true}` with no viewer id (the server refuses a foreign id; force with no id releases any holder).
- **Confirmation.** `TakeoverConfirmation` (the app's `showAdaptiveSheet`: a bottom sheet on iOS and Android phones, a dialog on a Mac and wide windows; one widget, not an iOS action sheet, so "Don't ask again" is an adaptive switch (`SwitchListTile.adaptive`) on every platform, left out when there is no account key to remember it under) with the corrected text, stored as `bot_screen.takeover.skip_confirm.<accountKeyFor(server, session)>` (bool) in shared preferences.
- **Input wiring.** `BotScreenViewerController.input` is a `ScreenInput` (the stream's client behind a counting sink, a `ScreenKeyboard`, a `ScreenPaste`) while `inControl` and the stream is open; it is dropped with the stream, which first releases held keys and clears the screen's clipboard. `ScreenGestureLayer(enabled: true, mode: touch|trackpad)` over the picture, sinking into it, mapping through the `TransformationController` the viewer owns; the trackpad cursor sits inside the picture's box, so it zooms with it. Hardware keys: a `Focus` with `onKeyEvent` around the viewer, calling `ScreenKeyboard.handle`, which does nothing while `input` is null. Routing on desktop:
  - macOS (and iPadOS, whose Command key is the same): ⌘V → Paste action; ⌘Q, ⌘W, ⌘H, ⌘M, ⌘Tab and ⌘` (window cycling) → `KeyEventResult.ignored` so the menu bar and the system get them; ⌘. → close the viewer; other ⌘ chords → Control around the key, so ⌘A is Ctrl+A (not `KeysymMapper(commandAsControl: true)`, which would send Control down as soon as ⌘ is pressed and leave it stuck when the chord is ⌘Tab or ⌘Q; the Command key itself is never sent, and each chord carries its own Control press and release); Escape → the screen.
  - Windows and Linux: Ctrl+V → Paste action; F8 → close the viewer (TigerVNC's own viewer reserves F8 the same way) and the toolbar's Send F8 sends it; Alt+Tab, Alt+F4 and Super chords are ignored (the system takes them); everything else, Escape included, goes to the screen.
  - No `MacCommandScope` is needed: the menu bar sees a key only when no Flutter widget handled it, and the focus handler handles ⌘C, ⌘X and ⌘A.
  - Keys and pointer buttons held when the focus leaves, the window goes inactive (Alt+Tab on a computer keeps the app in the foreground), the stream closes or control ends are released (`releaseAll`), since their key-up would never arrive; the input is also disposed, and its clipboard cleared, while the lease is still held, before a hand back or a close, because the bridge drops input from a stream that does not hold it; a repeating key is pressed again, and a held Paste or close chord does not act twice.
  - The mouse wheel: the viewer's `InteractiveViewer` gets `scaleEnabled: false` while in control on a computer, so the wheel scrolls the screen and never zooms the picture (and a trackpad pinch no longer zooms there); on a touch device `scaleEnabled` stays on for the two-finger pinch, since no wheel exists there and the layer claims it anyway.
- **On-screen keyboard.** Not a `TextField`: `SoftKeyboard` is a `DeltaTextInputClient` attached by the key bar's keyboard key, with `autocorrect: false`, `enableSuggestions: false`, `enableIMEPersonalizedLearning: false`, `smartQuotesType: SmartQuotesType.disabled`, `smartDashesType: SmartDashesType.disabled`, `keyboardType: TextInputType.visiblePassword`, no capitalization and no autofill. On iOS that is an ASCII-capable keyboard, so the soft keyboard types no ä or é; Paste covers them (Latin-1 text pastes). The key bar's keyboard key shows the keyboard unless it is on screen (`MediaQuery.viewInsetsOf`), so a keyboard the person dismissed with the system's key comes back, and the bar follows a connection the system closed. An insertion outside a composing range becomes press/release per character (a newline Return), a deletion BackSpace; a composing range is held and sent when it commits. After each keystroke the field is reset to one zero-width space with the caret after it, so no typed text accumulates and a backspace always has something to delete (an empty field sends no deletion on every platform); a keyboard that reports whole values instead of deltas is compared with what the field held. The keyboard closes with the stream's input and is opened again by the key bar.
- **Paste.** Read `Clipboard.getData(text/plain)` (iOS may show its paste permission prompt), `cutText` it (a `RfbClipboardError` shows "This text can't be pasted to the screen." under the header and logs `bot_screen.paste_refused` with its reason), press and release Control_L+v, then after 500 ms send `cutText('')` so the secret does not remain on the remote clipboard, or at once if the stream is about to close.
- **Key bar** (touch, while in control): keyboard, Esc, Tab, Ctrl and Alt (latched for the next key), ←, →, Paste, then the Touch/Trackpad switch, in a row that scrolls sideways when it does not fit (the keys that type come first). On a computer a tools row under the header holds Paste and, on Windows and Linux, Send F8; Hand Back is in the header on every platform and the Touch/Trackpad switch does not exist there (a mouse is absolute and the wheel is the screen's).
- **Catalog and design system.** Viewer states: watching with Take over, in control (touch with key bar, desktop with tools row) and the question (`TakeoverConfirmation`, its own component), trackpad with cursor, lost control, someone in control with Hand back to Hermes, force confirmation. `design/web` `BotScreenViewer` gains the same states; `BotScreenCard` gains "You're in control" and the force action.

Platforms: iOS, Android, macOS, Windows, Linux. No native, entitlement, manifest or Xcode change; the soft keyboard uses the standard text input client.

Invariants touched:

- Telemetry: `bot_screen.takeover`, `bot_screen.handback`, `bot_screen.lost_control` and `bot_screen.paste_refused` from the viewer controller through `AppEventLogger`; `took_over` and `input_events` (bucketed `0`, `1-10`, `11-100`, `>100`) on `bot_screen.stream`; breadcrumbs `bot_screen.takeover.pressed`, `.handback.pressed`, `.force_handback.pressed`, `bot_screen.input.mode` in the chrome. None holds text, key names, coordinates, viewer ids or profile names.
- Storage: one boolean per account in shared preferences; no secret.

## Risks / Trade-offs

- [A user who leaves the app in control leaves Hermes waiting] → By design (the server does the same for Hermes Desktop); the card says "You're in control" on return, and force hand back frees a lease the app lost track of.
- [Force hand back can evict a real person on another device] → Behind a confirmation that says so.
- [F8 on Windows and Linux shadows a key the remote may want] → Send F8 in the toolbar.
- [Two of the user's devices] → Each has its own viewer id; the second take over evicts the first, which says someone else took control.
