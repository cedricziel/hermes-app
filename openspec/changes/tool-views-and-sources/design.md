# Design

## Server surface

Read from the Hermes source at `d923a5eb` (the revision in `openapi/HERMES_REF` and `openrpc/HERMES_REF`), `tools/*.py`. No live backend was run for this pass, so every shape below is what the code builds, not a recorded answer. `test/real_backend_contract_test.dart` scripts `read_file` and `write_file` calls but records no result body for any tool named here, and no case runs a browser, image or `search_files` call. Each slice below starts by recording the shapes it uses (task 0.1).

A call's `result` reaches the app as the tool row's `content` text. From history `ToolCall.resultData` holds it when it decodes as a JSON object or list, and is null otherwise. Live, the gateway's `result` is stored as it arrives, so a JSON text may reach a view as a string: every parser here takes `resultData` and, when that is not a map or list, decodes `result` itself. `tool_error(message, **extra)` answers `{"error": "<bounded text>", ...extra}`.

The boolean flags of `read_file` (`truncated`, `is_binary`, `is_image`, `not_found`) are always sent, `false` when unset (`ReadResult.to_dict` drops only `None` and empty lists), so every parser reads them as **true**, never as present: a normal read carries all four as `false`. Keys that default to `None` (`truncated_by`, `next_offset`, `truncated_lines`, `extracted_document`, `hint`, `error`, `similar_files`) are absent when unset.

Unknown at this revision, to be recorded against a live backend in task 0.1: the result of `read_file` when its content is over the spill limit (the app would get a `<persisted-output>` text, not JSON, and falls back); whether `write_file` calls carry a rendered diff live (the diff entry comes first in the registry, so a call that has one keeps the diff body); the error keys of `browser_navigate` failures; whether a server path from `image_generate` is servable by `/api/media` or `/api/files/download` (the shape itself is settled: it can be one); the result of `vision_analyze`; whether `browser_vision`'s `screenshot_path` is servable by `/api/media` or `/api/files/download`.

Where the data comes from after a reload: a history row's `tool_calls` plus the `tool` rows whose `tool_call_id` answers them (`HermesChatRepository._toolCalls`), so every shape above is the same live and from history. **A turn from history is several assistant messages** (one per row that carries tool calls, each with empty text, then the row with the text), where a live turn is one message. The sources row therefore collects over the turn, from the last user message to the reply, not over one message.

## What the app has

- `ToolBodyRegistry` and `ToolBodyEntry` (`lib/src/chat/widgets/tool_body_registry.dart`): names, a predicate, a builder that returns null for a shape it does not know; a predicate or builder that throws is skipped. `standardToolBodyEntries` (`tool_call_bodies.dart`) lists the diff, `message_agent`, `terminal`, `web_search`, `todo` and `memory` entries. The card shows a registry body in place of its generic input and result and keeps "Raw arguments" under it.
- `ToolBodyFrame`: the body's rule above, padding, a 220 px height cap that scrolls.
- `ToolValueView` / `ToolValuePanel` (`tool_value_view.dart`): coloured text as sent, the label row, Copy, the hidden-character rule. The code view reuses them; it adds the gutter and the path header.
- `toolValueLanguage` (`tool_value_language.dart`): the language from the extension of a `path` argument. The Files palette (`--h-code-*`, `HermesCodeColors`).
- `WebSearchToolBody` parses `{url, title, description}` from `data.web`; the sources row reuses that parse.
- `MediaStore` and `ImageViewerPage`, Quick Look: the authenticated download of a server path (the `MEDIA:` route) and the zoom viewer. Quick Look takes a staged file, which is why a remote image does not use it.
- `launchUrl(uri, mode: LaunchMode.externalApplication)`: how every other external link opens.
- `wellFormedText`, `tool_hidden_chars.dart`: untrusted text.

## Decisions

### Code view (`read_file`, `write_file`)

- **Header.** The path, elided at its start (the file name stays), the language as a muted tag (`toolValueLanguage`; none for an unknown extension, which draws plain), Copy at the right (44 pt iOS, 48 dp Android, 28 pt Mac). Below the code, a meta line: "Lines 1–9 of 400" from `offset` and `total_lines`.
- **Gutter.** `read_file` content is parsed row by row against `^\s*(\d+)\|(.*)$`. The numbers become a non-selectable gutter and the text after the bar is the code. If any row fails the pattern the whole result is "not the expected shape" and the card falls back; nothing is guessed. The numbers are the file's own, so a read at offset 2001 starts at 2001. Each source line is one row: a wrapped line keeps its number on its first visual row (text wraps in place, no horizontal scroll, as in Files). The canvas draws the gutter as one column, so a wrapped line misaligns there; the widget builds one row per line.
- **Copy copies the text Hermes returned**, without the numbers, line by line. This is the one place the "text as sent" rule bends: the bar and numbers are Hermes' framing, not the file. A line Hermes cut at 2,000 characters (`... [truncated]`, `truncated_lines: true`) is copied as returned, cut, and the view says so in a note, "Some long lines were cut by Hermes.", so Copy never claims to be the file. `write_file` has no gutter problem: its `content` argument is the file.
- **Documents.** For .pdf, .docx, .xlsx, .pptx, .ipynb, .sqlite and similar files Hermes reads text out of the document and returns it in the same numbered rows with `extracted_document: true`. The view says so under the code, "Text taken from the document.", draws it plain (the extension names the document type, not a language), and Copy copies the extracted text, not the file.
- **Hermes masks secrets in what it returns.** `read_file` and `search_files` pass text through `redact_sensitive_text(file_read=True)`, which replaces credentials with `«redacted:…»`, `«redacted-secret»` or `«redacted-vault-secret»` (and `***` in some fields), and the result carries no flag that it did. The view can only see the markers: when the content holds `«redacted`, a note says "Hermes may have hidden passwords or keys in this text.", and Copy copies it as returned, masked. A bare `***` is not treated as a sign, since it is common in text.
- **`write_file` shows the content as sent** with a gutter from 1, coloured by the extension of `path`. Hermes' `tool.generating` event carries only the tool's name and the arguments arrive whole with `tool.start`, so a preparing card has no path or content: the header says "Preparing…" and nothing else. When the call runs, the path and the content show at once, coloured, under "Writing…", and the outcome notes join when the result arrives.
- **Outcome notes** sit under the code, each an icon and a word, never colour alone: "Wrote 312 bytes. Checked on disk." (`verified: true`; without it only "Wrote N bytes"); (`dirs_created` is not shown: it is true for almost every write); "Syntax check found a problem." with the lint `output` (`lint.status == "error"`; `"ok"` and `"skipped"` say nothing); the `lsp_diagnostics` text as "Diagnostics"; `warning`. `bytes_written` is shown as a size ("312 bytes", "4.2 KB").
- **Failed.** `read_file` with `error`: the path header, "Couldn't read this file." with the error text, and the `similar_files` as plain path rows (a path is text, not a button; nothing here opens a file). `write_file` with `error`: "Not written." with the text, then "What Hermes tried to write" and the code, so the refusal can be judged. The card's header already carries the error icon.
- **Not a text file.** `is_binary` (checked before `error`, because a detected binary file carries both) or `is_image`: the path header and one note, "Not a text file." with Hermes' description from `error` and the size when given. A bare refusal of a binary extension has no `is_binary` and is an ordinary "Couldn't read this file." `base64_content`, if a result ever carries it, is never drawn, copied or logged.
- **Cut short.** `truncated` (the read ended before the file did): a warning note, "Cut short. Lines 1–2,000 of 5,320. The next read starts at line 2,001." When `truncated_by` is `bytes` the note adds "The server stopped at its size limit." and the next line comes from `next_offset`. The numbers come from `offset`, `total_lines` and `next_offset` (otherwise offset plus the lines shown); a figure the result lacks is left out of the sentence.
- **Unexpected shape** (no `content` string, a content that does not parse, `<persisted-output>` text): `null`, so the generic view shows it, as today.

### Link preview (`browser_navigate`, `web_extract`)

- **One card per page**: a 36 pt monogram tile (the first letter of the host), the title (two lines, then an ellipsis), the host and path (one line), an optional excerpt (two lines). The whole card is one button: it opens the address in the system browser (`launchUrl`, external). A trailing "open in new" glyph says so. A long press or secondary click offers Open in browser and Copy link, for a web address only: a card for another scheme has neither, and one with embedded credentials has no Open in browser and its Copy link copies the address without the credentials.
- **No favicon, no thumbnail, no Open Graph image.** The issue asks for a favicon with a fallback. The app never requests one: a favicon request tells a third-party host that this user's agent visited the page, with the user's IP, and nobody tapped anything. The monogram is the only look. Decision recorded here so a later change does not add it unasked.
- **Only `http` and `https`.** Any other scheme (`ftp:`, `file:`, `javascript:`) draws the card with the line "Not opened: only web addresses open from here" and no tap. An address with embedded credentials (`user:pass@host`) is drawn with the host only and does not open; the credentials are never shown.
- **`browser_navigate`** shows one card (the result's `title` and final `url`; the call's `url` argument when the result has none) and, under it, "86 interactive elements on the page" from `element_count`. `bot_detection_warning` and `stealth_warning` are notes with an icon and a word ("This page may block automated visitors."), the server's text under it. `snapshot` is not drawn in the body: it sits in a collapsed "Page snapshot" disclosure (plain text, the 220 px cap) so the raw result stays reachable, since a registry body replaces the generic result.
- **`web_extract`** shows up to five cards. A result with `error` is a card without a tap and a failure note ("Couldn't read this page."). The excerpt is the first 160 characters of `content`, whitespace collapsed, markdown markers left as they are.
- **Failed `browser_navigate`** (`success: false`): the card for the call's address stays, with "Couldn't open this page." and the error text.
- **Running**: the card with the host and "Opening…"; no tap until the call settles.
- **Long titles and addresses** never widen the card: the title clamps to two lines, the host and path ellipsise at the end, and a title with no spaces wraps at any character.

### Image gallery (`browser_get_images`, `image_generate`, `browser_vision`)

- **Where an image comes from decides when it loads.** A server path (`browser_vision`'s `screenshot_path`, or an absolute path in an `image_generate` result) loads through `MediaStore` like a `MEDIA:` attachment, with the app's own credentials, so it loads at once, provided the server will serve it: `HermesMediaSource.image` tries `/api/media` (Hermes' media folders) and falls back to `/api/files/download` (one locked root), and whether a screenshot path lies inside either is unknown. A path the server refuses draws the tile as "Couldn't load" with the tap offered again. An address (an `image_generate` result or a `browser_get_images` `src`) is a third-party host: it loads only on a tap, "Tap to load · cdn.example.com", and only over `https`. `http` shows "Not secure. Open in browser" and loads nothing. After a tap the tile shows the picture; a second tap opens it in `ImageViewerPage`, the in-memory zoom viewer, on every platform. Quick Look and Save need a staged file, so a remote image has neither; a server screenshot, which is a `MediaStore` image, keeps what chat images have today. A load that fails shows "Couldn't load" and offers the tap again, once per tap; nothing is retried by itself.
- **Bounds and storage.** At most 10 MB and 15 s per remote image, decoded at tile size. The loader follows no redirect to a non-`https` address (a redirect to `http` is "Not secure. Open in browser"); a redirect to another `https` host is followed up to three times. A remote image lives in memory only (the loader's own cache, not `MediaStore`, never a file): it is dropped on sign-out, a server change and when App Lock covers the app, so it needs no file cleanup. Its decoded frames also sit in Flutter's shared `PaintingBinding.imageCache`, so the loader evicts its own keys from it at the same three moments. A server screenshot is an image in `MediaStore`'s in-memory cache, like a `MEDIA:` image: it is emptied on sign-out (`MediaStore.clear`) and survives an App Lock cover, which only deletes Files downloads, exactly as chat images do today; App Lock blanks the chat, so nothing draws it while locked.
- **Layout.** Several images: a grid, two columns on a phone, three from 560 pt, four from 760 pt, tiles 4:3 with the picture covering, the alt text (two lines) and "800 × 800 · cdn.shop.example" under an unloaded one. One image (`image_generate`, `browser_vision`): one tile, full width on a phone and at most 360 pt on a desktop, 16:9 or the aspect ratio the call asked for.
- **Many images.** Six tiles show and "Show all N" opens the rest in place. `browser_get_images` lists every `<img>` on the page, so images under 32 px on either side (icons, tracking pixels; a size of 0 means not loaded and is kept) are left out, and the header says how many: "9 images · 5 small ones hidden". "Load all" is a button that loads the shown tiles on one tap, still https only.
- **Generating.** `image_generate` while it runs: a dashed skeleton tile in the aspect ratio of the call, a spinner and "Generating image…", a `BusyBar` under it. No shimmer, as in Files, so reduced motion needs no variant.
- **Failed.** `success: false`: "No image made." and the error text. A gallery where every tile failed to load still lists them.
- **`browser_vision`** shows the screenshot above "What Hermes saw" and the `analysis` text.
- **Unexpected shape** (no `images` list, no address, a path that is not absolute): `null`, generic view.
- **Accessibility.** A tile is one button named by its alt text and state ("Load Front view of the blue backpack, 800 by 800, cdn.shop.example"). An image without alt text is named "image 3 of 9".

### Table (a list of flat rows)

- **What counts.** A result that decodes to a list of maps, or a map whose one large value is a list of maps (`search_files`' `matches`), or a `search_files` `matches_text` block read back into rows, where every row is a flat map: values are strings, numbers, booleans or null. The first row sets the column order and later keys join it; at most eight columns show ("+3 more columns" and the raw result says the rest). An empty list is not a table: from `search_files` it is "No matches" (below), and from any other tool it is the generic view, which already says what came back. Hermes answers a search with no match as `{total_count: 0}` with no `matches` key, which the entry also maps to "No matches"; `files` and `counts` answers (a file-name search, a count per file) are not row lists and fall back to the generic view. A row with a nested value makes the result "not the expected shape".
- **Which tools.** `search_files` is the one known tool at this revision. Because Hermes densifies, nearly every answer is `matches_text`: the entry reads it back into `path`, `line` and `content` rows, only when `matches_format` starts with `path-grouped:` and every line is a path line or a `  <line>: <content>` row; any other line makes the result "not the expected shape". Any other tool, an MCP server's result included, gets the table when its result has that shape; the entry is last in the registry, and its predicate excludes every tool name another entry serves (`ToolBodyRegistry` moves on to the next entry when a builder returns null, so being last is not enough: a `browser_get_images` or `web_extract` call whose own view declined its result must fall back to the generic view, not to a table). Which other tools answer a list of flat rows is unknown (task 0.1 records them).
- **Layout.** A header row that stays while the rows scroll in the 220 px cap, rows of one line each, a column as wide as its longest cell in the first 20 rows between 64 and 220 px, an ellipsis at the end of a longer cell. The table scrolls sideways on a phone and fits on a desktop when it can. Numbers are right-aligned with tabular figures; null is an em dash (read as "empty" by a screen reader); booleans are the words "true" and "false". Paths and code are monospace.
- **Rows.** 50 rows show, "Show 50 more" adds 50 up to 500, then "Showing the first 500 of N". A long press (touch) or a secondary click (Mac) on a row offers Copy row (as JSON).
- **Summary.** The header line reads "12 matches · 3 columns"; for `search_files` a `truncated` flag with `total_count_is_lower_bound` adds a warning note, "The search stopped early. There are at least 212 matches." `warning`, `limit_reason` and `_omitted` (results held back for files that may hold secrets; "N results were held back by Hermes." with the server's text) are shown the same way, with an icon and a word, so "12 matches" never hides withheld ones.
- **Semantics.** A screen reader gets a table: "row 3 of 12, path ..., line 24, content empty".
- **Running and failed.** Running shows "Searching…" (no rows, no skeleton). A failed call shows the error as the generic card does; there is no table without rows.

### Sources row (#461)

- **What is a source.** The distinct pages of the turn, in this order: pages the agent opened (`web_extract` results without `error`, `browser_navigate` results with `success: true`), then `web_search` hits not already listed. An opened page is surely read; a search hit may not have been, so the opened ones come first and keep their place when more arrive. Order inside each group is first seen. `browser_get_images`, `browser_snapshot` and the other browser tools add nothing (no page address in their result).
- **De-duplication.** By a normal form of the address: scheme and host lower-cased, a default port and a trailing slash on the root path dropped, the fragment dropped, the query kept. Only `http` and `https`; an address with embedded credentials is left out. The first title seen for an address wins, an empty or missing one is the host.
- **Where the turn is.** The sources are collected from the assistant messages since the last user message (live: the reply's own calls; from history: every assistant row of the turn, see Server surface) and drawn under the text of the last of them, above the message actions. A turn paged out of the loaded history (an earlier page not loaded) shows the sources of the part that is loaded until the rest loads.
- **When it shows.** Not while the reply streams (a row appearing under half a sentence moves the text). It shows once the reply is finished, stopped, or ended in an error that kept sources. No sources, no row, no placeholder.
- **Chips, not a list.** A chip is a 28 pt monogram tile, the title (one line, ellipsis) and the host (one line) under it, 44 pt high on iOS, 48 dp on Android and Windows and Linux, and 32 pt on one line (title, then host) on a Mac. Chips wrap. Three show on a phone, four on a desktop, with a "+N more" chip that expands the row in place ("Show fewer" collapses it); there is no sheet. The header reads "Sources · 7", "Source" for one. The host is never elided before the title. At the largest text size chips are full width and two show.
  - A list was the alternative (a disclosure "Sources (7)" over rows). Chips win because the row is the answer to "what did this draw on" at a glance and costs one line when collapsed; a list costs a tap before it shows anything.
- **Tap** opens the address in the system browser. A long press or secondary click offers Open in browser and Copy link; a source never has credentials in its address (those are left out of the row), so both always apply. Every chip is a focusable button; its label is "title, host".
- **Titles from the web are untrusted**: `wellFormedText`, the hidden-character rule, a 120 character cap before the ellipsis.
- **Quick panel and watch.** The main chat and conversation windows show the row. The quick panel's reply does not, and the watch and notifications never get it.
- **Survives a reload** because it is derived from the same tool results the history returns (acceptance criterion of #461). A tool row dropped by a compaction takes its sources with it; whether the messages route returns compacted tool rows is not known (task 0.1).

### States, all views

| State                                                | What shows                                                                                                                                                                           |
| ---------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Generating (`preparing`: only the tool's name is known) | The card header only says "Preparing…". No view builds a body: `tool.generating` carries no arguments, which arrive whole with `tool.start`. |
| Running                                              | The view's own running line: "Reading…", "Opening…", "Generating image…", "Searching…". A spinner or `BusyBar`, never a shimmer.                                             |
| Complete                                             | The view.                                                                                                                                                                            |
| Failed                                               | The card header has the error icon. The body shows the failure with an icon and a word and the server's text, and keeps what helps judge it (the path, the address, what was tried). |
| Cancelled                                            | As running's last state: the header says so; the body shows what arrived.                                                                                                            |

### Settled rules applied

- Status is never colour alone: every note has an icon and a word.
- Targets: 44 pt iOS, 48 dp Android, Windows and Linux, 28 pt Mac, for chips, tiles, link cards, Copy and the `+N more` chip. The tile's picture may be small; its tap area is not.
- Text size is honoured with no cap; the table scrolls, chips go full width, code wraps.
- Lost answers: nothing here sends a command or a write to the Hermes server, so there is nothing to resend. Two reads can fail. A remote image (a tap, to another host) ends within 15 s as "Couldn't load". A screenshot is a GET through `MediaStore.image`: one request to `/api/media` and, on a 403 or 415, one to `/api/files/download`, each under the managed client's 60 s deadline, so it can take up to about two minutes; its tile shows a spinner meanwhile and ends as "Couldn't load", and neither read is retried by itself: a tap offers it again. This pass adds no shorter bound for the screenshot fetch.

## Platforms

iOS, Android, macOS, Windows, Linux. watchOS and surfaces: none (not offered there). No native entitlement, manifest or Xcode change. Windows and Linux use the Material look and 48 dp. The Mac opens a link with the same `launchUrl`; Mark of the Web applies to staged files, not to a browser launch.

## Invariants touched

- Privacy rules: no title, address, path or text reaches a breadcrumb, span or log. The breadcrumbs carry counts and outcomes.
- API layering: no new Hermes route and no write; a screenshot is read through `MediaStore` and its existing routes. A remote image is the only request to another host, behind a tap.
- Localization: every string goes in the ARB files under the `chat` area anchor, never below the widget layer; tool names and server values (`read_file`, paths, titles, error text) stay as the server sent them.
- Tool call cards keep their keys, ids and open state (`tool_call_expansion.dart`); the views change only what is inside an opened card.
- Catalog first: each view is a plain-model widget in `lib/src/chat/widgets/` with use cases before any wiring.

## Observability

- Breadcrumbs (`Breadcrumbs`): `chat.sources.expanded` with the count of sources, `chat.sources.opened` with the same count, `chat.tool_image.loaded` with `outcome` of `ok`, `failed`, `too_large` or `insecure`. None carries an address, title or host.
- No span and no log event (see the proposal).
