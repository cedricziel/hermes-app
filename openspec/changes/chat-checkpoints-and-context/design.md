# Design

All server facts below were read from the Hermes source at the pinned revision (`openapi/HERMES_REF`, `d923a5eb`) and checked against `openrpc/hermes-gateway.openrpc.json`. Paths are relative to the Hermes repository. Where a fact could not be read it says so.

## Server surface

### Rules that hold for every method here

- Gateway methods over `/api/ws`, called with the **runtime** `session_id` the chat already owns. Opening a view never creates or resumes a session (same rule as `session-usage`). An unknown id answers 4001 `session not found`.
- `profile` is accepted by every contract. The `rollback.*` methods **ignore** it (`tui_gateway/methods_tools.py` `@_rpc(..., live_session=True)`; the session decides the cwd and checkpoint store); `session.compress` is profile-scoped (`@_profile_scoped`). The app sends it on every call, as `session.usage` does. **Run against a real backend (see "Checked on a real backend" below): a chat of a non-default profile writes its checkpoints into that profile's own `checkpoints/` folder, but `rollback.list`, `diff` and `restore` read the server's own home, so such a chat always lists nothing while `enabled` is `true`.** Only the default profile's chats show a list at this revision.
- `method not found` (-32601) means "this server has no such feature": the row is not drawn. It is never an error banner.

### `rollback.list` (`methods_tools.py:1210`)

- Params: `{session_id, profile?}`.
- Result: `{enabled: bool, checkpoints: [{hash, timestamp, message}]}`, newest first, at most `checkpoints.max_snapshots` (20). `message` is the manager's `reason` renamed (the test at `tests/tui_gateway/test_tui_gateway_server.py:12410` pins it). Example:
  `{"enabled":true,"checkpoints":[{"hash":"aaa111…","timestamp":"2026-09-29T10:00:00+00:00","message":"before write_file: a.py"}]}` (a test fixture; the real engine writes `before write_file` or `before patch` with **no file name**, `agent/tool_executor.py:111`)
- Disabled: `{"enabled":false,"checkpoints":[]}`. **Checkpoints are off by default** (`hermes_cli/config_defaults.py:499`, `checkpoints.enabled: false`); the `HERMES_TUI_CHECKPOINTS` environment variable overrides config for gateway sessions (`tui_gateway/checkpoints.py`).
- Not on the wire: file counts, insertions, deletions, short hash. The app derives a file count from the diff's `stat`, lazily.
- Reasons are free text: `before write_file`, `before patch`, `before terminal: <first 60 chars of the command>`, `pre-rollback snapshot (restoring to <8 chars>)`, sometimes with a trailing `[nested git repos not captured: …]`. The app maps the known prefixes to plain sentences and shows anything else as a neutral "Checkpoint". A terminal command is **never** displayed (it can hold a secret); the sentence is "Before a terminal command".
- Errors: 5020 (any exception, message is the exception text), 4001.

### `rollback.diff` (`methods_tools.py:1250`)

- Params: `{session_id, hash, profile?}`. `hash` may be a hash (4–64 hex) **or a 1-based index**; `_resolve_checkpoint_hash` (`tui_gateway/checkpoints.py:46`) tries `int(ref)` first, so a short all-digit hash is read as an index. The app always sends the full hash from `rollback.list`.
- Result: `{stat: string, diff: string, rendered?: string}`. `stat` is plain `git diff --stat`, untruncated. `diff` is plain `git diff --no-color` of **the checkpoint against the current working tree of the whole folder** (not only what this chat changed), **hard-cut to its first 4,000 characters with no marker** (`raw = r.get("diff","")[:4000]`). `rendered` is an ANSI rendering for a terminal; the app ignores it.
- Failures of the diff engine are swallowed: a bad hash, a busy store or a missing checkpoint returns an OK result with empty `stat` and `diff`, which looks like "no changes". The app therefore treats an empty answer for a checkpoint that was just listed as "Couldn't read the changes", not as "nothing changed", unless the list's own newest checkpoint was taken a moment ago (see states).
- Container backends (`terminal.backend` docker etc.): a real JSON-RPC error 5022 with the text `Checkpoints are not taken for terminal.backend=…: file paths belong to the container, not this host.` Shown as "Checkpoints don't cover this chat's workspace."
- Other errors: 4014 `hash required`, 5022 (including `Invalid checkpoint number. Use 1-N.`).

### `rollback.restore` (`methods_tools.py:1220`, engine `tools/checkpoint_manager.py:~1270`)

- Params: `{session_id, hash, file_path?, profile?}`. `file_path` must be relative and stay inside the cwd (`_validate_file_path`). **It is not a literal path in the normal case**: `GIT_LITERAL_PATHSPECS` is set only in the nested-repository branch (`checkpoint_manager.py:1339`); otherwise it is `git checkout <hash> -- <file_path>`, so glob characters in a name can match other files and `.` is accepted (restoring every file with no chat rewind; an observation, not relied on: see open question 5). The app therefore sends only paths it read from `stat`, and **refuses a per-file restore for a name containing `[`, `]`, `*`, `?`, `\`, `:` or starting with `-`** ("This file's name can't be restored one at a time. Use Restore all files.").
- Result (open object): success `{"success":true,"restored_to":"abc12345","reason":"before write_file","directory":"/home/u/proj","history_removed":3}`; failure `{"success":false,"error":"…"}`. `directory` is an absolute server path and is not shown.
- **Most failures are an OK answer with `success:false` and an `error` string**, not a JSON-RPC error: `No checkpoints exist for this directory`, `Checkpoint '<h>' not found`, `File path escapes the working directory via traversal`, `Restore selection matched no files in checkpoint: …`, `Checkpoint contains nested git repositories that were not captured (<paths>); rollback was not performed`, `Restore failed: <git error>`, `checkpoint store is busy: <path>`, the container refusal above. The app keeps a fixed set of plain sentences for the ones it recognises by prefix and otherwise says "Hermes couldn't restore the files." without the raw text.
- JSON-RPC errors: 4014 `hash required`; **4009 busy for a full restore while the chat is running** (a file-scoped restore is allowed mid-turn); 4001; 5021 (message may be `checkpoint restored, but session history rewind failed: …`: **files are restored, the chat is not rewound**; the app says exactly that and re-reads the chat).
- **What a restore does** (all read from the engine):
  - *It tries to save the current state first*: `_take(..., "pre-rollback snapshot (restoring to <h>)")` runs before any file is touched and, when it works, becomes the newest entry. Its result is **ignored** (`checkpoint_manager.py:1278`): nothing is saved if the store fails, the folder holds more than 50,000 files, or the tree is unchanged since the last checkpoint (then the newest checkpoint already holds this state). What the checkpoint never holds cannot come back: `DEFAULT_EXCLUDES` (`checkpoint_manager.py:97-158`) leaves out dependency and build output (`node_modules/`, `dist/`, `build/`, `target/`, `out/`, `.next/`, `.nuxt/`), caches, virtual environments, VCS folders (so nested repositories), compiled binaries, archives and videos, `.env` and `.env.*`, `.DS_Store` and `*.log`; `max_file_size_mb` (default 10) drops larger files. The app therefore says "Hermes tries to save…" and, after re-listing, looks for a **new** hash (absent from the list read before the restore) whose reason ends `restoring to <first 8 characters of the restored hash>`; an older "Before a restore" row at the top does not count. `_take` also returns early when the folder is unchanged since the newest checkpoint (`checkpoint_manager.py:~1490`).
  - *It overwrites files with the checkpoint's version* (`git checkout <hash> -- …`). **It does not delete files created after the checkpoint** on this path (the RPC calls `restore` with `safe=False`; only the CLI and messaging `/rollback` use the safe mode that deletes Hermes-created files and skips user-edited ones). It **does overwrite hand edits** made after Hermes last wrote the file.
  - *Full restore also rewinds the conversation*: with no `file_path`, on success the handler calls `_rewind_active_session_history(session, len(user_indices) - 1)` under the history lock, removing the **last real user message and everything after it** from the live session and, for a stored session, from the durable transcript (`SessionDB.rewind_user_turn`; rows stay on disk with `active=0`). `history_removed` is the number of messages removed. **It is always exactly the last user turn, whichever checkpoint is restored**: restoring checkpoint 7 of 10 still removes one turn. A checkpoint has no link to a message or turn, only `{hash, timestamp, reason}`.
  - *A file-scoped restore never touches the chat.*
- Scope: the checkpoint chain belongs to the **working folder**, not the chat. Every chat in that folder sees and restores the same list. Checkpoints are made at most once per folder per **model step**, not per turn (`new_turn()` runs once per tool-calling iteration, `agent/turn_iteration_prep.py:380`), just before the first `write_file`, `patch` or destructive-looking `terminal` command of that step; a step with no file write makes none. A real turn with a `patch` step and a later `write_file` step made two checkpoints. `/` and `$HOME` are never checkpointed. Files over 10 MB, `node_modules`, build output, `.env*`, `*.log` and nested git repositories are not captured.
- Each `rollback.diff` runs `git add -A` into the shared store under a lock, so the app reads a diff only for a checkpoint the user opens, never for every row.
- Timeouts: each git call is 30 s (60 s for add and checkout); the RPC has no timeout of its own. The app gives restore and diff a 90 s limit and says "may have happened" when it lapses (below).
- Wrinkle (read; the profile case above was run): `rollback.list` and `restore` use the session cwd exactly, while checkpoints are keyed by the nearest project-marker folder of the file written. A chat whose cwd is a sub-folder of the project root can see an empty list. The empty state words this as "No checkpoints yet for this chat's folder."

### `GET /api/ops/checkpoints` and `POST /api/ops/checkpoints/prune` (`hermes_cli/web_routers/ops.py:801-837`)

- GET: `{sessions:[{session, files, bytes}], total_bytes}`. Despite the name, `session` is a **store directory** (`store`, `legacy-<ts>`), not a chat. No per-folder or per-chat data.
- POST prune: `{ok:true, pid, name}` immediately; it starts `hermes checkpoints prune` in the background (retention 7 days, 500 MB, orphans deleted) with no stdin, so the orphan confirmation can abort and the call can do nothing while answering `ok:true`. With several profiles it requires an explicit `profile` (400 otherwise).
- **Not used by this change.** Both are server housekeeping with no result the app can show truthfully. Reconsidered when a Hermes release reports a prune result.

### `session.compress` (`tui_gateway/methods_session.py:2136`, `_compress_live` :2089)

- Params: `{session_id, profile?, focus_topic?}`. `focus_topic` is the raw `/compress` argument string, so it is also where `here N`, `--keep N`, `--preview` and `--dry-run` are parsed (`hermes_cli/partial_compress.py`). `extract_compress_flags` (`partial_compress.py:52-70`) strips `--preview`, `--dry-run`, `--dryrun` and `--aggressive` **anywhere** in the text (any case), then `parse_partial_compress_args` (`:21-49`) reads text starting with `up to here`, a first word `here` (any case), `--keep`/`-k N` or `--keep=N` as a partial compress (`agent/conversation_compression_manual.py:49-56`, reached from `tui_gateway/session_compression.py:281`). **The app refuses a focus in which any word starts with `-`, whose first word is `here` in any case, or that starts with `up to here`**, with "Write a topic, like “the database schema”. Leave out words that start with “-”, and don't start with “here”.", so free text can never be read as a flag; it does not use the flags in this change.
- Result: `{status: "compressed"|"aborted", removed, before_messages, after_messages, before_tokens, after_tokens, summary, usage, info, messages}`. `summary` is `CompressionSummary {noop, aborted, refused_would_grow, fallback_used, headline, token_line, note}`; example headline `Compressed: 42 → 9 messages`, token line `Approx request size: ~120,000 → ~30,000 tokens`. Token counts are rough estimates. `messages` is the replacement transcript in a shape the app does not parse: it **re-reads the chat over REST** (`ThreadNeedsRefetch`, existing).
- Special results: a conversation too short to leave a middle to summarise (0, 2 and 6 messages were all) → `status:"compressed"` with `summary.noop:true` ("No changes from compression: N messages"; 36 messages compressed to 24; the engine protects the first 3 and a tail of at least 20 messages, so the real floor is higher than the 4 messages that only gate the `compressing` status); summary generation failed → `status:"aborted"` with `summary.aborted` and a reason note; the summary would be larger → `refused_would_grow`; a placeholder summary was used → `fallback_used`; another compression holds the lock → `{compressed:false, lock_held:true, message}` (**not reached**: a second compress on a session that is compressing answers 4009 `session busy — a /compress is running; run /compress when it finishes.` first, so `lock_held` needs a second process); a compute-host session may answer `{status:"pending", turn_isolation:true, message}` and refresh later.
- Errors: **4009** while a reply runs or another compress runs (`session busy — …`); 5032 agent not built yet; 5005 anything else.
- **While it runs the session is `running`.** A prompt sent meanwhile is queued by the server and drained afterwards; the app's own queue (`queue-messages`) already covers this and Send is not blocked by the app.
- **What is lost, kept and stored:**
  - A helper model writes one summary of the middle of the conversation. It is the `compression` auxiliary slot (`auxiliary.compression`), falling back to the main model, so it **costs tokens on that model** (timeout floor 300 s).
  - Kept: the system prompt, the first 3 messages, a token-bounded tail (default lean: about 2.5% of the window, at least 20 messages and at least one user message), and the to-do snapshot. Old tool results are pruned first without a model call. A focus topic makes the summarizer keep that topic and compress the rest harder.
  - `compression.in_place` defaults to **true**: the session id does not change, there is no parent link, and the replaced messages stay in the database marked `active=0, compacted=1`. With `in_place: false` (legacy) the session rotates to a child id; the app already follows that (`stored_session_id`, thread re-keying in the transport's `hermes_gateway_transport_*.dart` parts).
  - What the user sees afterwards: `GET /api/sessions/{id}/messages` defaults to `include_compacted=false`, so a re-read shows the **compressed view, the summary message in place of the middle**. `?include_compacted=true` (a query parameter in the OpenAPI) returns the full history including archived rows. `session.history` returns active rows only.
  - **It cannot be undone.** Nothing restores archived rows into the live context. `session.undo` removes the last user turn; it is not an undo of compression.

### `session.context_breakdown` (`methods_session.py:1479`)

- Params: `{session_id, profile?}`. Allowed while a reply runs; read-only, no provider call.
- Result: `{categories:[{id,label,color,tokens}], context_max, context_percent, context_used, context_source, context_estimated, estimated_total, model, context_files:[{label,path,chars,est_tokens,loaded,status}]}`. Category ids: `system_prompt`, `tool_definitions`, `rules`, `skills`, `mcp`, `subagent_definitions`, `memory`, `conversation`. Every one but `conversation` is dropped when 0; `conversation` is always present. All numbers are rough estimates (about four characters a token). `context_used` is anchored to provider-reported tokens when there is an anchor; `estimated_total` is the sum of categories and can differ from it. `color` is a CSS variable name; the app ignores it and uses its own palette.
- Before the agent is built: `categories:[]`, `estimated_total:0`, figures from the usage mirror. Error 5000 `Could not compute context breakdown`. Real answer for a new chat: `context_max:0`, `context_used:0`, `model:""`, `context_source:"provider_usage"`, `context_estimated:false` and **no `context_files` key** at all.
- Which categories show: a bare profile fills four (`system_prompt`, `tool_definitions`, `subagent_definitions`, `conversation`); `rules` appeared with an `AGENTS.md` in the chat's folder, `memory` with a `memories/MEMORY.md`, and `mcp` only with `tools.tool_search.enabled: "off"` (otherwise the MCP tools are deferred behind `tool_search` and count nothing). `skills` **never appeared** in this setup although `session.info` listed ten skills, so seven of the eight were seen; why the skills index is missing is not known. The server lists them in its own order (not by size); the app sorts. Right after a compress the usage has no `context_used` and the breakdown says `context_source:"local_estimate"` until the next turn.
- `context_files` carries absolute paths of rule files on the server. The app shows only the label and token count, never the path.

### Checked on a real backend

Run against a throwaway Hermes at `d923a5eb` on a scripted model (`test/real_backend_contract_test.dart`, group "file checkpoints and context"; its answers are recorded, scrubbed, in `test/fixtures/gateway/`). What differed from the reading above is already folded in; the rest:

- `rollback.list`: `hash` is 40 hex characters, `timestamp` ISO with `+00:00`, `message` is the reason (`before patch`, `before write_file`, `pre-rollback snapshot (restoring to <8>)`, with ` [nested git repos not captured: <paths>]` appended). A folder whose nested repository has **no commit** gets no checkpoint at all (`git add -A` fails inside the engine and the list stays empty): the empty state is all the app can say. With `terminal.backend=docker` the list still answers `enabled:true`; the diff (5022) and restore (`success:false`) are what refuse.
- `rollback.diff`: `stat` and `diff` are stripped (no leading space on the first stat line, no trailing newline); the cut is exactly 4,000 characters; a hash that is a 1-based index works and an index out of range answers 5022 `Invalid checkpoint number. Use 1-N.`; a bad hash and a never-checkpointed folder both answer an OK empty pair.
- `rollback.restore`: a file-scoped success carries `file` and no `history_removed`; failures carry a `debug` key. Errors seen: `Checkpoint '<h>' not found`, `File path escapes the working directory via traversal: '<path>'` (with the path), `File path must be relative, got absolute path: '<path>'`, `Restore failed: error: pathspec '<name>' did not match any file(s) known to git` (the answer for a name the checkpoint lacks; `Restore selection matched no files` comes only from the safe mode and was not reachable), the nested-repository refusal with a `nested_repositories` list, the container refusal, and `No checkpoints exist for this directory` when the checkpoint store does not exist yet (a backend that never took one, or checkpoints off). 4009 while a reply runs was seen for a full restore, not for a file restore. 5021 and `checkpoint store is busy` could not be provoked.
- Checkpoints off (the default): `rollback.list` answers `{enabled:false, checkpoints:[]}`, edits leave no store behind, `rollback.diff` answers an empty pair and `rollback.restore` answers `No checkpoints exist for this directory`.
- `session.compress`: seen `compressed` (36 to 24 messages), no-op, `aborted` (a 401 from the summary model, and an empty summary), `refused_would_grow` (a huge summary) and `refused_would_grow` with `fallback_used` (a failing summary on a short chat). A 500 from the summary model on a long chat still compressed with `fallback_used:false`; `fallback_used` alone was not reproduced. A prompt sent while a compress runs answers `{status:"queued"}`; a compress while a reply runs answers 4009 whose text ends `then run /compress.` (it names `/compress` too: the app must not read that as "compressing"). `pending` needs a compute host.
- Two chats in one folder list the same checkpoints; a full restore of the oldest of several removed the last user turn only (`history_removed:6` for a turn of six messages) and left files created later in place.

### `session.usage` and live frames (already mapped)

- `session.usage` result and push `{usage}` (`UsageSnapshot`): `context_used`, `context_max`, `context_percent` (clamped 0–100), `context_estimated`, `compressions`, plus `context_source` (`local_estimate`, `provider_usage`, `provider_usage_plus_estimate`), which the app does not read yet and will. The context fields are **absent** when `last_prompt_tokens` is 0, for example a resumed chat before its first turn in this server process. The push comes once a second during a turn, only when counters changed; `message.complete.usage` is final.
- `session.info` carries the same `usage` after each turn and after a compress. The app maps only `running` and `stored_session_id` from it today; this change also feeds its `usage` to the same controller.
- `status.update {kind}` (today only `compacting` is special-cased in `gateway_event_mapper.dart`; `compressing`, `ready` and `compacted` flow into `SessionWaitUpdated`; PR 1 checks this does not change wait-tier behaviour): manual compress emits `compressing` (only when there are at least 4 messages), then the compressor's own `compacting` and `compacted`, and ends with `{kind:"status", text:"ready"}` (the server re-tags a bare `ready` as `status`; there is no `ready` kind); automatic compaction arrives as `compacting` (already mapped to "Compacting the conversation…") and ends with `compacted`. This change gives `compressing` and `compacted` their own wording and treats `compacted` as "re-read the usage".
- **The compression threshold is not on the wire** (`compression.threshold` default 0.5, floored at 0.75 for windows under 512K, 0.85 for some models). The app cannot say "Hermes will compress at N%", and does not pretend to.
- `cost_usd` is decoded by the app but `_get_usage` does not emit it at this revision (could not find where it is set). Not used here.
- `usage.bars` is the Nous subscription and top-up balance (`tui_gateway/billing_view.py`), not context. Not used.
- `session.history` returns the durable transcript with ids; the chat already reads history over REST. Not used.

## Client architecture

Follows `session-usage` and `chat-activity`; nothing below needs a server change.

### Transport and repositories

- `ChatTransport` gains `checkpoints` and `context` capabilities implemented in `HermesGatewayTransport` (`lib/src/chat/gateway/hermes_gateway_transport.dart`, split into parts by concern in #910; the new methods belong in a new `hermes_gateway_transport_checkpoints.dart` part, next to `_branching.dart` for `undoLastTurn`/`branchThread`). **Reads and the breakdown go through the owned-session path** (`readOwnedSession` in `hermes_gateway_transport.dart` with the `OwnedSessionBinding` checks in `hermes_gateway_transport_owned_sessions.dart`, extended beyond `session.usage` to `rollback.list`, `rollback.diff` and `session.context_breakdown`): a runtime the chat already owns, never a resume. `_commandRuntime` (in `hermes_gateway_transport_commands.dart`; it *does* call `session.resume`) is used only where the user explicitly acted: a tap on a checkpoint row in a stored chat that has no live runtime, a restore, or a compress, as `undoLastTurn` and `branchThread` do. A transport without them (mock chat, watch) returns the unsupported result.
- `CheckpointsRepository` (`lib/src/chat/checkpoints/`) wraps `rollback.*`, parses leniently (skip a row without a hash; a missing timestamp is unknown, never "now") and returns sealed results:
  - `CheckpointList` = `CheckpointsOff` | `CheckpointsOn(List<Checkpoint>)` | `CheckpointsUnsupported` (method-not-found) | `CheckpointsFailed(kind)`.
  - `CheckpointChanges` = `Changes(files, truncated)` | `NoChanges` | `ChangesUnreadable` | `ChangesRefused(container)` | `Failed(kind)`.
  - `CheckpointRestore` = `Restored(filesRestored?, historyRemoved)` | `RestoredHistoryNotRewound` (5021 text) | `RestoreRefused(reason)` | `Busy` | `MayHaveHappened` (timeout/lost answer) | `Failed(kind)`.
  - The kinds are a closed enum (`notFound`, `nestedRepositories`, `storeBusy`, `container`, `pathRejected`, `transport`, `other`); raw server text never leaves the repository.
- `ContextRepository` (`lib/src/chat/context/`) wraps `session.context_breakdown` and `session.compress`:
  - `ContextBreakdown` = `Breakdown(model, used, max, percent, estimated, categories)` | `BreakdownUnsupported` | `BreakdownFailed`.
  - `CompressionResult` = `Compressed(beforeMessages, afterMessages, beforeTokens, afterTokens, note, fallbackUsed)` | `NothingToCompress` | `CompressionAborted(note)` | `WouldNotShrink` | `CompressBusy` | `CompressLockHeld` | `CompressPending` | `CompressUnsupported` | `MayHaveHappened` | `Failed(kind)`.
  - Counts are bounded (0 to 10,000,000) and a `before < after` result is shown as returned, not corrected.
- **File list from `stat`.** `parseStat(stat)` reads `git diff --stat` lines `path | N +++---` and the trailing `N files changed`; a rename `a => b` or `{a => b}` shows the new path; a binary line (`Bin 0 -> 12 bytes`) is a file with no text diff. `parseDiff(diff)` splits on `diff --git a/<p> b/<p>`; a hunk list per file feeds `ToolDiffBody` (which already colours `+`/`-`/`@@` and strips the terminal heading). A file in `stat` with no section in `diff`, or a diff of exactly 4,000 characters (its last section may end mid-line; the parser tolerates that), marks the result `truncated`; those files show "Hermes cut this diff short" and still offer Restore this file. Paths with spaces or quotes (git's `"a\tb"` quoting) are kept verbatim for the request and shown unquoted; a path that cannot be parsed back is not offered for per-file restore. `git diff --stat` also shortens long names to `.../tail` (and quotes or renames others); such a file is listed, takes the diff section whose path ends the same way, and is shown as not restorable one at a time, because the app cannot read its real path back from `stat` and sends only paths it read exactly.

### Controllers

- `CheckpointsController` (one per chat thread, created by `ChatController.checkpointsIn(thread)` like `usageIn`): holds the list, the open checkpoint's changes (in memory only), the restore operation and its result. Owner scope `(connection, runtimeSessionId, profile)` as `UsageScope`; late answers after a scope change are dropped; everything is cleared on sign-out, profile switch, thread change, connection change and App Lock. It loads the list when the Activity panel opens (not at chat open, not on every turn) and re-reads after a turn ends while the details are open, after a restore, and on resume.
- `ContextController`: shares `SessionUsageController`'s snapshot for the Row (`context_used/max/percent/estimated`) and loads `session.context_breakdown` only when the details open, after a turn, after `compacted` and after a compress. It owns the compress operation, a `CompressionSuggestion` decision (below) and the last compress outcome line.
- Both hold at most one in-flight request per kind, with a 10 s limit for reads (no effect on the socket, as `requestKeepingConnection`) and 90 s for diff, restore and compress; a lapse is `MayHaveHappened`, and the controller **re-reads** (list; usage; chat) instead of sending again.

### Where it appears (no new screen)

`BoundActivityPanel` gets two sources. Tiers (`activity_tier.dart`, `ActivityKind.context` and `.checkpoints`, both `reference`; a compress or restore in flight is shown as `working` for its duration only, as a plain "Compressing the conversation…" / "Restoring files…" line, and settles into a reference note):

| Item | Panel section | Tier |
|---|---|---|
| Context row (bar, %, "about 124k of 200k tokens") | This session → first | For reference |
| Compression suggestion (85%+, idle, once) | Same row, expanded one line | For reference |
| Compressing… / Restoring… | Now | Working |
| File checkpoints row | This session | For reference |
| Outcome note ("Restored 3 files") | This session | For reference |

Nothing is Needs-you: neither feature blocks the agent. Neither adds the Activity button's waiting dot, a strip line, a notification, a badge, a widget or an App Intent.

Navigation inside the panel is a push: row → **Context details** (one page) and row → **Checkpoints** → **Changes** (file list) → **One file**. On a phone the panel is a detent sheet and the pages push inside it with a Back button; on iPad and wide Android/desktop the inspector docked at 760 pt pushes the same pages and shows Back; on a Mac the inspector does the same and View > Back (⌘[) goes back. Confirmations use `showAdaptiveSheet`: a bottom sheet on a phone, a dialog on a Mac and wide windows (never a Mac bottom sheet).

### Offering compression at the right moment

- The server compresses by itself at a threshold the app cannot see, so most chats never reach a point where the user must act. Manual compression exists for the cases where that fails or the user wants a fresh, small context.
- The **suggestion** appears on the Context row when all hold: `context_percent >= 85`, the chat is idle (not replying, no request waiting), `compressions` has not changed since the last dismissal, and it has not been shown for this fill. Dismissing ("Not now") or compressing records the `compressions` count and the percent; it shows again only after the context has dropped below 60% and refilled, or after a successful compress followed by a refill. State is in memory per thread. It never shows while the percent is unknown or `context_estimated` is true with `context_source == local_estimate` and the percent is below 95 (a guess does not earn a prompt).
- **No push of any kind**: no dot on the Activity button, no strip, no notification, no sound, no haptic.
- **"Compress conversation…"** also lives in the details page always (idle chats), and in the Mac menu bar as Chat > Compress Conversation… (disabled unless idle; `MacCommand.compress` (new)). The `/compress` slash command keeps working as it does and is unchanged.
- The confirmation (adaptive sheet/dialog) says, in this order: what happens ("Older messages are replaced by a short summary. Your first and latest messages stay word for word.": the compressor keeps the system prompt, the first 3 messages (`protect_first_n`, `context_compressor.py:2804`) and a token-bounded tail), what it costs ("A helper model writes the summary and uses tokens on your account."), what it cannot do ("This can't be undone."), and what the user sees ("The chat reloads and shows the summary where the older messages were."). Optional "Focus on (optional)" (Advanced, one line, hint "Keep details about…"; a focus the server would read as a command is refused inline, see `session.compress` above). Buttons: Cancel (default), Compress, outlined: not red, because it loses detail but not user data and the server keeps the archived rows, and not filled, because it removes older messages from the model's view for good. If a reply starts while the confirmation is open, Compress disables with "Wait for the reply to finish." A 4009 is split by its text (`tui_gateway/user_messages.py:86-94`): "a /compress is running" says "Hermes is compressing this chat. Try again when it's done."; otherwise "Wait for the reply to finish, then try again."
- After it: a transcript line (a local-only transcript row of the kind the app already uses for command output (ids with `-local-`, `chat_controller_commands.dart`); a small per-thread overlay re-applies these rows after the chat is re-read, since a REST refetch would drop them) "Conversation compressed · 42 → 9 messages"; counts only. The panel note says "Conversation compressed" with "42 → 9 messages · about 120k → 30k tokens". `NothingToCompress` says "There isn't enough to compress yet." `WouldNotShrink` says "Compressing wouldn't make this chat smaller." `CompressionAborted` says "Hermes couldn't write the summary, so nothing changed." with the server's reason shown only as a fixed category. `fallbackUsed` adds "Hermes couldn't summarize the older messages, so it dropped them."

### Restore flow and its words

- Checkpoint row action menu: "See changes", "Restore all files…". Changes view per-file: "Restore this file…".
- *Restore this file* confirmation: title "Restore this file?", body "`<file name>` goes back to how it was <relative time>, before <reason>. Changes made to it since, by you or Hermes, will be overwritten. Hermes tries to save the current version first. Your chat isn't changed. Another chat working in this folder can change this file again." Buttons Cancel (default), Restore file. Allowed while the agent works, with the extra line "Hermes is working in this folder right now. It may change the file again."
- *Restore all files* confirmation (only when idle; while replying the action is disabled with "Wait for the reply to finish."), the exact server behaviour, in plain words: title "Restore all files?", body "Files in this folder go back to how they were <time>, before <reason>: N files differ now. Changes made since, by you or Hermes, will be overwritten. Files created after that stay where they are. Hermes tries to save the current state first. `.env` files, logs, `node_modules`, build output, caches, virtual environments, archives, videos, compiled binaries and files over 10 MB aren't in checkpoints: this leaves them as they are, and no checkpoint can bring them back. Another chat working in this folder can change these files again. **This also removes your last message and Hermes' answers after it from this chat.** The chat doesn't track which message a checkpoint belongs to, so only your last message is removed, whichever checkpoint you pick. Other chats in this folder keep their messages but see the restored files." Between the bold sentence and the note under it, the message that will be removed (the same `isPrompt` message the composer gets back) is quoted in a tinted box with "If this is the message removed, it goes back into the message box, unsent." The server removes **its own** last user turn (`methods_tools.py:1237-1241`), which may not be the app's last prompt (another client, a queued send), so the quote is a preview, not a promise. Buttons Cancel (default), destructive "Restore all files" (red outlined, never filled). N comes from `stat` and reads "some" when the changes could not be read.
- **Send is held during a full restore.** `rollback.restore` checks `session.running` before the restore (`methods_tools.py:1229`) but rewinds under the history lock only after the files are checked out (`:1235-1242`), so a prompt sent meanwhile would be the turn removed. The app disables Send and holds its queue from the moment Restore all files is confirmed until the restore settles (success, failure or a lost answer).
- On success: a transcript line "Restored N files · removed your last message" ("Restored N files" when `history_removed` is 0). N is used only when it was read from this checkpoint's `stat` since the last turn ended; otherwise the line says "Files restored" (the server sends no count). A result note in the panel says "Hermes saved the previous state as the top checkpoint, “Before a restore”." **only when the re-read list holds a new safety checkpoint** (above), and otherwise "No new “Before a restore” checkpoint was added."; the chat is re-read; **the quoted message text goes into the composer unsent only when the re-read chat no longer holds it**; otherwise the composer is left alone and the note says "Files restored. Your last message in this app wasn't the one removed." (the app takes it when the confirmation opens from the last message for which `ChatMessage.isPrompt` is true, the rule `_promptsAfter` uses: local command rows, failed prompts and auto-continue rows do not count; only when `history_removed > 0`; appended under an existing draft like a deep-link prompt). The app's own send queue is held until the restore settles so a queued prompt does not drain into the rewound chat. After a full restore the panel returns to the checkpoint list, re-read, with the note on top; after a file restore it returns to Changes, re-read, with "Restored 1 file" and "Your chat isn't changed."
- **Undoing a restore.** The top checkpoint "Before a restore" is a normal checkpoint. Restoring all files from it also removes another last message (server behaviour), so its confirmation shows the same warning and the app does not make it a one-tap "Undo". Restoring one file from it is the safe, chat-free undo. Recommended follow-up, not in this change: a "files only" restore that loops per-file restores from `stat`.
- `RestoredHistoryNotRewound`: only a 5021 whose text starts with `checkpoint restored, but session history rewind failed` (every exception in the handler maps to 5021, `methods_tools.py:78-81`): "Files were restored, but the chat couldn't be rewound. Your messages are unchanged."; the chat and list are re-read and the composer is unchanged. Any other 5021, and a `success:false` starting `Restore failed:` (returned after the safety checkpoint, during the checkout, `checkpoint_manager.py:1349`), say "Hermes couldn't restore the files. Some may have changed." and re-list; never "Nothing changed." Only refusals returned before `_take` (`checkpoint_manager.py:1146-1258`: bad hash or path, no checkpoints, not found, nothing matched, nested repositories) and the container refusal say "Nothing was changed."
- `MayHaveHappened`: "Hermes didn't answer. The files may have been restored." The controller re-lists and re-reads the chat; it never resends.

### State and failure handling

- Loading: skeleton rows with a label ("Loading checkpoints…", "Reading the changes…"). Empty list on: "No checkpoints yet for this chat's folder. Hermes makes one just before it first edits a file in a turn." Off: "File checkpoints are off on your Hermes server. To use them, turn on `checkpoints.enabled` in its config." (the key is shown, no link to edit anything). Unsupported: row absent. Container refusal: "Checkpoints don't cover this chat's workspace." Old server (no `rollback.*`; or no `session.compress`/`context_breakdown`): row absent, `/compress` still works as before, no error. Offline/disconnected: values stay, marked "Not up to date", actions disabled. **A stored chat with no live runtime** (just opened, nothing sent yet): the Context row is absent (it reads only what the chat already owns); the checkpoints row reads "File checkpoints" with the caption "Not checked yet", and opening it resumes the session, as sending would, and lists. A stale hash ("Checkpoint not found", after a concurrent restore or pruning) re-lists and says "That checkpoint is gone." A restore while a compress runs answers 4009 with other wording and gets the same busy message.
- Partial failure: breakdown unreadable but usage known → Row and bar stay, details show the total and "Couldn't read what fills the context. Try again."
- Permission denied: not a case here (the gateway has no per-method permission); an HTTP 401 follows the normal sign-in rules.
- A profile switch, new chat, thread switch, sign-out or connection change cancels pending reads, drops their answers, and clears diffs and breakdowns. A restore or compress in flight when the app is backgrounded is not cancelled and is re-read on resume. Because the controllers are per thread, leaving the screen does not cancel an in-flight restore; its result lands in the thread's panel.
- App Lock: the rows show only counts ("N checkpoints"), without reasons, file names or diffs; details and diffs are not reachable while locked and are dropped when the lock covers the app; the compress and restore buttons are disabled.
- Conversation windows and the quick panel: no rows (no `checkpoints`/`context` controllers passed), as with the Bot screen card. The Mac menu item acts on the key window only when it has the controllers.

### Telemetry (fixed words, counts and outcomes only; never text, names, ids, URLs, paths, commands, file names, diff text or the focus text)

- Spans: `chat.checkpoints.list` (`outcome`: ok, off, unsupported, failed; `count` bucket), `chat.checkpoints.diff` (`outcome`, `files` bucket, `truncated`), `chat.checkpoints.restore` (`scope`: file, all; `outcome`; `history_removed` bucket), `chat.context.breakdown` (`outcome`), `chat.context.compress` (`outcome`, `focused` bool, `fallback_used`, `before`/`after` message-count buckets, `source`: manual).
- Breadcrumbs: `chat.checkpoints.opened`, `chat.checkpoints.restore_confirmed` (`scope`), `chat.context.opened` (`from`: row, suggestion, menu), `chat.context.suggestion` (`action`: shown, dismissed, accepted), `chat.context.compress_confirmed`.
- Log events once per failure streak: `chat.checkpoints.read_failed`, `chat.context.read_failed` (`kind`). Buckets: 0, 1, 2–5, 6–20, 21+.

### Secrets

No secret is handled. Diffs can contain secrets from the user's files; they follow "Security and privacy" in proposal.md: memory only, no logs, no screenshots-in-telemetry, cleared under App Lock and on close. Breadcrumbs carry fixed names only; exceptions raised for crash reports carry fixed kinds, never server error text (which can quote paths or commands); nothing here reaches notifications, the surface snapshot, the watch or Spotlight. A diff stays selectable for copying a selection, with no Share or Copy all action.

### Accessibility

- Rows and buttons 44 pt on iPhone and iPad, 28 pt pointer targets on the Mac, 48 dp on Android; a Refresh bar button on every platform (pull to refresh is extra); at the largest text size the confirmations' body scrolls, their buttons stack and the quoted message is capped with a fade; text scales to the largest accessibility size and the row wraps to two lines instead of truncating the percentage.
- The meter is not colour-only: the percentage and "about 124k of 200k tokens" are text, and the state word ("Nearly full" from 80%, "Full" at 100% or when more is used than the window) appears with an icon. The bar has a label "Context, 62 percent used, estimated". Category bars list name and number; the stacked bar is decorative (`ExcludeSemantics`) when the list is present.
- Diff lines carry `+`/`-` characters (already), so meaning is not colour only; a file's diff has a heading "Changes in `<file>`, 12 added, 3 removed". Reduced motion: no animated bar fills.
- A restore or compress result is announced once, politely (never interrupting), by outcome words ("Restored 3 files", "Conversation compressed"), never with file names. Focus returns to the row that opened the page.
- Destructive buttons keep their semantic role and the confirmation's default focus is Cancel.

### Decision records

1. **Rows, not a screen.** Both are reference info for the open chat; the Activity panel is where "For reference" lives and nothing here waits for the user.
2. **The restore choices mirror the server**, even though it is clumsy, because the app cannot change it: a checkpoint cannot be tied to a turn, and a full restore always drops one turn. We say so rather than pretend "undo this turn".
3. **No prune.** See Non-goals.
4. **Compress through `session.compress`, not the slash command**, so the result is structured, the busy state is known, and a lost answer can be re-read. The slash command remains.
5. **No filled button removes messages or changes files.** Compress is outlined and every Restore is red outlined; Cancel is the default in each confirmation. The design pass changed the brief's filled Compress for this.

## Open questions (with recommendation)

1. *Show the archived pre-compression messages?* The REST route can return them (`include_compacted=true`). Recommend: not in this change; the summary is the truth for the model and Hermes' own dashboard shows the compressed view. Revisit with "Earlier messages" if users ask.
2. *Partial compression (`here N`, `--keep N`) and `--preview`?* Recommend later; the focus field covers the common need, and the preview's cost (does it call the summarizer?) is unverified.
3. *Does `session.compress` run on the helper model's price?* Yes, the `compression` auxiliary slot, else the main model; the confirmation says "uses tokens on your account" without a number, because the app cannot know it.
4. *Is 85% right for the suggestion?* The server's own terminal UI turns the meter red above 80 and critical at 95; Hermes auto-compresses at 50 to 85%. Recommend 85. A blocked automatic compression is detectable only by parsing a warning's text, which the app does not do.
5. *Files-only restore for a whole checkpoint.* Looping per-file calls makes one pre-restore checkpoint each (pushing older ones out of the 20). Passing `file_path: "."` appears to restore everything without the chat rewind (`_validate_file_path` accepts it), but that is an accident of the engine, unverified on a running server, and globs are live, so it is not used. Recommend a follow-up after checking it against a real backend, ideally with Hermes adding an explicit option.
6. *Should "Restore all files" be offered for checkpoints other than the newest?* The chat rewind is the same single turn either way, which is wrong for older ones. Recommend offering it for every checkpoint but wording the warning as above, and keeping per-file restore as the primary action. If testers find it misleading, restrict it to the newest non-"Before a restore" checkpoint.
7. *`rollback.diff` has no per-file parameter and cuts at 4,000 characters.* Large changes can show only the first files' diffs. Recommend living with it and saying so; a REST route for a full diff would be a Hermes change.
8. *Folder vs chat scope.* Checkpoints are shared by all chats of a folder. Recommend one sentence in the confirmation (included) and no per-chat filter.
