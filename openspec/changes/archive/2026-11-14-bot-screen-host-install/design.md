# Design

## Context

Hermes (`tui_gateway/methods_display.py`): `display.install` refuses (5300, message only) on a non-Linux host, a sandboxed profile ("give that sandbox an image with the desktop stack"), a host without apt-get, dnf or pacman, and while another install runs; otherwise it claims the install, answers `{started, command, profile_key}` at once and runs the package manager on a thread. Output streams as `display.install.log` broadcasts to every client; the end is `display.install.done` with `code` (0 ok, -1 cancelled, -2 no sudo: the manual command was streamed) and a fresh `status`. When it needs sudo it calls `_ask("display.install.sudo", "", {profile_key}, timeout=300)`, which reaches only the connection that called `display.install` (its transport is carried into the worker thread), with an empty `session_id`; `{value: ""}` declines.

In the app, `HermesGatewayTransport` listens to `client.serverRequests` for methods outside `handledServerRequests` and answers `-32601` only when `_replying.containsKey(request.sessionId)`: other clients attached to a session may answer it, so the app stays silent otherwise. With `session_id: ""` that condition never holds, so `display.install.sudo` is ignored today and the server waits 300 s. `bot-screen-card` owns `BotScreenController` in `ChatScreen`, which is replaced on profile switch and disposed when the chat leaves the screen, so it cannot host a prompt for an install that outlives it.

## Decisions

- **Handler registry.** `HermesGatewayTransport.registerServerRequestHandler(String method, ServerRequestHandler handler)` returns an unregister callback that removes only its own registration; the handler is `Future<Map<String, Object?>> Function(GatewayServerRequest request, Object connection)`, where `connection` is the socket the request arrived on (the same token as `GatewayConnectionTransport.gatewayConnection`), so a handler can tell a request on the connection that started an install from one on any other. Only methods in `registrableServerRequests` (`{'display.install.sudo'}`) can be registered; one handler per method, a later registration replaces the earlier. The unhandled-request listener checks the registry first: a registered handler answers with its result; a `GatewayRpcException` it throws answers with that error (how a handler refuses), any other throw answers `-32603` without the message. For a method in `registrableServerRequests` with no handler, the transport answers `-32601` at once whatever the session, since that request reaches only the connection that started the install. Other unhandled methods keep today's behaviour.
- **App-level host.** `BotScreenInstalls` (`lib/src/bot_screen/install/`), created by `AppShell` per gateway and provided below it (`ChatScreen` reads it from the provider and gives it to its `BotScreenController`), holds each profile's install by profile name (the name `display.*` calls take; the default profile is `default`): running (the last 6 lines, whether a password was asked) or ended with an `InstallResult` (installed, refused with the server's message, unreachable, cancelled, no sudo with the command, failed with the last lines, may still be running). It follows `display.install.log` and `display.install.done` from `connectionEvents` by `profile_key`. The key is the status' `profile_key` known at the press (so lines that arrive before Hermes' answer count) and is confirmed by the answer. It registers the sudo handler only while an install it started runs.
- **Same connection.** The server sends `display.install.sudo` only to the connection that sent `display.install`. The repository's install call goes through `HermesGatewayTransport.requestKeepingConnectionOnClient`, which returns the client that actually carried the call, and that client is the install's connection (it is forgotten when `GatewayConnectionEvent.lost` reports it). The handler refuses (`-32602`) a request whose `profile_key` does not belong to a running install, that arrived on any other connection, or while a prompt for that install is open (also a repeat of the open request's id). A request that arrives before Hermes' answer waits for it, since the answer is what tells the connection. When the server withdraws a request (`request.cancel` with its id and `method: display.install.sudo`, on a timeout or an interrupt) the prompt of that request closes and the install may be asked again. When the prompt's code throws (anything but a gateway error), the handler answers `-32603` without the message and logs the fixed-word event `bot_screen.install.prompt_failed`.
- **Session and window.** The question is asked only while the session is authorised (`AppShell._authorizedOwner`); otherwise the answer declines. On macOS the shell first brings the main window forward (`ConversationWindows.showMainWindow`, the runner's `show` call, else `MacWindow.orderFront`), so the question does not open on a hidden window. `AppLockGate` wraps the covered app in `ExcludeFocus`, so keys typed on the lock screen cannot reach a field underneath.
`BotScreenController` reads the install for its profile from `BotScreenInstalls` (`install`, `canInstall`, `startInstall`) and takes over the status that comes with an install that ends after the controller was made (an ending already there at construction is not applied: the controller reads the server's status itself); `BotScreenCardModel.fromState` puts Installing before Not installed.
- **Gate.** Install on Server shows only when `installed` is false, `placement == "gateway"` and `install_command` is present.
- **Refusal.** A 5300 answer to `display.install` becomes `refused(message)`; the card shows "Couldn't start the install" and the message, with Install on Server again.
- **Missed done.** While an install runs, `BotScreenInstalls` reads `display.status` for that profile on app resume (`AppShell` calls `resumed()`) and after `GatewayConnectionEvent.lost`; `installed: true` ends it as `done(0, status)` with outcome `installed`. A 22-minute timer, started when Hermes answers `display.install`, ends it as `unknown` (Hermes waits up to 300 s for the password and runs the package manager for up to 900 s, about 1206 s in all) (card: "The install may still be running; check again later", with the status re-read). Both paths end the span.
- **No sudo.** On -2 the card says there is no sudo and shows the command to run by hand: the status' `install_command` from the done payload, falling back to the command `display.install` answered with, with a leading `sudo ` removed (a server with no sudo is run as the user who installs), in monospace with Copy, not log lines. Install on Server is hidden after that result.
- **Password UI.** `SudoPasswordPrompt` is the platform's alert (`AppAlertDialog`: a Cupertino alert on iOS and macOS, a Material `AlertDialog` elsewhere), not a sheet: a masked password question in an alert is the platform's own idiom, and one widget serves every platform. Its field is a `CupertinoTextField` on Apple and a `TextField` elsewhere, with `obscureText: true`, `autocorrect: false`, `enableSuggestions: false`, `enableIMEPersonalizedLearning: false`, `autofillHints: null` and smart dashes and quotes off. The keyboard type stays the default, because `visiblePassword` would make Android drop its password variation; `obscureText` already turns suggestions off there. Whether iOS still offers Save Password or QuickType for such a field is checked on a device (task 7.2). Install is disabled while the field is empty, answers the typed value once and clears the `TextEditingController`; Cancel, dismissal or a withdrawn request answers `{value: ""}`. The question reads "Your Hermes server (host) needs the password of its user to install the desktop for the profile \"name\"." and says it is sent once and not stored. `showSudoPasswordPrompt` presents it and records the `bot_screen.install.password` breadcrumb (`outcome`: `answered` or `cancelled`); if the install ends first (the `ended` future completes) the prompt closes and nothing is recorded. App Lock covers the prompt like any screen; it answers only when the user acts.
- **Host label.** The prompt names the dashboard's host from the connection's base URL and the install's profile (shown, never logged).
- **Catalog and design system.** Card states Installing (lines), install refused, cancelled, no sudo with the command, failed, may still be running; `SudoPasswordPrompt` per platform; `design/web` `BotScreenCard` states and a `SudoPasswordPrompt` component (`category: Surfaces`, like the other dialogs) built on `AlertDialog`, which gained `children` under its message; its input is `autoComplete="new-password"`.
- **Test seam.** `AppShell` takes an optional `gatewayConnect`, like its `plugins`, `cron` and `kanbanBuilder`, so a test can run the shell over the fake gateway.

Platforms: iOS, Android, macOS, Windows, Linux. No native change.

Invariants touched:

- Telemetry: span `bot_screen.install` and log `bot_screen.install` (`outcome`, `asked_password`) in `BotScreenInstalls`; breadcrumbs `bot_screen.install.pressed` (card) and `bot_screen.install.password` (`outcome`: `answered`, `cancelled`; `showSudoPasswordPrompt`). No password, command, lines, host or profile.
- Secure storage: the password is never stored, so no secure storage use.

## Risks / Trade-offs

- [A password typed on a phone goes to the server] → It is that server's own sudo password, asked for by its Hermes over the authenticated socket; the alternative is SSH. The prompt names the host.
- [The gateway reconnects during the install] → The sudo request was tied to the old connection; the server's ask times out and done reports a failure; the status re-read after the reconnect catches a success, and the card offers Install on Server again on failure.
- [Refusing `display.install.sudo` explicitly could race another client] → Only the connection that started the install receives it, so there is no other answerer.
