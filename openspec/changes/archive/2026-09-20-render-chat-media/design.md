## Context

`attach-files-in-chat` (merged) added `ChatAttachment` (name, kind, device `path`, server `remotePath`, size, embedded `bytes`) on `ChatMessage.attachments` and a pure parser for history rows. The mapper turns each into an `ImageMessage` (an image with a device path, embedded bytes, or now an absolute server path) or a `FileMessage` card. This change reuses that model for the agent's own files and adds a way to fetch bytes from the server. Verified against a live Hermes 0.21.1 backend (and by the contract test):

- `GET /api/media?path=<abs>` returns `{"data_url": "data:image/png;base64,..."}`; it needs the header or bearer (not `?token=`), an image extension (png, jpg, jpeg, gif, webp, svg, bmp, ico; else 415), a resolved path under Hermes' `images`, `screenshots` or `cache` directories (else 403 "Path outside media roots"), at most 25 MB (else 413), and 404 when missing.
- `GET /api/files/download?path=<abs>` returns raw bytes; absolute paths only (400 otherwise), at most 100 MB (413), sensitive names such as `auth.json` are 403, 404 when missing; header, bearer or `?token=`.
- Reply text is stored and streamed verbatim: `MEDIA:/abs/path` stays in the text of `message.delta` and `message.complete`. There is no structured media field.

## Goals / Non-Goals

**Goals:**

- One display path for agent files, and for attachments restored from history.
- Nothing about a fetch failure breaks a message.

**Non-Goals:**

- Changing which sessions or sources the app creates (see the finding under Risks).

## Decisions

- **Parse at mapping time, not at storage.** `ChatMessage.content` keeps the raw text so streaming and history stay simple; a pure `extractMedia(content, {complete})` returns visible text plus attachments and is used by the mapper for assistant messages only. Tags are read from whole words, not from code, and only with an absolute path (POSIX or a Windows drive); a path with spaces is quoted. While a reply is pending (`complete: false`) a tag that touches the end of the text, an unclosed quote, or a trailing partial `MEDIA:` word is held back, so a half-read path is never fetched. Ids derive from the message id (`id-media-N`) and follow the text, so the chat controller matches them across updates. A path named twice shows once, as Hermes' own extractor does.
- **Images: `/api/media` first, download route second.** Images under Hermes' media directories arrive as data URLs; a 403 or 415 falls back to the download route and the image is decoded from bytes; 404 and 413 are final. Alternative: always the download route; rejected because it is a bigger transfer, but it stays as the fallback. SVG is treated as a file, since Flutter cannot draw it.
- **Files: download route, bytes, then a cache file.** `HermesApiClient.fetchManagedFile` asks for `ResponseType.bytes` on the managed `Dio`, exactly like the Kanban attachment download (the generated method decodes JSON and would corrupt binary), so 401 refresh still applies and the token stays in the header. The bytes are written to `<cache>/hermes_media/<hash of server path>/<name>` through a `.part` file and a rename, so a half-written file is never reused. The plan said to stream to disk to keep memory flat; following the Kanban pattern instead means a file up to the server's 100 MB limit is briefly in memory. Accepted for now; a streamed `Dio.download` is the follow-up if that hurts. The file name is reduced to its last path segment with reserved characters replaced.
- **Generated client where it fits.** `getMediaApiMediaGet` returns the small JSON body and is used as is. Only the binary download is hand-written, as Kanban does. No change to `packages/hermes_api`.
- **Plugins.** `open_file ^4.0.0` opens a file with the system app on iOS, Android, macOS, Windows and Linux (`open_filex` is mobile only). `path_provider` gives the cache directory. `share_plus` is dropped: `file_picker`'s save dialog (already a dependency, used by Kanban) covers keeping a file, and the app that opens it has its own share. `share_plus` 12.x resolves against the pinned `win32` (13.x does not), so adding it later is possible. The image viewer is a plain `InteractiveViewer` route, since the zoom package on pub.dev has had no release since 2024.
- **State.** `MediaStore` (plain class, provided as `Provider<MediaStore?>` next to the auth controller, created eagerly so it is listening when the session ends) owns a size-bounded in-memory image cache (least recently used first out), the fetch futures keyed by server path (two taps fetch once) and `clear()`. It depends on a `MediaSource` interface (`HermesMediaSource` over the signed-in client) and a `MediaActions` interface (open and save; the platform one uses `open_file` and `file_picker`, tests use `FakeMediaActions`). Tests drive the real client against `FakeHermesServer`, so no fake source exists. `clear()` bumps a generation number, so a fetch that finishes after it keeps nothing. Widgets read the store with `context.read<MediaStore?>()`; without one, cards and thumbnails fall back to showing the name.
- **Sign-out.** `AuthController.signedOut` is a synchronous broadcast stream fired after the tokens are cleared in `signOut()`, `changeServer()` and when the server rejects the refresh token. The store subscribes and clears. Listening to `state` would miss a sign-out on a server without the auth gate (state stays `ready`). Concurrent 401s that end in a rotated token never reach these paths, so they do not fire it.
- **Fallback for images that fail.** A thumbnail that fails to load shows a card with the reason; only "could not download" retries on tap.

Platforms: all five. Android needs no FileProvider entry of its own (`open_file` ships one that covers the app cache). macOS needs no extra entitlement (`network.client` is present). watchOS is not affected. Invariants: bearer auth and refresh go through the managed `Dio`; tokens never appear in URLs; telemetry untouched.

## Risks / Trade-offs

- **What the model is told (task 1.1, read from hermes-agent's `agent/prompt_builder.py` and `tui_gateway/`).** The app sends `session.create` and `session.resume` without a `source`. The gateway then resolves the source from the server's environment: `desktop` only when the process has `HERMES_DESKTOP=1` (and not `HERMES_DESKTOP_TERMINAL`), otherwise `tui` (`_resolve_session_platform`). A normal `hermes dashboard` therefore runs these sessions as `tui`, and the `tui` prompt says: "there is no attachment channel and MEDIA:/path tags are NOT intercepted here (they print as literal text) — deliver a file by stating its absolute path or URL in plain text." So in a default setup the model is told not to write `MEDIA:` tags and will mostly name paths in plain text; tags then appear only where a tool result or the model writes them anyway. The `desktop` prompt says "Deliver files by writing MEDIA:/absolute/path/to/file", but it also teaches `::preview{file=...}` widgets and HTML previews this app cannot render, and marks the session `desktop`: it adds the `desktop_ui` toolset (terminal and preview panes, `focus_pane`, reactions, which answer "desktop only" without a desktop), changes the `Platform:` trailer, and a session resumed under another surface gets a surface-switch note (a prompt-cache break on long sessions). Sending `source: "desktop"` is therefore a separate decision, with its own spec, and is not done here. This change is still correct without it: it shows tags whenever they occur and history attachments, and it is the prerequisite for any such change.
- A path the server allows but this user has no right to read gets a "can't be opened from here" card, which is the right outcome.
- The cache can grow with use; it is cleared on sign-out only. A size-bound eviction is future work. A file downloaded in an earlier run is only removed at the next sign-out.
- The watch and any notification text show a reply's raw text, tags included; only the chat transcript reads the tags.
