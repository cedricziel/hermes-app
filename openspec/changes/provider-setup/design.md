# Design

## Context

See proposal.md for why. Everything below about Hermes was read from its source at `d923a5eb` (0.22.2, the revision `openapi/HERMES_REF` pins), in `hermes_cli/web_routers/config_env.py`, `oauth.py`, `models.py`, `ops.py`, `hermes_cli/web_server_oauth.py`, `hermes_cli/inventory.py`, `hermes_cli/provider_catalog.py`, `hermes_cli/credential_lifecycle.py`, `tui_gateway/methods_complete.py`, `methods_config.py` and `methods_onboarding.py`, and from Hermes' own desktop UI for the same job (`apps/desktop/src/app/settings/providers-settings.tsx`, `custom-endpoints-settings.tsx`, `store/onboarding.ts`), which shows the flow Hermes' authors intend. Task 1.1 confirms the shapes against a throwaway backend before code is written.

What the app has today: `HermesModelsRepository.load` reads `GET /api/model/options` (without `include_unconfigured`) and keeps only authenticated rows with models; `ChatController.modelOptionsState` is `incomplete` when none is left, the composer pill then reads "Set up a model" and `showModelSetup` shows a dialog with `hermes model`. Helper models (`HelperModelsScreen`) and the Profiles screen's default model use the shared `showModelPicker`.

Platforms: iOS, iPadOS, Android, macOS, Windows, Linux. watchOS is not affected. No native code, entitlement, manifest or Xcode project change: the provider's page opens with the existing `url_launcher` use, and the key field uses Flutter's own text-field flags.

### Server surface

All routes below are in `openapi/hermes-agent.openapi.json` and in the generated client, all without a response schema (`{}`), so the app parses every answer leniently and skips what does not fit. Every route that touches credentials takes `?profile=`; the app always sends the profile it shows (see "Which profile"). Errors are FastAPI `{"detail": "..."}` bodies.

Authentication: routes marked "token" call `_require_token`. Behind the dashboard's auth gate the app's bearer session satisfies it; on a loopback dashboard without the gate the page token the app already sends (`X-Hermes-Session-Token`) does. Nothing new is needed, but a 401 from these routes after a successful `GET` is the token missing and is handled like any other 401 by `AuthController`.

**Reading what is connected**

- `GET /api/model/options?profile=&include_unconfigured=true` (`models.py:138`). Same builder as the chat's picker (`build_model_options_payload`), plus a skeleton row for every canonical provider not yet configured. Answer: `{"providers": [row…], "model": "<default model>", "provider": "<default provider slug>"}`. A row: `slug`, `name`, `is_current`, `is_user_defined`, `models` (ids), `total_models`, `authenticated` (false only for a skeleton), and on skeletons `auth_type` (`api_key`, `oauth_device_code`, `oauth_external`, `external_process`, `copilot`, `aws_sdk`, `vertex`, `virtual`, …), `key_env` (the provider's first key variable) and `warning`; optional `limit`, `pricing`, `capabilities`. The `moa` row (`auth_type` `virtual`) and the managed local-runtime row are not providers to connect. A normal open reads provider catalogs from Hermes' disk cache and warms missing ones in the background (`non_blocking_catalogs`), so a provider connected a moment ago can list no models yet (see Risks). 503 `Restart required: …` when the server's code changed under it.
- `GET /api/env?profile=` (`config_env.py:259`). A map of variable name to `{is_set, redacted_value, description, url, category, is_password, tools, advanced, channel_managed, provider, provider_label, provider_profiles, provider_primary, custom}`. Provider keys have `category: "provider"`; `provider` is the catalog slug and `provider_primary` marks the key the provider's card should ask for; `url` is where the provider issues keys. `redacted_value` is a display sentinel such as `«redacted:sk-p...7890»` (`«redacted:***»` for a short value) and is refused if sent back (400). Example row: `"OPENROUTER_API_KEY": {"is_set": true, "redacted_value": "«redacted:sk-o...4f2a»", "description": "OpenRouter API key", "url": "https://openrouter.ai/keys", "category": "provider", "is_password": true, "advanced": false, "provider": "openrouter", "provider_label": "OpenRouter", "provider_primary": true, "custom": false, …}`.
- `GET /api/providers/oauth?profile=` (`oauth.py:683`). `{"providers": [{"id", "name", "flow": "device_code" | "external", "cli_command", "docs_url", "disconnect_hint", "disconnect_command", "disconnectable", "status": {"logged_in", "source", "source_label", "token_preview", "expires_at", "has_refresh_token", "last_refresh"?, "error"?}}]}`. Device-code providers at `d923a5eb`: `nous` (Nous Portal), `openai-codex` (ChatGPT or Codex subscription), `minimax-oauth`, `xai-oauth`. External: `qwen-oauth`, `copilot-acp`, `anthropic`, `claude-code`, and any accounts-tab provider a plugin adds. `token_preview` is the last six characters; the app does not show it.
- `GET /api/providers/custom-endpoints?profile=` (`config_env.py:728`). `{"endpoints": [{"id", "name", "base_url", "model", "models", "api_mode", "context_length", "discover_models", "has_api_key", "api_key_preview", "is_current", "source"}], "current": {"provider", "model", "base_url"}}`. `api_key_preview` is `${KEY_ENV}` or a redacted sentinel; `source` is `providers`, `custom_providers` (legacy) or `direct-config`.
- `GET /api/credentials/pool?profile=` (`ops.py:344`). `{"providers": [{"provider", "entries": [{"index" (1-based), "id", "label", "auth_type", "source", "priority", "last_status", "request_count", "token_preview", "has_refresh"}]}]}`. `source` such as `env:OPENAI_API_KEY`, `manual`, `device_code`. Used only to explain a provider that stays connected after its key was removed.

**Connecting**

- `POST /api/providers/validate` body `{"key": "<VAR>", "value": "<key>"}` (token; `config_env.py:997`; no profile, writes nothing). Answers `{"ok", "reachable", "message"}`. Hermes has live probes only for `OPENROUTER_API_KEY`, `OPENAI_API_KEY`, `XAI_API_KEY`, `GEMINI_API_KEY` (10 s timeout); every other key answers `{"ok": true, "reachable": false, "message": ""}` ("cannot check"). A rejected key: `{"ok": false, "reachable": true, "message": "That API key was rejected. Double-check it and try again."}`; unreachable: `{"ok": false, "reachable": false, "message": "Could not reach the provider to verify the key."}`; a 429 counts as accepted. Hermes' desktop stopped blocking on this check because it rejected too many working setups (corporate proxies, regional blocks), which is why the app offers "Save anyway".
- `PUT /api/env?profile=` body `{"key": "<VAR>", "value": "<key>", "provider_setup": true}` (`config_env.py:328`). Writes the profile's `.env`, rotates any stale `config.yaml` copy of the previous value and seeds the credential pool. Answers `{"ok": true, "key": "<VAR>", "config_updates": [...]}`. 400 with Hermes' reason for a redacted sentinel, an invalid or denylisted name, or a key an administrator or managed install locks; 404 for an unknown profile.
- `POST /api/providers/oauth/{id}/start?profile=` (token; `oauth.py:806`). Answers `{"session_id", "flow": "device_code", "user_code", "verification_url", "expires_in", "poll_interval"}`; Nous' `verification_url` already carries the code. The Codex start waits up to 10 s for OpenAI's code (504 "device-auth timed out before returning a user code"). 400 for an unknown or external provider, and for Nous when the account is already signed in (Hermes' sentence in `detail`); 500 with the provider's reason. Sessions live in the server's memory for 15 minutes.
- `GET /api/providers/oauth/{id}/poll/{session}?profile=` (no token; `oauth.py:868`). `{"session_id", "status": "pending" | "approved" | "denied" | "expired" | "error" | "cancelled", "error_message", "expires_at", "reason", "account_email", "model", "retryable", "retry_after"}`. 404 when the session is unknown (expired, or the server restarted); 400 on a profile mismatch. On `approved` the server has already saved the credential.
- `DELETE /api/providers/oauth/sessions/{session}?profile=` (token). `{"ok": true}` or `{"ok": false, "message": "session not found"}`. Stops the server's poller so a later approval saves nothing.
- `POST /api/providers/custom-endpoints/validate` body `{"name", "base_url", "model", "api_key"?, "api_mode"?}` (no profile). Hermes probes `{base}/models`, then `{base}/v1/models`, from the server, then a one-token request on the API type's route. `{"ok", "reachable", "message", "models", "model_details", "transport_checked", "resolved_base_url"}`. `ok: false, reachable: true` is a warning (Save stays possible, as in Hermes' UI); `resolved_base_url` is the address that answered and is the one to save.
- `POST /api/providers/custom-endpoints?profile=` body `CustomEndpointUpdate` `{"id", "name", "base_url", "model", "api_key", "api_mode", "context_length", "discover_models", "make_default", "models", "model_details"}`. The key goes to `.env` under a derived variable and the entry references it by `key_env`. **An `api_key` of `""` clears the stored key; `null` (omitted) keeps it**, so an edit sends `api_key` only when the person typed in the key field. `api_mode` `null` keeps a hand-written one. Answers the list plus `{"ok": true, "id"}`. 400 `name required`, `base_url required`, `base_url must include scheme and host`, `model required`, or the redacted-preview refusal.
- `POST /api/providers/custom-endpoints/{id}/activate?profile=` makes an endpoint the default (`{"ok", "provider", "model"}`; 404 unknown, 400 incomplete).
- `GET /api/model/recommended-default?provider=<slug>&profile=` (`models.py:176`). `{"provider", "model", "free_tier"}`; `model` may be empty. It builds the inventory with blocking catalogs, so it also warms the provider's model list.
- `POST /api/model/set?profile=` body `{"scope": "main", "provider", "model", "confirm_expensive_model"?}` (`models.py:376`). Answers `{"ok": true, …}`, or `{"ok": false, "confirm_required": true, "confirm_message": "…"}` for an expensive model (nothing saved). 503 `Restart required`. Helper models already use the same route with `scope: auxiliary`.

**Removing**

- `DELETE /api/env?profile=` body `{"key": "<VAR>"}` (`config_env.py:1067`). Clears the `.env` entry and every mirror: env-seeded pool entries, the provider's model cache rows and matching `config.yaml` copies; OAuth and manually added pool entries of the same provider stay. 404 `<VAR> not found in .env`; 400 with Hermes' reason for a locked key.
- `DELETE /api/providers/oauth/{id}?profile=` (token). `{"ok": true, "provider"}`; 400 when `disconnectable` is false (with `disconnect_hint`, e.g. "Remove the API key from Settings → Keys instead."); 409 "No stored credentials were removed for …"; 500.
- `DELETE /api/providers/custom-endpoints/{id}?profile=`. Removes the entry and its key, and clears the default model when it pointed there. 404 unknown.
- `DELETE /api/credentials/pool/{provider}/{index}?profile=`. Removes one pool entry for good by its 1-based position (`{"ok", "count", "cleaned", "hints"}`; 404 bad index). Not used: see Removing.

**Not used, and why**

- `POST /api/env/reveal` (token, five per 30 s, audit-logged): see "Reveal" below.
- `POST /api/providers/oauth/{id}/submit`: answers 400 for every provider at `d923a5eb`; no PKCE paste flow exists.
- `POST /api/credentials/pool` (add a second key): out of scope.
- `GET /api/model/info`: context length and capabilities of the configured model; nothing in this job needs them.
- Gateway `model.save_key`, `model.disconnect`, `model.options`: same effects as the REST routes (`model.save_key` writes through the same `save_provider_env_credential`). REST keeps one client, one error shape and the generated code, and the app's other settings screens are REST. `model.disconnect` (every key and OAuth grant of a provider at once) is the one thing REST spreads over several calls; the app does it per credential instead, so the person sees what each removal does.
- Gateway `setup.status` and `setup.runtime_check`: built for the desktop's own backend and its boot record; `/api/model/options` already says whether anything can serve a chat, and Hermes' desktop deliberately stopped gating on `setup.runtime_check` after connecting.
- Gateway `onboarding.*` and `free_tier.*`: `onboarding.state` answers `eligible: false` on any backend that is not the desktop's local one, and the free tier is only offered there.
- `reload.env`: the dashboard and the gateway are one process; a saved key is visible to new sessions at once. Chats that are already running keep their credentials until a new chat, which the screen says.

## Goals / Non-Goals

**Goals:**

- A fresh server becomes usable from a phone in under a minute: open the app, tap "Connect a model", paste a key, keep the suggested model, chat.
- The person always sees which profile a credential belongs to and what a removal will stop.
- No key is ever kept, logged or visible outside the moment it is typed.
- Everything that lists models (composer pill, Helper models, Profiles default model) agrees with the screen after a change.

**Non-Goals:** see proposal.md. Design-level: no editing of a provider's non-key variables, no listing of `.env` variables that belong to tools or messaging, no per-chat credentials.

## Decisions

**Which profile.** The screen is opened for one profile and every request that reads or writes profile state carries it as `profile=<name>` (the two check routes, `POST /api/providers/validate` and `POST /api/providers/custom-endpoints/validate`, take no profile and write nothing): from the chat sidebar the chat's profile (`ChatController.profile`), from the Mac Profiles page the selected profile. A server that reports no profiles gets no `profile` parameter, and Hermes uses its own. Hermes keeps keys, account sign-ins and endpoints per profile (each profile has its own `.env`, `auth.json` and `config.yaml`; a named profile never inherits the default profile's keys, `agent/secret_scope.py`), so the screen's subtitle names the profile and the empty state says "Keys you add here are used by the <name> profile only." Answers that arrive after the screen was rebound to another profile are dropped (a generation counter, as in `MemorySettingsController`). A sign-in started for a profile keeps following that profile.

**Where it lives.**

- iPhone and Android phones: the chat drawer gets "Model providers" right before "Helper models"; it pushes the screen (`SettingsScaffold`, title "Model providers", subtitle "<profile> · N connected"). A provider's detail is a pushed page; the connect forms are full-height sheets (`showAdaptiveSheet`), the sign-in step is a page inside that sheet.
- iPad full screen and other windows from 900 pt (`isWideLayout`): the list sits beside the selected provider's detail, like Plugins and MCP servers; connect forms are dialogs (`showAdaptiveSheet`).
- macOS: a "Model providers" section on the Profiles page (`ProfileSection.providers`, detail "N connected", placed before Helper models) and the same sidebar action; the screen uses the Mac toolbar through `SettingsScaffold`, list beside detail from `kMacSplitBreakpoint` (560 pt of content width, since the Mac sidebar takes room `isWideLayout`'s 900 pt does not expect), forms in dialogs (never a bottom sheet); File > New is not claimed. Escape closes a form; Return submits it when the primary button is enabled.
- The composer pill's "Set up a model" and the welcome view's card open the screen for the chat's profile directly in its connect state ("Add a provider" in front).

**Merging four answers into one list.** `ProvidersRepository.load(profile)` reads `GET /api/model/options` (with `include_unconfigured=true`), `GET /api/env`, `GET /api/providers/oauth` and `GET /api/providers/custom-endpoints` in parallel and returns a sealed `ProvidersSnapshot` (`ProvidersLoaded` with per-source failures, `ProvidersUnsupported`, `ProvidersFailed`). It builds one `ProviderEntry` per provider:

- Identity: the options row's `slug` and `name`; for an account, the OAuth row's `id` and `name` (account ids are their own slugs, e.g. `openai-codex`); for an endpoint, the endpoint's `id` and `name`.
- How it connects (`ConnectMethod`), first match wins: `account` when the OAuth catalog lists the slug with `flow: device_code` (this beats the registry's `auth_type`, which says `oauth_external` for `openai-codex` and `xai-oauth` although the dashboard signs them in with a code); `key` when the options skeleton says `auth_type: api_key` with a `key_env`, or `/api/env` has a `provider_primary` key for the slug; `onServer` (show the command) for an OAuth row with `flow: external` and for `oauth_external`, `external_process`, `copilot`, `aws_sdk`, `vertex` and any `auth_type` the app does not know; `endpoint` for custom endpoints. A provider can have a key method and an external account at once (Anthropic: an API key, or the account through `hermes auth add anthropic`); the key form is then the primary action and "Use an Anthropic account instead" shows the server command. Rows with `auth_type: virtual` (`moa`) and the managed local-runtime row are left out.
- Connected: an options row with `authenticated` not false, an OAuth row with `status.logged_in`, or any custom endpoint. Its credentials: the `/api/env` provider key that `is_set` (preview: last four characters from `redacted_value`, none when it is `***`), the OAuth sign-in (with `source_label`), the endpoint's key (`has_api_key`), and extra pool entries. Only entries with `source: manual` and `auth_type: api_key` count as extra keys: sign-ins also create pool entries (`device_code`, `hermes_pkce`, `claude_code`, see `agent/credential_pool.py`), whose `token_preview` is the tail of an access token and must never be shown as "saved key ending in …"; `env:` entries mirror a listed key. Other entries are not listed and not counted.
- Default: `is_current` on the options row or endpoint, and the answer's top-level `model` and `provider`.
- Order: the default model's provider first, then connected providers in Hermes' order (the options answer is in `hermes model` order), then endpoints; "Add a provider" lists unconnected ones with "Recommended" first (Nous Portal, OpenRouter, OpenAI, Anthropic, from a constant in the app; the server sends no ranking), then the rest alphabetically, with a search field above 12 entries.

A source that fails does not hide the others: without `/api/env` keys can still be added (the variable is the skeleton's `key_env`) but previews and signup links are missing; without `/api/providers/oauth` account sign-in is not offered; without custom endpoints that section is hidden with a note. `GET /api/model/options` failing is the whole screen failing ("Couldn't load providers" with Try again), since it alone says what can chat. A 404 on a source reads as "not offered by this server", never as an error; a 404 on `/api/model/options` is `ProvidersUnsupported`.

**Connect with an API key.** The form shows the provider's name, one field "API key", the link "Get a key from <provider>" (the `/api/env` row's `url`, opened in the browser, shown only when it is an `https` URL), and Save. On Save the app trims the value, refuses an empty one, and calls `POST /api/providers/validate` with the key variable (6 s budget on the app side):

- `ok: true, reachable: true` → saves.
- `ok: true, reachable: false` (no probe for this provider) → saves; the confirmation says "Saved. Your first chat will show whether the key works."
- `ok: false, reachable: true` with Hermes' rejection message (the provider answered 401/403) → nothing is saved; the field shows Hermes' message and the form hides the bar's Save and offers "Edit key" (primary; Return triggers it on desktop and focuses the field) and "Save anyway" (secondary). A key saved with "Save anyway" (after a rejection or a provider error) counts as unchecked: the default-model step carries "Saved. Your first chat will show whether the key works.", never a plain "You're ready".
- `ok: false, reachable: true` with "Provider returned HTTP <n> for this key." (any other status, typically a 5xx while the provider is down; `config_env.py:1064`) → nothing is saved yet; the form shows Hermes' message under the heading "<provider> didn't answer normally", with "Save anyway" (primary here, since the key is probably fine) and "Try again". The app tells the two apart by Hermes' message prefix "Provider returned HTTP"; any other text is treated as a rejection.
- `ok: false, reachable: false`, a timeout, or the check failing → saves, with "Saved, but Hermes couldn't reach <provider> to check it."
  Then `PUT /api/env` with `provider_setup: true`. A save whose answer is lost ("may have happened") is never resent: the app re-reads the snapshot. For a first key, the provider now being connected through that key variable counts as saved. For a replacement nothing the server returns identifies the submitted key: the connection looks the same with the old key, and `redacted_value` shows only four leading and four trailing characters, which an old and a new key of the same provider can share (prefixes like `sk-or-v1` are common). So after a lost answer every replacement stays unknown: the form opens again with "Couldn't tell whether the key was saved. Paste it again to be sure." Saving the same key again is harmless (`PUT /api/env` writes the same value). For a first key that does not connect, the form opens with "Couldn't tell whether the key was saved. Paste it again to be sure." Replacing a saved key is the same form titled "Replace key"; it never shows the old value.

**Sign in with an account.** `ProviderSignIn` (owned by `ProviderSetupController`, one per profile and provider) calls `start`, then shows the code (large, monospaced, grouped as the provider gave it, with Copy) and "Open <provider>" (the `verification_url`, opened in the browser after the link check below), and polls `poll` every `poll_interval` seconds (at least 2, at most 10). On iOS and Android the timer pauses while the app is in the background and resumes with one immediate poll when it returns; on desktop it keeps running. It ends on `approved` (re-read the snapshot, then the default-model step), `denied` ("The sign-in was declined"), `expired` or a 404 ("The code expired. Start again"), `error` (Hermes' `error_message`, or "Sign-in failed" when empty), or after `expires_in` plus 30 s without an answer (treated as expired, the session cancelled). Polling failures back off like the minute polls (`network/poll_backoff.dart`) and show "Can't reach your server. Still waiting…" without ending the sign-in. Cancel calls `DELETE /api/providers/oauth/sessions/{id}`, so an approval that comes later saves nothing; leaving the sign-in page or the app does not cancel: the controller keeps polling while the providers screen exists and the list shows the provider as "Waiting for sign-in…" with Continue and Stop (labels "Continue sign-in to <provider>", "Cancel sign-in to <provider>"); Stop asks "Stop signing in to <provider>?" first. When the providers screen itself is closed the follower stops polling without cancelling; the server keeps the session up to 15 minutes, and a sign-in approved meanwhile shows as connected the next time the screen loads. Start failures show Hermes' `detail` (for example Nous' "already signed in" sentence, or OpenAI's device-code authorization notice) with "Check again", which re-reads the snapshot (the account may already be connected) and offers Sign in again.

When the providers screen closes (or sign-out, a server change), the follower stops without cancelling, so "keeps following" means: while the person is on the sign-in step, elsewhere in the providers screen, or in another app. A Nous poll answer's `model` does not say whether Hermes changed anything: the free-tier promotion poller sets it only when `settle_after_upgrade` changed the default (`web_server_oauth.py:235`), but the plain sign-in poller (`_nous_plain_poller`, used when there is no free-tier identity, `web_server_oauth.py:357-359`) sets it to whatever default the config already carries, since `settle_after_upgrade` returns the current model with `changed: false` when the config is not on the free tier's route (`anon_auth.py:1174-1175`), and the poll answer does not include `changed`. So the app ignores the poll's `model`. It keeps the profile's default from the snapshot read before the sign-in started, re-reads the snapshot on approval, and only when the re-read default is non-empty and differs from that (Hermes moved it) shows "New chats use <model>" with Change. When the re-read default is empty (Hermes clears it when it has no eligible recommendation, `anon_auth.py:1186-1193`), the step asks the person to choose ("Choose a model for new chats") and saves nothing; otherwise the default-model step follows the rule above, including "Keep <current model>". "Signed in as <email>" is shown only when `account_email` is present (Nous only). Hermes' `source_label` is not shown, since it can be a file path on the server.

External account providers show "Connect <provider> on your server" with the `cli_command` Hermes gives (selectable, Copy) and "Check again", which re-reads the snapshot. The app never starts an Anthropic subscription sign-in: Hermes marks it external on purpose.

**Custom endpoint.** Fields: Name ("Shown in the model picker"), Address ("https://… · Hermes connects to it from your server, so localhost means the server itself"), API key (optional, obscured), then "Check connection". Under Advanced: API type (Automatic, Chat Completions, Responses, Anthropic Messages; `api_mode` `""`, `chat_completions`, `codex_responses`, `anthropic_messages`) and Model (typed by hand when the endpoint lists none). Check sends `POST …/custom-endpoints/validate`; the result is one of: models found (a model menu, the first selected), a warning (`ok: false, reachable: true`, Hermes' message, Save still allowed when a model is typed), unreachable ("Hermes couldn't reach <address> from your server."). The address saved is `resolved_base_url` when the check returned one, and the form says so when it differs ("Hermes will use <resolved>"). An address that is `http://` to a host the app's `isLocalHost` rule (`lib/src/auth/server_address.dart`) does not accept, with an API key typed, shows the warning "This address isn't encrypted. Your key would be sent to it in plain text." and Save asks "Send the key unencrypted?" (Cancel default, "Save anyway") before sending; this mirrors the app's own `allowCleartext` rule, except that "local" means local to the Hermes server, since the server, not the device, makes the call. Save sends `POST …/custom-endpoints` with `make_default` true when the profile has no default model (otherwise the default-model step asks), `models` from the check, and `api_key` only when the field was touched (an edit with the field untouched omits it, so the stored key stays; a cleared field asks first "Remove the saved key for <name>?"). Endpoint addresses and names are shown in the UI; they are never logged.

**Choosing the default model.** After a provider connects (any method), the app asks `GET /api/model/recommended-default?provider=<slug>` (8 s budget), re-reads the snapshot, and shows "Use <model> for new chats?" with the recommended model, "Choose another model…" (the shared picker limited to this provider) and "Keep <current model>" when the profile already had a working default. On a profile with no usable default before, the recommended model is saved at once (as Hermes' desktop does on first run) and the step reads "New chats use <model>" with Change. When Hermes recommends nothing (`model` empty, or the call fails), the app saves nothing and asks the person to choose ("Choose a model for new chats", the picker limited to this provider). It never falls back to the provider's first listed model: Hermes warns that aggregator lists lead with their most expensive model (`models.py:183`). Saving is `POST /api/model/set` `scope: main`; `confirm_required` shows an alert titled "Use this model?" with Hermes' `confirm_message` as its body and "Use it anyway" / Cancel and resends with `confirm_expensive_model: true`. The screen's "Default model" row at the top shows the model's display name where Hermes gives one, with the id as secondary text when they differ, and opens the same picker over every connected provider (`withEffort: false`). The Profiles screen keeps `PUT /api/profiles/{name}/model`; both write `model.provider` and `model.default`, so they agree (an open question below covers unifying them).

**Removing.** The detail page's destructive row depends on the credential: "Remove key" (`DELETE /api/env`), "Sign out" (`DELETE /api/providers/oauth/{id}`; when `disconnectable` is false the row is replaced by the `disconnect_command` to run on the server, else by Hermes' `disconnect_hint`, except when the sign-in's `status.source` is `env_var`: Hermes' hint then points at the web dashboard ("Remove the API key from Settings → Keys instead.", `oauth.py:647`), so the app shows its own "Remove key" row for that provider instead of the text), "Delete endpoint" (`DELETE …/custom-endpoints/{id}`). Hand-added pool keys (see "Connected" above) are listed read-only with "Manage this key on your server with `hermes auth`." and no button: `DELETE /api/credentials/pool/{provider}/{index}` addresses an entry by position only, and positions shift when the pool changes (`agent/credential_pool_admin.py` `remove_index`), so neither a re-read nor any client-side check can guarantee the app removes the key the person confirmed; removal is permanent. In-app removal waits for an identity-checked route upstream. Each asks first, naming the provider and profile; when the provider serves the default model the alert adds, in the destructive style, "New chats in <profile> can't start until you pick another model." After the call the snapshot is re-read. If the provider is still connected (another key, a sign-in, a hand-added key), the detail says "Still connected through <n> other saved credential(s)" and lists them. A 404 on removal ("not found") counts as already removed. A lost answer re-reads; nothing is resent.

**Path parameters.** The generated client puts path parameters into the URL unencoded (as noted for Plugins). Endpoint ids keep dots and colons (`local-127.0.0.1:8283`, `config_env.py:368`) and pool provider slugs can be `custom:<name>`, so the repository percent-encodes `endpoint_id`, `provider_id`, `provider` and `session_id` before calling the generated method, with a test for each.

**Links from the server.** Every address Hermes sends that the app opens (the key `url`, `verification_url`, `docs_url`) goes through one check before `launchUrl`: an absolute `https` URL with a host (and `http` only for a host `isLocalHost` accepts); anything else (`javascript:`, `hermes://`, `file:`, relative) is not opened and its button is hidden. Addresses are shown as text only when they pass.

**Reveal (decided: not offered).** `POST /api/env/reveal` would put a whole key on a phone screen, into the app switcher's snapshot and onto screen recordings, it is limited to five reveals per 30 seconds per server and every call is written to the server's log. The job it serves (checking which key is saved) is met by the last four characters and the provider's own console; the job of fixing a wrong key is met by Replace key. So the app never calls it, and the spec forbids showing a full saved key.

**Secrets on the device.** Every secret field follows the app-wide rule written in `docs/architecture/settings-screens.md` ("Secret fields"): Typed secrets are obscured by default and have a Show/Hide control (a 44 pt touch target on iOS and iPadOS, 48 dp on Android, a standard Mac button) labelled "Show key" / "Hide key". Under the field a muted line, announced to screen readers, reads "<N> characters entered"; the count is never stored. A shown value is hidden again when the lifecycle leaves `resumed` (`inactive` included), when a check or save starts, after any failed save, and when the form closes; the shown state is never persisted or restored. Going inactive or to the background only hides a shown value: the typed text stays, so a person can copy a key from another app and come back. The typed text is cleared only when App Lock locks the app, when the form closes (a successful save closes it), and when the answer to a save is lost: the key may already be saved, so the field is cleared and the message asks to paste it again. After a plain failed save (a refusal, an error answer) the typed value stays in the field, hidden, so it can be edited. A saved value is never revealed (no `POST /api/env/reveal`). The field is the shared `SecretFieldRow` (`lib/src/widgets/secret_field_row.dart`), built on `GroupedTextFieldRow` with `obscureText: true`, `autocorrect: false`, `enableSuggestions: false`, `enableIMEPersonalizedLearning: false`, `smartDashesType`/`smartQuotesType` disabled, `keyboardType: TextInputType.visiblePassword` on Android, no `autofillHints`, one line, and no `restorationId` (state restoration would write it to disk); toolsets uses the same widget. The value lives in the field's `TextEditingController` and in the request. Requests go through the shared `Dio`; the request logging and span interceptors record method, route template and status only, never bodies (a test sends a key through every write path with telemetry on and asserts it appears in no span attribute, log record or breadcrumb). Errors are caught in the repository and mapped to typed failures carrying Hermes' `detail` or a fixed sentence. A 422 is the exception: FastAPI's validation answer echoes the submitted body in `input`, `api_key` included, so a 422 body is never parsed, shown or logged (it becomes the fixed "Hermes didn't accept the request"), and the app always sends every required field of `CustomEndpointUpdate` (`name`, `base_url`, `model`, with `model: ""` before a model is picked) and of `EnvVarUpdate` (`key`, `value`) so the case does not arise; a `DioException` is never rethrown or turned into a string, since its `requestOptions.data` holds the key. Nothing here writes to shared preferences, secure storage, the surface snapshot, notifications, Spotlight or widgets. The device code is shown and copyable (it is meant to be typed elsewhere) and is never logged. App Lock needs nothing extra: the gate covers the screen like every other, and a sign-in keeps polling under it.

**Keeping pickers consistent.** `ProviderSetupController` exposes `changes` (a counter bumped after every successful write). `ChatScreen` listens while the screen is open and calls `ChatController.refreshModelOptions()` when it changes and when the screen closes, so the composer pill leaves "Set up a model" as soon as a provider is connected; Helper models and the Profiles screen read their options when opened, as now. The chat's own `GET /api/model/options` stays without `include_unconfigured`, so the composer's picker keeps showing only usable models.

**First run.** `ModelOptions.fromJson` (the chat's own read, without `include_unconfigured`) additionally records two facts it currently drops: whether a row is `authenticated` but lists no models (`warming`), and whether the top-level `provider` names a provider that is not among the authenticated rows (`currentMissing`: Hermes leaves such a provider out when its credential is gone, `inventory.py:724-736`). When `currentMissing` is set (whatever `modelOptionsState` says: another provider may still be ready while the default's provider is gone, and sending is disabled then too), or when `modelOptionsState` is `incomplete`, the starter prompts are replaced by one of three cards, `currentMissing` first:

- `currentMissing`: "Reconnect your model's provider" / "New chats in <profile> use <model>, but its provider's key is missing or no longer works." / "Reconnect", which opens the screen on that provider: its detail while it is connected (Replace key), else the way to connect it (its key form, Sign in, or the server command).
- `warming` (and not `currentMissing`): "Hermes is loading your models" / "A provider is connected, but its model list isn't ready yet." / "Check again" (re-reads the chat's model options). It does not lead to "Connect".
- otherwise: "Connect a model to start chatting" / "Your Hermes server has no model provider for <profile> yet." / "Connect a model".

A key that Hermes could not or did not check and turns out to be wrong or out of credit is not caught here (the provider lists models from Hermes' catalog either way); the first chat fails with the provider's error as any failed reply does, and that failed reply gets a "Check model providers" action that opens the screen on the default model's provider. The composer pill's "Set up a model" opens the same flow; `showModelSetup` remains only for a server whose providers screen is unsupported (404), with its terminal command. The send stays disabled as today.

**Hiding on an old server.** The sidebar action and the Profiles section are shown while `ChatController.models` exists and its last `GET /api/model/options` was not a 404 (the existing `unsupported` state). Inside the screen, each optional source's 404 hides its part as described above. The minimum Hermes for the whole feature is the pinned `d923a5eb` (0.22.2); the contract test records the shapes there.

**Telemetry.** Recorded through the connection's telemetry (`HermesRepositories.telemetry`), so spans carry `hermes.*` server attributes:

- Span `providers.load` in `ProvidersRepository.load`: `sources_ok` (0–4), `sources_failed` (0–4), `connected` (bucket `0`, `1`, `2-5`, `>5`).
- Span `providers.key.save` around check and save: `checked` (`accepted`, `rejected`, `provider_error`, `unchecked`, `unreachable`), `outcome` (`saved`, `not_saved`, `unknown`, `failed`), `forced` (Save anyway).
- Span `providers.signin` from start to end: `outcome` (`approved`, `denied`, `expired`, `cancelled`, `failed`, `abandoned`), `polls` (bucket).
- Span `providers.endpoint.check`: `outcome` (`models`, `warning`, `unreachable`, `failed`), `models` (bucket). Span `providers.endpoint.save`: `outcome`, `made_default`, `edit`.
- Span `providers.remove`: `kind` (`key`, `account`, `endpoint`), `outcome` (`removed`, `already_gone`, `refused`, `unknown`, `failed`).
- Span `providers.default_model.set`: `outcome` (`saved`, `declined`, `failed`), `confirm_asked`.
- Log `providers.connected` (`method`: `key` | `account` | `endpoint`, `first`: bool) once per connection made, so setup success can be counted; log `providers.read_failed` (`source`: `options` | `env` | `oauth` | `endpoints` | `pool`, `error_type`) once per source per load, to see contract drift.
- Breadcrumbs `providers.opened` (`source`), `providers.connect.started` (`method`), `providers.remove.confirmed` (`kind`).

None holds a key, code, provider slug, endpoint name or address, model id, profile name or Hermes' message text. Provider slugs are left out even though they are catalog words, to keep the rule simple.

## Risks / Trade-offs

- [A provider connected a moment ago lists no models in `/api/model/options` (non-blocking catalogs)] → `recommended-default` builds with blocking catalogs first, which warms the cache; if the provider still lists none, the default-model step shows the recommended model alone with "Hermes is still loading this provider's models" and Retry. Task 1.1 measures it against a real backend.
- [Hermes' key check rejects a working key (proxy, region)] → "Save anyway" is always offered after a rejection; nothing is hard-blocked.
- [The sign-in session lives in the server's memory] → a server restart ends it (poll 404); the app says "The code expired. Start again".
- [A key passes the check (or cannot be checked) but has no credit or the wrong scope] → it is only found when a reply fails; the failed reply's "Check model providers" action (First run, above) leads to Replace key.
- [The app is closed while a sign-in is pending] → the server keeps polling the provider for up to 15 minutes and saves the credential on approval; the next load shows it connected. Cancel is only sent when the person asks.
- [Removing the default model's provider leaves the profile unable to chat] → the confirmation says so in the destructive style, and the welcome card appears in the chat.
- [Four reads per open] → in parallel, each with the client's timeout; `GET /api/model/options` on its cache path answers fast.
- [Hermes adds or renames providers and auth types] → unknown `auth_type`s become "Connect on your server" with `hermes auth add <slug>`; rows that do not parse are skipped and counted in `providers.read_failed`.
- [Managed installs lock keys] → Hermes' 400 reason is shown as it is ("…managed…"), and the write is not retried.

## Migration Plan

None. Nothing is stored on the device; `showModelSetup` stays for servers without the routes.
