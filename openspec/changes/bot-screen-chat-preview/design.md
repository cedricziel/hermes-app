# Design

## Context

`bot-screen-status` and `bot-screen-card` give `ChatScreen` one `BotScreenController` per chat profile, with `watch()` demand handles and the foreground/unlocked/window gates already driven by `ChatScreen`. Tool calls render through `chat_builders.dart`: a run of calls the agent made back to back becomes a `ToolCallGroup` (`lib/src/chat/widgets/tool_call_group.dart`), which shows a single call as its own `ToolCallCard` and folds two or more behind a header that starts collapsed. The Activity panel opens through `_toggleActivity` in `chat_screen_navigation.dart`, which flips `_activityOpen` on wide layouts and opens a detent sheet on phones; calling it while the inspector is open closes it.

## Decisions

- **Which run shows it.** While a reply is pending, `chatMessageToFlyer` (the mapper, which sees the whole reply, where a message builder sees one run) marks the run that holds the reply's latest tool call named `computer_use` with `kMetaScreenPreview` (a `ScreenPreviewRun`: the reply's id and start time), whatever that call's status, since the preview lasts until the reply ends. No other run is marked. When the reply ends (completed, failed or stopped), no run qualifies. `chat_builders.dart` only draws the preview for a marked run. Of two replies pending at once (a turn Hermes runs by itself and the prompt's), only the newer one shows it.
- **Slot placement.** `ToolCallGroup` gets `Widget? preview`, drawn outside any card and in the same place for every run: below the card of a run of one call, below the header of a longer run, where it stays visible while the group is folded. A run of one call is a column of card and preview, so the card keeps its state when the preview comes and goes. `ToolCallCard` gets no slot. Both widgets stay plain and catalog-ready.
- **`BotScreenPreview`** (`lib/src/bot_screen/widgets/bot_screen_preview.dart`) takes a plain model (`frame(bytes, aspectRatio)`, `suppressed(byYou)`, `hidden`) and `onTap`; a small binding listens to the controller and maps its state, drawing nothing unless the screen runs. It is one button for assistive technology, labelled "Hermes's screen, live. Hermes is in control" (or who holds control), and the person-in-control pill is at least 44 pt tall under Apple chrome. `gaplessPlayback: true` avoids flicker on refresh, frames decode no wider than they are drawn and are never upscaled, and a frame leaves the image cache when a newer one or the end of the preview replaces it.
- **On-screen demand.** The binding holds a `watch()` handle only while some part of it is inside the viewport of its scrollable and its page is not covered (`TickerMode`, as `BotScreenDemand` does); a widget built in the `ListView` cache extent but off screen holds none. `OnScreen` (`lib/src/bot_screen/widgets/on_screen.dart`, about 50 lines) does the check: after each frame it transforms the preview's `RenderBox` into `RenderAbstractViewport.maybeOf(box)` and tests overlap with the viewport, a box with no area counting by its top edge, and reports changes only. A zero-size box (a preview with nothing to show yet) is therefore found, and the watch it holds is what reads the status, so the preview can appear. It is in-repo instead of the `visibility_detector` package: that package's upstream (`google/flutter.widgets`) is archived, its last release is from 2023 and it still declares `sdk <3.0.0`, and it has open issues with slivers, bottom sheets and swipe-back. The handle is released on dispose.
- **Keeping its state.** The preview is keyed per reply (`BoundBotScreenPreview.keyFor`, a `GlobalKey` kept for the last few replies), so it keeps its state, frame and watch when it moves between a run's shapes or to a later run, or when an approval shifts the children around it. A reply that is not the newest pending one draws nothing and holds no watch; the controller's preview registry says which owns it.
- **Open-only action.** `_openActivity({required String source})` in `chat_screen_navigation.dart` opens the inspector or the sheet and does nothing if the inspector is already open; `_toggleActivity` keeps its behaviour. The preview calls `_openActivity(source: 'preview')`, which records the existing `chat.activity.opened` crumb with that source.
- **Shared poll attribute.** `BotScreenController` passes its current watcher count to `BotScreenRepository.thumbnail(watchers:)`, which sets it on the thumbnail span.
- **Who holds the controller.** `ChatScreen` passes its controller and the open-only action to `boundChatThreadView`, which builds a `ScreenPreviewBuilder` for `ChatThreadView`.
- **Design system sync.** `design/web` `ToolCallGroup` gets `preview?: ReactNode` and a `BotScreenPreview` component (`docs/BotScreenPreview.md`, `category: Agent activity`), documented in JSDoc so the synced prompt explains them.

Platforms: iOS, Android, macOS, Windows, Linux. No native change. `ConversationWindowScreen` and `QuickPanelScreen` pass no controller, so their transcripts show no preview.

Invariants touched: telemetry. Breadcrumbs `bot_screen.preview.shown` (in the binding, once per reply via the reply's id kept in memory, when its preview is the newest and on screen with something to show) and `bot_screen.preview.tapped`; the thumbnail span's `watchers` count. No user content, ids or names.

## Risks / Trade-offs

- [A streaming reply rebuilds the run often] → The preview listens only to the controller; the run rebuild does not refetch.
- [Checking visibility ourselves] → One post-frame callback per mounted preview, which exists for the newest pending reply only; it reports changes only and costs a transform per frame.
- [Two surfaces (card and preview) on screen at once] → One poll, counted as two watchers.
