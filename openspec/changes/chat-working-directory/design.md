# Design

## Context

Read from the Hermes source at `d923a5eb` (the revision `openapi/HERMES_REF` pins) and its contracts (`openrpc/hermes-gateway.openrpc.json`, `openapi/hermes-agent.openapi.json`). Paths below are in the Hermes repository. Nothing was run against a live backend; items that need it are in the final verification tasks.

### Model

- A **project** is a named set of folders in a per-profile SQLite file `$HERMES_HOME/projects.db` (`hermes_cli/projects_db.py`). One folder is primary. A project row:

  ```json
  {
    "id": "p_1a2b3c4d",
    "slug": "demo",
    "name": "Demo",
    "description": null,
    "icon": null,
    "color": null,
    "board_slug": null,
    "primary_path": "/home/me/code/demo",
    "archived": false,
    "created_at": 1760000000,
    "folders": [
      {
        "path": "/home/me/code/demo",
        "label": null,
        "is_primary": true,
        "added_at": 1760000000
      }
    ]
  }
  ```

  A chat has no project field: its project is whichever non-archived project has a folder equal to, or an ancestor of, the chat's `cwd` (longest folder wins; `project_for_path`, `projects_db.py:462-477`). "Active project" is only a per-profile pointer that nothing here needs.

- A **chat's working directory** is the `cwd` column of its stored session (with `git_branch` and `git_repo_root`). `GET /api/sessions` rows carry all three (`list_sessions_rich(compact_rows=True)` leaves out only prompt columns; `hermes_state_sessions.py:~1108`). `session.list` and `session.active_list` rows carry none. The app already reads `git_repo_root`/`cwd` into `ChatThread.folderPath` for `chat-folder-grouping`.
- Paths are on the Hermes host (or, for a profile with an SSH terminal backend, on the remote: `~`-relative or absolute remote paths). The app never resolves them locally.

Every `projects.*` method and the REST routes take `profile`; unknown profile gives gateway error `4064` or REST 404. `projects.*` errors are `5061` (generic), `5062` (no such project), `5063` (bad argument); an older server answers `-32601`. `projects.changed` (an empty payload, 2 s poll of `projects.db`) and the rest of `projects.*` are not used in this change.

How the Hermes dashboard does it (`web/src/components/ChatWorkspacePicker.tsx`): one select with "Default · <default_cwd>", then each project folder, then discovered repos by recency, then "Other path…" (a text field), a "Rescan repositories" button, applied only to a fresh chat. The desktop's folder dialog (`RemoteFolderPicker`) browses `/api/fs/list` with a breadcrumb and a ".." row. The app follows the same shape and adds the phone concerns.

### Facts that shape the design

1. `session.create` swallows a bad path, so validating only on the server's answer is not enough: the app checks the path first where it can and always compares `info.cwd` afterwards.
2. `cwd_explicit: true` is what makes a deliberate pick win over a named profile's configured workspace. A picked folder sends it; "Default" sends neither field.
3. `session.workspace.move` is non-destructive and has no busy refusal, so it can serve idle chats that have no runtime session. The app still offers it only while no reply runs, because an agent mid-tool-call changing directory under itself is a surprise nobody asked for.
4. `GET /api/fs/list` is subject to the hosted-files lock and shows symlinked folders as files; `complete.path` is not and follows symlinks. They complement each other.
5. `info.project` and the tree disagree for auto-discovered repos (only saved projects resolve on `info`). The app resolves a project from `projects` itself, with the server's rule, so it never claims a project the server would not.

## Goals / Non-Goals

**Goals:**

- The user can always tell which server folder a chat runs in, before the first message and afterwards.
- Choosing a folder for a new chat is one or two taps for a known project or repo.
- A wrong folder is never silent: not on creation, not after a move.
- Nothing about the folder is stored or sent anywhere but the user's own server.

**Non-Goals:** the list under "Not in this change".

## Decisions

**Where the folder is shown (decided).**

- A new chat (the welcome view): a `WorkingDirectoryRow` directly above the composer, "Runs in <folder name>" with "<path> · on your server" below and the branch when known; a tap opens the picker. It uses the profile's `default_cwd` while nothing is picked and says "Server default" beside it, so the default is visible, not hidden.
- An open chat: a second line under the header title with the folder name and branch ("demo · main"), a tap opens a details sheet (full path "on your server", project, "Change folder…" when allowed). The first send is never gated on it.
- The line is hidden (not an error) when the chat has no folder data and the server lacks the workspace routes.
- Risky folders get a plain note in the picker and the row ("This is your server's home folder, which holds many projects."): the folder equals `home` or `/`.

**Picker content (decided).** One list, in this order: Server default (path), then a section per source:

1. **Projects**: each non-archived project, one row per folder (project name; the folder label or last path segment when it has several folders; the primary one first). Tapping a project with one folder picks it; several folders show their rows inline, never a hidden second step.
2. **Recent**: `repos` from the same response not already under a project folder, newest activity first, with a count ("12 chats").
3. **Browse folders on your server** and **Type a path** rows, which push `FolderBrowser` and `PathEntry`.

A search field filters projects and repos on the device when the project and recent rows together are more than eight. The workspaces read is owned by a `WorkspaceCatalogLoader` (one per new-chat recipient profile, kept while the welcome view shows, cleared on profile switch, sign-out and Change Server), because the row above the composer needs `default_cwd` and the project tag before the picker opens; the picker reuses its answer and re-reads on open (and again on Rescan, `scan=1`, shown only when `scan_enabled` is true and "Rescan" says "Look for projects on your server"); a stale list is acceptable while it re-reads. When the list comes back empty the picker says so and offers Browse and Type.

**Browsing (decided).** `FolderBrowser` starts at the server default or the folder's parent, lists folders only (`isDirectory`), keeps a breadcrumb of the path, and shows "Use this folder" as the primary action. It reads `GET /api/fs/list` per level, treating a 200 with `error` as a failure shown in the list ("Couldn't open this folder. Hermes isn't allowed to read it." for `EACCES`, "This folder doesn't exist on your server." for `ENOENT`). Browsing inside a locked root still works, so a 403 has three meanings, told apart by its detail: the boundary ("Path is outside the managed read boundary") on the first read (from the default or a project folder) hides Browse for the visit; the boundary on a later level (going up past the allowed root) says "This folder is outside what this server lets you browse" for that level, with "Use" disabled; any other 403 (an SSH profile maps `EACCES` to 403) or a 200 with `EACCES` says "Couldn't open this folder. Hermes isn't allowed to read it." with "Use" still enabled for that folder. A lost connection (503) is "unreachable". It says "This server only lets you browse its own folders. Choose a project or type a path." No creating folders in v1.

**Typing (decided).** `PathEntry` is a text field with the keyboard type URL, autocorrect off, and a suggestion list from `complete.path` for the typed text (debounced 250 ms, only the latest answer kept, `meta == "dir"` rows only; a lone `/` or `~/` lists the roots). The field must start with `/` or `~`: a relative path is never accepted, since Hermes would resolve it against its own directory and the result could not be compared. The app builds the next text itself from the directory part of what was typed plus the suggestion's `display` (the entry name and a `/`) and ignores `text`: for a non-`@` word Hermes returns `text` relative to its completion root (an absolute word such as `/home/me/co` gives `../me/code/`), and `complete.path` cannot send `cwd_explicit`. Hermes applies its 30-item cap to files and folders together before the app filters to folders, so a folder in a directory with many files may be missing; the field says "Keep typing to narrow the list" when 30 items came back, and Browse is the way to see every folder. Selecting a suggestion extends the text; "Use this folder" is enabled when the path exists as a folder: an `fs/list` read of that path answers without `error` (when `fs/list` is locked, the choice is accepted and the post-create check is the safeguard). Never "device files": the field's label is "Folder on your server".

**Choosing (decided).** The draft holds a `WorkspaceChoice` (`path`, optional project name and branch for display, `source`) on `ChatThread.workspaceChoice` for a not-yet-created chat, like `modelChoice`. It lives in memory, is cleared on sign-out, profile switch (the recipient's profile decides defaults) and once the chat is created, and is never persisted. `ChatTransport.send` gets `WorkspaceChoice? workspace`; `HermesGatewayTransport` adds `cwd` and `cwd_explicit: true` to `session.create` only when the chat is new and a folder was picked. A resume sends nothing (`session.resume` takes no cwd and the stored one is used). Sends that carry no choice behave as today.

**After creation (decided).** The transport returns the session's `info.cwd`, `branch` and `project` through a new `WorkspaceBound` event (alongside `ThreadBound`). The controller sets the thread's working directory from it. When a folder was picked and the resolved path differs from the pick (compared after trimming trailing separators and expanding a leading `~` with `home`; paths are always absolute or `~`-led, so there is no relative rule), the chat shows an in-transcript notice "Hermes started in <folder> instead of <picked folder>. The folder may not exist on your server, or this profile may use its own folder." with one action, "Choose another folder", opening the picker. The prompt was already sent, which is why the notice is also what the picker's pre-check tries to make rare. The log event `workspace.cwd_mismatch` counts it.

**Moving an existing chat (decided).** From the details sheet (and the Mac thread menu, "Change Folder…"), the same picker opens with the chat's current folder marked; picking shows a confirmation: title "Change the folder for this chat?", body "Hermes will read files, edit them and run commands in <folder> for new messages. Nothing is moved or deleted. Files already written stay where they are.", actions "Change folder" and "Cancel" (Cancel default). On confirm the app calls `session.workspace.move` with the stored id and profile, shows the new folder from the answer, and updates the list row's folder (the thread's `folderPath` becomes the answer's `git_repo_root`, falling back to `cwd` when that is null or empty, and it regroups under `chat-folder-grouping`). A refused answer (`4017`) says "That folder doesn't exist on your server." and keeps the old one; `4007` says "This chat no longer exists on your server." and `4064` "This chat's profile no longer exists on your server.", both with "Nothing was changed."; `-32601` hides the control for the connection. `5007`, a lost answer and a move with no answer after 10 s say "Couldn't change the folder. Checking…" and re-read the chat's row (`GET /api/sessions/{id}?profile=<profile>`, whose row carries `cwd`; `sessions.py:562`) instead of resending, then show what the read found: the new folder, "Folder changed to <folder>."; the old folder, "The folder wasn't changed. Try again." The success text always comes from the server's answer or its read, never from what the app expected. The control is disabled with the reason "Wait for the reply to finish." while the chat replies, and the check runs again when the person confirms: a reply that started meanwhile closes the confirmation with that reason and nothing is sent. While the move is in flight, Send is held with "New messages wait until this is done.", because Hermes lets a live agent follow a move even mid-turn (`methods_session.py:1101-1104`). A chat that is a Bot Chat registry, a branch in progress or another profile's chat that is not open offers no change.

**Design pass (decided).** The Claude Design canvas "Hermes: Working directory" (https://claude.ai/artifact/JypA8yLhwweV9b6uZA2jpp; decisions, corrections and added copy in the brief's "Design (done)" section) settles the look and these behaviours:

- Every waiting state ends after 10 s, and none of them sends anything again by itself: the row's "Looking up your folder…" (then "Runs in the server's default folder", tappable; the picker then shows the failure); the picker's "Loading projects…" (then the "Couldn't load your projects." banner); "Opening <folder>…" in Browse (then "Couldn't open this folder." with Try again); "Checking…" in Type a path (then "Couldn't check this folder." with "Check again", "Use this folder" disabled); a scan (then "Couldn't finish looking for projects. Try again.", list unchanged); a move's lost answer, "Couldn't change the folder. Checking…" (then "Couldn't confirm the change" with "Check again", a re-read, and "Change folder…" offered again). The 10 s run from the request, on a monotonic clock; a late answer that arrives afterwards still updates the screen.
- The move request itself ends after 10 s without an answer and becomes a lost answer: the row is re-read with the chat's `profile`, never resent. The re-read decides the outcome ("Folder changed to <folder>." or "The folder wasn't changed. Try again."); `5007` takes the same path, re-read first.
- **Reading a 403.** One constant, `Path is outside the managed read boundary` (`web_server_files.py:217`), matched as a case-insensitive substring of `detail`; a `detail` that is not a string counts as unrecognised. A recognised boundary on the first read hides Browse for the visit; on a later level it is "outside", with "Use" disabled. "File is not readable" (an SSH profile's `EACCES`, `files.py:287,296`) is "not allowed". Any other 403 text is read the least capable way: "Use" disabled and, on the first read, Browse hidden.
- **Old server or missing folder.** An SSH profile answers a missing folder with HTTP 404 "File not found", the same status as a server without the route. The picker probes `GET /api/fs/list` once when it opens (at the server default); a 404 there means "unsupported" and hides Browse, and a 404 after a successful probe means the folder is gone. `ENOTDIR` on SSH arrives as 400 and is shown as missing.
- **"Use" after `EACCES`** stays enabled, because the server accepts any existing folder (it only checks that it is a directory), with "Hermes may not be able to work here." above it, in Browse and in Type a path.
- **Search** appears when the project and recent rows together are more than eight.
- **Scan.** "Found 1 new folder." in the singular. When the profile's `desktop.repo_scan_roots` (default `[]`, `config_defaults.py:2627`) is empty, read from `GET /api/config?profile=` when More opens, no scan is sent and the picker says "No folders to scan. Scan folders are set on the server." (the catalog's `scan_enabled` is true by default even with no roots).
- **Typed suggestions.** When Hermes returned its 30 items and none was a folder, only "Keep typing to narrow the list." shows.
- **Mismatch notice.** "Hermes started in <folder> instead of <picked>. The folder may not exist on your server." The clause "or this profile may use its own folder" is added only when the create was retried without `cwd_explicit`.
- **Offline picker.** Browse and Type are shown disabled with the reason in their section footer: "You're offline. Browse and Type need your server."
- **Up** in Browse is unrestricted within what the server lets you browse; stopping at a git root is a Files rule (server-files), not this picker's.
- **Shared with server-files.** One widget each: the breadcrumb is server files' `FilePathBar`, the folder list is `FilesBrowserView`'s list in a "pick a folder" mode, and the path text takes server files' `ServerPath` model. Whichever change lands first builds them in `lib/src/files/widgets/` (or `lib/src/widgets/` if a third user appears); the other uses them.
- **Accessibility.** The full path is reachable by touch: in the details sheet, and by a long press on any cut path (a tooltip with the full path; on the desktop the text is selectable). Breadcrumb segments are focusable buttons labelled with their full path. Mac pointer targets are at least 28 pt, touch targets 44 pt (48 dp). The search field has a label. Status and tags always carry words.
- A disabled control always shows its reason next to it and exposes it as its description: "Wait for the reply to finish.", "You're offline.", "Changing the folder…", "Checking the folder…".
- "Use “<folder>”" in Browse names the current folder and is disabled only for a missing level or one outside the boundary.
- The move's confirmation never has a filled or red action; Cancel is the default (bold on Apple; on Android two text buttons, Cancel first). Its outcomes show in the details sheet as a `Banner`.
- In a move the chat's folder is a checked row marked "Current"; when no list holds it, it is added at the top of Projects (or Recent when no project matches).
- On the Mac "Change Folder…" is shown disabled while the chat replies and hidden only when the server lacks `session.workspace.move`.
- Largest text: nothing is capped. At accessibility sizes the header's folder line moves out of the bar into a full-width row under it, paths wrap in full instead of being cut, and detail rows stack label over value.
- Paths are cut in the middle everywhere they are cut (row, picker rows, folder section headers that show a path), with "· on your server" kept; the full path is always in the semantics label and the details.
- The picker's rows and the typed-path suggestions show the bare path, not "· on your server": the sheet's subtitle already says "On your server" and every row is a server folder. Every other place a path stands alone (row, details, confirmation) keeps the suffix.
- The scan's outcome is a line under the list (an inline bar that is announced when it appears), not a snackbar: the picker is its own sheet, so a toast over the chat would sit behind it. The host clears it.
- "· on your server" is set with non-breaking spaces, so a wrapped path moves the whole suffix to the next line.

**Why not `session.cwd.set` (decided).** It requires the runtime session id (the app resumes lazily and holds none for an idle chat), refuses a running session with `4009`, and for a stored chat the next `session.resume` reads the stored `cwd` anyway, which `workspace.move` writes.

**Why not validate with `projects.for_cwd` (decided).** It falls back silently, so it cannot say "does not exist", and without `cwd_explicit` it answers with a named profile's own workspace rather than the asked folder. `GET /api/fs/list` says `ENOENT` and `ENOTDIR` directly; `complete.path` supplies the typed suggestions.

**Project resolution (decided).** `WorkspaceProjects.projectFor(path)` is a pure function over the loaded `projects`: the non-archived project with the longest folder that equals the path or is an ancestor (segment-wise, separators and a trailing slash normalised, case-sensitive on POSIX paths). The header and picker use it; when workspaces could not be read there is no project line, not a guess. The server's `info.project` wins on a just-created chat.

**Profile (decided).** Every workspaces, `fs/list`, `complete.path` and move call sends the chat's profile explicitly (`profile` query / param), `default` for none, as the Bot Screen calls do. A new chat picks its recipient profile first (messenger navigation), the folder row follows that profile's `default_cwd` and project list, and a profile switch resets the pick. The Mac profile switcher behaves the same. The server's active profile and CLI default are never changed.

**Layering.** `moveWorkspace` lives on `HermesWorkspacesRepository` (through `GatewayRequester`), not on `ChatTransport`; `ChatTransport.send` gains only the creation-time `WorkspaceChoice`, and a queued send never carries one (a draft's first send is never queued). The generated client has `GET /api/chat/workspaces` and `GET /api/fs/list` without response schemas, so `HermesWorkspacesRepository` calls them through `authController.api!.raw` and parses leniently (a project without `id`/`name`, a repo without `root`, an entry without `path` is skipped; unknown fields ignored; `error` in `fs/list` is a typed failure). Gateway methods go through the shared gateway request method (`GatewayRequester`), with method-not-found mapped to `unsupported`.

```dart
sealed class WorkspacesResult<T> {}
final class WorkspacesOk<T> extends WorkspacesResult<T> { final T value; }
final class WorkspacesUnsupported<T> extends WorkspacesResult<T> {}      // 404 / -32601
final class WorkspacesFailed<T> extends WorkspacesResult<T> { final WorkspacesFailure kind; }
enum WorkspacesFailure { notFound, notAllowed, notADirectory, unreachable, busy, unknown }
```

`WorkspaceCatalog { List<WorkspaceProject> projects; List<WorkspaceRepo> repos; String defaultCwd; String home; bool scanEnabled }`. `FolderListing { List<FolderEntry> folders; }`. `PathSuggestion { String text; String display; }`. `MovedWorkspace { String cwd; String? branch; String? gitRepoRoot }`.

**Controllers.**

- `WorkspacePickerController` (one per picker visit, plain `ChangeNotifier`): the catalog read with its state (loading, ready, partial: projects failed but browse works, failed, unsupported, rescanning), the search text, the browse path stack and listing, the typed text and suggestions (latest answer only), and the selection. Late answers after dispose or a profile change are dropped.
- `ChatController` (new private part `chat_controller_workspace.dart`, per the part convention): holds the working directory of each thread (from the REST row, `WorkspaceBound`, or a move), the draft choice, the mismatch notice, and `moveWorkspace(thread, choice)` with the in-flight guard and the re-read after a lost answer. Thread rows keep `folderPath` for grouping; new `ChatThread.workingDirectory` and `branch` are the display values (raw `cwd`), so the header never shows a repo root when the chat runs in a subfolder.

**Where reached (decided).**

- Phone: the new-chat welcome shows the row above the composer; an open chat shows the line under the title; tapping either opens the picker as an adaptive sheet (`showAdaptiveSheet`) with Browse and Type as pushed pages inside it.
- iPad and wide Android/desktop: the same row and line; the picker is a dialog (`showAdaptiveSheet` gives a dialog on wide windows), Browse and Type pages are in-dialog navigation.
- Mac: the chat toolbar shows the folder as a titled button (`MacToolbar`) that opens a popover-style dialog; the thread menu and sidebar row menu gain "Change Folder…" (`ThreadAction.changeFolder`, shown only when allowed); File menu gets no new item. No bottom sheet anywhere on the Mac.
- The conversation windows show the line and the details; they offer no change in v1 (a window has no `AuthController` or gateway of its own, so the picker and move stay in the main window; the Mac thread menu item acts in the main window). The quick panel, Ask Hermes, the watch and links keep the default, which the quick panel's first message shows as it does today (no row).

**Telemetry.** As listed in the proposal; fixed names and outcomes only. The `workspace.list` span carries `hermes.*` server attributes, counts (`projects`, `repos`) and `outcome`; none of the paths, names or branches.

**Old server and hiding.** A catalog `404`/`405` or the `GET /api/chat/workspaces` route missing makes the picker "unsupported": the row still shows the path from `default_cwd` if known, else the row is hidden, and Browse/Type are not offered; the chat header line is driven by the REST row fields and appears whenever they are present. A move that answers `-32601` marks `session.workspace.move` unsupported for this connection and hides "Change folder…". An older server that has the routes but not `cwd_explicit` rejects the unknown param with `4000`; the transport retries `session.create` once without `cwd_explicit` (Hermes validates params against its contract, so a server whose contract predates the flag answers 4000; a server with no contract ignores the key) and then relies on the post-create comparison. The notice therefore never states a single cause.

**State, failures and secrets.** Failures are values, never thrown to the UI: unreachable (offline: "You're offline. Connect to choose a folder on your server." with the default row still usable), unsupported, permission denied (`EACCES`, 403), not found. A lost answer to a move is "may have happened" and is re-read, never resent. No credentials are involved. Paths and project names are never logged, put in a span, breadcrumb, crash report or thrown message (a `DioException` carries the request URI with its `path` query, and the `4017` text echoes the raw path, so the repository maps failures to kinds without the URI or the server's text), written to preferences, the surface snapshot, the Spotlight index, Handoff payloads, widgets, the watch bridge or notifications. App Lock covers the app, so the row and sheets are covered with the rest; picker state is dropped when the app locks while a picker is open (the sheet closes), and sign-out clears the draft choice and the cached catalog.

**Accessibility.** The row, line and picker rows are 44 pt / 48 dp targets with labels that read "Folder: <folder>, <path> on your server, branch <branch>". The selected row exposes `selected`. Text scales: the folder name wraps to two lines and the path middle-truncates with the full path in the semantics label and the details sheet. Project and repo rows do not rely on colour; the "Server default", "Project" and "Recent" labels are text. Reduced motion removes the sheet's slide and the breadcrumb scroll animation. Keyboard (desktop): Tab order is search, list, Browse, Type, primary action; Escape closes; Return picks the focused row; the Mac toolbar button has a tooltip.

## Risks / Trade-offs

- **Silent fallback on create** (mitigated by pre-check and the comparison notice, but the first prompt has then already been sent to the wrong folder). A hard block would need a server change. Mitigation: the picker's choices come from the server's own lists or an `fs/list`-checked path, so a mismatch is rare; and the notice appears immediately.
- **A moved chat's history refers to the old folder.** The confirmation says so; no attempt to rewrite history.
- **`/api/fs/list` hides symlinked folders and can be locked on hosted deployments.** Typed paths with `complete.path` cover the first; the locked case still offers projects and recents.
- **Remote (SSH) profiles accept any `/`- or `~`-shaped folder.** `_workspace_cwd` (`session_workdir.py:171-181`) returns an SSH path raw, so `session.create` and `session.workspace.move` succeed on a folder that does not exist on the remote, `info.cwd` equals the pick and the mismatch notice cannot fire. The typed-path check (`fs/list` on the remote: 404 "File not found") is the only guard there; a project or recent folder that has since gone is not caught.
- **A 4017 can follow a stored move.** With a live agent bound to the chat, the stored row is updated before the live re-home, which can still answer `4017` (`methods_session.py:1131-1138`); the app keeps showing the old folder, and the next read of the row corrects it.
- **Remote (SSH) profiles** list and complete on the remote but the workspaces `home` is the dashboard host's. The app shows paths as reported and does not compare `~` paths for the mismatch notice (it compares only absolute ones).
- **Contract drift**: the workspaces and `fs/list` shapes are untyped; the contract test guards them on every real-backend run.

## Migration Plan

None: additive. Existing chats keep showing their folder from the rows they already load.

## Open Questions

1. **Browse with `fs/list` or `complete.path` only?** Recommendation: `fs/list` for browsing (structured folders, "up" and breadcrumbs, same as the desktop app), `complete.path` for typing; accept the symlink gap.
2. **`session.workspace.move` or `session.cwd.set` for changing a chat?** Recommendation: `workspace.move` (decided above); confirm on a live backend that a chat resumed afterwards runs in the new folder and that a chat idle in the app keeps working.
3. **Should the move be allowed while a reply runs?** Recommendation: no in v1 (the server allows it; the product reason is surprise).
4. **Create-folder in the browser (`POST /api/files/mkdir`, no `profile` param, creates parents)?** Recommendation: later; it makes a typo a new directory.
5. **Remember the last folder on the device?** Recommendation: no; the server's recents already follow use, and storing paths locally adds privacy surface.
6. **Show a project when the server's `info.project` is null but the client match finds one?** Recommendation: yes, client rule equals the server's, shown on existing chats and the picker.
7. **Warn for a dirty or non-git folder?** Recommendation: no; `project.facts` is a later, separate change.
8. **Verify on a live backend that a `hermes_app` chat created with no `cwd` stores the launch directory** (read from `_persisted_session_cwd`, not observed). Tracked in the last tasks.
