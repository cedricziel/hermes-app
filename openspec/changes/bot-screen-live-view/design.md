# Design

## Context

`display.observe` (Hermes `tui_gateway/methods_display.py`) mints a single-use 30 s ticket and a viewer id for the calling gateway connection and returns `{ticket, path, viewer_id, ...status}`; when the screen is not running it answers error 5300 with only a message, so the reason is not machine-readable. `/api/display/ws` (`hermes_cli/web_routers/display.py`) closes with 4401 for a bad ticket, 4001 when the screen's socket is missing, 1003 for an unframeable or text message, and 4000 for a holder evicted by another person; Host/Origin refusal happens before accept and surfaces as HTTP 403. While a viewer is attached the bridge touches `bot-desktop/activity` at most once a minute, so the idle auto-stop leaves the screen running.

`bot-screen-rfb-client` gives `openDisplaySocket` (typed errors, readable close code) and `RfbClient` (framebuffer, events, byte and encoding counters). `bot-screen-card` gives the card's `onEnlarge` slot (null today) and `bot-screen-chat-preview` the preview's `onTap`, which opens the Activity panel. `InspectorLayout` (`lib/src/widgets/inspector_layout.dart`) docks a 380 pt panel from 760 pt and overlays the same 380 pt panel below that; it is not a full-window surface.

## Decisions

- **`BotScreenRepository.observe(profile, {viewerId})`** returns a `BotScreenObservation` (ticket, path, viewer id and the status; its `toString` shows none of them) or a failure; a failure triggers a `display.status` read in the controller to pick Off (not running) or Error.
- **`BotScreenViewerController`** (`lib/src/bot_screen/viewer/`) owns observe → open → handshake, holds `paused` from visibility, lifecycle, App Lock and profile, and maps endings:

  | Ending                                     | Action                                                                                               |
  | ------------------------------------------ | ---------------------------------------------------------------------------------------------------- |
  | 1000 sent by the app                       | none                                                                                                 |
  | 4000                                       | observe again and reconnect as a watcher                                                             |
  | 4001, or 1000/1001 with no error          | Off state, no retry; for 1000/1001 only after `display.status` says not running, else as "anything else" |
  | 4401                                       | observe again once; a second 4401 is an error                                                        |
  | 1003                                       | protocol error, no retry                                                                             |
  | HTTP 403 (`DisplaySocketError.notAllowed`) | "Viewing isn't allowed from this app", no retry                                                      |
  | anything else, decode failures included    | full-jitter backoff, 300 ms base, 15 s cap, 5 attempts, then "Can't reach the screen" with Try Again |

  A screen that stops while watched usually arrives as a plain close 1000 (the bridge's read of Xvnc hits EOF and closes the socket), not 4001, so a clean 1000 or 1001 reads the status first: Off when not running, no failure logged, span outcome `gone`. The stream goes live on its first update, not on the handshake (the framebuffer is black until then), and the attempt counter resets only then, so a server that accepts and closes cannot loop; a 4000 counts as an attempt too. Anything unmapped thrown on the way (observe, status, start) is logged with `step: observe`, `error_type: unexpected` and no message, and retried. Pausing closes with 1000 and drops the framebuffer; resuming observes again (a ticket works once).

- **Control in the picture.** The controller follows the `BotScreenController`'s lease and holds a status-only `watch(frames: false)` for its life: the status is read every 3 s while the screen runs, which notices a takeover that no broadcast reported, with no thumbnail requested for a picture it draws itself. The `display.observe` answer carries the status, and `BotScreenController.adoptStatus` takes it (unless a newer lease is held), so the lease is known when the picture starts. While `holder: human` and the hash matches no viewer id this app holds (in this change it never does), `framebuffer` is null and the phase is `blanked`: the view shows a blank surface with "Someone else is in control" and keeps the stream open, so the picture returns as soon as control goes back to Hermes. Until the lease is known no picture is shown either (fail closed).
- **Drawing.** After each update `FramebufferPicture` builds a `ui.Image` with `ui.decodeImageFromPixels` (RGBA8888, which copies the pixels at once), at most once per frame via `SchedulerBinding.scheduleFrameCallback`, paints it with `RawImage` (`BoxFit.contain`) inside an `InteractiveViewer` (min scale 1, max 4×) whose widget stays mounted through a reconnect, a blank and coming back, so the zoom survives, and disposes the previous image once the next is ready. Decoding stays on the UI isolate: a benchmark of one full 1280x800 ZRLE update (all raw tiles, a mix of solid and palette-RLE tiles, all solid) took 2.5 to 8.5 ms AOT and 13 to 20 ms in JIT on an Apple-silicon Mac, under the 16.7 ms of a 60 Hz frame, and incremental updates are far smaller. That is an Apple-silicon number only: a mid-range Android phone needs a profile-build measurement before this is called settled, and decoding moves to an isolate if a full update costs more than a frame there.
- **Presentation.** `showBotScreenViewer` pushes a route on the root navigator, chosen by device: a window whose shortest side is under 600 pt (`kViewerPhoneShortestSide`, so a phone in landscape too) gets a `MaterialPageRoute` (the platform's own transition, full screen, following orientation), a larger one an opaque `PageRouteBuilder` over a black barrier that covers the whole window. A route, not a root `Overlay` entry, so that dialogs and pages opened while it is up (Settings, the Sign Out confirmation, the menu bar's "Always allow", deep links, the platform-hint prompt) are drawn above it, the chat's `MacCommandScope` is no longer the current route's (⌘N, ⌥⌘I and ⌘F do nothing to the hidden chat), the system's Back pops the viewer and not the chat, and focus returns on close. The whole view sits in a `SafeArea`, and the header is the viewer's own (44 pt on iOS, 52 pt on a Mac, 56 pt on Material, black in both themes like the image viewer), not `MacToolbar`, which takes its colours from the theme. On a Mac, in a page or the layer, it leaves room for the traffic lights, puts Close at the trailing edge and is a `MacWindowDragArea`, as `MacToolbar` is. Escape is `DismissIntent` (the app's default shortcut) through an `Actions` above an autofocused `Focus`: a widget handler, not a menu chord, so no menu item owns Escape. `BotScreenViewer` tells the controller whether its route is on screen (`visible`, from `TickerMode`, as `BotScreenDemand` does), so a route that covers it pauses the stream. Closing ends the stream at once; a route closed from the owner's `dispose` is removed after the frame, since the navigator must not change while the tree unmounts.
- **Openers.** `ChatScreen` passes `_openViewer(source)` as the card's `onEnlarge` (and the card's picture tap, through `BoundActivityPanel.onEnlargeScreen`) and as the preview's `onTap`, replacing `_openActivity` there. It creates the `BotScreenViewerController` when the viewer opens, gives it the same `foreground` and `unlocked` gates as the screen controller (a phone counts only `resumed` as in front, a desktop window also `inactive`, so losing focus does not end the stream), and closes the viewer when the chat changes profile, when the chat is no longer the shell's visible destination, and in `dispose`, which also covers sign-out.
- **Design system sync.** `design/web/src/components/BotScreenViewer/` (header, picture area, connecting, reconnecting, off, blanked, not allowed, cannot reach) with `docs/BotScreenViewer.md`, `category: Screens`, the category of the other full screens such as `ImageViewerScreen`.

Platforms: iOS, Android, macOS, Windows, Linux. No native, entitlement, manifest or Xcode change.

Invariants touched:

- Telemetry: span `bot_screen.stream` in `BotScreenViewerController` from the connection's telemetry (`outcome`, `close_code`, `encodings_used` from `RfbClient.encodingsSeen`, `kib_received` bucketed `<256`, `256-4096`, `>=4096`); log `bot_screen.stream_failed` (`step`, `error_type` from the typed failure kind) through `AppEventLogger`; breadcrumbs `bot_screen.viewer.opened` and `.closed` in the presentation. No ticket, URL, viewer id, profile or pixels.

## Risks / Trade-offs

- [An open viewer costs the server bandwidth and can keep a changing screen from its idle stop (the bridge stamps activity at most once a minute, and only when Xvnc sends bytes; a static screen can still be stopped)] → The stream closes whenever the viewer is not visible.
- [Building a `ui.Image` per update allocates] → Coalesced to one per frame; the framebuffer is reused.
- [Blanking while someone else holds control hides a picture Hermes Desktop still shows] → Chosen for privacy, consistent with the thumbnail.
