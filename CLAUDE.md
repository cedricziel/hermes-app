# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Flutter client (iOS, Android, macOS, Windows, Linux) for the Hermes Agent web dashboard (`hermes dashboard`, from NousResearch/hermes-agent). The user enters a self-hosted server URL, signs in, and chats with the agent. The sign-in flow is specified in `openspec/specs/auth/spec.md`, and `openapi/README.md` covers the generated client.

## Commands

```bash
flutter pub get
flutter run
dart format .                     # CI runs: dart format --output=none --set-exit-if-changed .
flutter analyze
flutter test
flutter test test/auth_controller_refresh_test.dart          # one file
flutter test --plain-name "some test name"                   # one test
dart run tool/setup_git_hooks.dart  # installs the dart_pre_commit hook (format + analyze on staged Dart files); once per clone, shared by worktrees
flutter run -d macos -t widgetbook/main.dart   # component catalog (Widgetbook); see the `component-catalog` skill
```

CI (`.github/workflows/ci.yml`) runs format and analyze, and the tests in four parallel jobs split by file (`scripts/test-shard.sh <index> 4`; shard 0 is the Widgetbook test alone); `Analyze & test`, the required check, passes once all of them did. Then it builds Android (debug APK), iOS (simulator), macOS and Linux (release bundle, packaged by `scripts/package-linux.sh`). Releases attach a Linux tar.gz and .deb (x86_64, arm64) to the GitHub release. Every release is cut as a GitHub pre-release and its build goes to TestFlight; promoting one to a full release starts `app-store.yml`, which runs `fastlane submit` to send that version's TestFlight build to App Review on iOS and macOS, which goes live by itself once approved. It needs the `REVIEW_CONTACT_*` and `REVIEW_DEMO_*` (demo server URL, user, password) secrets. A version already in review or released is skipped, so promoting one you submitted by hand does no harm. Run it by hand with `dry_run` (the workflow's default input) to update the listing without submitting. The iOS build needs the watchOS platform installed and an explicit simulator: `flutter build ios --simulator -d <udid>`.

Commits follow Conventional Commits; release-please builds `CHANGELOG.md` and bumps `pubspec.yaml` from them. Don't edit the version by hand.

### Running against a real backend

- `scripts/dev-backend.sh start|stop|url` runs a throwaway Hermes dashboard on an OS-assigned port with its own `HERMES_HOME` (needs `hermes` on PATH).
- `scripts/dev-app.sh start|reload|restart|screenshot|logs|stop` runs the macOS app against it and can screenshot the window. State lives in `.dart_tool/hermes-dev/`.
- `scripts/store-screenshots.sh ios|mac|finish` retakes the App Store and README screenshots; the `store-screenshots` skill (`.claude/skills/store-screenshots/SKILL.md`) has the procedure and the traps.
- The `verify-in-app` skill (`.claude/skills/verify-in-app/SKILL.md`) has the full loop and its rules. Never point the app or `hermes` at the real `~/.hermes`, and never run `hermes dashboard --stop`.
- Building the macOS app rewrites tracked `ios/` and `macos/` Xcode files. Stage files by name, never `git add -A`, and `git restore` those afterwards.
- `test/real_backend_contract_test.dart` checks the response shapes the repositories parse against a live backend. It skips unless `HERMES_DEV_URL` is set. Tests that call a model also need `HERMES_DEV_MODEL_CALLS=1`, and the Telegram pairing test needs `HERMES_DEV_TELEGRAM_PAIRING=1`. It runs in CI as a non-required check (`real-backend-contract.yml`, Hermes pinned by `HERMES_REF`).

### Regenerating the API client

```bash
scripts/fetch_openapi_spec.sh [ref]       # rebuild openapi/ from hermes-agent main or a ref; needs gh, curl, uv
./scripts/generate_hermes_api_client.sh   # needs a JDK (npx openapi-generator-cli) and dart on PATH
```

`update-hermes-contracts.yml` runs both every Monday, refreshes `openrpc/` from the same Hermes commit, and opens one PR when either changed.

`verify-hermes-api-client.yml` fails CI if `openapi/`, `scripts/` or `packages/hermes_api/` change without a matching regenerated client. Never hand-edit `packages/hermes_api`. Fix template bugs in `scripts/patch_openapi_for_dart.py` or `scripts/patch_generated_dart_client.py`. `packages/hermes_api/pubspec.lock` is committed on purpose.

## Architecture

**State and routing.** `lib/main.dart` sets up telemetry and `provider` (`AuthController`, `ThemeController`, `NotificationSettings`, `ShareController`). `lib/src/app.dart` picks the screen purely from `AuthController.state` (`HermesConnectionState`): setup, login or `AppShell`. There are no named routes. `shell/app_shell.dart` navigates between Chat, Bots, Kanban and Schedules. Bots uses the shared gateway and explains when the dashboard lacks Bot Mode support. The Kanban tab (`lib/src/kanban/`) only exists while the server reports the Kanban plugin as on, and the Schedules tab (`lib/src/schedules/`, the server's cron jobs) only while `/api/cron/delivery-targets` answers. Both are re-checked on connect and on app resume. The board is shared by every profile, so Kanban requests (and the plugin check) send no `profile`; the job form asks for the delivery targets and blueprints of the job's profile. A page stays alive behind the others once opened; the board closes its event stream while it is not on screen (`KanbanBoardController.active`, set from `Visibility.of` and the app lifecycle) and resumes from its cursor. On macOS the board has the Mac toolbar (`widgets/kanban_mac_toolbar.dart`, on `macos/mac_toolbar.dart`) and opens a task in an inspector on the right (`KanbanInspector`, `widgets/kanban_inspector_layout.dart`: docked from 760 pt, over the board below that) instead of a sheet; View > Inspector (⌥⌘I) and File > New (⌘N, titled New Task) come from its `MacCommandScope`. Opening a run of a job goes through `ChatOpenRequests` to the chat screen. `AuthController` owns the whole connection lifecycle: server URL discovery, sign-in, token storage and refresh, and the authenticated `Dio` instance.

**Auth.** Both OIDC and password sign-in use the same RFC 8252 flow (`auth/native_login_flow.dart`, `pkce.dart`): a browser, loopback HTTP listener, PKCE, then a bearer token pair kept in secure storage (`auth/token_store.dart`; on iOS readable after the first unlock, so a watch request can wake the locked phone app and still find the session). The browser (`auth/sign_in_browser.dart`) is an `ASWebAuthenticationSession` sheet on iOS and macOS (`WebAuthSession.swift` in each runner, channel `hermes_app/web_auth`), which App Review requires, and the external browser elsewhere. Hermes only accepts a loopback `redirect_uri`, so on Apple platforms the listener answers the callback with a redirect to `hermes-app-signin://` to end the sheet. Tokens refresh before use and again on any 401. Concurrent 401s must not sign the user out, and sign-in must never be left spinning (regressions fixed in 0.1.8 and 0.1.9). If `/api/status` reports `auth_required: false`, sign-in is skipped. A failed connect is classified in `auth/connect_failure.dart`; the setup screen adds a VPN hint for tailnet/private addresses, and `network/network_signals.dart` (`connectivity_plus` plus app resume) makes `AuthController` retry the saved server after a network failure. VPN detection is only a hint, never a gate: iOS and macOS cannot report it. `--dart-define=HERMES_SERVER_URL=<url>` overrides the saved server address, for dev and tests.

**Two API layers.**

- `packages/hermes_api` is a generated `dart-dio` client for the backend's OpenAPI spec (`openapi/hermes-agent.openapi.json`). Reach it through `authController.api!.raw`, which shares the managed `Dio`, instead of adding hand-rolled calls.
- `lib/src/api/hermes_api_client.dart` hand-writes only `/api/status`, `/api/auth/providers` and `/api/auth/me`, because the spec has no response schemas for them. It also hand-writes the Kanban attachment download (`fetchKanbanAttachment`), because the generated method decodes the body as JSON and cannot return a file's bytes.
- Many routes (sessions, profiles, messaging, skills, plugins) also lack response schemas, so the generated methods return untyped JSON. The repositories (`chat/hermes_chat_repository.dart`, `profiles/`, `messaging/`, `skills/`, `plugins/`, `schedules/hermes_cron_repository.dart`) parse those rows leniently and skip rows that don't fit. The contract test above guards these shapes.

**Chat** (`lib/src/chat/`, built on `flutter_chat_ui`).

- History is loaded over REST by `HermesChatRepository`. Sending and streaming go through the `ChatTransport` interface (`chat_transport.dart`), a sealed `ChatEvent` stream. The real implementation, `gateway/hermes_gateway_transport.dart`, speaks JSON-RPC over the dashboard's `/api/ws` websocket (`session.create` or `session.resume`, then `prompt.submit`, with replies as `message.delta` events). Both session calls send `source: hermes_app` (`gatewaySessionSource`); without it Hermes records the session as `tui` and gives the agent the terminal UI's prompt hint. `gateway_rpc_client.dart` and `gateway_connection.dart` handle the socket. Gateway frames become `ChatEvent`s in `gateway/gateway_event_mapper.dart`. `openrpc/hermes-gateway.openrpc.json` is Hermes' own list of every frame and server request (see `openrpc/README.md`), and `test/gateway/gateway_contract_test.dart` records what the app does with each one. `review.summary` (what Hermes' background review saved after a turn: memories, user profile, skills) becomes `ReviewSummarized`, which the controller attaches to the latest finished reply (`ChatMessage.reviewNotes`, shown by `widgets/review_summary_note.dart`). A reply ends on whichever comes first: `message.complete`, or `session.info {running: false}` (`ReplyCompleted` or `SessionInfo`; Hermes clears its running flag after the completion, so that report is the settled signal). `settles` in `gateway/gateway_replay.dart` ignores an idle report within 15 s of the submit until the turn has begun, since it can describe the turn before. An `error` event is held and shown as the failure when the session settles with no completion; a failed completion's own message wins. A reply that settled without a completion keeps its text, and a late `message.complete` on `followUps` lands on the same reply. A reply silent for 45 s is checked with `session.active_list` and ended as broken only when its thread is no longer listed as running, in `send` and in the follow-up relay while it is replying. `prompt.submit` answers `streaming`, `queued` (the reply waits for its turn's `message.start`), or `redirected`/`steered` (the server folded the text into the running turn: `PromptFolded` drops the placeholder, the running turn's reply goes on in its own send). The controller drains the queue on `SessionInfo(running: false)` from `followUps`, or 2 s after the completion, and sends with `queued: true` so the server queues the prompt instead of folding it. After a reply ends the transport keeps listening to its session, and `ChatTransport.followUps` carries the turns nobody here submitted: goal continuations, queued prompts, a delta or tool event whose `message.start` was missed (it opens a reply). The turn Hermes runs on its own after a resume that reports `auto_continue` is not among them: `send` claims it (`_Unsolicited`) so the submitted prompt keeps its own reply. Each frame of that turn, its requests and their withdrawal included, goes out on the send's own stream as it arrives, wrapped in `UnsolicitedEvent`, and `ChatController._onOwnTurnEvent` streams it into a reply opened in front of the prompt's user message (`_insertReply(before:)`; the server runs that turn first and stores it there, so a refetch, Copy Transcript and Retry/Edit of the prompt agree with the live order). The turn shows live and is never replayed on `followUps`. An idle report ends it only once a turn-opening frame came (an approval alone does not open one), a late completion lands on it, and its end settles neither the queue nor a stop in flight. Its requests can be answered while it runs and are withdrawn when it ends, the prompt's reply says Hermes is finishing the interrupted turn until then, and a send that gives up fails both replies and refetches. Session and prompt calls time out, `checkConnection` (called when the app resumes) drops a socket the OS killed during sleep, and the RPC client pings every 15 s and closes itself after 45 s without any frame. A reply still running when its connection drops is not failed outright: the transport reconnects with full-jitter backoff (300 ms to 15 s, 5 attempts or 60 s), resumes the session, and replays what it missed. Every event frame carries a `seq` per runtime session; `ReplayLedger` (`gateway/gateway_replay.dart`) keeps the highest one seen and the `replay_epoch` from `gateway.ready`, and `session.events.since` fills the gap, with the frames that arrived meanwhile merged in and none shown twice. When the replay is truncated or the server restarted (epoch changed), a running turn is rebuilt from the resume answer's `inflight.assistant` (`ReplyRebuilt`, with the deltas sent after the snapshot still delivered) and an ended one by a REST re-read (`ThreadNeedsRefetch`, then the stored reply); `open_requests` are shown once by id. `approval.cancelled` withdraws the open approvals of its session (`InputRequestsCancelled`).
- Domain messages (`chat_models.dart`) map to flyer messages in `chat_message_mapper.dart`. `chat_controller_sync.dart` applies before/after diffs to the `InMemoryChatController`. Custom message kinds and cards (tool calls, approval and clarify requests) live in `chat_message_kinds.dart` and `widgets/`. Tool calls follow assistant-ui: `tool.generating`, `tool.start` and `tool.complete` are matched by `tool_id` (name as fallback) into `ToolCall`s with args, result data, diff and timing; a run of calls is one `ToolCallGroup`; `widgets/tool_call_bodies.dart` gives terminal, web search, todo and diff calls their own view, with `ToolCallCard`'s input and result as the fallback; an approval Hermes raises while a call runs is bound to it in `chat_reply.dart` and shown inside that call's card. The design for agent input requests is in `openspec/changes/archive/2026-09-19-agent-input-requests/`. Text Hermes writes before a tool call, or checkpoints mid-turn with a `message.interim` event, is sealed into `ChatMessage.sealedProse` (`chat_reply.dart`) instead of being folded into the trailing `content`, so the mapper can render it where it was actually written and `message.complete` never overwrites it.
- The composer is Hermes' own `ChatComposer` (`widgets/chat_composer.dart`), not flutter_chat_ui's `Composer`: a card with the field on top and attach, the model pill, the dictation microphone and send below it. `buildChatComposer` puts it in a `Positioned` that stays a direct child of the `Chat` stack and reports its height to the package's `ComposerHeightNotifier`, as the package's own composer does.
- The welcome view's starter prompts (`starter_prompts.dart`) come from the active profile's context: a failed cron job, a blocked or in-review Kanban task, the latest chat and the most-used skill, one each, padded with generic prompts. `StarterContextLoader` reads them in parallel, leaves out a source that fails or takes more than 5 s, and `ChatScreen` reloads it for another profile or after five minutes. Job, task and skill prompts go into the composer; a chat prompt opens that chat.
- The composer's model pill (`lib/src/models/widgets/composer_model_pill.dart`) picks a model and reasoning effort per chat from `GET /api/model/options` (`HermesModelsRepository`, loaded with each profile's threads, hidden when that fails). The pick lives on `ChatThread.modelChoice` and goes out with `ChatTransport.send`: as `session.create` overrides for a new chat, as session-scoped `config.set` (`model`, `reasoning`) on resume when it changed. Nothing is written to the profile's config; that is the Profiles screen's job, which sets a profile's default model (no effort, Hermes keeps none for the main model) with `PUT /api/profiles/{name}/model` through the same picker (`showModelPicker(withEffort: false)`). The Kanban create form reuses the pill and picker with the plugin's own list (`GET /api/plugins/kanban/model-options`, no capabilities, so every model gets Minimal to Ultra) and the picker's default entry (`onUseDefault`, which the pill passes on); when the list is empty it falls back to a typed model name, like the dashboard. The task panel shows a task's override (`model_override`, `provider_override`, `reasoning_effort` on the task row) and applies the last pick once when the picker closes; bulk edit sets or clears only the effort.
- On macOS the sidebar is a source list (`lib/src/macos/mac_source_list.dart`): 28 pt destination rows (Kanban captioned "All profiles") and threads under recency sections (`thread_sections.dart`; Pinned, Today, Previous 7/30 days, Older) whose folded state `MacSidebarController.sections` keeps in shared preferences. `MacThreadRow` shows Archive and More on hover; More and a right-click open `macThreadMenuItems`, built on `AdaptiveMenuItem` (shortcut text, destructive) and `AdaptiveMenuController.open(at:)`. Copy Transcript copies Markdown and reads a thread's unloaded pages through `ThreadHousekeeping.history`.
- On macOS search and New Chat live in the toolbar (`widgets/mac_chat_toolbar.dart`, on the shared `MacToolbar`): `MacToolbarSearchField` (a button below a 1000 pt window), ⌘F from a `HardwareKeyboard` handler in `ChatScreen`, Escape to end. While `ThreadSearch.active` the sidebar shows `MacSearchResults` (Chats/Messages, recent searches) with a This profile / All profiles switch; `ChatController._searchAllProfiles` fans out one search per profile and skips a failing one. Below 760 pt (`isMacCompact`) `MacSplitView` opens the sidebar over the content (`MacSidebarController.toggle(compact: true)`, `closeOverlay`), and `ChatScreen`/`AppShell` keep the Mac split view at every width.
- The sidebar's search field (`widgets/thread_search_view.dart`) searches the active profile's sessions with `GET /api/sessions/search` (`HermesChatRepository.searchThreads`; FTS5 snippets mark matches with `>>>`/`<<<`). `ThreadSearch`, owned by `ChatController`, debounces typing by 300 ms, keeps only the latest query's answer and is cleared on a profile switch; while the field holds text the results replace the thread list. A result opens through `ChatController.open(fetchMissing: true)`, so a chat older than the loaded pages is fetched first.
- With no repository, `ChatScreen` falls back to `mock_chat_data.dart`. A canned reply is used when there is no transport.

**Voice** (`lib/src/voice/`). Dictation follows assistant-ui's dictation element: the composer's microphone (shown when `GET /api/audio/voice-config` reports usable speech-to-text for the chat's profile; `stt disabled` or `no credentials` hide it) records 16 kHz mono PCM with `record` (`voice_recorder.dart`), and the waveform (`widgets/voice_waveform.dart`) stands in for the field until the transcript is inserted at the cursor, never sent. `DictationController` streams the audio to the `/api/audio/transcribe-stream` socket when `stt.streaming` says the provider can transcribe live (`TranscribeStream`, opened by `hermesMixedSocketConnect` with the same ticket or token as `/api/ws`), and otherwise, or when that fails, uploads the recording as WAV through `HermesChatRepository.transcribe` with a longer timeout (`receiveTimeoutExtra`, applied by `RequestTimeoutInterceptor` on every client `AuthController` builds). It holds an `stt-lease` while recording, drops the recording when the app leaves the foreground or the profile changes, and records breadcrumbs without text. Conversation windows offer no dictation, so `record` is not registered in their engine. The hands-free voice conversation is planned in `openspec/changes/voice-conversation/`.

**Bot Mode hosted groups** (`lib/src/bot_mode/group_protocol/`). `HermesGroupsRepository` accepts the shared authenticated gateway request method and uses only `groups.*` RPCs, with existing method/status tracing. Protocol 2, advertised methods, `idempotent_send`, `monotonic_log` and a ready driver gate execution; readable history survives driver downtime. Rooms from `groups.list` are hosted server-driven rooms, distinct from Desktop legacy metadata rooms with a client driver. Membership is frozen at 2–6 unique local profiles. `GroupReplay` incorporates validated pages before advancing its cursor and fences stale responses/authority changes; `GroupSendOperation` retains a send UUID and reconciles lost receipts against `user:${sha256(client_event_id)}` before explicit retry. Approvals quote exact pending coordinates with once/deny; retries require an advertised action. Hosted clarify/sudo/secret requests have no room response path in the verified protocol and may leave a member waiting; the UI explains this and offers Stop. The `verify-bot-mode-contract` skill (`.claude/skills/verify-bot-mode-contract/SKILL.md`) describes recurring isolated-home conformance checks. No transcript, grant or token is stored in preferences.

**Bot Mode roster and chats** (`lib/src/bot_mode/`). `BotModeRosterRepository` reads profile metadata, keeps unknown `hermes-bots` fields in revision-checked edits, and creates profiles without copying messaging channels. The roster shows managed bots separately from profiles that can be added. `BotModeChatRepository` resolves one hidden `Bot Chat` registry per profile and adopts its current compression tip. The shell opens that stored session with its profile through the existing chat renderer; `BotChatContext` supplies the friendly title and local teammate handles. The stored session ID alone does not identify its owner.

**Bot Mode group UI** (`lib/src/bot_mode/groups/`). The Bots screen lists hosted rooms and opens the group transcript. Membership is fixed at creation, messages are text only, and the server drives member turns. The screen polls room events while visible, shows pending approvals and failures, and offers Stop and explicit retry. Creation and active-work views explain the unsupported interactive-input limitation. Desktop legacy metadata rooms are separate.

**Profile scope on macOS** (`lib/src/profiles/`). `ChatProfiles`, owned by `AppShell`, holds the server's profiles and the chat's current one; `ChatScreen` reports its profile with `showing` and attaches `loadThreads` as the switch handler. On macOS `AppShell` puts `MacProfileSwitcher` above the destinations and adds a Profiles destination (`MacProfilesPage`: the profiles beside the selected one's home with counts read lazily, each opening the existing screen for that profile). The Mac sidebar has no per-profile management rows and ends in `MacAccountFooter` (Settings… opens `showSettingsDialog`, which `AppShell` also registers as the menu bar's `MacCommand.settings`, next to `connectionDetails` and `signOut`; Sign Out asks first through `confirmSignOut`). The page reads Messaging and plugins per profile through `HermesMessagingRepository.forProfile` and `HermesPluginManagerRepository.forProfile`. `AppShell` owns the `MacSidebarController` so a pick closes the compact overlay.

**Settings pages** (`lib/src/widgets/settings_scaffold.dart`, `grouped_list.dart`, `settings_search_field.dart`). Skills, Messaging, Plugins, MCP servers and Helper models share one chrome. `SettingsScaffold` takes a title, a subtitle (profile · count), `SettingsBarAction`s (a button, or `.menu` with `AdaptiveMenuItem`s that act through `onTap`), optional tabs and a `SettingsSearch`, and draws the platform's bar: iOS a 44 pt bar with the title centered, macOS the `MacToolbar` with back, tabs (`MacToolbarTabs`), search and actions in it, Material a 56 pt bar with pill tabs (`PillSegmentedControl`, which `AdaptiveTabBar` now draws on Material). There is no floating button; adding is a bar action. Lists are `GroupedListView` of `GroupedSection`s (header, footer, inset separators) holding `GroupedRow`s (title, inline meta, one-line subtitle, warning line, muted value and chevron, or a trailing widget) and `GroupedSwitchRow`s; `GroupedMetrics.of(context)` has each platform's sizes.

**Plugins** (`lib/src/plugins/`). The chat sidebar's Plugins row opens a screen with three tabs. Installed lists the dashboard's agent plugins (`GET /api/dashboard/plugins/hub`) and enables, disables, updates, removes and hides them; it does not list Kanban or Achievements, which the hub reports apart as dashboard-only extensions. Catalog (`GET /api/dashboard/plugins/catalog`, loaded when first opened) searches the curated catalog and installs from it, and installs from a Git URL behind an unreviewed-code warning; the typed URL can hold a token, so it is never logged or kept. Providers (the `providers` object of the same hub, loaded when first opened) picks the memory provider and context engine: only providers the server reports as ready can be picked, the rest list what they need on the server (the app runs nothing), and Save sends only the fields that changed to `PUT /api/dashboard/plugin-providers`. `PluginsController`, `CatalogController` and `ProvidersController` hold the state. Details are a bottom sheet below 900 px and a pane at 900 px or wider. The screen shows the chat's profile (or the one picked on the Mac Profiles page): `HermesPluginManagerRepository.forProfile` sends `profile` to the hub, visibility and provider routes, but install, enable, disable, update and remove take none, so Hermes runs them for the dashboard's own profile. The generated client puts a plugin's name into the path unencoded, so the repository encodes it. An install can outlast the client's 30 s timeout, so a timeout is reported as "still installing", not as a failure.

**MCP servers** (`lib/src/mcp/`). List, switch, test and remove the MCP servers of the active profile, opened from the chat sidebar. `HermesMcpRepository` wraps the generated MCP calls and parses leniently. `McpServersController` holds one visit's state (the profile learned first, the list, the test results), and `McpServersScreen` and `McpServerDetail` render it, side by side from 900 logical pixels. The "Add" button is a menu: "Browse the catalog" opens `McpCatalogScreen` (Hermes' approved catalog, searched and filtered on the device; `McpCatalogController`), where an entry that is not installed opens `McpInstallPanel` (a bottom sheet, or the right-hand pane from 900 logical pixels) and an installed one opens its server. `McpInstallController` sends the install and, for entries Hermes builds on the server, polls `GET /api/actions/{name}/status`. Credentials live only in the panel's text fields and go into the install request. `McpSignInScreen` waits while the user approves an OAuth sign-in in the browser (`McpServersController.startSignIn`, then polling `GET /api/mcp/oauth/flows/{id}`); Hermes keeps the token and the app never sees the code. "Add a custom server" opens `McpAddServerScreen` (remote or command server) and the overflow menu's "Edit as JSON" opens `McpJsonEditorScreen`, which loads the whole map from `GET /api/config` (the servers route is lossy) and saves it with `PUT /api/mcp/servers`. A command server makes the Hermes host run a program, so `McpServersController.addServer` and `replaceServers` take a required `McpReviewer` and send nothing until it confirms; the screens pass `showMcpCommandReview` (bottom sheet, dialog from 900 px). Bearer tokens, environment values and the editor's text stay in screen state and are cleared after the request.

**Helper models** (`lib/src/settings/helper_models_screen.dart`). The chat sidebar's "Helper models" row lists the chat profile's auxiliary task slots (`GET /api/model/auxiliary`) and opens the shared `showModelPicker` for one, with its "Use the profile's default" entry. The pick is saved once, when the picker closes, with `POST /api/model/set` (`scope: auxiliary`; the default entry sends `provider: auto`, empty model, which Hermes runs on the main model). Hermes may answer `confirm_required` for an expensive model; the screen asks and resends with `confirm_expensive_model`. Changes apply to new sessions only. Below the slots, a "Mixture of agents" section lists the default preset's advisors and aggregator (`GET /api/model/moa`, `MoaSetup`); a change sends the whole config back with `PUT /api/model/moa`, only that slot edited, and keeps the MoA rows closed until it answers. The section is left out when MoA cannot be read.

**Notifications** (`lib/src/notifications/`). Local notifications when a reply finishes or the agent needs the user, gated by `attention_policy.dart` and user settings. A second source is `schedules/schedule_alerts.dart`: while the app is in front, `ScheduleWatcher` (owned by the shell) polls every profile's cron jobs each minute and announces a run since the last look; Hermes has no push channel, so nothing arrives while the app is closed. On iOS a reply sent from the phone is also a Live Activity (`lib/src/live_activities/`, the `live_activities` plugin, the `HermesLiveActivity` widget extension): `ChatController` starts it on send (ActivityKit only starts one while the app is in front) and moves it with the reply's events, one per chat, labelled with the notification bodies so nothing a reply or request said reaches the Lock Screen. Updates made in the background mark it stale a minute later, since nothing updates it once iOS suspends the app. A finished one stays 15 minutes; stop, deletion, sign-out, the dialog's switch and the next launch end it. The plugin updates an activity only by the id ActivityKit gave it, and does not see a tap that launched the app, which `SceneDelegate` keeps for the `hermes_app/live_activity` channel.

**Telemetry** (`lib/src/telemetry/`). OpenTelemetry to SignalDB through the `flutter_otel` package and its `dart_otel_*` siblings from pub.dev (source: `cedricziel/flutter-otel`, ours — file upstream PRs there rather than working around gaps locally). It is off unless `OTEL_EXPORTER_OTLP_ENDPOINT` is passed via `--dart-define`. When off, no SDK exists and no `traceparent` header is added. Telemetry code must never break the app (see `safely.dart`). Spans, request logs and `AuthController` events describe the Hermes server they belong to with `hermes.*` attributes (version, install ID, auth, gateway mode, profile count, health) read from its `/api/status` answer (`telemetry/hermes_server_attributes.dart`): `Telemetry.forConnection` builds an interceptor and event logger per connection, `AuthController` swaps them when a probe succeeds and drops them when a connect starts or on Change Server, so a request keeps the server it was sent to. They are never resource attributes, since one app can talk to several servers. Breadcrumbs don't get them, except `server.connected` with the version. The connection's telemetry travels with `HermesRepositories` (`telemetry`, captured in `forAuth`): screens build a new gateway or Kanban tracer for each socket from it (`telemetry.gateway()`, `.kanban()`; a tracer links messages to the last upgrade it traced, so two sockets never share one), and the gateway transport, Kanban board, plugin and skills screens log through its `events`. The watch bridge and `TokenStore` keep the root logger. The gateway transport logs `gateway.reconnect`, `gateway.turn_settled` and `gateway.event_unmapped` (a frame type the app shows nothing for, once per type per connection) through the `AppEventLogger`, never with message text. Uncaught Flutter and async errors are logged with full message, stack trace and recent breadcrumbs via `flutter_otel`'s `installCrashReporting`/`BreadcrumbTrail`, wired up in `Telemetry.logUncaughtErrors`/`Telemetry.events`: unlike the package's privacy-preserving `installUncaughtErrorLogging` (type only, for an arbitrary OTLP endpoint), the crash reporter keeps full detail because the endpoint here is always the operator's own self-hosted SignalDB. A recurring error is logged once and then summarized with a repeat count, and message and stack are trimmed to fit SignalDB's attribute size limit (details in `openspec/specs/telemetry/spec.md`). The crash record's breadcrumbs also say what the user was doing: `Breadcrumbs` (`telemetry/breadcrumbs.dart`, provided next to `AppEventLogger`; `Breadcrumbs.none` when telemetry is off or no provider is above) adds a crumb to the same trail without exporting a log record. `AppShell` records `nav.destination` and `app.lifecycle` (resumed, paused), `ChatController` records `chat.threads.loaded` (`switched`, `count`), `chat.thread.selected|new|closed`, `chat.open.requested|failed` and `chat.reply.started|ended` (`outcome`), and `ConversationWindows` records `window.opened|closed|key`; the gateway's `gateway.*` events are crumbs already, so they are not repeated. Crumbs hold fixed names, counts, flags and outcomes only: never text, titles, profile names, server addresses or ids. The trail keeps the last 40.

**macOS menu bar** (`lib/src/macos/mac_menu_bar.dart`, `mac_commands.dart`). In a Mac window the app sets its own `PlatformMenuBar` (Hermes, File, Edit, View, Chat, Window, Help), which replaces `MainMenu.xib`'s menu. A screen offers commands by wrapping its content in `MacCommandScope(commands: {MacCommand.x: MacCommandHandler(callback, title: ...)})`; an item is disabled while no visible scope offers its command (null callback also disables), the innermost or latest scope wins, and `priority` overrides that. Edit items send the text intents to the focused widget, and Delete… (⌘⌫) deletes to the line start while a text field has focus. Menu shortcuts reach the menu only when no Flutter widget handled the key, so don't add a `HardwareKeyboard`/`Shortcuts` handler for a chord the menu owns. File > New (`MacCommand.newChat`, ⌘N) follows the page in front: New Chat on Chat, New Task on Kanban, New Schedule on Schedules, each page retitling it through its scope. Tests answer `SystemChannels.menu` and set `MacWindow.enabled` (`test/macos/mac_menu_bar_test.dart`).

**Conversation windows** (macOS, `lib/src/windows/`). A chat can open in a window of its own (double-click in the sidebar, the thread menu, File > Open in New Window ⌥⌘O). Each window is its own engine and isolate (`desktop_multi_window`; Flutter's own multi-window API is master-only), started through `main(["multi_window", id, args])` into `runConversationWindow`. A conversation window holds no session and never refreshes one: `WindowAuthInterceptor` asks the main window for each request's headers (`AuthController.windowAuthHeaders`, which refreshes only when the rejected token is the current one), and `MainFlutterWindow.swift` registers only a few plugins in its engine (no secure storage, notifications or macos_window_utils). Only the main engine sets the menu bar, telemetry and notifications. `ConversationWindows` (main isolate) tracks the open windows and the key one, persists them for the next launch (frames through `NSWindow` frame autosave), closes them on sign-out, and forwards "Show in Main Window" to the shell. Each engine keeps its own state: a window reloads its chat when it becomes key, and the main window reloads the chats that were open in a window when it becomes key (`ChatController.refreshThread`). The main window is hidden, not released, when closed, so its engine keeps serving the windows; ⌘0 or the Dock icon brings it back. `ConversationWindowsMenu` (in `HermesApp`'s builder) lists the windows in the Window menu and, while one is key, routes the menu bar's window and chat commands to it with a priority-1 `MacCommandScope`. Handoff advertises the key conversation window's chat, and a handed-over chat that has a window opens there.

**Native pieces.** `ios/ShareExtension` (share sheet, `receive_sharing_intent`, linked by a version-pinned path in `project.pbxproj`, so a plugin upgrade must be mirrored there) and `ios/HermesLiveActivity` (the Live Activity widget extension, bundle ID `com.cedricziel.hermesApp.LiveActivity`), `ios/HermesWatch` (the watchOS companion app embedded in the iOS app; it has no network of its own and asks the phone, which answers in `lib/src/watch/`). macOS has its own share inbox (`share/macos_share_inbox.dart`). Debug builds use bundle ID `com.cedricziel.hermesApp.dev`, so every extension's Debug ID must be prefixed with it. Release and TestFlight builds go through `fastlane` (lanes in `fastlane/Fastfile`, store metadata in `fastlane/metadata/`).

## Testing conventions

Tests drive the real generated client and Dio pipeline against `test/support/fake_hermes_server.dart`, an `HttpClientAdapter` with per-route responses, rather than mocking the client. Other helpers in `test/support/`: `fake_chat_transport.dart`, `memory_token_store.dart`, `fake_share_inbox.dart`, `pump_chat.dart`.

`test/workflows/` walks whole user flows (onboarding, chat, kanban, skills/messaging/settings) on phone and desktop, light and dark, and saves a screenshot per step to `build/workflow_screenshots/` (`workflow-screenshots` skill). Look at them after a UI change.

`widgetbook/` is a Widgetbook catalog of single widgets in each state (`component-catalog` skill). **UI work starts in the catalog, not in the app.** For any new widget, redesign or layout/state change, build or change it as a use case first, as a plain-model widget (models and callbacks, no controller or repository), and get every state, both themes and phone and desktop width right there. Only then wire it into a screen, and check the screen with a workflow test or `verify-in-app`. A widget a screen builds inline gets pulled out into `lib/src/*/widgets/` so it can have a use case. `test/widgetbook_test.dart` builds every use case in both themes, and `widgetbook.yml` publishes the catalog to GitHub Pages from `main` (`scripts/build-widgetbook.sh` builds it).

## Specs

`openspec/` holds spec-driven change proposals (`openspec/specs/` for current behavior, `openspec/changes/` for work in progress). Start a change with `/opsx:propose "<idea>"`; project context for it lives in `openspec/config.yaml`. Design history lives under `openspec/changes/archive/`.

## Skills

Project skills live in `.claude/skills/<name>/SKILL.md` (frontmatter `name` and a `description` that says when to use it). When you learn something reusable about working in this repo, such as a workflow, a gotcha or a verification step, write it to a skill rather than to memory, so it is checked in and shared.

- Amend the existing skill when the new knowledge fits it. Fix a skill that turns out to be wrong or stale as soon as you notice.
- Create a new skill when the knowledge is a distinct, repeatable task no current skill covers. Keep the description specific enough that it triggers at the right time.
- Use memory only for things that are personal to the user or don't belong in the repo.
- Commit skill changes with the work that prompted them, or on their own as `docs:`.

## Dependencies

Before writing platform or infrastructure code by hand (storage, permissions, sharing, notifications, deep links, auth flows, and the like), check pub.dev for a mature, maintained plugin and prefer it over a homegrown implementation. Judge maturity by recent releases, publisher, platform coverage, popularity and open issues. If none fits, say why in the PR. The existing choices (`flutter_chat_ui`, `receive_sharing_intent`, the generated `hermes_api` client) follow this rule.
