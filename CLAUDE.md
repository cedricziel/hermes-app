# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Flutter client (iOS, Android, macOS, Windows, Linux) for the Hermes Agent web dashboard (`hermes dashboard`, from NousResearch/hermes-agent). The user enters a self-hosted server URL, signs in, and chats with the agent. The sign-in flow is specified in `openspec/specs/auth/spec.md`, and `openapi/README.md` covers the generated client.

## Commands

```bash
flutter pub get
flutter run
dart format .                     # CI runs: dart format --output=none --set-exit-if-changed .
flutter analyze
flutter test
flutter test test/auth_controller_refresh_test.dart          # one file
flutter test --plain-name "some test name"                   # one test
dart run tool/setup_git_hooks.dart  # installs the dart_pre_commit hook (format + analyze on staged Dart files); once per clone, shared by worktrees
flutter run -d macos -t widgetbook/main.dart   # component catalog (Widgetbook); see the `component-catalog` skill
```

CI (`.github/workflows/ci.yml`) runs format and analyze, and the tests in four parallel jobs split by file (`scripts/test-shard.sh <index> 4`; shard 0 is the Widgetbook test alone); `Analyze & test`, the required check, passes once all of them did. Then it builds Android (debug APK), iOS (simulator), macOS and Linux (release bundle, packaged by `scripts/package-linux.sh`). Releases attach a Linux tar.gz and .deb (x86_64, arm64) to the GitHub release. Every release is cut as a GitHub pre-release and its build goes to TestFlight; promoting one to a full release starts `app-store.yml`, which runs `fastlane submit` to send that version's TestFlight build to App Review on iOS and macOS, which goes live by itself once approved. It needs the `REVIEW_CONTACT_*` and `REVIEW_DEMO_*` (demo server URL, user, password) secrets. A version already in review or released is skipped, so promoting one you submitted by hand does no harm. Run it by hand with `dry_run` (the workflow's default input) to update the listing without submitting. The iOS build needs the watchOS platform installed and an explicit simulator: `flutter build ios --simulator -d <udid>`.

Commits follow Conventional Commits; release-please builds `CHANGELOG.md` and bumps `pubspec.yaml` from them. Don't edit the version by hand.

### Running against a real backend

- `scripts/dev-backend.sh start|stop|url` runs a throwaway Hermes dashboard on an OS-assigned port with its own `HERMES_HOME` (needs `hermes` on PATH).
- `scripts/dev-app.sh start|reload|restart|screenshot|logs|stop` runs the macOS app against it and can screenshot the window. State lives in `.dart_tool/hermes-dev/`.
- `scripts/store-screenshots.sh ios|mac|finish` retakes the App Store and README screenshots; the `store-screenshots` skill (`.claude/skills/store-screenshots/SKILL.md`) has the procedure and the traps.
- The `verify-in-app` skill (`.claude/skills/verify-in-app/SKILL.md`) has the full loop and its rules. Never point the app or `hermes` at the real `~/.hermes`, and never run `hermes dashboard --stop`.
- Building the macOS app rewrites tracked `ios/` and `macos/` Xcode files. Stage files by name, never `git add -A`, and `git restore` those afterwards.
- `test/real_backend_contract_test.dart` checks response shapes against a live backend and skips unless `HERMES_DEV_URL` is set. Free loopback scripted-model turns run without provider credentials. Paid-provider tests need `HERMES_DEV_MODEL_CALLS=1`; external Telegram pairing needs `HERMES_DEV_TELEGRAM_PAIRING=1`. CI leaves both flags unset. The standalone `real-backend-contract.yml` remains advisory and resolves its source revision from matching `openapi/HERMES_REF` and `openrpc/HERMES_REF` through `python3 -I scripts/hermes_contracts.py resolve`. Its summary distinguishes setup, tests, and cleanup outcomes. The pinned backend uses Python 3.14.

### Regenerating the API client

```bash
scripts/fetch_openapi_spec.sh [ref]       # rebuild openapi/ from hermes-agent main or a ref; needs gh, curl, uv
./scripts/generate_hermes_api_client.sh   # needs a JDK (npx openapi-generator-cli) and dart on PATH
```

`update-hermes-contracts.yml` runs both every Monday, refreshes `openrpc/` from the same Hermes commit, and opens one PR when contract JSON or either provenance file changes. It regenerates the Dart client only when OpenAPI JSON changes. Run `python3 -I scripts/test_hermes_contracts.py` to check revision resolution and update detection.

`verify-hermes-api-client.yml` fails CI if `openapi/`, `scripts/` or `packages/hermes_api/` change without a matching regenerated client. Never hand-edit `packages/hermes_api`. Fix template bugs in `scripts/patch_openapi_for_dart.py` or `scripts/patch_generated_dart_client.py`. `packages/hermes_api/pubspec.lock` is committed on purpose.

## Architecture

**State and routing.** `lib/main.dart` sets up telemetry and `provider` (`AuthController`, `ThemeController`, `NotificationSettings`, `ShareController`). `lib/src/app.dart` picks the screen purely from `AuthController.state` (`HermesConnectionState`): setup, login or `AppShell`. There are no named routes. `shell/app_shell.dart` navigates between Chat, Bots, Kanban and Schedules. Bots uses the shared gateway and explains when the dashboard lacks Bot Mode support. The Kanban tab (`lib/src/kanban/`) only exists while the server reports the Kanban plugin as on, and the Schedules tab (`lib/src/schedules/`, the server's cron jobs) only while `/api/cron/delivery-targets` answers. Both are re-checked on connect and on app resume. The board is shared by every profile, so Kanban requests (and the plugin check) send no `profile`; the job form asks for the delivery targets and blueprints of the job's profile. A page stays alive behind the others once opened; the board closes its event stream while it is not on screen (`KanbanBoardController.active`, set from `Visibility.of` and the app lifecycle) and resumes from its cursor. On macOS the board has the Mac toolbar (`widgets/kanban_mac_toolbar.dart`, on `macos/mac_toolbar.dart`) and opens a task in an inspector on the right (`KanbanInspector`, `widgets/kanban_inspector_layout.dart`: docked from 760 pt, over the board below that) instead of a sheet; View > Inspector (⌥⌘I) and File > New (⌘N, titled New Task) come from its `MacCommandScope`. Opening a run of a job goes through `ChatOpenRequests` to the chat screen. On macOS a task's attachment rows are Quick Look targets too (`KanbanTaskController.preview` and `open` stage the file through the same `MediaStore`). `AuthController` owns the whole connection lifecycle: server URL discovery, sign-in, token storage and refresh, and the authenticated `Dio` instance.

**Auth.** Both OIDC and password sign-in use the same RFC 8252 flow (`auth/native_login_flow.dart`, `pkce.dart`): a browser, loopback HTTP listener, PKCE, then a bearer token pair kept in secure storage (`auth/token_store.dart`; on iOS readable after the first unlock, so a watch request can wake the locked phone app and still find the session). The browser (`auth/sign_in_browser.dart`) is an `ASWebAuthenticationSession` sheet on iOS and macOS (`WebAuthSession.swift` in each runner, channel `hermes_app/web_auth`), which App Review requires, and the external browser elsewhere. Hermes only accepts a loopback `redirect_uri`, so on Apple platforms the listener answers the callback with a redirect to `hermes-app-signin://` to end the sheet. Tokens refresh before use and again on any 401. Concurrent 401s must not sign the user out, and sign-in must never be left spinning (regressions fixed in 0.1.8 and 0.1.9). If `/api/status` reports `auth_required: false`, sign-in is skipped. A failed connect is classified in `auth/connect_failure.dart`; the setup screen adds a VPN hint for tailnet/private addresses, and `network/network_signals.dart` (`connectivity_plus` plus app resume) makes `AuthController` retry the saved server after a network failure. VPN detection is only a hint, never a gate: iOS and macOS cannot report it. An untrusted certificate (Caddy's `tls internal`) is its own failure kind with a hint on trusting the root; on Android, where Dart reads only the system store, `network/user_certificates.dart` adds the user-installed CA certificates to the default `SecurityContext` at launch, in `prepareBackgroundIsolate` and on resume. `--dart-define=HERMES_SERVER_URL=<url>` overrides the saved server address, for dev and tests.

**Headless runtime** (`lib/src/background/`). Work that has no screen (a notification button, later background refresh and App Intents) goes through `withHeadlessHermes(body, task:)`, never through an `AuthController` of its own: that one signs the user out when a refresh is rejected. It connects to the saved server (`kSavedServerUrlKey`) with the stored session and returns a sealed `HeadlessOutcome`: `HeadlessDone`, `HeadlessSignedOut`, `HeadlessLocked` (keychain unreadable before the first unlock; `TokenStore.readState` tells that from an empty store) or `HeadlessUnreachable` (also a timeout or a throwing body); callers switch over all four. It refreshes at most once per run and writes the new pair back only when storage still holds the refresh token it spent; it adopts a pair another isolate rotated (`sameOwner` and `isNewerThan`, the rule `AuthController` uses) and never clears the stored session, so a rejected refresh just ends the run. `HeadlessHermes` gives the app's `HermesRepositories`, `profiles()`, a gateway `transport()` on its own socket (closed when the run ends), `annotate(name, count)` for its `background.task` span and `refreshSnapshot({pending})`, which builds and stores the surface snapshot. Everything a winding-down run waits for (a stuck body, a refresh still storing its pair, the sockets) shares one `closeGrace` window. Each `@pragma('vm:entry-point')` function calls `prepareBackgroundIsolate()` (`entry_points.dart`) first. On iOS a second engine registers plugins through `BackgroundPlugins.register(with:)`, not `GeneratedPluginRegistrant`: the URL, share and Live Activity plugins would handle every event twice. `LoneAnswerer` (notification buttons in the iOS background isolate) runs on it.

**Two API layers.**

- `packages/hermes_api` is a generated `dart-dio` client for the backend's OpenAPI spec (`openapi/hermes-agent.openapi.json`). Reach it through `authController.api!.raw`, which shares the managed `Dio`, instead of adding hand-rolled calls.
- `lib/src/api/hermes_api_client.dart` hand-writes only `/api/status`, `/api/auth/providers` and `/api/auth/me`, because the spec has no response schemas for them. It also hand-writes the Kanban attachment download (`fetchKanbanAttachment`), because the generated method decodes the body as JSON and cannot return a file's bytes.
- Many routes (sessions, profiles, messaging, skills, plugins) also lack response schemas, so the generated methods return untyped JSON. The repositories (`chat/hermes_chat_repository.dart`, `profiles/`, `messaging/`, `skills/`, `plugins/`, `schedules/hermes_cron_repository.dart`) parse those rows leniently and skip rows that don't fit. The contract test above guards these shapes.

**Chat** (`lib/src/chat/`, built on `flutter_chat_ui`).

- `ChatController` keeps shared state, its public instance API, and lifecycle in `chat_controller.dart`. Private library parts group history, commands, durable queues, sending, streaming, session bindings/state, progress, connectors, billing, request answers, and system surfaces. `ChatScreen` owns resources and lifecycle in `chat_screen.dart`, with private parts for layout, composer, recipients, sharing, navigation, external openings, and conversation windows. Keep feature changes in the corresponding part. Public controller methods delegate explicitly to private extensions so callers and subclasses retain the same instance API. Parts share their root library's imports and private state; they are not independently owned controllers.

- History is loaded over REST by `HermesChatRepository`. Sending and streaming go through the `ChatTransport` interface (`chat_transport.dart`), a sealed `ChatEvent` stream. The real implementation, `gateway/hermes_gateway_transport.dart`, speaks JSON-RPC over the dashboard's `/api/ws` websocket (`session.create` or `session.resume`, then `prompt.submit`, with replies as `message.delta` events). Both session calls send `source: hermes_app` (`gatewaySessionSource`); without it Hermes records the session as `tui` and gives the agent the terminal UI's prompt hint. `gateway_rpc_client.dart` and `gateway_connection.dart` handle the socket. Gateway frames become `ChatEvent`s in `gateway/gateway_event_mapper.dart`. `openrpc/hermes-gateway.openrpc.json` is Hermes' own list of every frame and server request (see `openrpc/README.md`), and `test/gateway/gateway_contract_test.dart` records what the app does with each one. `review.summary` (what Hermes' background review saved after a turn: memories, user profile, skills) becomes `ReviewSummarized`, which the controller attaches to the latest finished reply (`ChatMessage.reviewNotes`, shown by `widgets/review_summary_note.dart`). A reply ends on whichever comes first: `message.complete`, or `session.info {running: false}` (`ReplyCompleted` or `SessionInfo`; Hermes clears its running flag after the completion, so that report is the settled signal). `settles` in `gateway/gateway_replay.dart` ignores an idle report within 15 s of the submit until the turn has begun, since it can describe the turn before. An `error` event is held and shown as the failure when the session settles with no completion; a failed completion's own message wins. A reply that settled without a completion keeps its text, and a late `message.complete` on `followUps` lands on the same reply. A reply silent for 45 s is checked with `session.active_list` and ended as broken only when its thread is no longer listed as running, in `send` and in the follow-up relay while it is replying. `prompt.submit` answers `streaming`, `queued` (the reply waits for its turn's `message.start`), or `redirected`/`steered` (the server folded the text into the running turn: `PromptFolded` drops the placeholder, the running turn's reply goes on in its own send). The controller drains the queue on `SessionInfo(running: false)` from `followUps`, or 2 s after the completion, and sends with `queued: true` so the server queues the prompt instead of folding it. After a reply ends the transport keeps listening to its session, and `ChatTransport.followUps` carries the turns nobody here submitted: goal continuations, queued prompts, a delta or tool event whose `message.start` was missed (it opens a reply). The turn Hermes runs on its own after a resume that reports `auto_continue` is not among them: `send` claims it (`_Unsolicited`) so the submitted prompt keeps its own reply. Each frame of that turn, its requests and their withdrawal included, goes out on the send's own stream as it arrives, wrapped in `UnsolicitedEvent`, and `ChatController._onOwnTurnEvent` streams it into a reply opened in front of the prompt's user message (`_insertReply(before:)`; the server runs that turn first and stores it there, so a refetch, Copy Transcript and Retry/Edit of the prompt agree with the live order). The turn shows live and is never replayed on `followUps`. An idle report ends it only once a turn-opening frame came (an approval alone does not open one), a late completion lands on it, and its end settles neither the queue nor a stop in flight. Its requests can be answered while it runs and are withdrawn when it ends, the prompt's reply says Hermes is finishing the interrupted turn until then, and a send that gives up fails both replies and refetches. Session and prompt calls time out, `checkConnection` (called when the app resumes) drops a socket the OS killed during sleep, and the RPC client pings every 15 s and closes itself after 45 s without any frame. A send that cannot open its socket or session (connect, `session.create`/`resume` unanswered) tries again on a new connection, 3 attempts in all with the reconnect backoff; an error the gateway answered is final, and `prompt.submit` is never resent. A reply still running when its connection drops is not failed outright: the transport reconnects with full-jitter backoff (300 ms to 15 s, 5 attempts or 60 s), resumes the session, and replays what it missed. Every event frame carries a `seq` per runtime session; `ReplayLedger` (`gateway/gateway_replay.dart`) keeps the highest one seen and the `replay_epoch` from `gateway.ready`, and `session.events.since` fills the gap, with the frames that arrived meanwhile merged in and none shown twice. When the replay is truncated or the server restarted (epoch changed), a running turn is rebuilt from the resume answer's `inflight.assistant` (`ReplyRebuilt`, with the deltas sent after the snapshot still delivered) and an ended one by a REST re-read (`ThreadNeedsRefetch`, then the stored reply); `open_requests` are shown once by id. `approval.cancelled` withdraws the open approvals of its session (`InputRequestsCancelled`).
- Domain messages (`chat_models.dart`) map to flyer messages in `chat_message_mapper.dart`. `chat_controller_sync.dart` applies before/after diffs to the `InMemoryChatController`. Custom message kinds and cards (tool calls, approval and clarify requests) live in `chat_message_kinds.dart` and `widgets/`. Tool calls follow assistant-ui: `tool.generating`, `tool.start` and `tool.complete` are matched by `tool_id` (name as fallback) into `ToolCall`s with args, result data, diff and timing; a run of calls is one `ToolCallGroup`; `widgets/tool_call_bodies.dart` gives terminal, web search, todo and diff calls their own view, with `ToolCallCard`'s input and result as the fallback; an approval Hermes raises while a call runs is bound to it in `chat_reply.dart` and shown inside that call's card. The design for agent input requests is in `openspec/changes/archive/2026-09-19-agent-input-requests/`. Text Hermes writes before a tool call, or checkpoints mid-turn with a `message.interim` event, is sealed into `ChatMessage.sealedProse` (`chat_reply.dart`) instead of being folded into the trailing `content`, so the mapper can render it where it was actually written and `message.complete` never overwrites it.
- Agent activity outside the transcript is sorted into tiers (`activity/activity_tier.dart`: Needs you, Working, For reference; `openspec/changes/chat-activity-*`). The Activity panel (`activity/widgets/activity_panel.dart`, filled by `BoundActivityPanel`) lists Now, Plan and This session; the header's Activity button (a toolbar button on a Mac, View > Inspector ⌥⌘I, routed to a key conversation window too) opens it as an inspector (`widgets/inspector_layout.dart`, shared with Kanban: docked from 760 pt, over the chat below) or, on a phone, a detent sheet. For reference items (usage, side answers, notices, the acknowledgement, idle billing, settled and connection-wide connector activity) live only there; the strip above the transcript keeps Working and Needs-you items, and an empty or unsupported state draws nothing. Breadcrumbs `chat.activity.opened` (`surface`, `source`) and `chat.activity.closed`.
- The composer is Hermes' own `ChatComposer` (`widgets/chat_composer.dart`), not flutter_chat_ui's `Composer`: a card with the field on top and attach, the model pill, the dictation microphone and send below it. `buildChatComposer` puts it in a `Positioned` that stays a direct child of the `Chat` stack and reports its height to the package's `ComposerHeightNotifier`, as the package's own composer does.
- The welcome view's starter prompts (`starter_prompts.dart`) come from the active profile's context: a failed cron job, a blocked or in-review Kanban task, the latest chat and the most-used skill, one each, padded with generic prompts. `StarterContextLoader` reads them in parallel, leaves out a source that fails or takes more than 5 s, and `ChatScreen` reloads it for another profile or after five minutes. Job, task and skill prompts go into the composer; a chat prompt opens that chat.
- The composer's model pill (`lib/src/models/widgets/composer_model_pill.dart`) picks a model and reasoning effort per chat from `GET /api/model/options` (`HermesModelsRepository`, loaded with each profile's threads, hidden when that fails). The pick lives on `ChatThread.modelChoice` and goes out with `ChatTransport.send`: as `session.create` overrides for a new chat, as session-scoped `config.set` (`model`, `reasoning`) on resume when it changed. Nothing is written to the profile's config; that is the Profiles screen's job, which sets a profile's default model (no effort, Hermes keeps none for the main model) with `PUT /api/profiles/{name}/model` through the same picker (`showModelPicker(withEffort: false)`). The Kanban create form opens the same picker from a Model value row with the plugin's own list (`GET /api/plugins/kanban/model-options`, no capabilities, so every model gets Minimal to Ultra) and the picker's default entry (`onUseDefault`); when the list is empty it falls back to a typed model name, like the dashboard. The task panel shows a task's override (`model_override`, `provider_override`, `reasoning_effort` on the task row) and applies the last pick once when the picker closes; bulk edit sets or clears only the effort.
- On macOS the sidebar is a source list (`lib/src/macos/mac_source_list.dart`): 28 pt destination rows (Kanban captioned "All profiles") and threads under recency sections (`thread_sections.dart`; Pinned, Today, Yesterday, Previous 7/30 days, Older) whose folded state `MacSidebarController.sections` keeps in shared preferences. `MacThreadRow` shows Archive and More on hover; More and a right-click open `macThreadMenuItems`, built on `AdaptiveMenuItem` (shortcut text, destructive) and `AdaptiveMenuController.open(at:)`. Copy Transcript copies Markdown and reads a thread's unloaded pages through `ThreadHousekeeping.history`.
- On macOS search and New Chat live in the toolbar (`widgets/mac_chat_toolbar.dart`, on the shared `MacToolbar`): `MacToolbarSearchField` (a button below a 1000 pt window), ⌘F from Edit > Find (`MacCommand.find`, offered by `ChatScreen`'s `MacCommandScope`), Escape to end. While `ThreadSearch.active` the sidebar shows `MacSearchResults` (Chats/Messages, recent searches) with a This profile / All profiles switch; `ChatController._searchAllProfiles` fans out one search per profile and skips a failing one. Below 760 pt (`isMacCompact`) `MacSplitView` opens the sidebar over the content (`MacSidebarController.toggle(compact: true)`, `closeOverlay`), and `ChatScreen`/`AppShell` keep the Mac split view at every width.
- The sidebar's search field (`widgets/thread_search_view.dart`) searches the active profile's sessions with `GET /api/sessions/search` (`HermesChatRepository.searchThreads`; FTS5 snippets mark matches with `>>>`/`<<<`). `ThreadSearch`, owned by `ChatController`, debounces typing by 300 ms, keeps only the latest query's answer and is cleared on a profile switch; while the field holds text the results replace the thread list. A result opens through `ChatController.open(fetchMissing: true)`, so a chat older than the loaded pages is fetched first.
- On macOS an attachment is a Finder item (`widgets/quick_look_target.dart`): a click selects it (the target owns a `FocusNode`, so a text field taking focus ends the selection and keeps its spaces), a double-click (the system's interval, press to press) opens it, Space toggles the system Quick Look panel and a secondary click offers Quick Look, Open and Save…. Its click recognizer never claims the arena and ignores a press that moved as far as a drag-out starts after, so `DragOut` and inner buttons are unaffected. `AttachmentCard`, `AttachmentThumbnail` and the Kanban attachment rows wrap themselves in it; elsewhere it is its child and a click still opens. Files are staged into `MediaStore` first (`stage`, `stageBytes`, `stageCopy`: the shared `hermes_media` cache, safe-name rule and sign-out `clear()`, which also closes the panel; a 24 h `sweep` runs at launch), and `QuickLook` (`media/quick_look.dart`, channel `hermes_app/quick_look`, `macos/Runner/QuickLookPanel.swift`; a `QuickLookResponder` after each engine's Flutter view controller in the responder chain, main window and conversation windows alike, takes control of the panel, and Space or Escape close it while it is key) shows them. No menu chord is involved: Space and Enter are handled only while the target itself holds the focus.
- With no repository, `ChatScreen` falls back to `mock_chat_data.dart`. A canned reply is used when there is no transport.

**Deep links** (`lib/src/deep_links/`). The app opens `hermes://chat?profile=&id=&prompt=`, `hermes://new?profile=&dictate=1&prompt=`, `hermes://requests`, `hermes://kanban` and `hermes://schedules?profile=&job=` (scheme registered on iOS, macOS and Android; `app_links` delivers the links, with Flutter's own deep-link routing switched off in `Info.plist` and the manifest). `parseDeepLink` and `deepLinkUri` are the only code that reads or writes these URLs: every producer (widgets, quick actions, Spotlight, intents, notifications) must build its link with `deepLinkUri(target)`, never by hand. `DeepLinks` (provided in `main.dart`) keeps the latest link until `AppShell` takes it, so a link opened on the sign-in screen is applied after sign-in and sign-out drops it. `AppShell._openDeepLink` hands chats to the chat through `ChatOpenRequests` (`request(prompt:)`, `requestNew`, `requestOldestPending`); Kanban and Schedules links wait for the first `_detect()` and are ignored by a server without the tab. A `prompt` is added under the composer's draft and never sent; `dictate=1` starts the microphone only if the profile offers it. Breadcrumbs `deeplink.opened` and `deeplink.ignored` hold fixed words only. `hermes-activity://` (Live Activity) and `hermes-share` (macOS share inbox) are separate schemes.

**Voice** (`lib/src/voice/`). Dictation follows assistant-ui's dictation element: the composer's microphone (shown when `GET /api/audio/voice-config` reports usable speech-to-text for the chat's profile; `stt disabled` or `no credentials` hide it) records 16 kHz mono PCM with `record` (`voice_recorder.dart`), and, after the Claude app, the field stays read-only with the words recognized so far at the cursor (`DictationDraft`, which gives the draft back on cancel or failure) while the controls row shows cancel, the waveform (`widgets/voice_waveform.dart`) with the engine's name, stop and send. Send while dictating stops, waits for the transcript (`DictationController.whenSettled`) and sends the draft, but nothing after a failed transcription; otherwise the transcript is never sent. `DictationController` streams the audio to the `/api/audio/transcribe-stream` socket when `stt.streaming` says the provider can transcribe live (`TranscribeStream`, opened by `hermesMixedSocketConnect` with the same ticket or token as `/api/ws`), and otherwise, or when that fails, uploads the recording as WAV through `HermesChatRepository.transcribe` with a longer timeout (`receiveTimeoutExtra`, applied by `RequestTimeoutInterceptor` on every client `AuthController` builds). It holds an `stt-lease` while recording, drops the recording when the app leaves the foreground or the profile changes, and records breadcrumbs without text. On iOS and macOS dictation defaults to the device's own recognizer (`DictationSettings`; the Dictation setting in the account menu and Settings… switches to Hermes, and a language the device cannot recognize falls back to it): `packages/hermes_speech` (a local plugin, one Swift source for both) runs Apple's `SpeechAnalyzer` on the same PCM, and `OnDeviceSpeech` wraps its channels, one app-wide instance because the event channel has a single native listener. With it no `/api/audio/` route is called and no recording is kept; `ChatScreen` fetches a missing model by itself and shows the microphone once it is installed (each app has to request it once even when the system already has it); the waveform says which engine is listening. Conversation windows offer no dictation, so neither `record` nor `hermes_speech` is registered in their engine. The watch has no recognizer (watchOS has no Speech framework); its voice messages reach the phone as AAC (`transcribe`), and `WatchBridge.onDeviceTranscriber` runs `OnDeviceSpeech.transcribeFile` on them while the engine is the device, with Hermes as the fallback. The hands-free voice conversation is planned in `openspec/changes/voice-conversation/`.

**Bot Mode hosted groups** (`lib/src/bot_mode/group_protocol/`). `HermesGroupsRepository` accepts the shared authenticated gateway request method and uses only `groups.*` RPCs, with existing method/status tracing. Protocol 2, advertised methods, `idempotent_send`, `monotonic_log` and a ready driver gate execution; readable history survives driver downtime. Rooms from `groups.list` are hosted server-driven rooms, distinct from Desktop legacy metadata rooms with a client driver. Membership is frozen at 2–6 unique local profiles. `GroupReplay` incorporates validated pages before advancing its cursor and fences stale responses/authority changes; `GroupSendOperation` retains a send UUID and reconciles lost receipts against `user:${sha256(client_event_id)}` before explicit retry. Approvals quote exact pending coordinates with once/deny; retries require an advertised action. Hosted clarify/sudo/secret requests have no room response path in the verified protocol and may leave a member waiting; the UI explains this and offers Stop. The `verify-bot-mode-contract` skill (`.claude/skills/verify-bot-mode-contract/SKILL.md`) describes recurring isolated-home conformance checks. No transcript, grant or token is stored in preferences.

**Bot Mode roster and chats** (`lib/src/bot_mode/`). `BotModeRosterRepository` reads profile metadata, keeps unknown `hermes-bots` fields in revision-checked edits, and creates profiles without copying messaging channels. The roster shows managed bots separately from profiles that can be added. `BotModeChatRepository` resolves one hidden `Bot Chat` registry per profile and adopts its current compression tip. The shell opens that stored session with its profile through the existing chat renderer; `BotChatContext` supplies the friendly title and local teammate handles. The stored session ID alone does not identify its owner.

**Bot Mode group UI** (`lib/src/bot_mode/groups/`). The Bots screen lists hosted rooms and opens the group transcript. **Notifications** (`lib/src/notifications/`). Local notifications when a reply finishes or the agent needs the user, gated by `attention_policy.dart` and user settings. Each notification is grouped per chat or scheduled task (`AttentionNotification.groupKey`, `chat:<profile>/<thread id>` or `job:<profile>/<job id>`; thread identifier on iOS and macOS; Android bundles by itself), and a request (any `hermes.request.*` category, or a secret or input the app cannot ask for: `timeSensitive`) uses the time-sensitive interruption level so it can break through a Focus (the user can turn that off in system settings); replies and tasks stay at the default. The iOS Runner carries the time-sensitive entitlement; on the Mac the fastlane lane adds it to `Release.entitlements` before it archives (`set_info_plist_value`), because it is restricted and a local ad-hoc `flutter build macos --release` would be killed at launch with it checked in (`test/notifications/time_sensitive_entitlement_test.dart` guards both). `BadgeController` (`badge_controller.dart`, on `app_badge_plus`) sets the app icon badge (iOS, Android) and the Dock badge (macOS) to the length of the surface snapshot's `pending` list, and removes it when nobody is signed in, after sign-out and while notifications are off; macOS has a `SurfaceSnapshotStore` on `MemorySurfaceStorage` for that alone, and its `SurfaceSnapshots` runs `localOnly` (open requests from the chat screen, no server reads, no `surface.*` telemetry). On iOS and macOS an approval shows its command and a question the question, under a category whose hidden-preview placeholder hides the text on a locked screen, with buttons that answer it (`request_notifications.dart`: the category and action ids, the payload, `answerFor`; Android keeps the generic text). `flutter_local_notifications` cannot set the placeholder, so `hermes_app/notification_categories` in each Runner re-registers the categories and keeps the ones made for single questions. While App Lock is on, requests keep the generic text and get no buttons. An answer goes out with `request.answer` on a fresh gateway transport (`request_answers.dart`; an event-frame request falls back to `approval.respond`/`clarify.respond`). On iOS the Runner owns the notification center delegate (`NotificationActions` in `AppDelegate.swift`), because a launch for a background button has no scene and so no engine: it begins a background task and starts the plugin's headless engine itself. That isolate hands the answer to the running app's isolate through `IsolateNameServer` (offer, then confirm), or answers alone, one answer at a time with a fresh `AuthController` each, all within 25 s of the button. A stored session records its dashboard (`HermesSession.serverUrl`); before a refresh, and after a rejection, `AuthController` takes over a newer stored pair of the same user and dashboard instead of spending a used refresh token or signing out. On macOS the app's isolate gets it. A failed or expired answer posts "Couldn't send your answer". A second source is `schedules/schedule_alerts.dart`: while the app is in front, `ScheduleWatcher` (owned by the shell) polls every profile's cron jobs each minute and announces a run since the last look; Hermes has no push channel, so nothing arrives while the app is closed. The one thing that runs then is the periodic background refresh (`lib/src/background/background_refresh.dart`, `background_scheduler.dart`; `workmanager`): `BackgroundScheduler` registers it while signed in, every 15 minutes at the earliest on iOS (BGAppRefreshTask) and Android (WorkManager), and cancels it on sign-out, expiry or a change of server; the system decides when, and whether, it runs. The whole task, from readying the isolate to the telemetry flush, has 25 s (`backgroundRefreshTask`), so the run gets what is left after its 3 s grace and 2 s flush. A run is `withHeadlessHermes(task: 'refresh')` over a list of independent `BackgroundStep`s (20 s each): `OpenRequestsStep` lists each profile's `session.active_list`, reads `approval.pending` of the sessions that are `waiting`, and posts one generic notification per chat for each request id not yet in `hermes.background.announced.v1` (newest 200; the approval's command is never read), through `requestCategoryFor` so it carries the buttons of an approval raised in front; `SnapshotStep` calls `HeadlessHermes.refreshSnapshot(pending:)`, which rebuilds the snapshot with every profile's chats and replaces its pending list. The app in front and a run both write the snapshot, which carries a `revision`: every write saves the stored revision plus one, a run saves only if the revision is still the one it built from (`SurfaceSnapshotStore.writeIfCurrent`, else it drops its build and logs `surface.snapshot.write_skipped`), and the foreground adopts a newer stored snapshot as its base on resume and before each build. Three more steps (`background_alerts.dart`, `background_spotlight.dart`) report what happened while the app was away, the two that notify only when notifications are on, all only when the app is not in front, with the texts and per-chat or per-job notification ids of the app in front, so a run the app already announced is replaced, not added: `RunningRepliesStep` reads `hermes.background.running.v1` (profile, chat id and time of each chat whose reply ran when `ChatScreen` was paused, written by `ChatController.rememberRunningReplies` for every profile, including replies it carried out of a profile it left, each with the time it was first remembered; cleared on resume, at start and on sign-out; entries expire after 24 h) and asks `session.active_list` once per profile on the run's socket. It announces only on positive evidence: the session is listed `idle` and the newest stored message is the assistant's text (title from `loadThread`, then `loadMessagePage(limit: 5)`, 4 s each, in parallel), with `replyPreview` as the body. A session that is absent or has an unknown status, a chat that ends on the prompt, a tool call or empty text (a lost or stopped turn looks the same) are forgotten silently, there is no "Reply failed" in the background, and a chat whose history cannot be read stays for the next run. It records the chat in `hermes.background.replied.v1`, posts, and only then forgets it; `ChatController` takes that record before it announces a `ReplyCompleted`, so the replay on return does not announce again (the record is cleared on pause, at start, when the user sends in the chat and `replayGrace` after the app returns). `ScheduleAlertsStep` runs when the schedule setting is on and `/api/cron/delivery-targets` answers: `runsSince` against `hermes.schedules.baseline.v1` (`ScheduleBaseline`, job key to last run time, under `accountKeyFor(server, user)` so another server or account reads none, and cleared on sign-out on every platform), muted jobs skipped, `alertsFor` unchanged, notifications first and the baseline saved after; `ScheduleWatcher` reads and saves the same baseline at every look after any pending removal, and an availability check that could not tell (offline, 5xx) leaves it alone. The first look on a device or after the setting is switched on only records. `SpotlightRefreshStep` waits for `SnapshotStep.written` and lets a `ChatSpotlightIndexer` (App Lock through its `locked` callback) bring the index in step with the stored snapshot; unlike the other two it does not depend on the notification setting, only on the Spotlight switch, and it skips a run while the app is in front. It uses `SpotlightIndex.forPlatform(indexOnly: true)` and the Runner's `Spotlight.installIndexing`, which has no `take`, `opened` or `becameAvailable`, so the main engine keeps the taps. The run's span gets `replies.finished` and `schedules.ran` as counts. While the app is in front (its `AppPresence` port answers `resumed`) the run announces nothing (WorkManager runs while the app is open); an announced wait is remembered by session and turn, so a refused `approval.pending` (counted as `background.requests_unreadable`) is never announced twice. Only an empty storage (`HeadlessSignedOut.nothingStored`) cancels the task, and the scheduler re-registers it on resume when the system lost it; on iOS it logs `background.refresh.unavailable` when Background App Refresh is off. Nothing is posted while notifications are off, and a run never signs the user out: signed out cancels the task, locked and unreachable change nothing. The dispatcher (`backgroundRefreshDispatcher`) always answers `true` and flushes telemetry before it returns. On iOS a reply sent from the phone is also a Live Activity (`lib/src/live_activities/`, the `live_activities` plugin, the `HermesLiveActivity` widget extension): `ChatController` starts it on send (ActivityKit only starts one while the app is in front) and moves it with the reply's events, one per chat, labelled with the notification bodies so nothing a reply or request said reaches the Lock Screen. It declares the `.small` supplemental family, which watchOS 11 shows in the Smart Stack (title, a short state word, the timer; derived from the stored state in Swift). A turn sent from the watch gets none: it reaches the phone in the background, where ActivityKit cannot start an activity. Updates made in the background mark it stale a minute later, since nothing updates it once iOS suspends the app. A finished one stays 15 minutes; stop, deletion, sign-out, the dialog's switch and the next launch end it. So do a turn that can no longer be followed (a profile switch while only the follow-up listener fed it, a closed chat) and a stop the server had nothing to stop; the turn Hermes runs ahead of a prompt does not finish the prompt's activity, and a follow-up turn never moves a finished one. The plugin updates an activity only by the id ActivityKit gave it, and does not see a tap that launched the app, which `SceneDelegate` keeps for the `hermes_app/live_activity` channel.

**Ask Hermes** (iOS App Intent; `lib/src/intents/ask_hermes.dart`, `intents_channel.dart`, `tapped_transport.dart`, `ios/Runner/IntentsBridge.swift`, `HermesSurfaceKit/AskHermes.swift` and `AskHermesIntent.swift`). Siri and Shortcuts send one question and get the reply back without opening the app, also on a locked device (the user's choice; App Lock is the opt-out). `AskHermesIntent` runs `perform()` in the app's process; `AskHermes.answer` owns the 25-second clock and says "Still working — I'll notify you." when it runs out, while the ask goes on; Dart decides 500 ms earlier (`kAskMargin`) so it always speaks first. `IntentsBridge` is the one bridge to Dart for every intent (its header documents the channel `hermes_app/intents`: `ask`, `expire`, `unavailable`, `openLink` from Swift; `ready`, `finished`, `closed` from Dart): the app's engine once that said ready, else a background engine on `intentsMain` (`entry_points.dart`, plugins from `NotificationActions.registerPlugins`) that gets `AskHermes.readyWait` (12 s; a cold start was measured at 5.4 s) and stops 10 s after its last call, kept alive when it was merely slow and reported later as `intent.unavailable` (`ready_timeout`, `engine_start_failed`). It holds a `UIApplication` background task until Dart says `finished` or iOS expires it, and gives up the engine's line at Swift's deadline. New intents add methods to that channel (`IntentsChannel._onCall`) rather than engines. `AskHermes` (Dart) runs `WatchRequestHandler`'s `send` on `withHeadlessHermes(task: 'intent.ask')`, through `TappedTransport` so it sees `ThreadBound`, `PromptFolded` and `ReplyCompleted`; it maps each `HeadlessOutcome` to an `AskOutcome` and Swift words them (the reply is spoken without Markdown, an approval or question never reaches Siri). "Reply ready" and "Reply failed" are posted only after "Still working" was said; request notifications always. Once "Still working" was said the chat is added to `RunningReplies` (`fromAsk`, which the chat screen's pauses keep) so a background run announces the reply if the process is suspended (only once Hermes has the question: a frame, or `PromptAcknowledgement.promptAccepted`, which the gateway transport sets when `prompt.submit` is answered); `clear` on the app's return keeps those entries and `clearAll` on sign-out drops them; the ask forgets the entry when it announced the reply itself, and a turn that ends without a reply (a timeout, a closed socket) posts no "Reply failed" but is left to that check. A question that never reached Hermes after "Still working" posts one "Couldn't send your question" notification whose payload (`q`, at most 4000 characters, none under App Lock) opens a new chat with it unsent (`NotificationTarget.newChat`); a prompt Hermes accepted whose socket then died posts nothing of the kind. A prompt Hermes folded into the chat's running turn answers "Added to the running chat." With App Lock on nothing is sent: the intent calls `continueInForeground` and the bridge hands `hermes://new?prompt=` (`AskHermes.handOverLink`, `DeepLink`) to Dart's `DeepLinks.open` over `openLink`, so a cold launch holds it until the shell is up. The span `background.task` keeps the runtime's `outcome`; the intent's own is `ask.outcome`, with `engine` and `continued` (App Lock and blank asks get a span of their own), and the log event `intent.ask` has `outcome` and `waited_s`. Never log the question, reply, title, profile or ids.

**Surface snapshot** (`lib/src/surfaces/`). One JSON string under `hermes.surface.v1` in the App Group's `UserDefaults` (the `home_widget` plugin; Android keeps it in the plugin's preferences) is what widgets, quick actions, Spotlight and App Intents read, since an extension holds no token and opens no connection. It holds the signed-in flag, current profile, the server's profile names, up to 10 recent chats across profiles (title, a snippet of at most 120 characters, a `hermes://` link), open requests (chat title and kind only, never the command, question or secret), Kanban blocked and in-review counts, and the next schedule run and last failed job; Kanban and schedules are null when the server lacks them. No token, server address or identity, ever. `SurfaceSnapshots` (provided in `main.dart` on iOS and Android) writes it while the app is in front: `ChatController.onSurfaceChange` reports the chat list loading, a reply ending and a request opening or closing with `ChatHints` (the open profile's chats, no extra request), debounced 2 s; other profiles' chats, Kanban and schedules are read at most every 5 minutes and on every move to the background (`SurfaceSnapshotBuilder`: a source that fails or takes over 5 s keeps its previous section). While App Lock is on, titles, snippets and job names are written empty (counts and links stay), and toggling it rewrites at once. Sign-out, an expired session and Change Server write the signed-out form. An unchanged snapshot is still stored again with the newer `updatedAt` (no listener call; widgets reload only when that time is an hour past the one they last reloaded for, since their stale note is due six hours after it), so widgets do not keep saying "Open Hermes to refresh". A reader must treat titles and snippets as `.privacySensitive()` and must never add content the notification body does not already allow. Add a widget's kind to `kSurfaceWidgetKinds` (`widget_kinds.dart`) so a write reloads it; a kind that fails to reload is logged as `widgets.reload_failed` and the others still reload. A kind that reads only the signed-in flag (New Chat, Dictate, Quick launch) is also in `kSignedInOnlyWidgetKinds` and reloads only when that flag flips, to save WidgetKit's reload budget. `WidgetUsageReporter` logs `widgets.installed` (kinds, families and counts) at most once a day. A widget with no snapshot, a signed-out one or one older than six hours says "Open Hermes to sign in" or "Open Hermes to refresh", and while App Lock is on rows without a title draw a redacted placeholder, never an invented title.

**Request intents** (iOS, `lib/src/intents/request_intents.dart`, `ios/HermesSurfaceKit/.../RequestIntents.swift`, `ios/Runner/RequestIntentsBridge.swift`). "Pending Requests" (no unlock needed) says what waits, from `OpenRequestsStep` read fresh and stored with `refreshSnapshot(pending:)`, falling back to the stored snapshot with "As of <time>," when Dart cannot reach the server; "Answer Approval" (`requiresAuthentication`) reads the approval's command with `ChatTransport.pendingApprovals`, confirms with it, then answers through `RequestAnswerSender` / `answerOpenRequest(..., raisedAsEvent: true)`, the notification buttons' path. Both run in a Flutter engine the Runner's `RequestIntentsBridge` starts on `requestIntentsMain` (channel `hermes_app/request_intents`, calls one at a time, engine kept 10 s) and go through `withHeadlessHermes`; every `HeadlessOutcome` has a sentence ("Sign in to Hermes first.", "Unlock your iPhone first.", "Can't reach your Hermes server."). With App Lock on the list is a count and an answer is refused. The flows live in `HermesSurfaceKit` behind `RequestIntentsBackend`, so `swift test` runs them with a fake.

**Spotlight** (iOS and macOS, `lib/src/spotlight/`, each Runner's `Spotlight.swift`). `SpotlightSettings` defaults to enabled when `hermes.spotlight` has no saved value; saved opt-outs remain off. Settings exposes the switch on both platforms, and the iOS account menu also opens it. `ChatSpotlightIndexer` follows surface snapshots and indexes up to ten recent chats with titles and snippets, skipping unnamed chats. Native calls run serially; subsequent updates change only modified items and remove dropped ones. Switching off, sign-out, server changes and App Lock remove indexed content; failed removals retain a dirty flag for retry. iOS uses a named index with complete file protection and waits for protected data availability. macOS uses a named index and checks `isIndexingAvailable()`, without promising iOS lock-screen protection. Search results arrive through native continuation handlers, remain pending until taken by Dart, and use the existing deep-link flow. On macOS, a result also brings the main window forward. Handoff remains ineligible for search. Existing events report operations, domains and error types without user content.

**Watch complications** (`lib/src/watch/watch_complication.dart`, `ios/HermesComplication`). A watchOS WidgetKit extension embedded in the watch app (bundle ID `com.cedricziel.hermesApp.watchkitapp.widgets`) offers Voice Chat (`accessoryCircular`, `accessoryCorner`) and a chat status (`accessoryRectangular`, which the Smart Stack shows). `WatchComplicationStatus` publishes the latest turn's state (working, waiting, ready, failed, from the Live Activity's `nextActivityState`, restarted when a finished chat opens another turn or asks), a time, a rising `seq`, the watch's thread id and the chat title only once the gateway or server named the chat (`ChatThread.named`; never the prompt, a file name or the server's preview), never any text, and only the state while App Lock is on. It is fed from `ChatController._announce` (replies sent from the phone) and `WatchRequestHandler._send` (turns sent from the watch), because neither the notifier nor the Live Activity sees both; `WatchRelay.swift` sends a change of state (a stop and a sign-out clear included, App Lock stripping a title too; not the first working of a watch turn) with `transferCurrentComplicationUserInfo` (budgeted), and everything else, or that once the budget is spent, with `updateApplicationContext`; a turn that starts on a chat replaces the chat's earlier ones and a working or waiting one is forgotten after 30 minutes; an undelivered payload is sent again with the next change. The watch app (`ComplicationUpdates`, in `WCSessionTransport`'s delegate) applies it only if its `seq` is newer than the last one, stores it in the App Group `group.com.cedricziel.hermesApp` and reloads the timelines (the `.watchConnectivity` background task holds the app until the session has nothing pending); `Core/ComplicationStatus.swift` (decoding, store, the relevance plan, the `hermes-watch://` links) is shared by the package, the watch app and the extension. A working or waiting status the phone did not renew for 30 minutes is not shown, since a suspended phone app cannot report the end. The extension and the watch app need App Groups enabled on their App IDs (fastlane's `bootstrap_app` says so).

**Telemetry** (`lib/src/telemetry/`). OpenTelemetry to SignalDB through the `flutter_otel` package and its `dart_otel_*` siblings from pub.dev (source: `cedricziel/flutter-otel`, ours — file upstream PRs there rather than working around gaps locally). It is off unless `OTEL_EXPORTER_OTLP_ENDPOINT` is passed via `--dart-define`. When off, no SDK exists and no `traceparent` header is added. Telemetry code must never break the app (see `safely.dart`). Spans, request logs and `AuthController` events describe the Hermes server they belong to with `hermes.*` attributes (version, install ID, auth, gateway mode, profile count, health) read from its `/api/status` answer (`telemetry/hermes_server_attributes.dart`): `Telemetry.forConnection` builds an interceptor and event logger per connection, `AuthController` swaps them when a probe succeeds and drops them when a connect starts or on Change Server, so a request keeps the server it was sent to. They are never resource attributes, since one app can talk to several servers. Breadcrumbs don't get them, except `server.connected` with the version. The connection's telemetry travels with `HermesRepositories` (`telemetry`, captured in `forAuth`): screens build a new gateway or Kanban tracer for each socket from it (`telemetry.gateway()`, `.kanban()`; a tracer links messages to the last upgrade it traced, so two sockets never share one), and the gateway transport, Kanban board, plugin and skills screens log through its `events`. The watch bridge and `TokenStore` keep the root logger. The gateway transport logs `gateway.reconnect`, `gateway.turn_settled`, `gateway.event_unmapped` (a frame type the app shows nothing for, once per type per connection) and `gateway.send_failed` (the step a send stopped at and the kind of error) through the `AppEventLogger`, never with message text. Uncaught Flutter and async errors are logged with full message, stack trace and recent breadcrumbs via `flutter_otel`'s `installCrashReporting`/`BreadcrumbTrail`, wired up in `Telemetry.logUncaughtErrors`/`Telemetry.events`: unlike the package's privacy-preserving `installUncaughtErrorLogging` (type only, for an arbitrary OTLP endpoint), the crash reporter keeps full detail because the endpoint here is always the operator's own self-hosted SignalDB. A recurring error is logged once and then summarized with a repeat count, and message and stack are trimmed to fit SignalDB's attribute size limit (details in `openspec/specs/telemetry/spec.md`). The crash record's breadcrumbs also say what the user was doing: `Breadcrumbs` (`telemetry/breadcrumbs.dart`, provided next to `AppEventLogger`; `Breadcrumbs.none` when telemetry is off or no provider is above) adds a crumb to the same trail without exporting a log record. `AppShell` records `nav.destination` and `app.lifecycle` (resumed, paused), `ChatController` records `chat.threads.loaded` (`switched`, `count`), `chat.thread.selected|new|closed`, `chat.open.requested|failed` and `chat.reply.started|ended` (`outcome`), and `ConversationWindows` records `window.opened|closed|key`; the gateway's `gateway.*` events are crumbs already, so they are not repeated. Crumbs hold fixed names, counts, flags and outcomes only: never text, titles, profile names, server addresses or ids. The trail keeps the last 40.

**macOS menu bar** (`lib/src/macos/mac_menu_bar.dart`, `mac_commands.dart`). In a Mac window the app sets its own `PlatformMenuBar` (Hermes, File, Edit, View, Chat, Window, Help), which replaces `MainMenu.xib`'s menu. A screen offers commands by wrapping its content in `MacCommandScope(commands: {MacCommand.x: MacCommandHandler(callback, title: ...)})`; an item is disabled while no visible scope offers its command (null callback also disables), the innermost or latest scope wins, and `priority` overrides that. Edit items send the text intents to the focused widget, and Delete… (⌘⌫) deletes to the line start while a text field has focus. Menu shortcuts reach the menu only when no Flutter widget handled the key, so don't add a `HardwareKeyboard`/`Shortcuts` handler for a chord the menu owns. File > New (`MacCommand.newChat`, ⌘N) follows the page in front: New Chat on Chat, New Task on Kanban, New Schedule on Schedules, each page retitling it through its scope. View > Back (⌘[) is offered by a pushed `SettingsScaffold` while its route is current (not under a dialog or sheet) and leaves that page. Tests answer `SystemChannels.menu` and set `MacWindow.enabled` (`test/macos/mac_menu_bar_test.dart`). The menus are described once in `menu_layout.dart` (`menuLayout`: sections, groups, `MenuEntry` with its chord and platforms); `macMenus` renders it for the Mac, and on iOS and iPadOS `IpadMenuBridge` (`ipad_menu_bridge.dart`, mounted by `MacMenuBar` with iOS chrome) sends it once plus each command's enabled flag and title over `hermes_app/menu` to `ios/Runner/KeyCommandMenu.swift`, which builds `UIKeyCommand`s in `buildMenu(with:)` and answers `canPerformAction` from that state. Flutter sees a key first; for an enabled item UIKit then runs the command once, for a disabled one the key stays with the app. The iPad has no Open in New Window, Close Window, sidebar or inspector items and no chord for Delete…; ⌘F is `MacCommand.find` on both (on iPad `ChatScreen` offers it from the layout while the sidebar is beside the chat and focuses its search field). Breadcrumb `menu.command`, log `ipad_menu.sync_failed`.

**Conversation windows** (macOS, `lib/src/windows/`). A chat can open in a window of its own (double-click in the sidebar, the thread menu, File > Open in New Window ⌥⌘O). Each window is its own engine and isolate (`desktop_multi_window`; Flutter's own multi-window API is master-only), started through `main(["multi_window", id, args])` into `runConversationWindow`. A conversation window holds no session and never refreshes one: `WindowAuthInterceptor` asks the main window for each request's headers (`AuthController.windowAuthHeaders`, which refreshes only when the rejected token is the current one), and `MainFlutterWindow.swift` registers only a few plugins in its engine (no secure storage, notifications or macos_window_utils). Only the main engine sets the menu bar, telemetry and notifications. `ConversationWindows` (main isolate) tracks the open windows and the key one, persists them for the next launch (frames through `NSWindow` frame autosave), closes them on sign-out, and forwards "Show in Main Window" to the shell. Each engine keeps its own state: a window reloads its chat when it becomes key, and the main window reloads the chats that were open in a window when it becomes key (`ChatController.refreshThread`). The main window is hidden, not released, when closed, so its engine keeps serving the windows; ⌘0 or the Dock icon brings it back. `ConversationWindowsMenu` (in `HermesApp`'s builder) lists the windows in the Window menu and, while one is key, routes the menu bar's window and chat commands to it with a priority-1 `MacCommandScope`, which also disables View > Back so a settings page in the main window stays put. Handoff advertises the key conversation window's chat, and a handed-over chat that has a window opens there. The quick panel (`lib/src/quick_panel/`, change `mac-quick-panel`) is one more engine of this kind, started with `QuickPanelLaunch` (`kind: panel`): on its first `presentPanel` call `QuickPanel.swift` moves its view controller into a non-activating floating `NSPanel` and orders the plugin's window out, so the panel takes keys without bringing Hermes forward. A global shortcut opens it: the Swift package KeyboardShortcuts (Xcode SPM on the Runner, pinned in `Package.resolved`) registers the user's chord (none by default) in `QuickPanelShortcut.swift` and forwards presses over `hermes_app/quick_panel` to `GlobalShortcut`; `QuickPanelShortcut` (Dart) toggles the panel through `ConversationWindows.togglePanel` while signed in and shows the main window otherwise. Settings… records the chord with the package's native recorder (`AppKitView` `hermes_app/shortcut_recorder`). The panel is never saved or listed in the Window menu, closes on sign-out, and gets the dictation plugins conversation windows leave out. `QuickPanelScreen` holds one chat on the main window's current profile (`profile.current` on the main channel): before the first send the panel is just the composer and as tall as it, after it the chat's `ChatThreadView` (`welcome: false`) at a fixed height (`resizePanel`, capped at 60% of the screen natively). A show continues the chat when it was used within five minutes on the same profile (`QuickPanelSession`) and otherwise starts empty. Open in Hermes (⌘O) hides the panel, then asks the main window (`panel.showInWindow`) to open the chat, with the composer's draft, through `ConversationWindows.open`. Dictation there goes through `ComposerDictation` (`lib/src/voice/`), as in `ChatScreen`, and the chat view's callbacks, latest-reply tracking and model pill come from `lib/src/chat/chat_thread_bindings.dart`, shared by the chat screen, conversation windows and the panel.

**Dock menu** (macOS, `lib/src/macos/dock/`, `macos/Runner/DockMenu.swift`). AppKit asks for the Dock icon's menu synchronously, so Dart pushes what it shows (`DockMenuBridge.update`, method `dockMenu` on the `hermes_app/app` channel, `MacApp.setDockMenu`) and `AppDelegate.applicationDockMenu` builds it from the copy in memory: New Chat, up to five recent chats of the shown profile (remote, not Bot Chat registries, newest first, titles cut to 40 characters), Show Main Window (native only, so it works in every state). `DockMenuController` (provided in `main.dart` on a Mac) holds the state, which `DockMenuGate` sets from `AuthController` and `AppLockController` (`off` unless connected, `locked` while covered, else `ready`); only `ready` carries titles, and `ChatScreen` supplies them from `_changed` and clears them in `dispose`. A pick comes back as `dockNewChat` or `dockOpenChat`; `ChatScreen._showChat` (shared with Handoff) focuses the chat's conversation window or restores it in the main window. New Chat while locked waits for `AppLockController.unlock()` (which returns whether the app is unlocked and joins a prompt already open) and is dropped if the unlock fails, the app locks again, the user signs out or a newer pick replaced it. Breadcrumbs `dock.menu.action` and `dock.menu.deferred` and the event `dock.menu.open_failed` hold no titles, ids or profile names.

**Watch Handoff.** The `threads` answer (and every `send` answer that names a thread, which `ConversationModel` adopts for a new chat) adds `serverUrl` (canonical), `profile` and `sessionId` (the raw session id) per chat, left out when either is unknown. The open chat's `ConversationView` advertises an `NSUserActivity` of the `HERMES_HANDOFF_TYPE` type with the same v1 payload the phone and Mac accept (`threadId` = the raw session id); the watch only passes the address on. `ios/Flutter/HandoffType.xcconfig` is the one iOS definition of the type, included by the iOS configs and `HermesWatch.xcconfig`, and `ios/HermesWatch/Info.plist` declares it (the macOS configs hold the same pair).

**Drag out** (macOS, `lib/src/drag_out/`, `macos/Runner/DragOut.swift`). Chat attachments and Kanban task attachments drag out of the app as files (file promises: the bytes are read only when the receiver asks). Widgets never touch the platform: they wrap their child in `DragOut(kind:, item:, child:)`, which asks the `DragOutSource?` provider (set in `main.dart`, `MacDragOutSource` on macOS, null elsewhere, so conversation windows and the catalog see none) to make it draggable. `MacDragOutSource` watches the pointer (a `Listener`, not the gesture arena, so taps, selection and scrolling are untouched) and after 6 px with the primary mouse button down calls `startDrag` on the `hermes_app/drag_out` channel. `DragOutController` (Swift, registered by one line in `MainFlutterWindow.awakeFromNib`) remembers the window's latest left-button `NSEvent`s with a local monitor, starts `beginDraggingSession` on the Flutter view from them, allows copy only outside the app (so `desktop_drop` cannot take the file back), and at the session end posts a synthetic `leftMouseUp` to the Flutter view (the session swallows the real one, which would leave Flutter's button state stuck). Files go out as `NSFilePromiseProvider`s: on demand Swift asks Dart (`readFile`), which answers with the path of a local file (`DragOutFile.localPath`, copied natively) or, when there is none, the bytes; a 60 s timeout fails the promise, and `fileWritten`, `readTimedOut` and `ended` report back; text goes out as an `NSPasteboardItem` with plain text and Markdown. `DragOutItem` is `DragOutFile(name:, read:)` or `DragOutText`; names go through `sanitizeDragFileName`. `DraggableAttachment` (`chat/attachments/`) wraps `AttachmentCard`/`AttachmentThumbnail` in `chat_builders.dart` and offers the picked path or the `MediaStore.file` cache copy as the local file, bytes only for an embedded attachment; `DraggableKanbanAttachment` wraps a task panel row and reads through `KanbanTaskController.readAttachment`. `DragOutTelemetry` records the `drag_out.started` breadcrumb, `drag_out.promise` span and `drag_out.completed` event (slugs only, never names or ids). The drop side stays `desktop_drop`; the controller registers no drag destination. Message text and chats drag out too: `MessageDragGrip` (`chat/widgets/`, wrapped around the bubble in `_buildText`; a gutter beside the message holds the grip on hover, so it never covers content; the gutter stays but the grip is off while a reply streams, and neither exists where there is no source) drags `DragOutText(message.text)` as plain text and Markdown; a Mac sidebar row (`ThreadSidebar._row`) drags `threadDragItem` (`chat/thread_export.dart`), a `<title>.md` promise of `# <title>` plus the Copy Transcript Markdown, read through `ThreadHousekeeping.history` only on the drop (`DragOutKind.thread`, failure `history`; a promise Swift times out is `timeout` and cancels the read between pages). A started drag cancels the pointer in the gesture binding, so releasing near where it began is not a click. Tests: `FakeDragOutSource`, a mocked channel for `MacDragOutSource`, `macos/RunnerTests/DragOutTests.swift` for the promises; the catalog uses `CatalogDragOutSource`.

**Staying alive and the menu bar item** (macOS, `lib/src/macos/menu_bar_extra/`, `lib/src/shell/app_presence.dart`, `lib/src/macos/mac_app.dart`). Closing the last window leaves the app running with its Dock icon (`applicationShouldTerminateAfterLastWindowClosed` is false, the activation policy never changes); Cmd-Q, Hermes > Quit and the menu bar item's Quit end it, the last through `MacApp.terminate` (channel `hermes_app/app`). `AppDelegate.refreshWindowless()` tells Dart when no window is on screen (`MacApp.windowlessChanges`) and holds a `beginActivity` against App Nap meanwhile. `AppPresence.foreground` counts `hidden` and `inactive` as running on macOS, so `ScheduleWatcher` keeps its minute timer; `AppPresence.focused` stays `resumed` only, so notifications still post with no window. The menu bar item is an `NSStatusItem` in the runner (`MenuBarStatusItem` at the end of `MainFlutterWindow.swift`, created by the main engine only, not `tray_manager`: 0.8.0 builds a C++ core for every platform). Dart sends it the icon state (SF Symbols `bubble.left`, `ellipsis.bubble`, `exclamationmark.bubble`, as template images) and the whole menu in one `update` call on `hermes_app/menu_bar_extra`, and hears `selected` (an item key) and `opened`. `MenuBarExtraModel.of(chat)` reads the replying threads and pending requests the `ChatController` already holds (no polling, no request on open; replies running only in a conversation window are not listed) and is compared with `==` so the menu is sent only when it changed. `buildMenuBarMenu` makes the rows: approvals are submenus with the card's own choices (`offeredApprovalChoices`, `approvalChoiceLabels`), other requests open their chat, and New Chat, Show Main Window and Quit end it. `MenuBarExtra` (plain Dart, over the `MenuBarTray` boundary) acts on a pick: approvals go through `ChatController.answerApproval` like the card, "Always allow" asks first (`confirmAlwaysAllow`), an answer that did not go through opens the chat, and a chat with a conversation window is focused instead of opened in the main one. `MenuBarExtraHost` (in `HermesApp`'s builder, so a signed-out app keeps its item) owns it and provides a `MenuBarExtraLink` that `ChatScreen` connects its controller to while it is on screen; `MenuBarExtraSettings` (`menuBarExtra.enabled`, on by default; the "Menu bar item" switch in Settings) hides the item without changing the stay-alive. While the app is locked (`AppLockController.covered`; the host sits above `AppLockGate`) the menu shows counts, "Unlock Hermes…" and the fixed entries only, with no title, command or choice. Row keys come from what a row does (`approve:<thread>:<request>:<choice>`), so a pick on a changed menu does nothing (crumb `menubar.stale_pick`); an approval is answered once (in flight from the pick, rechecked after the "always" question); the runner applies an update only when the open menu closes; the item stays hidden until `MenuBarExtraSettings.loaded`. Crumbs `menubar.opened`, `menubar.action` and `menubar.stale_pick` and the log `menubar.approval_answered` carry counts and fixed names only (`choice` is once, session, always, deny or other).

**Native pieces.** The iOS Runner declares the background refresh's BGTask identifier `$(PRODUCT_BUNDLE_IDENTIFIER).refresh` (`BGTaskSchedulerPermittedIdentifiers`, `UIBackgroundModes: fetch`) and registers its launch handler in `didFinishLaunching` (`WorkmanagerPlugin.registerPeriodicTask(withIdentifier:earliestBeginInSeconds:)`), because BGTaskScheduler refuses a handler added later; it does not run on macOS. `ios/ShareExtension` (share sheet, `receive_sharing_intent`, linked by a version-pinned path in `project.pbxproj`, so a plugin upgrade must be mirrored there) and `ios/HermesLiveActivity` (the app's one WidgetKit extension despite its name, bundle ID `com.cedricziel.hermesApp.LiveActivity`: the Live Activity, the Home Screen widgets Recent chats, Needs you and Board, and the Lock Screen and StandBy ones (Needs you's accessory families, New Chat, Dictate and Quick launch), which draw the surface snapshot only; new widgets join its `HermesLiveActivityBundle`, and renaming the target would orphan its provisioning profile), `ios/HermesSurfaceKit` (the Swift package the system surfaces share: `SurfaceSnapshot`, the lenient reader of the snapshot, and the pure `RecentChatsModel`/`NeedsYouModel`/`NeedsYouAccessoryModel`/`QuickLaunchModel`/`BoardModel` that decide what each widget shows, the App Intents `ChatEntity`/`ProfileEntity` (queries answered from the snapshot: recent chats newest first, a chat the snapshot no longer holds still opens as "Chat"; under App Lock, when every title is empty, no chat is offered; the app's "New chat" label is shown with profile and age and never matched; the Open Chat control's label is fixed) with `OpenChatIntent`, `NewChatIntent`, `DictateIntent` and the Open Chat control's `OpenChatControlIntent` (each returns an `OpenURLIntent` on a `DeepLink`; compiled into the Runner and the extension, whose bundle also holds the New Chat, Dictate and Open Chat controls in `IntentControls.swift`; the one `AppShortcutsProvider`, `HermesAppShortcuts`, and the `hermes_app/intents` channel that `lib/src/intents/intent_shortcuts.dart` calls after each snapshot write are Runner-only, in `ios/Runner/HermesAppShortcuts.swift`), and `DeepLink`, the only Swift builder of `hermes://` links, whose output `test/deep_links/deep_link_fixture_test.dart` pins in `Tests/Fixtures/deep_links.json` (`UPDATE_DEEP_LINK_FIXTURE=1` rewrites it); the extension compiles its sources directly, in the same module, so its tests run with `swift test` in CI's "Test watch core" job; `test/fixtures/surface_snapshot_v1.json` is the Dart-written fixture its tests decode, kept equal to the copy in `ios/HermesSurfaceKit/Tests/Fixtures/`), `ios/HermesWatch` (the watchOS companion app embedded in the iOS app; it has no network of its own and asks the phone, which answers in `lib/src/watch/`. It keeps the chat list and the listed chats in its Caches directory, hands the requests that never reached the phone over with the next one, which the phone logs as `watch.delivery.failed`, and offers fixed quick-reply chips (Continue, Yes, No, Summarize) and double tap (starts or stops and sends a voice message) in a chat. A send that waits on an approval or a question answers `waiting` at once and the watch asks again with the same send id while the user answers from the mirrored notification; see the `watch-simulator` skill). macOS has its own share inbox (`share/macos_share_inbox.dart`), which also carries the Services menu's "Ask Hermes" (`NSServices` in `macos/Runner/Info.plist`, `AskHermesService.swift`): the provider queues the selection in memory (never on disk, at most 20,000 characters), `AppDelegate` merges it into the `take` answer, and the inbox turns it into a `SharedQuote`, which `ChatScreen` puts, block-quoted and unsent, in the composer of a new chat (`ShareController` holds only the latest and drops it on sign-out). On macOS, Debug builds use bundle ID `com.cedricziel.hermesApp.dev` (`macos/Runner/Configs/AppInfo.xcconfig`), so every macOS extension's Debug ID must be prefixed with it; iOS uses `com.cedricziel.hermesApp` in every configuration. Release and TestFlight builds go through `fastlane` (lanes in `fastlane/Fastfile`, store metadata in `fastlane/metadata/`).

## Testing conventions

Tests drive the real generated client and Dio pipeline against `test/support/fake_hermes_server.dart`, an `HttpClientAdapter` with per-route responses, rather than mocking the client. Other helpers in `test/support/`: `fake_chat_transport.dart`, `memory_token_store.dart`, `fake_share_inbox.dart`, `pump_chat.dart`.

`test/workflows/` walks whole user flows (onboarding, chat, kanban, skills/messaging/settings) on phone and desktop, light and dark, and saves a screenshot per step to `build/workflow_screenshots/` (`workflow-screenshots` skill). Look at them after a UI change.

`widgetbook/` is a Widgetbook catalog of single widgets in each state (`component-catalog` skill). **UI work starts in the catalog, not in the app.** For any new widget, redesign or layout/state change, build or change it as a use case first, as a plain-model widget (models and callbacks, no controller or repository), and get every state, both themes and phone and desktop width right there. Only then wire it into a screen, and check the screen with a workflow test or `verify-in-app`. A widget a screen builds inline gets pulled out into `lib/src/*/widgets/` so it can have a use case. `test/widgetbook_test.dart` builds every use case in both themes, and `widgetbook.yml` publishes the catalog to GitHub Pages from `main` (`scripts/build-widgetbook.sh` builds it).

## Specs

`openspec/` holds spec-driven change proposals (`openspec/specs/` for current behavior, `openspec/changes/` for work in progress). Start a change with `/opsx:propose "<idea>"`; project context for it lives in `openspec/config.yaml`. Design history lives under `openspec/changes/archive/`.

## Skills

Project skills live in `.claude/skills/<name>/SKILL.md` (frontmatter `name` and a `description` that says when to use it). When you learn something reusable about working in this repo, such as a workflow, a gotcha or a verification step, write it to a skill rather than to memory, so it is checked in and shared.

- Amend the existing skill when the new knowledge fits it. Fix a skill that turns out to be wrong or stale as soon as you notice.
- Create a new skill when the knowledge is a distinct, repeatable task no current skill covers. Keep the description specific enough that it triggers at the right time.
- Use memory only for things that are personal to the user or don't belong in the repo.
- Commit skill changes with the work that prompted them, or on their own as `docs:`.

## Dependencies

Before writing platform or infrastructure code by hand (storage, permissions, sharing, notifications, deep links, auth flows, and the like), check pub.dev for a mature, maintained plugin and prefer it over a homegrown implementation. Judge maturity by recent releases, publisher, platform coverage, popularity and open issues. If none fits, say why in the PR. The existing choices (`flutter_chat_ui`, `receive_sharing_intent`, the generated `hermes_api` client) follow this rule.
