# Other Hermes KPIs

- **Adoption:** App Store Connect first-time downloads, redownloads, installs, and retention, each named as Apple's metric and time period. Downloads and installs are not active people.
- **Reliability:** In SignalDB Errors or `query_ir` over logs, count error records by `exception.type`, service version, and environment. Compare error counts with session counts only if the same population and window are actually covered. Check current crash-reporting implementation before describing what error messages or stacks contain; `docs/architecture/telemetry.md` (moved from `CLAUDE.md`) and `PRIVACY.md` disagree.
- **Network performance:** Use Catalog/Traces or `query_ir` for request count, failed request share, and p95 duration, grouped by `http.route`, method, version, and environment. The app records only the first two route segments. A request or gateway event count measures operations, not users.
- **Sign-in:** Count `auth.sign_in.started`, `.succeeded`, `.failed`, and `.cancelled` in logs for the same window; success rate is succeeded / started when the events are complete. Session refresh and expiry, gateway RPC/event failures, and error codes are further diagnostic signals.

- **Hermes servers:** Requests and `auth.*` events carry the connected server's `hermes.*` attributes (`hermes.version`, `hermes.install_id`, `hermes.auth.required`, `hermes.gateway.mode`, `hermes.profile.count`, `hermes.overall`, and more; see `openspec/specs/telemetry/spec.md`), and `server.connected` is logged once per connection. Count distinct servers by distinct `hermes.install_id` on `server.connected` (a server that cannot persist one sends none). Break failed requests or `auth.sign_in.failed` down by `hermes.version` to tell an app bug from a server release. Gateway and Kanban socket spans (`messaging.system` `hermes.gateway`/`hermes.kanban`) and `gateway.*`, `kanban.*`, `plugins.*` and `skills.job` events carry them too, so reconnect storms or stalls can be broken down by `hermes.version`. These are log and span attributes, not resource attributes.

Telemetry is off in builds without `OTEL_EXPORTER_OTLP_ENDPOINT`; release configuration is in `fastlane/Fastfile` and `lib/src/telemetry/telemetry_config.dart`. Absence of data may mean no instrumented build or no matching events. Use `openspec/specs/telemetry/spec.md` to check emitted events and attributes before asserting a KPI is available.

## Reply loss (R) and reconnect success (C)

Events from the reply-loss diagnosis (added together; builds before them send none, so split by `service.version` and start the window at the first version that has them). Every attribute is a fixed name, bucket, flag or count. Before filtering, check each field name with `resolve_attribute` for tenant `homelab`, and how the event name is stored (it is the log record's event name; the queries below write it as `event.name`, replace it with what `resolve_attribute` says). Tenant `homelab`, dataset `apps`, service `hermes-app`; app versions split by the resource attribute `service.version`. Run with `query_ir(tenant="homelab", dataset="apps", query=...)`; the queries are templates, no result is recorded here.

**R, reply failure rate** = replies that failed / replies that ended for good, per window and per `service.version`.
- Numerator: `chat.reply.ended` with `outcome = failed`.
- Denominator: `chat.reply.ended` with `outcome` in (`completed`, `failed`). `stopped`, `folded` and `withdrawn` are the user's choice and left out. `lost_connection` is not an end: the same reply logs a later `chat.reply.ended` (completed or failed) when the pick-up settles it, so a reply is counted once, by its last event. A reply still held when the app is killed, overtaken by a new send in the same chat, or archived or removed while held is never counted (`ReplyDiagnostics.begin` and `forget` drop the held reply), so R is a lower bound. A reply settled as failed (session gone, server restarted, unconfirmed) is counted once, as failed, whichever path settled it; if its turn then goes on and fills the same bubble, that is no second `chat.reply.ended` and never a `completed` for it, so R keeps the failure and its denominator is not inflated. How often that happens is `chat.reply.late_event` (`kind` completed or delta) after a failed end, which measures how many counted failures were false alarms; check it against the legacy proxy, `gateway.send_failed` with `step = reply` over prompt-submit spans, which is an upper bound.
- Window: name it (7 or 30 days), count over complete days, and say how many installations (`app.installation.id`) the window covers.

```json
{"irVersion":9,"from":"logs","range":{"from":"now-7d","to":"now"},"result":"table","pipeline":[{"where":{"field":"service.name","op":"eq","value":"hermes-app"}},{"where":{"field":"event.name","op":"eq","value":"chat.reply.ended"}},{"where":{"field":"outcome","op":"in","value":["completed","failed"]}},{"aggregate":{"by":["service.version","outcome"],"aggs":[{"fn":"count","as":"replies"}]}}]}
```

R per version is `failed / (completed + failed)` from that table. Cause split: the same query with `"by":["service.version","cause","step"]` and `outcome = failed`. `cause` is one of `reconnect_gave_up`, `session_gone`, `server_restarted` (the server restarted and its turn died with it), `turn_ended`, `unconfirmed` (the server could not be made to say how the turn ended), `connection_closed`, `timeout`, `rejected`, `profile`, `not_sent`, `server_error`, `other`; `away` (`under_5s` .. `over_600s`) says whether the app was in the background, `reconnect_attempts` how hard the app tried: it counts holds plus pick-ups of that reply, so a pick-up that failed and was held again counts twice.

**C, reconnect success rate** = reconnect episodes of a running reply that re-attached to the same reply / episodes. One `gateway.reconnect` event is logged per episode (a drop of a reply on screen), after its last attempt.
- Numerator: `gateway.reconnect` with `outcome` in (`replayed`, `ended`, `rest_refetch`, `reclaimed`): the server still had the reply and its text or end was recovered. Count `rest_refetch` separately to see how many needed a re-read.
- Denominator: all `gateway.reconnect` events, whose other values are `failed` (gave up: no network or no answer within the 60 s window or 5 answered attempts) and `gone` (the server lost the turn).
- Why it failed, per attempt: `gateway.reconnect_attempt` grouped by `result` (`no_network`, `refused`, `timeout` = resume or connect hung, `closed`, `busy` = 4009, `rejected`, `resume_gone`, `credential` = the server refused the credential (HTTP 401 or 403) when a socket ticket was fetched, `http_error` = any other HTTP answer to that fetch, `bad_certificate`, `cancelled`, `window_expired`, `other`), `stage`, `close_code` and `duration`. An attempt with `final = true` is one that ended the episode by reaching the server (`connected` or `resume_gone`). An episode that gave up has no `final = true` attempt: its attempts all have `final = false` and the `gateway.reconnect` event with `outcome = failed` closes it. Read the causes of a give-up from the attempts that did not connect (group `result`, `stage`, `error_type` where `final = false`; the last attempt of the episode, by `attempt`, is the one that ran out of budget). The `drops` attribute counts the earlier reconnects of the same reply.
- A lost reply picked up later (when the chat is opened or the app returns) is `gateway.reattach` by `outcome`: `same_reply`, `finished_while_away`, `finished_no_reply`, `gone`, `unreachable`; `refetch = true` when the pick-up asked for the thread to be read again (replay or snapshot could not restore the reply), `false` when the replay restored it. A held reply that ends by an idle report after the user pressed Stop is `outcome = stopped` and stays out of R's denominator.
- How the socket ended: `gateway.socket_closed` by `reason` (`heartbeat_silence`, `remote_close`, `error`, `local_drop`, `app_closed`) and `close_code`, with `reply_running = true` for the ones that hurt. `app.lifecycle` (only while a reply runs, or on the return of one that did) joins by time to show a drop right after `paused`; its `away` bucket is the time in the background.
- `chat.reply.late_event` (`kind`: delta, tool, completed, request) says frames still arrived for a reply already declared failed (once per kind and reply); `kind = completed` is the strong signal that the server finished what the app failed. `chat.queue.state` (`held`, `paused`, `drained`, `abandoned`, with a `count` bucket) says what happened to the prompts behind it.

```json
{"irVersion":9,"from":"logs","range":{"from":"now-7d","to":"now"},"result":"table","pipeline":[{"where":{"field":"service.name","op":"eq","value":"hermes-app"}},{"where":{"field":"event.name","op":"eq","value":"gateway.reconnect"}},{"aggregate":{"by":["service.version","outcome"],"aggs":[{"fn":"count","as":"episodes"}]}}]}
```
