# Roadmap

Started 14 November 2026 from a full review of the app: structure, practice, bugs, alignment with Hermes and what is missing. This file is the checklist for that work. It is kept current as items merge.

## Rules

- Every item ships as its own pull request (a small finding may ride in the PR that found it, marked `(with #N)`), reviewed by an isolated reviewer agent with fresh context, and merged through auto-merge armed by the orchestrator after a recorded isolated review (see Decisions), or by hand after reading `Analyze & test` as success on the exact head for a docs-only PR (F.262). A CodeRabbit comment counts as a review only when it actually reviewed the diff.
- A bug fix starts with a failing test.
- A UI change starts with a Claude Design pass (the "Hermes App" design system), then a Widgetbook use case, and only then the screen. The React copies in `design/web` are updated with it.
- A new feature starts with an OpenSpec change (`openspec/changes/<name>/`).
- Pull requests that are ready together are stacked (each one based on the branch below it, linked as a GitHub stack) and merged bottom-up: after the lower PR merges, the upper one is retargeted, main is merged in, the new head is reviewed (merge-only is enough), its checks are read, then it is reported READY.
- Every commit goes through the pre-commit hook (`dart run tool/setup_git_hooks.dart`). A failing hook is fixed, never bypassed.
- Leads run the `verify` skill before a PR that changes connection, sign-in, API, gateway or chat behaviour.
- A pre-release is cut (the release-please PR is merged) after each completed wave. Promoting a pre-release to App Review is the owner's step.
- We own only the client. Anything that needs a Hermes change is listed under "Upstream" and is not built here.
- Anything found along the way (by a reviewer, a lead, CI or a proposal) that is not fixed in the PR that found it is added to "Found along the way" in the same or the next roadmap update, with where it came from. Nothing is left only in a PR description.

## Status values

`merged` (with PR), `open` (PR up, in review or CI), `building`, `queued`, `blocked` (with the reason), `dropped` (with the reason). `investigating` and `measuring` mark work that has no PR yet. In wave 4, `proposal building` means the OpenSpec proposal is being written and has no PR yet, and `proposal open #N` means the proposal PR is up and no implementation has started. `(with #N)` after a status means the work ships inside PR #N and takes that PR's state.
