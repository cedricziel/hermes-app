# Gateway transport (chat streaming)

History is loaded over REST by `HermesChatRepository`. Sending and streaming go through the `ChatTransport` interface (`chat_transport.dart`), a sealed `ChatEvent` stream. The real implementation, `gateway/hermes_gateway_transport.dart`, speaks JSON-RPC over the dashboard's `/api/ws` websocket (`session.create` or `session.resume`, then `prompt.submit`, with replies as `message.delta` events). The class keeps its state and public methods in that file; private extensions in its `hermes_gateway_transport_*.dart` parts hold the rest (`owned_sessions`, `commands`, `sending`, `turns`, `reconnect`, `follow_ups`, `requests`, `branching`, `checkpoints`, `connection`), and `helpers` holds its private helper classes. Both session calls send `source: hermes_app` (`gatewaySessionSource`); without it Hermes records the session as `tui` and gives the agent the terminal UI's prompt hint. `gateway_rpc_client.dart` and `gateway_connection.dart` handle the socket. Gateway frames become `ChatEvent`s in `gateway/gateway_event_mapper.dart`. `openrpc/hermes-gateway.openrpc.json` is Hermes' own list of every frame and server request (see `openrpc/README.md`), and `test/gateway/gateway_contract_test.dart` records what the app does with each one. `review.summary` (what Hermes' background review saved after a turn: memories, user profile, skills) becomes `ReviewSummarized`, which the controller attaches to the latest finished reply (`ChatMessage.reviewNotes`, shown by `widgets/review_summary_note.dart`). A reply ends on whichever comes first: `message.complete`, or `session.info {running: false}` (`ReplyCompleted` or `SessionInfo`; Hermes clears its running flag after the completion, so that report is the settled signal). `settles` in `gateway/gateway_replay.dart` ignores an idle report within 15 s of the submit until the turn has begun, since it can describe the turn before. An `error` event is held and shown as the failure when the session settles with no completion; a failed completion's own message wins. A reply that settled without a completion keeps its text, and a late `message.complete` on `followUps` lands on the same reply. A reply silent for 45 s is checked with `session.active_list` and ended as broken only when its thread is no longer listed as running, in `send` and in the follow-up relay while it is replying. `prompt.submit` answers `streaming`, `queued` (the reply waits for its turn's `message.start`), or `redirected`/`steered` (the server folded the text into the running turn: `PromptFolded` drops the placeholder, the running turn's reply goes on in its own send). The controller drains the queue on `SessionInfo(running: false)` from `followUps`, or 2 s after the completion, and sends with `queued: true` so the server queues the prompt instead of folding it. After a reply ends the transport keeps listening to its session, and `ChatTransport.followUps` carries the turns nobody here submitted: goal continuations, queued prompts, a delta or tool event whose `message.start` was missed (it opens a reply). The turn Hermes runs on its own after a resume that reports `auto_continue` is not among them: `send` claims it (`_Unsolicited`) so the submitted prompt keeps its own reply. Each frame of that turn, its requests and their withdrawal included, goes out on the send's own stream as it arrives, wrapped in `UnsolicitedEvent`, and `ChatController._onOwnTurnEvent` streams it into a reply opened in front of the prompt's user message (`_insertReply(before:)`; the server runs that turn first and stores it there, so a refetch, Copy Transcript and Retry/Edit of the prompt agree with the live order). The turn shows live and is never replayed on `followUps`. An idle report ends it only once a turn-opening frame came (an approval alone does not open one), a late completion lands on it, and its end settles neither the queue nor a stop in flight. Its requests can be answered while it runs and are withdrawn when it ends, the prompt's reply says Hermes is finishing the interrupted turn until then, and a send that gives up fails both replies and refetches. Session and prompt calls time out, `checkConnection` (called when the app resumes) drops a socket the OS killed during sleep, and the RPC client pings every 15 s and closes itself after 45 s without any frame. A send that cannot open its socket or session (connect, `session.create`/`resume` unanswered) tries again on a new connection, 3 attempts in all with the reconnect backoff; an error the gateway answered is final, and `prompt.submit` is never resent. A reply still running when its connection drops is not failed outright: the transport reconnects with full-jitter backoff (300 ms to 15 s, 5 attempts or 60 s), resumes the session, and replays what it missed. Every event frame carries a `seq` per runtime session; `ReplayLedger` (`gateway/gateway_replay.dart`) keeps the highest one seen and the `replay_epoch` from `gateway.ready`, and `session.events.since` fills the gap, with the frames that arrived meanwhile merged in and none shown twice. When the replay is truncated or the server restarted (epoch changed), a running turn is rebuilt from the resume answer's `inflight.assistant` (`ReplyRebuilt`, with the deltas sent after the snapshot still delivered) and an ended one by a REST re-read (`ThreadNeedsRefetch`, then the stored reply); `open_requests` are shown once by id. `approval.cancelled` withdraws the open approvals of its session (`InputRequestsCancelled`).

`hermes_gateway_transport_checkpoints.dart` holds `rollback.list`, `rollback.diff`, `rollback.restore`, `session.context_breakdown` and `session.compress`, behind `CheckpointsTransport` and `ContextTransport` (`chat/checkpoints/checkpoints_transport.dart`). Reads take the `OwnedSessionBinding` of a runtime the chat already owns and never resume; a restore and a compress (and the list of a stored chat opened on purpose) go through `_commandRuntime`. Answers are parsed leniently in `chat/checkpoints/checkpoint_models.dart` and `chat/context/context_models.dart` into sealed results; server text (reasons, commands, paths, error messages, labels) never leaves those parsers. A restore or compress is sent once; no answer within `longTimeout` (90 s) or a closed socket after the request went out is `MayHaveHappened`, and the caller re-reads. Reads give up after `readTimeout` (10 s) without dropping the socket. A compress focus is refused unless `isAcceptableFocus` (the server reads `--flags`, a first word `here` and `up to here` as commands).

`status.update` frames of kind `compacting` and `compressing` become a `ReplyStatus` carrying a `ReplyStatusKind` (`compacting`, `compressing`) and no text; the thinking row words it from the ARB files (`chatStatusCompacting`, `chatStatusCompressing`), so it follows the reader's language; `compacted` becomes `ContextCompacted` (only the runtime id), which the chat controller takes as "re-read the usage, and the context breakdown while it is open" and nothing else; every other kind is a `SessionWaitUpdated` as before (`compressing` used to be one too, and nothing cleared it). `ContextCompacted` is a session report like `SessionUsageUpdated`: `_QueuedGate` and `_Unsolicited` pass it through without counting it as the turn's, and no consumer takes it for progress, an answer, a reply opening or a request (`test/gateway/context_compacted_consumers_test.dart`). `session.info` carries the session's `usage` after each turn and after a compress; `SessionInfo.usage` feeds the same `SessionUsageController` as `session.usage` and `message.complete.usage` (a snapshot, so taking it again counts nothing twice). The recorded answers of the checkpoint and context methods are in `test/fixtures/gateway/` (`rollback_*.json`, `session_compress.json`, `session_context_breakdown.json`; invented content).
