# Bot Screen

**Bot Screen** (`lib/src/bot_screen/`, the profile's own Linux desktop that `computer_use` drives; the card, the transcript preview, the live viewer, its control lease and, from `bot-screen-takeover`, taking over and input are the UI). `BotScreenRepository` reads `display.status`, `display.start` and `display.thumbnail` over the shared gateway and returns a sealed `BotScreenResult` (`BotScreenOk`, `BotScreenUnsupported` for method-not-found, `BotScreenFailed` with a kind), never an exception. Every call sends an explicit `profile`, `default` for a null one, because Hermes otherwise answers for its launch home. Display calls go through `GatewayRequester.requestKeepingConnection` (on `HermesGatewayTransport` and `SessionChatTransport`) with a 10 s timeout counted from the send, which excludes connect time: unlike `request`, a timeout abandons that request (`GatewayRpcClient.requestWithin`) and throws `GatewayRequestTimeout`, leaving the socket and any running reply alone. So a socket that died unnoticed is found only by the heartbeat or by `isStale` (45 s) plus `checkConnection`'s probe, about 50 s. `GatewayRpcException.data` and `dataCode` carry the error's `data` (`viewer_mismatch`). `BotScreenController` is one per profile and connection: `watch()` handles count demand, and while demand is held, the status says running, and `foreground` and `unlocked` hold, it requests a frame every 3 s with one call in flight. It follows `display.status` and `display.lease` broadcasts from `connectionEvents` that carry its `profile_key`, and re-reads the status on gaining demand, when the connection is lost while shown, when `foreground` turns true, and with every 10th frame request (lease changes by other server processes are not broadcast). An answer that arrives after `unlocked = false` or dispose is discarded; frames live in memory only. A failed status read is retried while a surface asks (1 s doubling to 32 s) and failing frame reads back off; answers asked for before a status or lease broadcast are dropped; a missing or unreadable lease counts as a person in control. A server that answers method-not-found has no Bot Screen (Hermes before v2026.9.24). Span `bot_screen.thumbnail` and the events `bot_screen.unsupported` (once per repository) and `bot_screen.read_failed` (once per failure streak) hold outcomes, a size bucket and a method only, never a frame, install command, blocker text, profile or `profile_key`. The `verify-bot-screen` skill runs a Linux container with a real screen.

**Bot screen card** (`widgets/bot_screen_card.dart`, a plain-model widget over `BotScreenCardModel`, catalog use cases in `widgetbook/bot_screen_use_cases.dart`, mirrored in `design/web`): `BotScreenCardModel.fromState` picks exactly one state in this order: not offered (`supported: false`), not installed (the install command only for `placement: gateway`, else the sandbox sentence), blocked, starting, off (with why the last start failed), error, then the running screen (a frame, or no picture while a person holds control or the frame is suppressed). It is null before the first answer and on an old server. `BoundActivityPanel` lists it first under Now (`ActivityKind.screen`, Working) when it has a `screen` controller and the screen runs, or the open chat holds a `computer_use` tool call; the strip above the transcript never reads the controller. `BotScreenDemand` wraps the panel and holds a `watch()` while it is mounted and `Visibility.of` is true, which is also what makes the status get read at all. `ChatScreen` owns one controller per `_chat.profile` (`chat_screen_bot_screen.dart`, replaced on a profile switch, the old one disposed after the frame) and sets `foreground` (resumed, the page visible, and on a Mac a window on screen through `MacApp.windowlessChanges`; not the route, since the phone's Activity sheet is a route above the chat) and `unlocked` (`AppLockController.covered`). Releasing the last watch, leaving the foreground and App Lock all drop the frame and bump the generation, so a thumbnail answer already on its way is discarded; the listeners are told a microtask later, since the gates can flip during a build. `BotScreenDemand` also counts a panel under a pushed page (`TickerMode` off) as hidden. Try Again is `BotScreenController.retry()`. Conversation windows and the quick panel pass no controller, so they show no card and request no frames. Enlarge shows only when `onEnlarge` is given, and the card's picture does the same; `ChatScreen` gives it `_openViewer('card')` through `BoundActivityPanel.onEnlargeScreen`. Breadcrumbs `bot_screen.card.shown` (`state` slug, on a state change only) and `bot_screen.start.pressed`, event `bot_screen.start` (`outcome`: started, blocked, error).

**Transcript preview** (`widgets/bot_screen_preview.dart`, a plain-model widget over `BotScreenPreviewModel`, which projects the card's state: the running frame, a person in control, else hidden; catalog use cases in `widgetbook/bot_screen_use_cases.dart`, mirrored in `design/web`): while a reply is pending, `chatMessageToFlyer` marks the run of tool calls that holds the reply's latest `computer_use` call (`kMetaScreenPreview`, a `ScreenPreviewRun`), whatever that call's status, and no other run; it stops when the reply ends (completed, failed or stopped). `buildChatBuilders` hands the run's `ToolCallGroup` a `preview` from the `ScreenPreviewBuilder` that `boundChatThreadView` makes when it is given a `screen` controller (only `ChatScreen`, so conversation windows and the quick panel show none). The group draws it outside any card and in one place: below the card of a run of one call, below the header of a longer run, so it neither jumps nor loses its frame when a run grows. `BoundBotScreenPreview` is keyed per reply (`keyFor`) so its state, frame and watch move with it, and of several pending replies only the newest draws it. It holds a `watch()` only while `OnScreen` (`widgets/on_screen.dart`, an in-repo check run after each frame: the preview's `RenderBox` against `RenderAbstractViewport.maybeOf`, a zero-size box counting by its top edge) reports it inside the viewport and its page is not covered (`TickerMode`), so a preview the list built in its cache extent asks for nothing; with nothing to show it draws nothing yet still takes part, since the watch is what reads the status. We do not use `visibility_detector`: its upstream is archived and it has open sliver and swipe-back issues. Frames decode at the drawn width, never upscaled, and leave the image cache when replaced or dropped. A tap calls `ChatScreen._openViewer('preview')`, which opens the live viewer over the chat (the Activity panel is left as it is). Breadcrumbs `bot_screen.preview.shown` (once per reply) and `bot_screen.preview.tapped`, no attributes; the `bot_screen.thumbnail` span carries `watchers`, the surfaces sharing the poll.

**Install on Server** (`install/`, `widgets/sudo_password_prompt.dart`). The card's install body, log lines and spinner row are the shared `lib/src/widgets/install_parts.dart` (also used by the Tools install section); with reduced motion the spinner is a still hourglass. `BotScreenInstalls` (one per `AppShell` gateway, provided below it; `ChatScreen` reads it and hands it to its `BotScreenController`, so where there is no shell there is no button) holds each profile's install by profile name, so it outlives the chat, the panel and a profile switch. `BotScreenRepository.install` sends `display.install` through `HermesGatewayTransport.requestKeepingConnectionOnClient`, which also returns the connection that carried it; a server refusal is a `BotScreenFailed` carrying Hermes' `message` and is not logged as a read failure. The install follows `display.install.log` (last 6 lines) and `display.install.done` (0 installed, -1 cancelled, -2 no sudo, else failed) by `profile_key`, which the status gives before Hermes answers so early broadcasts are not lost; the controller takes over the status that comes with an install that ends after it was made (one already ended at construction is not applied). The server asks for the password with the sessionless server request `display.install.sudo`, which reaches only the connection that sent `display.install`. `HermesGatewayTransport.registerServerRequestHandler` (only for methods in `registrableServerRequests`) lets `BotScreenInstalls` answer it while an install runs; the handler is handed the arriving connection and refuses (`-32602`) a request whose `profile_key` is not a running install, that arrived on another connection than the one `display.install` went over, or that comes while a prompt for that install is open. A request that overtakes Hermes' answer waits for it. `request.cancel` for the request (a server timeout or interrupt) closes its prompt and frees the install for the next ask; a throw other than a gateway error answers `-32603` without its message and logs `bot_screen.install.prompt_failed`. With no handler the transport refuses it at once (`-32601`) whatever its session, instead of the server waiting out its 300 s. The question is `showSudoPasswordPrompt` over the shell's navigator, wherever the user is, and only while the session is authorised (else it declines); on macOS the shell first brings the main window forward (`ConversationWindows.showMainWindow`, the runner's `show`), and `AppLockGate` wraps the covered app in `ExcludeFocus`, so keys typed on the lock screen cannot reach it. `SudoPasswordPrompt` is the platform's alert naming the host and the profile, with an obscured field (autocorrect, suggestions, keyboard learning and autofill off; the keyboard type stays the default so Android keeps its password variation); Install answers once and clears the field, while Cancel, dismissal and an install that ended first (which closes the prompt) answer ''. The password is never stored, logged, put in telemetry or kept; log lines, the install command and the host are shown, never logged. A missed done is made up by reading `display.status` when the app resumes (`AppShell`), after the connection was lost and after 22 minutes (outcome `unknown`). On no sudo (-2) the card shows the install command without its `sudo` prefix and offers no Install on Server. Span and event `bot_screen.install` hold `outcome` and `asked_password` only; breadcrumbs `bot_screen.install.pressed` and `bot_screen.install.password` (`outcome`: answered or cancelled).

**Display stream and input** (`lib/src/bot_screen/rfb/` and `lib/src/bot_screen/input/`; only the live viewer uses them). The bot's own desktop is Xvnc, which Hermes bridges onto `/api/display/ws`. `openDisplaySocket` (`display_socket.dart`) opens it on the dashboard's origin and path prefix with only `display_ticket` in the query (never the gateway token or ticket) and returns the `WebSocketChannel` uncast, so the close code is readable and the app can close with a status code; it builds on `connectWebSocketChannel` in `gateway_connection.dart`, which uses `IOWebSocketChannel` because the default adapter drops the HTTP status of a refused upgrade. Failures become `DisplaySocketError` (`notAllowed` for HTTP 403, `untrustedCertificate`, `unreachable`), whose text holds neither the URL nor the ticket: never rethrow or log the raw exception. `RfbClient` (`rfb_client.dart`) is an RFB 3.8 client: security type None, shared, a fixed 32-bit true-colour pixel format (wire pixels R, G, B, padding; the framebuffer is RGBA with alpha 255), SetEncodings ZRLE, CopyRect, Raw, DesktopSize, and an incremental update request after each update (a non-incremental one after a resize). It writes the handshake, SetPixelFormat, SetEncodings and FramebufferUpdateRequest by itself, and input only when called: `pointer`, `key`, `scroll` and `cutText` (the `RfbInputSink` interface in `rfb_input_sink.dart`, which the viewer's `ScreenInput` calls while this device is in control). They throw `StateError` before ServerInit and after the end (checked before the arguments, so a bad value there is a `StateError` too), clamp coordinates to the framebuffer, send a wheel notch as a press and release of button 4 to 7 with the held buttons kept (at most 50 notches per axis and call), and never log or keep what they send; an `ArgumentError` for a bad value never carries the value. It never sends SetDesktopSize or QEMU key events, and nothing `rfb_filter.py` cannot frame. `cutText` is classic ClientCutText in Latin-1, at most 256 KiB: a character outside Latin-1 throws `RfbClipboardError.notLatin1` and nothing is replaced, longer text throws `tooLarge`, and `\r\n` and `\r` go out as `\n`. The TigerVNC extended clipboard is not used (Xvnc takes clipboard data only when it asked for it, a lazy exchange for a later change), so non-Latin-1 text cannot be pasted yet, though typing it works through Unicode keysyms. `lib/src/bot_screen/input/` has `KeysymMapper` (non-printing keys from a table, Latin-1 characters as themselves, control characters that are keys as those keys, other code points as `0x01000000 + codepoint`; a control character without a key of its own, NUL and the other C0 and C1 controls, throws, and Ctrl+letter comes from the logical key with Control pressed; `commandAsControl` maps Meta to Control), `ScreenGeometry` (a position on the zoomed picture to a clamped framebuffer pixel, trackpad movement divided by the zoom, `ScrollAccumulator` for 40-pixel notches) and `ScreenGestureLayer`, which turns touch (absolute) or trackpad-style (relative, with a `virtualPointer` for a cursor) fingers, mouse and the wheel into pointer calls from raw pointer events; it repeats no identical pointer message and releases a held button when disabled, disposed or given another sink or mode. Arena rule: while enabled, a hidden `_ClaimRecognizer` wins every single-pointer gesture against the viewer under the layer (a mouse button at once, a finger once it moves past the touch slop, a trackpad pan/zoom gesture once it pans with its scale within 0.05 of 1), so a one-finger or mouse drag, and a trackpad two-finger scroll, go to the screen and do not pan the viewer; two-pointer gestures stay with the viewer (a second finger landing before the first passed the slop, and a trackpad pinch, make the recognizer reject), and the layer sends nothing for them. A wheel click of a mouse scrolls at least one notch, smooth wheel deltas gather at 120 px per notch, a trackpad's at 40. In trackpad mode a tap followed within `kDoubleTapTimeout` by a press that moves holds the primary button at the virtual pointer for the drag (tap and drag; a second tap that does not move is a second click). It is disabled by default (no listener, no recognizer). An `InteractiveViewer` zooms on the mouse wheel by itself, so whoever places the layer decides its `scaleEnabled`. Everything arrives as `RfbEvent`s, and malformed or truncated data, a socket error or a server limit exceeded ends the stream as `RfbEnded` with a typed `RfbFailure` and `RfbStep`, never as a throw; a server close with nothing half-received ends with no failure, so check whether `RfbConnected` arrived. `close(code)` accepts 1000 or 3000-4999 and throws `ArgumentError` otherwise. ZRLE (`zrle.dart`) keeps one zlib-format stream per connection and is fed exactly each rectangle's length-prefixed data. ServerCutText (the agent's clipboard) is skipped unread. `bytesReceived` and `encodingsSeen` are for the live view's span. Tests: `test/support/fake_rfb_server.dart` (`FakeDisplayChannel`, `RfbSession`, server message builders, `DeflateSyncStream`, which compresses and ends each rectangle with a Z_SYNC_FLUSH through `RawZLibFilter` as Xvnc does, and `ZlibSyncStream`, which writes stored blocks). `ZLibEncoder` itself cannot flush without finishing the stream.

**Live viewer** (`lib/src/bot_screen/viewer/`, `widgets/bot_screen_viewer_view.dart`, catalog `Bot screen viewer`, mirrored in `design/web` as `BotScreenViewer`): watching only sends no input and a tap on the picture only zooms and pans; while this device is in control it sends input (see Input). `BotScreenRepository.observe` (`display.observe`, `BotScreenObservation`: ticket, path, viewer id and status, whose `toString` shows none of them) and `BotScreenViewerController` (observe, `openSocket` -> `RfbClient`, `phase`, `framebuffer`, `revision`) hold the ticket and viewer id in memory only; neither goes into a log, span, breadcrumb or exception text. The controller holds a status-only `BotScreenController.watch(frames: false)` for the lease (the status is read every 3 s while the screen runs, which notices a takeover no broadcast reported, with no thumbnail requested), seeds the lease from the `display.observe` answer (`adoptStatus`: not over a newer lease, not across profiles), and hides the picture (`framebuffer` null, phase `blanked`) while someone else holds control and until the lease is known. Endings: 1000 sent by the app needs nothing; 4000 observes again at once and counts as an attempt; 4001 is Off, no retry; a plain server close 1000 or 1001 (how a stopped screen usually arrives, the bridge's read of Xvnc hits EOF) reads `display.status` first, Off when not running (span outcome `gone`, no failure logged), else like any other ending; 4401 observes again once (reset on a first picture) and then fails; 1003 is a protocol error, no retry; HTTP 403 (`DisplaySocketError.notAllowed`) is "Viewing isn't allowed", no retry; anything else, decode failures included, reconnects after `reconnectDelay` (full jitter, 300 ms to 15 s) at most 5 times, then `unreachable` with Try Again (`retry()`). The stream goes live and the attempts reset on the first `RfbUpdated`, not on `RfbConnected` (the framebuffer is black until then). A failed observe reads `display.status` to tell Off (not running) from an error, and anything unmapped that `_connect` or `startScreen` meets is logged as `step: observe`, `error_type: unexpected` (no message) and retried. The display socket pings every 15 s and gives up connecting after 10 s (`kDisplayPingInterval`, `kDisplayConnectTimeout`; only that socket), so a half-open link ends. `foreground`, `unlocked` and `visible` (`BotScreenViewer` sets it from `TickerMode`, so a route above that covers it pauses the stream) close the stream with 1000, drop the picture and observe again on return (while this device is in control they close it with 4100, see Control lease); `ChatScreen` sets the viewer's gates apart from the card's (`_syncBotScreenGates`: `foreground` is false only once the app is paused, hidden or detached, and `unlocked` is false while App Lock covers the app or a phone is `inactive`, so a watching viewer closes at once as before), and closes the viewer on a profile switch, when the chat is no longer the shell's visible destination, and in `dispose`. `showBotScreenViewer` (`bot_screen_viewer_presenter.dart`) pushes a route on the root navigator, not an `Overlay` entry, so dialogs opened over it draw above it, the chat's menu commands and Back do not reach the chat, and Escape (`DismissIntent`) closes it: a `MaterialPageRoute` when the window's shortest side is under 600 pt (`kViewerPhoneShortestSide`, landscape phones included), else an opaque black `PageRouteBuilder`. The view is in a `SafeArea`, and on a Mac the header leaves room for the traffic lights and is a `MacWindowDragArea`. Its handle's `close` is safe while the owner unmounts (the route is removed after the frame). `FramebufferPicture` turns the RGBA framebuffer into one `ui.Image` per frame with `decodeImageFromPixels` (the engine copies the pixels at once; the previous image is disposed when the next is ready). ZRLE decoding stays on the UI isolate: a full 1280x800 update decoded in 2.5 to 8.5 ms AOT (13 to 20 ms in JIT) on an Apple-silicon Mac, under one 60 Hz frame, and later updates are small; that is an Apple-silicon number only, and a mid-range Android phone still needs a profile-build measurement. Span `bot_screen.stream` (`outcome`, `close_code`, `encodings_used`, `kib_received`), event `bot_screen.stream_failed` (`step`, `error_type`) and breadcrumbs `bot_screen.viewer.opened` (`surface`, `source`) and `.closed`. The card's Enlarge and picture open it with `source: card`, the transcript preview's tap with `source: preview`. The Computer use details of the Tools screen open it with `source: tools`, only when the chat holds a Bot Screen controller whose status was read and is not unsupported (`ChatScreen` holds a status-only `watch` while the Tools screen is open).

**Control lease** (`BotScreenViewerController`, `BotScreenViewerIds`, `widgets/force_hand_back.dart`): `display.lease.acquire`, `display.lease.release` and the forced release go through `BotScreenRepository.acquire`, `release` and `forceRelease`. Acquire and release are pinned: `HermesGatewayTransport.requestOn(connection, ...)` (also on `GatewayRequester` and `SessionChatTransport`) sends on that connection only and throws `GatewayConnectionClosed` without opening another when it is gone, because Hermes honours a viewer id on the connection that minted it alone. `observe` goes through `requestKeepingConnectionOnClient` (`connectionRpc`) so `BotScreenObservation.connection` is read in the same microtask as the answer; a repository without `pinnedRpc` fails lease calls as closed instead of sending them unpinned. `viewer_mismatch` (`data.code`) is `BotScreenFailure.mismatch`. `BotScreenViewerIds` (held by `ChatScreen` for the app run, given to every `BotScreenController` and viewer) keeps each minted id's lease hash (first 12 hex characters of its SHA-256) and the latest id (the next observe asks for it, which the server honours on the same connection); a lease names this device exactly when it is `holder: human` and its `viewer_hash` is one of them (`BotScreenController.inControlHere`, `someoneElseInControl`), so a lease from before an app restart matches nothing and shows as someone else's. The ids, like the ticket, are never stored or logged and a printed object shows none. `BotScreenController.adoptLease` takes the lease of an acquire or release answer at once (not over a newer epoch; the same epoch is taken, since acquiring a lease you hold bumps nothing). `BotScreenViewerController.control` is `watching`, `acquiring`, `inControl` or `lost`: `takeOver()` acquires on the observing connection and, on a closed connection or `viewer_mismatch`, observes again and retries once, reopening the stream with the new ticket because the server accepts input only on the stream of the id that holds the lease; `handBack()` releases the same way and when the connection changed under the lease (the id cannot be released over the new one) it closes the stream with 1000 instead, which the bridge takes as the holder's release, reads the status, and opens a new stream as a watcher (while shutting down the close counts as the hand back without waiting for an answer, since the gateway may be going away too); a forced release is never sent without the user's confirmation, and a repeat release or acquire is retried on a closed connection, an unknown id or no answer; after an observe that starts a new stream a lease that names an earlier id of this app is taken over with the new id without asking (a reconnect mid-login; logged `resumed`, not `retried`), but never while a stream of the viewer is open, since the bridge answers a new holder by closing the old holder's stream with 4000, and never once the viewer is shutting down (a take over still in flight then is released). The one exception is a shut down while in control with the stream paused (4100) and the pinned connection gone: the viewer observes on the new connection and, only while the lease still names an id of this app and the release budget has not run out, acquires with the new id in order to release it. `inControl` means the lease names the open stream's own id (`_streamViewerHash`, that id's lease hash): a lease naming another id of this app reads as watching and Take over repairs it, so input goes only on the stream that holds the lease, and a take over whose retry observed a new id reopens the stream with that id whatever the acquire answers. A 4000 while handing back or shutting down is not lost control. While covered in control the picture is hidden at once (`phase` `connecting`, no framebuffer) though the stream stays open through the grace period, so an app switcher snapshot cannot capture what is typed. `control` is also `releasing` while a hand back is on its way (the header says Handing back…), and the notice of lost control is worded from the lease (`lostText`: Hermes took control back, or someone else took control) and shown while the picture is blanked too. Losing control (another holder in a status or broadcast, or a 4000 close, logged once whichever comes first) sets `lost` until `dismissLost`, a take over or the lease being this device's again. While in control a pause that means leaving (`foreground` or `visible` false) closes the stream with 4100, which the bridge treats as a dropped link and keeps the lease for, a cover (`unlocked` false) does so only after `coverGrace` (2 s), and returning observes with the same id; while watching every pause closes with 1000 as before. `shutDown(reason)` is what the owner calls in place of `dispose`: it releases (2 s budget, `kViewerReleaseBudget`) and then closes with 1000, so `close`, `sign_out`, `profile` and `server` (from the auth state when `ChatScreen` is disposed) are logged as `bot_screen.handback`; when that release did not get through within the budget, `dispose` lets go of the ids this viewer used with `BotScreenViewerIds.letGo(forget: true)` (in memory only, each viewer counts its ids with `retain`, and an id another live viewer uses is kept) and then tells the screen controller (`viewerIdsChanged`), so an open card stops saying "You're in control" without waiting for a status read, so the lease they may still hold reads as someone else's and the card and the blanked notice offer Hand back to Hermes instead of the next viewer resuming it without asking (existing copy, which says someone else took control); an acquire for a new id that answers after the budget is judged by that id and still released, and past the budget its id is never added. A viewer that shuts down while in control retires its id (`BotScreenViewerIds.retire`): `latest` stops offering it, so a viewer opened inside the release budget observes with no id, gets a new one and takes the lease over from the closing one, whose late release then names an id that no longer holds it. Once the server answered the release the id is offered again. While shutting down, a release path leaves a lease alone when it names an id that another live viewer of the app uses (`_heldByAnotherViewer`, from `BotScreenViewerIds.usersOf`; one opened meanwhile): that counts as done, so the closing viewer never takes control back from it. An id nobody uses any more (a dead viewer's) is not another viewer's, and the release still frees it. The new id a shutting-down viewer mints to give the lease back is retired too, and offered again with the first. Limit: that viewer's own acquire after an observe snapshot can still take the lease back if the closing viewer's release lands in between (a narrow window, untested). Limit: a release by closing the stream (`_releaseByClosing`) counts as done without a check, so if that close never reaches the bridge the lease stays and a reopen in the same run resumes it; a `dispose` that still holds control sends the release itself. The release request leaves before anything is awaited so a teardown can start it. Escape closes the viewer only while this device is not in control. `HermesGatewayTransport.requestOn` probes a pinned connection that went quiet (`isStale`) before sending and drops a dead one, as `_client` does. The Hand back to Hermes question has Cancel as its default and the destructive answer plain, and a failure is said in the viewer's own `ScaffoldMessenger`, since the viewer is a route and a snackbar of the screen below would be hidden. Hand back to Hermes (`confirmForceHandBack`, a `ForceHandBackDialog` that says whoever is using the screen loses control) is offered by the card and by the viewer's blanked notice when a person holds a lease this app does not hold; `BotScreenController.forceHandBack` sends `release {force: true}` with no viewer id. Logs `bot_screen.takeover` (`outcome`: acquired, refused, retried for a user's take over that needed a new id, resumed for the reconnect's silent re-acquire, error), `bot_screen.handback` (`reason`) and `bot_screen.lost_control` (`cause`), span attribute `took_over` on `bot_screen.stream`, breadcrumbs `bot_screen.handback.pressed` and `bot_screen.force_handback.pressed`; never a viewer id or its hash. `test/support/fake_display_server.dart` plays the server's lease rules (ids minted per connection, last writer wins, a release by a non-holder ignored, forced release, `display.lease` broadcasts) on a `FakeGateway`.

**Input** (`lib/src/bot_screen/input/`, `widgets/bot_screen_key_bar.dart`, `bot_screen_desktop_tools.dart`, `takeover_confirmation.dart`, `trackpad_cursor.dart`, `takeover_setting.dart`). Take over asks first (`TakeoverConfirmation` in `showAdaptiveSheet`: a bottom sheet on a phone, a dialog on a Mac and wide windows; no iOS action sheet) unless `TakeoverSetting` says the user chose not to be asked: one boolean `bot_screen.takeover.skip_confirm.<accountKeyFor>` in shared preferences, never the server address; `ChatScreen` builds it from `AuthController.accountKey` (none without one, which always asks). `BotScreenViewerController.input` is a `ScreenInput` (the stream's client behind a counting sink, a `ScreenKeyboard` and a `ScreenPaste`) while this device is in control and the stream is open and has shown its first picture (until then input and the key bar are not offered), and goes with the stream: keys and pointer buttons still held are released and the screen's clipboard emptied before the close, and, because the bridge drops input from a stream that does not hold the lease, before a hand back or close releases it (`input` is null while releasing); a window that goes inactive lets go of its keys too, and nothing is sent once the input is disposed. The span `bot_screen.stream` carries `input_events` (`0`, `1-10`, `11-100`, `>100`), never which. `BotScreenViewer` puts a `ScreenGestureLayer` over the picture (its `TransformationController` is its own, so the layer maps through the same zoom), a `TrackpadCursor` inside the picture's box in Trackpad mode, and, on iOS and Android, the key bar under the stage (keyboard, Esc, Tab, Ctrl and Alt latching for the next key, the arrows, Paste, then the Touch or Trackpad switch, scrolling sideways when it does not fit) or, elsewhere, a tools row under the header (Paste, and Send F8 off a Mac). `scaleEnabled` is false for the viewer while in control on a computer, so the mouse wheel scrolls the screen and does not zoom the picture; a finger's pinch stays on a touch device. `ScreenKeyboard.handle` maps hardware keys through `KeysymMapper`: on macOS and iOS ⌘V is Paste, ⌘. closes the viewer, ⌘Q, ⌘W, ⌘H, ⌘M, ⌘Tab and `` ⌘` `` are left to the app and the system (`KeyEventResult.ignored`), the Command key itself is never sent and any other ⌘ chord goes as Control around the key (⌘A is Ctrl+A); elsewhere Ctrl+V is Paste, F8 closes the viewer, Alt+Tab, Alt+F4 and every Super chord are left to the system; Escape and everything else go to the screen. A held Paste or close chord repeating does nothing more, a repeating key is pressed again, and a key is released with the keysyms that went down with it. `releaseAll` runs when the picture loses keyboard focus, the stream closes or control ends, since the release would never come. The menu bar needs no scope: a Flutter handler that handles ⌘A keeps the menu from seeing it. `SoftKeyboard` is a `DeltaTextInputClient` attached by the key bar's keyboard key, with `visiblePassword`, autocorrect, suggestions, keyboard learning, smart quotes and dashes off, no capitalization and no autofill; the field holds one zero-width space, composing text is held and sent only when committed (text as key presses, a deleted character as BackSpace, a line break and the action key as Return), and the field is reset after each keystroke so nothing accumulates; a keyboard that reports whole values is compared with what the field held. It closes with the stream's input. `ScreenPaste` reads the clipboard text, sends it as the screen's clipboard, presses Control+V and clears the screen's clipboard 500 ms later (at once if the stream is about to close); text outside Latin-1 or over 256 KiB is refused with "This text can't be pasted to the screen." under the header and nothing is sent. Nothing typed, pasted or pointed at is kept or logged: `bot_screen.paste_refused` carries `reason` (`not_latin1`, `too_large`), and the breadcrumbs `bot_screen.takeover.pressed` and `bot_screen.input.mode` (`mode`) carry fixed words.
