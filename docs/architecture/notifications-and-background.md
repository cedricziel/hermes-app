# Notifications and background work

**Notifications** (`lib/src/notifications/`). Local notifications when a reply finishes or the agent needs the user, gated by `attention_policy.dart` and user settings. Each notification is grouped per chat or scheduled task (`AttentionNotification.groupKey`, `chat:<profile>/<thread id>` or `job:<profile>/<job id>`; thread identifier on iOS and macOS; Android bundles by itself), and a request (any `hermes.request.*` category, or a secret or input the app cannot ask for: `timeSensitive`) uses the time-sensitive interruption level so it can break through a Focus (the user can turn that off in system settings); replies and tasks stay at the default. The iOS Runner carries the time-sensitive entitlement; on the Mac the fastlane lane adds it to `Release.entitlements` before it archives (`set_info_plist_value`), because it is restricted and a local ad-hoc `flutter build macos --release` would be killed at launch with it checked in (`test/notifications/time_sensitive_entitlement_test.dart` guards both). `BadgeController` (`badge_controller.dart`, on `app_badge_plus`) sets the app icon badge (iOS, Android) and the Dock badge (macOS) to the length of the surface snapshot's `pending` list, and removes it when nobody is signed in, after sign-out and while notifications are off; macOS has a `SurfaceSnapshotStore` on `MemorySurfaceStorage` for that alone, and its `SurfaceSnapshots` runs `localOnly` (open requests from the chat screen, no server reads, no `surface.*` telemetry). On iOS and macOS an approval shows its command and a question the question, under a category whose hidden-preview placeholder hides the text on a locked screen, with buttons that answer it (`request_notifications.dart`: the category and action ids, the payload, `answerFor`). Android shows the same text and buttons (`RequestCategory.androidActions`: at most three, Always allow dropped when four are offered, a question cut to two choices and Other… when more do not fit) only when the body shows what is asked, posted with secret visibility, because the plugin can set neither a public version nor an authentication requirement, and tagged `hermes.request` (`kAnswerableTag`), because the plugin lists no payloads for active notifications: App Lock withdraws them by that tag, and a post for the chat cancels the other variant of its id. A request the background refresh posts with the generic body gets no buttons there. The plugin's `ActionBroadcastReceiver` (declared in the manifest) runs `answerRequestInBackground` in its own engine even while the app runs, so `RequestAnswers` registers the hand-off port on Android too. `flutter_local_notifications` cannot set the placeholder, so `hermes_app/notification_categories` in each Runner re-registers the categories and keeps the ones made for single questions. While App Lock is on, requests keep the generic text and get no buttons. An answer goes out with `request.answer` on a fresh gateway transport (`request_answers.dart`; an event-frame request falls back to `approval.respond`/`clarify.respond`). On iOS the Runner owns the notification center delegate (`NotificationActions` in `AppDelegate.swift`), because a launch for a background button has no scene and so no engine: it begins a background task and starts the plugin's headless engine itself. That isolate hands the answer to the running app's isolate through `IsolateNameServer` (offer, then confirm), or answers alone, one answer at a time with a fresh `AuthController` each, all within 25 s of the button. A stored session records its dashboard (`HermesSession.serverUrl`); before a refresh, and after a rejection, `AuthController` takes over a newer stored pair of the same user and dashboard instead of spending a used refresh token or signing out. On macOS the app's isolate gets it. A failed or expired answer posts "Couldn't send your answer".

A second source is `schedules/schedule_alerts.dart`: while the app is in front, `ScheduleWatcher` (owned by the shell) polls every profile's cron jobs each minute and announces a run since the last look; Hermes has no push channel, so nothing arrives while the app is closed.

The one thing that runs then is the periodic background refresh (`lib/src/background/background_refresh.dart`, `background_scheduler.dart`; `workmanager`): `BackgroundScheduler` registers it while signed in, every 15 minutes at the earliest on iOS (BGAppRefreshTask) and Android (WorkManager), and cancels it on sign-out, expiry or a change of server; the system decides when, and whether, it runs. The whole task, from readying the isolate to the telemetry flush, has 25 s (`backgroundRefreshTask`), so the run gets what is left after its 3 s grace and 2 s flush. A run is `withHeadlessHermes(task: 'refresh')` over a list of independent `BackgroundStep`s (20 s each): `OpenRequestsStep` lists each profile's `session.active_list`, reads `approval.pending` of the sessions that are `waiting`, and posts one generic notification per chat for each request id not yet in `hermes.background.announced.v1` (newest 200; the approval's command is never read), through `requestCategoryFor` so it carries the buttons of an approval raised in front; `SnapshotStep` calls `HeadlessHermes.refreshSnapshot(pending:)`, which rebuilds the snapshot with every profile's chats and replaces its pending list. The app in front and a run both write the snapshot, which carries a `revision`: every write saves the stored revision plus one, a run saves only if the revision is still the one it built from (`SurfaceSnapshotStore.writeIfCurrent`, else it drops its build and logs `surface.snapshot.write_skipped`), and the foreground adopts a newer stored snapshot as its base on resume and before each build.

Four more steps (`background_alerts.dart`, `background_spotlight.dart`) report what happened while the app was away, the three that notify only when notifications are on, all only when the app is not in front, with the texts and per-chat or per-job notification ids of the app in front, so a run the app already announced is replaced, not added: `RunningRepliesStep` reads `hermes.background.running.v1` (profile, chat id and time of each chat whose reply ran when `ChatScreen` was paused, written by `ChatController.rememberRunningReplies` for every profile, including replies it carried out of a profile it left, each with the time it was first remembered; cleared on resume, at start and on sign-out; entries expire after 24 h) and asks `session.active_list` once per profile on the run's socket. It announces only on positive evidence: the session is listed `idle` and the newest stored message is the assistant's text (title from `loadThread`, then `loadMessagePage(limit: 5)`, 4 s each, in parallel), with `replyPreview` as the body. A session that is absent or has an unknown status, a chat that ends on the prompt, a tool call or empty text (a lost or stopped turn looks the same) are forgotten silently, there is no "Reply failed" in the background, and a chat whose history cannot be read stays for the next run. It records the chat in `hermes.background.replied.v1`, posts, and only then forgets it; `ChatController` takes that record before it announces a `ReplyCompleted`, so the replay on return does not announce again (the record is cleared on pause, at start, when the user sends in the chat and `replayGrace` after the app returns). `ScheduleAlertsStep` runs when the schedule setting is on and `/api/cron/delivery-targets` answers: `runsSince` against `hermes.schedules.baseline.v1` (`ScheduleBaseline`, job key to last run time, under `accountKeyFor(server, user)` so another server or account reads none, and cleared on sign-out on every platform), muted jobs skipped, `alertsFor` unchanged, notifications first and the baseline saved after; `ScheduleWatcher` reads and saves the same baseline at every look after any pending removal, and an availability check that could not tell (offline, 5xx) leaves it alone. The first look on a device or after the setting is switched on only records.

A fourth source is messages from Hermes (`lib/src/agent_messages/`; a profile's messenger plugin saves each `hermes send --to hermes_app:inbox` as a session with an id starting `hermes-app-`, source `hermes_app` and `unread: true`): `AgentMessageWatcher` (owned by the shell on Android, iOS and macOS; the Notifications dialog's "Messages from Hermes" switch, `NotificationSettings.agentMessages`) lists every profile's deliveries each minute while the app is in front, and `AgentMessagesStep` does the same in a background run, both through `lookForMessages` (`listDeliveries` up to three pages of `GET /api/sessions?source=hermes_app&order=created`, then `findMessages`) and `messageAlertsFor` (the chat's title, the message text as body, the `hermes.message.new` category, a summary above five; App Lock hides title and text). The step is quiet while the app is in front or notifications are off and writes and posts nothing when the profile names cannot be read (`HeadlessHermes.profiles()` gave its `[null]` fallback). `AgentMessageRecord` (`hermes.agent_messages.baseline.v1`: per profile the start time of the newest chat dealt with, under `accountKeyFor`, cleared on sign-out) is shared and saved before the notifications are posted, and only if no other look moved it meanwhile (`writeIfCurrent`; a look that lost posts nothing), so a chat one announced the other does not announce again; the step also skips the save when the app has come to the front or its time is nearly up, so a cut-off run repeats instead of losing messages. The first look only records. A tap carries the `'m': 1` payload marker (`NotificationTarget.message`) and `ChatScreen` opens it with `fetchMissing: true`, which switches the profile and fetches the chat; the summary only shows Chat. Opening an unread chat marks it read (`HermesChatRepository.markRead`, `PATCH /api/sessions/{id}` with `unread: false`; a failure logs `chat.mark_read_failed`), and a find in the shown profile reloads the list through `AgentMessageFinds` and `ChatController.refreshThreadList`. Logs `agent_messages.announced` and `agent_messages.look_failed` carry `background` and no content. `SpotlightRefreshStep` waits for `SnapshotStep.written` and lets a `ChatSpotlightIndexer` (App Lock through its `locked` callback) bring the index in step with the stored snapshot; unlike the other three it does not depend on the notification setting, only on the Spotlight switch, and it skips a run while the app is in front. It uses `SpotlightIndex.forPlatform(indexOnly: true)` and the Runner's `Spotlight.installIndexing`, which has no `take`, `opened` or `becameAvailable`, so the main engine keeps the taps. The run's span gets `replies.finished`, `schedules.ran` and `agent_messages.found` as counts. While the app is in front (its `AppPresence` port answers `resumed`) the run announces nothing (WorkManager runs while the app is open); an announced wait is remembered by session and turn, so a refused `approval.pending` (counted as `background.requests_unreadable`) is never announced twice. Only an empty storage (`HeadlessSignedOut.nothingStored`) cancels the task, and the scheduler re-registers it on resume when the system lost it; on iOS it logs `background.refresh.unavailable` when Background App Refresh is off. Nothing is posted while notifications are off, and a run never signs the user out: signed out cancels the task, locked and unreachable change nothing. The dispatcher (`backgroundRefreshDispatcher`) always answers `true` and flushes telemetry before it returns.

On iOS a reply sent from the phone is also a Live Activity (`lib/src/live_activities/`, the `live_activities` plugin, the `HermesLiveActivity` widget extension): `ChatController` starts it on send (ActivityKit only starts one while the app is in front) and moves it with the reply's events, one per chat, labelled with the notification bodies so nothing a reply or request said reaches the Lock Screen. It declares the `.small` supplemental family, which watchOS 11 shows in the Smart Stack (title, a short state word, the timer; derived from the stored state in Swift). A turn sent from the watch gets none: it reaches the phone in the background, where ActivityKit cannot start an activity. Updates made in the background mark it stale a minute later, since nothing updates it once iOS suspends the app. A finished one stays 15 minutes; stop, deletion, sign-out, the dialog's switch and the next launch end it. So do a turn that can no longer be followed (a profile switch while only the follow-up listener fed it, a closed chat) and a stop the server had nothing to stop; the turn Hermes runs ahead of a prompt does not finish the prompt's activity, and a follow-up turn never moves a finished one. The plugin updates an activity only by the id ActivityKit gave it, and does not see a tap that launched the app, which `SceneDelegate` keeps for the `hermes_app/live_activity` channel.
