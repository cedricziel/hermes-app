# Native pieces (Runner targets, extensions, packages)

**Native pieces.** Nothing builds audio or CallKit objects before the user starts dictation, playback or a call: a plugin's `register` and `init` never create an `AVAudioEngine` graph, a `CXProvider` or `CXCallController`, or touch `AVAudioSession` (building them at launch interrupts other apps' audio on iOS). `HermesCallsPlugin` makes its provider, controller and `CallAudio` in `start` and drops them when the call ends (the provider a few seconds later, so CallKit's `didDeactivate` still arrives); `test/native_audio_launch_test.dart` pins this on the Swift source and `test/app_audio_launch_test.dart` pins the Dart side. The iOS Runner declares the background refresh's BGTask identifier `$(PRODUCT_BUNDLE_IDENTIFIER).refresh` (`BGTaskSchedulerPermittedIdentifiers`, `UIBackgroundModes: fetch`; it also declares `audio` and `voip` for voice calls, see `packages/hermes_calls`) and registers its launch handler in `didFinishLaunching` (`WorkmanagerPlugin.registerPeriodicTask(withIdentifier:earliestBeginInSeconds:)`), because BGTaskScheduler refuses a handler added later; it does not run on macOS. `ios/ShareExtension` (share sheet, `receive_sharing_intent`, linked by a version-pinned path in `project.pbxproj`, so a plugin upgrade must be mirrored there) and `ios/HermesLiveActivity` (the app's one WidgetKit extension despite its name, bundle ID `com.cedricziel.hermesApp.LiveActivity`: the Live Activity, the Home Screen widgets Recent chats, Needs you and Board, and the Lock Screen and StandBy ones (Needs you's accessory families, New Chat, Dictate and Quick launch), which draw the surface snapshot only; new widgets join its `HermesLiveActivityBundle`, and renaming the target would orphan its provisioning profile), `ios/HermesSurfaceKit` (the Swift package the system surfaces share: `SurfaceSnapshot`, the lenient reader of the snapshot, and the pure `RecentChatsModel`/`NeedsYouModel`/`NeedsYouAccessoryModel`/`QuickLaunchModel`/`BoardModel` that decide what each widget shows, the App Intents `ChatEntity`/`ProfileEntity` (queries answered from the snapshot: recent chats newest first, a chat the snapshot no longer holds still opens as "Chat"; under App Lock, when every title is empty, no chat is offered; the app's "New chat" label is shown with profile and age and never matched; the Open Chat control's label is fixed) with `OpenChatIntent`, `NewChatIntent`, `DictateIntent` and the Open Chat control's `OpenChatControlIntent` (each returns an `OpenURLIntent` on a `DeepLink`; compiled into the Runner and the extension, whose bundle also holds the New Chat, Dictate and Open Chat controls in `IntentControls.swift`; the one `AppShortcutsProvider`, `HermesAppShortcuts`, and the `hermes_app/intents` channel that `lib/src/intents/intent_shortcuts.dart` calls after each snapshot write are Runner-only, in `ios/Runner/HermesAppShortcuts.swift`), and `DeepLink`, the only Swift builder of `hermes://` links, whose output `test/deep_links/deep_link_fixture_test.dart` pins in `Tests/Fixtures/deep_links.json` (`UPDATE_DEEP_LINK_FIXTURE=1` rewrites it); the extension compiles its sources directly, in the same module, so its tests run with `swift test` in CI's "Test watch core" job; `test/fixtures/surface_snapshot_v1.json` is the Dart-written fixture its tests decode, kept equal to the copy in `ios/HermesSurfaceKit/Tests/Fixtures/`), `ios/HermesWatch` (the watchOS companion app embedded in the iOS app; it has no network of its own and asks the phone, which answers in `lib/src/watch/`. It keeps the chat list and the listed chats in its Caches directory, hands the requests that never reached the phone over with the next one, which the phone logs as `watch.delivery.failed`, and offers fixed quick-reply chips (Continue, Yes, No, Summarize) and double tap (starts or stops and sends a voice message) in a chat. A send that waits on an approval or a question answers `waiting` at once and the watch asks again with the same send id while the user answers from the mirrored notification; see the `watch-simulator` skill). macOS has its own share inbox (`share/macos_share_inbox.dart`), which also carries the Services menu's "Ask Hermes" (`NSServices` in `macos/Runner/Info.plist`, `AskHermesService.swift`): the provider queues the selection in memory (never on disk, at most 20,000 characters), `AppDelegate` merges it into the `take` answer, and the inbox turns it into a `SharedQuote`, which `ChatScreen` puts, block-quoted and unsent, in the composer of a new chat (`ShareController` holds only the latest and drops it on sign-out). On macOS, Debug builds use bundle ID `com.cedricziel.hermesApp.dev` (`macos/Runner/Configs/AppInfo.xcconfig`), so every macOS extension's Debug ID must be prefixed with it; iOS uses `com.cedricziel.hermesApp` in every configuration. Release and TestFlight builds go through `fastlane` (lanes in `fastlane/Fastfile`, store metadata in `fastlane/metadata/`). On Android, Auto Backup stays on but `AndroidManifest.xml` points `android:fullBackupContent` (Android 11 and older, `res/xml/backup_rules.xml`) and `android:dataExtractionRules` (12 and newer, `res/xml/data_extraction_rules.xml`, cloud backup and device transfer) at rules that exclude the `home_widget` plugin's `HomeWidgetPreferences.xml` and `InternalHomeWidgetPreferences.xml` from the `sharedpref` domain: the surface snapshot holds chat titles and snippets and must not reach a backup or a new phone, which writes its own. Anything else the app stores is unchanged (the `shared_preferences` file is still backed up). `flutter_secure_storage`'s Keystore-bound values cannot be decrypted on another device after a restore: stores with the default `resetOnError` reset and read as empty, but the chat queue's keys (`lib/src/chat/queue_storage/queue_keys.dart`, `resetOnError: false`) would throw, since the plugin only logs then. That is not a regression of this change, and whether the plugin's preferences should also be excluded is an open question.

**Android themed icon.** `res/mipmap-anydpi-v26/ic_launcher.xml` carries a `<monochrome>` layer, `res/drawable/ic_launcher_monochrome.xml`, so Android 13+ themed icons tint the logo instead of falling back to the untinted one. It is a 108dp vector of the launcher foreground's chat bubble with the wing cut out (even-odd fill, path from `design/icon-foreground.svg`), drawn at 0.82 of the foreground scale and centred, so every point lies inside the 66dp circular safe zone (radius 33dp; measured max 32.8dp). There is no `ic_launcher_round`: the adaptive icon is the only one. `design/generate-icons.sh` does not produce it; edit the vector by hand when the logo changes.

**Secure window (Android).** `MainActivity.kt` serves the channel `hermes_app/secure_window` with one method, `setSecure(bool)`, which only calls `window.addFlags(FLAG_SECURE)` or `clearFlags(FLAG_SECURE)` and holds no state. The counting is Dart's: `SecureWindow` (`lib/src/server_care/secure_window.dart`) keeps the number of pages that asked, sends `true` when the first one does and `false` when the last lets go, and does nothing off Android (iOS has no such flag; there `PrivateSurface` blanks the page while the app is inactive). The Logs page holds it while it is on screen; a page that fails to start releases it. No plugin was used (`screen_protector` and `no_screenshot` were weighed; see `openspec/changes/server-care/design.md`, open question 1).

**Android icon resources.** The notification small icon is `res/drawable/ic_stat_hermes.xml` (`kAndroidStatusIcon` in `local_notification_service.dart`, used by `AndroidInitializationSettings`): Android draws only the alpha channel of a small icon, and the adaptive launcher icon is opaque, so using it showed a white square. The vector is the launcher foreground's chat bubble with the wing cut out (even-odd fill, same path as `design/icon-foreground.svg`, scaled into 24dp). Resources that code or the system look up by name are listed in `res/raw/keep.xml` so resource shrinking keeps them; add new ones there. No brand colour is set on notifications: none is defined in the Dart theme.

**Predictive back (Android).** `AndroidManifest.xml` sets `android:enableOnBackInvokedCallback="true"` on `<application>` (`test/android_predictive_back_test.dart` pins it); targetSdk 36 only turns it on by itself from Android 16, so without it Android 13 to 15 get no peek animation. With it the system decides at gesture start whether back pops, from `canPop`, so a screen that guards leaving declares that up front: `PopScope(canPop: <not dirty or busy>, onPopInvokedWithResult: (didPop, _) { if (!didPop) <confirm> })`, never a lazily computed answer or a navigation done while `canPop` is true. Nested navigators (the chat's phone layout, the Activity panel, the workspace picker) sit under `NavigatorPopHandler`, which forwards a back the nested stack can take. `WillPopScope` is not used.

**Linux window size.** `linux/runner/window_size.h` holds the rule (GTK-free): minimum 360 x 480, default 1280 x 720 clamped to 90 percent of the work area and never below the minimum. `my_application.cc` sets the minimum with `gtk_window_set_geometry_hints` (`GDK_HINT_MIN_SIZE`), reads the work area of the monitor under the pointer on X11 (on Wayland the pointer position is unknown before the window is mapped, so it is the monitor at the origin; else the primary one) with `gdk_monitor_get_workarea`, sets that default size and centres the window (`GTK_WIN_POS_CENTER`). A 1366 x 768 laptop with a 728 px work area opens at 1229 x 655. `test/linux/linux_window_size_test.dart` pins the constants and the calls in the source and compiles the function with `g++` (skipped when there is none). Centring and the work-area clamp hold on X11 only: on Wayland `GTK_WIN_POS_CENTER` does nothing (the compositor places the window) and GTK 3's Wayland backend has no work-area support (`gdk_monitor_get_workarea` returns the full monitor geometry), so the window may cover a panel there.
