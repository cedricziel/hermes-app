# Memory

**Memory settings** (`lib/src/memory/`, below the entries on `MemoryScreen`). `MemorySettingsRepository` reads `GET /api/config?profile=` for five keys (`memory.user_profile_enabled`, `memory.memory_enabled`, `memory.write_approval`, `memory.nudge_interval`, `display.memory_notifications`; a missing or ill-typed one shows Hermes' default) and writes one key at a time with `PUT /api/config?profile=` (deep merge, so nothing else changes). `MemorySettingsController` (owned by `MemoryDestination`, rebound with `MemoryController` on every profile) shows a change at once, sends one write per key at a time (a change meanwhile goes out after it) and puts the control back on the last confirmed value with "Couldn't change <setting>. Try again." A value the app does not offer (an interval of 15, a report mode of `loud`) is shown as it is and kept as a choice. `write_approval` applies at once; the other keys when a chat starts. The Storage section reads `GET /api/memory?profile=` for the active provider (`""` is the built-in files; `missing` is an error banner, `needs_config` and `unavailable` a warning) and opens Plugins on Providers for that profile. Reset memory… asks (`MemoryResetAlert`) and sends `POST /api/memory/reset?profile=<explicit>` with `target` `memory`, `user` or `all`; only `ok: true` counts as done, a lost answer is "may have happened" and is read again, never resent, and the entries, settings and provider are read again afterwards. Spans `memory.settings.fetch`, `memory.settings.write` (`key`), `memory.status.fetch` (`provider_status`), `memory.reset` (`target`), logs `memory.setting_changed` and `memory.reset_outcome`, breadcrumbs `memory.setting_toggled` and `memory.reset_confirmed`: fixed slugs only, never profile, provider or file names.

**Memory proposals** (`lib/src/memory/`, "Waiting for you"). Hermes stages memory writes while `memory.write_approval` is on (and a background review's replace or remove even when it is off) and skill writes under `skills.write_approval`; nothing but the slash commands lists them. `MemoryProposalsRepository` runs `/memory pending` and `/skills pending` (in parallel; one failing kind keeps the other, `Unknown command` is unsupported) through `MemoryProposalSession`, which gives every command a new thread-less gateway session of the profile: at Hermes d923a5eb `session.create` plus `slash.exec` leaves no stored session, so no empty chat reaches the list (the contract test checks it on every run). `parseMemoryPending`/`parseSkillsPending` read the text leniently (`memory_proposals.dart`: `⏳` progress lines skipped, unknown lines kept and counted, `patchs entry:` detail lines for the pinned entry, background summaries `(<action> on <target>): - replace: …`, a batch or unknown wording is the "Change" badge with the raw summary); a non-empty answer with no item is unreadable. `MemoryDecisions` (shared with the chat tool card) runs `/memory|/skills approve|reject <id>`; only lines under "Failed:" are failures (the "Overwrote/Patched/Removed entry" lines after an approval also read `<id>: …`). Approve all and Reject all send one command per listed id, never `all`. `MemoryProposalsController` (owned by `MemoryDestination`, rebound with the profile, late answers dropped, everything cleared on rebind) feeds the waiting card on `MemoryScreen` and `MemoryProposalsScreen` (list beside detail at `isWideLayout`, a page below; Ask before saving reuses `MemorySettingsController`). `MemoryWaitingCount` counts for the "Memory · N waiting" sidebar entries (read when threads load, on resume at most every five minutes, after leaving Memory) and the Mac Profiles page ("N waiting"). Spans `memory.proposals.fetch|decide|diff`, logs `memory.proposal_decided` and `memory.proposals.parse_lenient`, breadcrumbs `memory.inbox.opened` and `memory.inbox.decide`: fixed names, counts and outcomes only.
