# Watch

**Watch complications** (`lib/src/watch/watch_complication.dart`, `ios/HermesComplication`). A watchOS WidgetKit extension embedded in the watch app (bundle ID `com.cedricziel.hermesApp.watchkitapp.widgets`) offers Voice Chat (`accessoryCircular`, `accessoryCorner`) and a chat status (`accessoryRectangular`, which the Smart Stack shows). `WatchComplicationStatus` publishes the latest turn's state (working, waiting, ready, failed, from the Live Activity's `nextActivityState`, restarted when a finished chat opens another turn or asks), a time, a rising `seq`, the watch's thread id and the chat title only once the gateway or server named the chat (`ChatThread.named`; never the prompt, a file name or the server's preview), never any text, and only the state while App Lock is on. It is fed from `ChatController._announce` (replies sent from the phone) and `WatchRequestHandler._send` (turns sent from the watch), because neither the notifier nor the Live Activity sees both; `WatchRelay.swift` sends a change of state (a stop and a sign-out clear included, App Lock stripping a title too; not the first working of a watch turn) with `transferCurrentComplicationUserInfo` (budgeted), and everything else, or that once the budget is spent, with `updateApplicationContext`, where `WatchRelay.complicationContext` replaces every complication key of the held context (a title or chat id the payload omits is dropped, `watchSession` and `watchRequests` stay); a turn that starts on a chat replaces the chat's earlier ones and a working or waiting one is forgotten after 30 minutes; an undelivered payload is sent again with the next change. The watch app (`ComplicationUpdates`, in `WCSessionTransport`'s delegate) applies it only if its `seq` is newer than the last one, stores it in the App Group `group.com.cedricziel.hermesApp` and reloads the timelines (the `.watchConnectivity` background task holds the app until the session has nothing pending); `Core/ComplicationStatus.swift` (decoding, store, the relevance plan, the `hermes-watch://` links) is shared by the package, the watch app and the extension. A working or waiting status the phone did not renew for 30 minutes is not shown, since a suspended phone app cannot report the end. The extension and the watch app need App Groups enabled on their App IDs (fastlane's `bootstrap_app` says so).

**Watch Handoff.** The `threads` answer (and every `send` answer that names a thread, which `ConversationModel` adopts for a new chat) adds `serverUrl` (canonical), `profile` and `sessionId` (the raw session id) per chat, left out when either is unknown. The open chat's `ConversationView` advertises an `NSUserActivity` of the `HERMES_HANDOFF_TYPE` type with the same v1 payload the phone and Mac accept (`threadId` = the raw session id); the watch only passes the address on. `ios/Flutter/HandoffType.xcconfig` is the one iOS definition of the type, included by the iOS configs and `HermesWatch.xcconfig`, and `ios/HermesWatch/Info.plist` declares it (the macOS configs hold the same pair).

The watch has its own lock (passcode, wrist detection). The phone's App Lock does not gate the watch app, and no new change may make the watch's access depend on the phone's lock state. The complication rule (no title or chat id while App Lock is on) is the intended effect. Existing exceptions, being removed in a follow-up PR stacked on this one: `_requestsWanted` in `WatchBridge` requires App Lock off, and `_onCall` replies `locked` to `request_details` and `request_answer` under App Lock. The phone notification for a watch-sent turn and the complication title still follow App Lock; that is phone-side privacy, not watch access. The urgent complication path also writes the application context, so a later context delivery cannot bring back an older title.
