# Chat

**Chat** (`lib/src/chat/`, built on `flutter_chat_ui`).

- `ChatController` keeps shared state, its public instance API, and lifecycle in `chat_controller.dart`. Private library parts group history, commands, durable queues, sending, streaming, session bindings/state, progress, connectors, billing, request answers, and system surfaces. `ChatScreen` owns resources and lifecycle in `chat_screen.dart`, with private parts for layout, composer, recipients, sharing, navigation, external openings, and conversation windows. Keep feature changes in the corresponding part. Public controller methods delegate explicitly to private extensions so callers and subclasses retain the same instance API. Parts share their root library's imports and private state; they are not independently owned controllers.
- Branching: every finished reply's action bar has "Branch in new chat" (`MessageActions.onBranch`, offered only by `ChatScreen` through `boundChatThreadView(branchable: true)`), and the Mac thread menu has "Branch in New Chat" (`ThreadAction.branch`, through `ThreadHousekeeping.branch`). `ChatController.branch` counts the prompts Hermes holds after the chosen message (`_promptsAfter`: commands shown only here and failed prompts do not count), and `ChatTransport.branchThread` sends `session.branch_whole` (`session.branch` on an older gateway) on the resumed chat, then `session.undo` that many times on the copy. Hermes' own `count` is not used: it counts stored rows with text, which the app's messages cannot be mapped to. A copy whose undo failed (`BranchIncomplete`) is deleted again; a gateway without either method gets "can't branch". The copy holds the prompts and replies with text, not the tool calls, and opens through `open(fetchMissing: true)`. Breadcrumb `chat.branch` (`outcome`, `from`).
- History: a chat's first page is read when it opens (`_readFirstPage`, `chat_controller_history.dart`). A send never waits for it: the prompt, reply placeholder, Live Activity and network send happen on tap. When the page lands in a chat that already holds rows, `_mergedWithPage` puts history above them and shows a turn both hold once, matching a held prompt to a page row only by its receipt (`prompt.submit`'s `user_row_id`, the same `messages.id` as the REST row's `id`). The held copy wins unless it failed here while Hermes stored a final answer (an assistant row with text, no tool calls and no continuing `finish_reason`). Hermes' stop gates (verify-on-stop, `pre_verify`) store their candidate answer as such a row with `finish_reason` `verification_required` or `verify_hook_continue` (the kanban guard's `kanban_terminal_required` is not stored, and is listed anyway) and keep the turn going (checked in `agent/turn_stop_gates.py` at the ref in `openapi/HERMES_REF`), so those do not count as answered; `message.interim` text itself is not stored as its own row. A turn that ended on such a row (iteration budget spent, interrupted) cannot be told apart from rows alone, so a failed turn then keeps its error copy until the chat is read again. A send into a stored chat whose first page has not landed never retitles it from the prompt: its empty messages say nothing about its name. A receipt that arrives after the page removes the page's copy of that prompt (`_dropStoredCopy`). A prompt that never gets a receipt (a compute-host turn, `turn_isolation`, answers `prompt.submit` without `user_row_id`) cannot be told from a stored row with the same words, so it can show twice, and branching from a reply above it then counts it twice, until the chat is read again (`refreshThread`). Rows only this app has (command lines, review notes, stops) stay. Load older drops a page whose chat was re-read meanwhile. Listing the chats again for the profile already in view (`loadThreads`) keeps the threads a send is running in, with their queues and the selection, like the refresh after a send does. What those threads' turns stand on carries over (queue review, suspension and settle state, owned-session and session-state records, and a protected queued send's epoch and generation, the `kept` block of `_loadThreads`), so a queued prompt still lands in the transcript when the server accepts it and a prompt queued behind the turn still sends once it ends. A thread whose send ended while the list was read is kept too. A running protected send is marked current from the moment the read starts, so an acceptance that lands mid-read still inserts its prompt. Kept threads keep their history paging cursor (`_olderRows`), and one whose first page was cut off by the read is read again; their owned-session binding is not carried, since the usage meter binds with it. Known gaps: a prompt queued behind the turn whose enqueue straddles the end of the read fails with the draft kept (`_enqueueProtected` checks `_queueEpoch`), and a kept thread whose send ended during the read shows its local copy, not the server's newer title or pin state, until the next list read. A queued prompt whose dispatch starts just before the commit (it captures `_queueEpoch` before reading the store) can stay queued until the next send or enqueue instead of sending when the turn ends. On a profile switch with a protected send running, the send stays current until the switch commits, so it may still submit to the profile being left. A command that re-reads the chat (`_refreshAfterSlash`, after `/undo` or a Bot Chat compaction) merges the same way, over the rows sent or run here only: stored rows come from the page, so an undone turn goes, while a reply still streaming and command lines stay. A settled turn sent here whose row the page lacks goes too (undone, or older than the page, which Load older brings back); one without a receipt goes when the page holds a prompt with the same words. A turn whose receipt lands after the page was read and which ends at once can vanish from view until the chat is read again.
- Domain messages (`chat_models.dart`) map to flyer messages in `chat_message_mapper.dart`. `chat_controller_sync.dart` applies before/after diffs to the `InMemoryChatController`. Custom message kinds and cards (tool calls, approval and clarify requests) live in `chat_message_kinds.dart` and `widgets/`. Tool calls follow assistant-ui: `tool.generating`, `tool.start` and `tool.complete` are matched by `tool_id` (name as fallback) into `ToolCall`s with args, result data, diff and timing; a run of calls is one `ToolCallGroup`; `widgets/tool_call_bodies.dart` gives terminal, web search, todo, diff and `memory` calls their own view, with `ToolCallCard`'s input and result as the fallback. The memory body (`widgets/memory_tool_body.dart`, outcome from `memory/memory_tool_outcome.dart`) reads `tool.complete`'s result as saved, staged (waiting for approval) or full; a full file is a `ToolCallStatus.warning`, not a failure. A staged card's Approve and Reject run `/memory approve|reject <id>` through `ChatTransport.runSlashCommand` on the chat's stored thread (`ChatController.memoryDecisionsIn`, `memory/memory_decisions.dart`; offered through `MemoryDecisionsScope`, so the catalog shows no buttons), and the Activity panel's background-review notes link to `MemoryDestination` for the chat's profile; an approval Hermes raises while a call runs is bound to it in `chat_reply.dart` and shown inside that call's card. The design for agent input requests is in `openspec/changes/archive/2026-09-19-agent-input-requests/`. Text Hermes writes before a tool call, or checkpoints mid-turn with a `message.interim` event, is sealed into `ChatMessage.sealedProse` (`chat_reply.dart`) instead of being folded into the trailing `content`, so the mapper can render it where it was actually written and `message.complete` never overwrites it.
- Agent activity outside the transcript is sorted into tiers (`activity/activity_tier.dart`: Needs you, Working, For reference; `openspec/changes/chat-activity-*`). The Activity panel (`activity/widgets/activity_panel.dart`, filled by `BoundActivityPanel`) lists Now (the Bot screen card first, see Bot Screen, then working items: the session status, process output with its omission note, live mixture-of-agents progress), Plan and This session; the header's Activity button (a toolbar button on a Mac, View > Inspector ⌥⌘I, routed to a key conversation window too) opens it as an inspector (`widgets/inspector_layout.dart`, shared with Kanban: docked from 760 pt, over the chat below) or, on a phone, a detent sheet. For reference items (usage, side answers, notices, the acknowledgement, idle billing, settled and connection-wide connector activity) live only there; Working items live there too, and an empty or unsupported state draws nothing. There is no strip: between the header and the transcript only the activity line is drawn (plus a Bot Chat banner, which is not activity).
- Needs-you dock (`activity/needs_you_queue.dart`, `activity/bound_needs_you_dock.dart`, `activity/widgets/needs_you_*.dart`; `openspec/changes/chat-activity-needs-you`). What waits on the user is one card docked directly above the composer: billing verification details (`billingTier`), a connector operation of the chat's own session with an offered action (`connectorTier`, which keeps an answer in flight and a display-only operation) and a reclaimed or failed-restore session (`sessionStateTier`, kinds `reclaim` and `resume`, both with Reopen). `NeedsYouQueue` reads those three sources of the open chat whenever its `ChatController` notifies, orders items by first-seen time (keys and times only, never a code, link, name or reason), keeps the shown position on its item or its slot, and reports `onArrived` once per item, when it first becomes the shown one (not while behind another, not for what a chat held when opened, not while the dock is not drawn; keys carry no runtime id); `ChatScreen`, `ConversationWindowScreen` and the expanded `QuickPanelScreen` each own one (a conversation window has its own `ChatController`, so it shows its own chat's items only; the one-line quick panel shows none) and pass it to `boundChatThreadView(needsYou:)`. `buildChatComposer` builds the dock above `ChatComposer` in the same `Positioned` column, so the height reported to `ComposerHeightNotifier` and the transcript's padding include it and it moves with the keyboard, attachments and dictation; `needsYouCompactFor` reads the view's own metrics (a Scaffold body has consumed the keyboard inset) and collapses the card on a small phone with the keyboard open. Arrivals are announced once per item with `SemanticsService.sendAnnouncement` (polite, a fixed sentence per kind, never the code, link, target or reason; the dock's container label is not a live region, so it is not announced twice), and `ActivityButton`, `ChatHeader`, `MacChatToolbar` and the conversation window toolbar take `waiting` for a marker and the label "Activity, N need you". Breadcrumbs `chat.activity.needs_you.shown` (`kind`, `count`) and `.paged` (`count`). `ConnectorOperationController` ends the wait for a connector answer after 10 s: no result or a thrown error is `unconfirmed`, a status other than ok is `refused` (both offer Skip and Continue again; nothing is resent, the transport's later 30 s error changes nothing and logs nothing, a late settlement still settles; log outcome `unconfirmed`), method-not-found stays unavailable. Skip is per target: one in the action row when exactly one target can be skipped, otherwise one under each skippable target in the body (`controller.skip`). While the connection is lost (`ChatController.connectionLostFor`) `suspend()` keeps a connector operation as a display-only model (names, states, deadline; no link, authority or responder), the dock draws its actions disabled with the Offline line, the reconnect replay builds a new controller and a retirement or the deadline removes it; billing details are released on a drop; a reclaimed or failed-restore item stays and its Reopen stays enabled (the gateway reconnects lazily, so selecting the chat is what restores the connection). Breadcrumbs `chat.activity.opened` (`surface`, `source`) and `chat.activity.closed`.
- Activity line (`activity/working_summary.dart`, `activity/working_summary_source.dart`, `activity/bound_activity_line.dart`, `activity/widgets/activity_line*.dart`, `activity/widgets/mac_toolbar_subtitle.dart`; `openspec/changes/chat-activity-line`). While the open chat has a Working item that reports a sentence, one button under the header (above a Bot Chat banner) says what Hermes is doing and opens the Activity panel (`_toggleActivity(source: 'line')`, breadcrumb `chat.activity.opened` and nothing else); it folds away when the turn settles. `ChatController.workingSummaryIn(thread)` reads the sources through `WorkingSummarySource`: `status.update` texts per kind (memory recalls included, kept in `ChatSessionState.recallWaits` because they are not waits), the goal title, loop prompt and heartbeat prompt while their section is `active`, process cards that are not closed, the newest live mixture-of-agents card (phase `Aggregating` is combining answers), a resume that is `loading`, and an open plan task (`TodoSnapshot`; the counter needs every task to be of a supported shape). One controller-wide integer sequence stamps sentences and counters; a source takes the next number only when its value changes and keeps it until it clears, so a control tick, heartbeat or repeated snapshot never steals `newest`. `WorkingSummary.compute` picks the newest sentence and at most two counters that do not repeat it; the line renders them (`ActivityLineModel.fromSummary`), and server text goes only to the widget, never to a breadcrumb, span or log. `boundChatThreadView(onOpenActivity:)` draws the line (null draws none: the quick panel, macOS); `ChatScreen` passes null while the inspector is docked or drawn over the chat, and on macOS, where the summary goes to the toolbar instead: `workingToolbarSubtitle` returns a non-null `subtitle` while working plus a `subtitleBuilder` that draws `MacToolbarSubtitle` for `MacChatToolbar` and `ConversationWindowToolbar`, each window reading its own `ChatController`.

Job, task and skill prompts go into the composer; a chat prompt opens that chat.
- The composer's model pill (`lib/src/models/widgets/composer_model_pill.dart`) picks a model and reasoning effort per chat from `GET /api/model/options` (`HermesModelsRepository`, loaded with each profile's threads, hidden when that fails). The pick lives on `ChatThread.modelChoice` and goes out with `ChatTransport.send`: as `session.create` overrides for a new chat, as session-scoped `config.set` (`model`, `reasoning`) on resume when it changed. The Kanban create form opens the same picker from a Model value row with the plugin's own list (`GET /api/plugins/kanban/model-options`, no capabilities, so every model gets Minimal to Ultra) and the picker's default entry (`onUseDefault`); when the list is empty it falls back to a typed model name, like the dashboard. The task panel shows a task's override (`model_override`, `provider_override`, `reasoning_effort` on the task row) and applies the last pick once when the picker closes; bulk edit sets or clears only the effort.

## Agents of a chat

`ChatController.subagentsIn(thread)` gives a stored chat its `SubagentRoster` (`lib/src/chat/subagents/`): one row per delegated agent, merged from the chat's `subagent.*` frames (fed from the reply, follow-up and own-turn paths) and `subagent.list`. Rosters are keyed by the stored thread id, follow a rotated id (`_retargetBoundThread`), and are dropped with their thread, on a profile switch, when the owned session is retired, when the activity gate closes and on dispose. The roster reads the list only while something `watch()`es it, the app is in front (`ChatRosterEnvironment` follows the app lifecycle, the activity gate and App Lock), there is a connection and the session is attached on it; it never resumes a session, and a 4001 blocks reads until the connection changes or the session is attached here (`markAttached`, called when the owned binding is established). `SubagentDetailController` is the per-agent detail state (output tail, stop, notes) and works against the roster through `AgentDetailHost`. Goals, summaries, output and notes live in memory only; logs and spans carry fixed words. 

The Activity panel draws the roster: `BoundActivityPanel` lists agents under Now (running) and This session (ended, 20 kept, the rest counted), nested up to three levels. `ActivitySelection` (`activity_selection.dart`) holds the chosen `AgentKey` and whether Stop was asked for; `BoundAgentDetail` builds one `SubagentDetailController` per selection (`subagentsIn` is called once per selection, never per frame) and maps it to the plain `AgentDetailModel` in `agent_detail_mapper.dart`. The panel keeps its sections mounted behind the detail, so Back returns to the same scroll offset; Escape goes back first (the detail takes focus on open, also where an inspector overlays the chat) and closes the inspector only from the list. A selection for another chat or profile is cleared. Stop always goes through `confirmStopAgent`, bound to the chosen agent, and the row's Stop only selects the agent with the stop confirmation open. A note goes out only on Send to agent, as `subagent.steer`; the composer's draft is never touched. Conversation windows hold no session, so their panel is `readOnly`: the detail describes the agent, shows "can't be controlled here", and reads nothing, so a locked or hidden window never reads subagent state. Dialogs opened from the panel close themselves when the agent ends (`dismissWhen`).

**Background programs of a chat.** `ProcessOutputState` (one per thread, scoped to the owned session binding) holds the program cards fed by `agent.terminal.output`/`terminal.close` and, once `process.list` names a program, its command, state, exit code and run time (`applyList`, merged by id; `applyKill` for a `process.kill` answer). The list's `output_tail` and a kill's `output` only seed a card with no text (flagged as cut when Hermes cut them), never replace or extend frame output; only a running listed program without a card gets one, and only into a free or finished card's slot, so it never evicts a running card; a running card the list drops reads as ended; a card the list never named keeps its old wording and no state (`processCardInfo` in `process_card_mapper.dart` returns null). The roster reads `process.list` on the same `watch()` demand, gates, timer and `PollBackoff` as `subagent.list` (one round reads both, a round counts its failures once, and a card frames opened that no read has looked for gets one read of its own), attached-only through `ProgramCards` (implemented by `ChatController`); method-not-found or a 4001 stops program reads for the connection, 5032 (agent still starting) and 5010 are quiet failed reads, and answers after a chat, attachment, connection or account change are dropped. `ProcessStopController` (`subagents/process_stop_controller.dart`, one per card, bound to its `ProcessKey`) sends one `process.kill` through `act` only between `startStop` and `confirmStop`, maps the four statuses (4044 reads as not found), re-reads the list on a lost answer within 10 s and never resends (a re-read showing the program exited claims nothing; the card's own state says what happened), closes the confirmation when the program ends (`confirmationClosed`, for `dismissWhen`) and queues nothing offline. `process.stop` (every program of the server) is not in the transport's allow-list. Only the outcome is logged (`process.stop`), and `process.stop.pressed` has no attribute. In the panel each program card is a `BoundProcessCard` (`activity/bound_process_card.dart`): it maps the card with `processCardInfo` and the controller's phase with `processStopStatusOf`, builds its `ProcessStopController` on the first Stop press (one per card, disposed with it), asks with `confirmStopProgram` bound to that program and closed by `dismissWhen` when it ends, and keeps Stop on screen (inert) while asking, sending or checking. A server without `process.kill` gets one sentence ("This server can't stop programs.") and Stop goes. A `readOnly` panel (a conversation window) passes no roster: its cards show what frames said, with no Stop, no program reads and no controller.

## Checkpoints and context controllers (`lib/src/chat/checkpoints/`, `lib/src/chat/context/`)

`CheckpointsController` and `ContextController` are plain `ChangeNotifier`s, one per chat, built on `CheckpointsTransport`/`ContextTransport` (see gateway.md) and a `ChatActionBridge` of callbacks into the chat (replying, re-read the chat, hold Send, last prompt, composer hand-back). They are not yet owned by `ChatController` or drawn; the widget PRs wire them. Rules that are easy to break:

- A restore or compress starts with `beginRestore`/`beginCompress`, which return a single-use intent that fixes the chat (and checkpoint and file) and sends nothing; only `confirmRestore`/`confirmCompress` send, and only if the controller's scope is still the intent's. A lost answer (`MayHaveHappened`, a throw) ends as "couldn't confirm", re-reads the list or usage and the chat, and sends nothing again; offering the action again takes a new intent.
- A full restore is refused while the chat replies, and holds Send (`holdSend`, `sendHeld`) from confirmation until it settles, a lost answer included. A file restore is allowed mid-reply (`agentWorking`) and only for a restorable path read from the opened checkpoint's changes.
- "Restored N files" uses N only when the changes were read since the last turn ended; the "Before a restore" checkpoint is claimed only for a new hash whose reason names the restored hash; the quoted prompt goes to the composer only when the re-read chat no longer holds it.
- Reads (list, diff, breakdown) run on the owned binding; answers that arrive after a scope change, close or App Lock are dropped; App Lock keeps only the checkpoint count and the percentage. The suggestion shows at 85% or more, idle, not for a local estimate below 95, and after Not now or a compress only once the context fell below 60% and refilled.
- Telemetry goes through `ActionTelemetry`: fixed names, outcomes, flags and count buckets; the focus, file names, hashes, reasons, quoted prompt and server text never reach a span, breadcrumb or log (tests check this).
