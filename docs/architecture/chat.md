# Chat

**Chat** (`lib/src/chat/`, built on `flutter_chat_ui`).

- `ChatController` keeps shared state, its public instance API, and lifecycle in `chat_controller.dart`. Private library parts group history, commands, durable queues, sending, streaming, session bindings/state, progress, connectors, billing, request answers, and system surfaces. `ChatScreen` owns resources and lifecycle in `chat_screen.dart`, with private parts for layout, composer, recipients, sharing, navigation, external openings, and conversation windows. Keep feature changes in the corresponding part. Public controller methods delegate explicitly to private extensions so callers and subclasses retain the same instance API. Parts share their root library's imports and private state; they are not independently owned controllers.
- Branching: every finished reply's action bar has "Branch in new chat" (`MessageActions.onBranch`, offered only by `ChatScreen` through `boundChatThreadView(branchable: true)`), and the Mac thread menu has "Branch in New Chat" (`ThreadAction.branch`, through `ThreadHousekeeping.branch`). `ChatController.branch` counts the prompts Hermes holds after the chosen message (`_promptsAfter`: commands shown only here and failed prompts do not count), and `ChatTransport.branchThread` sends `session.branch_whole` (`session.branch` on an older gateway) on the resumed chat, then `session.undo` that many times on the copy. Hermes' own `count` is not used: it counts stored rows with text, which the app's messages cannot be mapped to. A copy whose undo failed (`BranchIncomplete`) is deleted again; a gateway without either method gets "can't branch". The copy holds the prompts and replies with text, not the tool calls, and opens through `open(fetchMissing: true)`. Breadcrumb `chat.branch` (`outcome`, `from`).
- History: a chat's first page is read when it opens (`_readFirstPage`, `chat_controller_history.dart`). A send never waits for it: the prompt, reply placeholder, Live Activity and network send happen on tap. When the page lands in a chat that already holds rows, `_mergedWithPage` puts history above them and shows a turn both hold once, matching a held prompt to a page row only by its receipt (`prompt.submit`'s `user_row_id`, the same `messages.id` as the REST row's `id`). The held copy wins unless it failed here while Hermes stored a final answer (an assistant row with text and no tool calls). A receipt that arrives after the page removes the page's copy of that prompt (`_dropStoredCopy`). A prompt that never gets a receipt (a compute-host turn, `turn_isolation`, answers `prompt.submit` without `user_row_id`) cannot be told from a stored row with the same words, so it can show twice, and branching from a reply above it then counts it twice, until the chat is read again (`refreshThread`). Rows only this app has (command lines, review notes, stops) stay. Load older drops a page whose chat was re-read meanwhile. Listing the chats again for the profile already in view (`loadThreads`) keeps the threads a send is running in, with their queues and the selection, like the refresh after a send does. What those threads' turns stand on carries over (queue review, suspension and settle state, owned-session and session-state records, and a protected queued send's epoch and generation, the `kept` block of `_loadThreads`), so a queued prompt still lands in the transcript when the server accepts it and a prompt queued behind the turn still sends once it ends. A thread whose send ended while the list was read is kept too. A running protected send is marked current from the moment the read starts, so an acceptance that lands mid-read still inserts its prompt. Kept threads keep their history paging cursor (`_olderRows`), and one whose first page was cut off by the read is read again; their owned-session binding is not carried, since the usage meter binds with it. Known gaps: a prompt queued behind the turn whose enqueue straddles the end of the read fails with the draft kept (`_enqueueProtected` checks `_queueEpoch`), and a kept thread whose send ended during the read shows its local copy, not the server's newer title or pin state, until the next list read. A queued prompt whose dispatch starts just before the commit (it captures `_queueEpoch` before reading the store) can stay queued until the next send or enqueue instead of sending when the turn ends. On a profile switch with a protected send running, the send stays current until the switch commits, so it may still submit to the profile being left. A command that re-reads the chat (`_refreshAfterSlash`, after `/undo` or a Bot Chat compaction) merges the same way, over the rows sent or run here only: stored rows come from the page, so an undone turn goes, while a reply still streaming and command lines stay. A settled turn sent here whose row the page lacks goes too (undone, or older than the page, which Load older brings back); one without a receipt goes when the page holds a prompt with the same words. A turn whose receipt lands after the page was read and which ends at once can vanish from view until the chat is read again.
- Domain messages (`chat_models.dart`) map to flyer messages in `chat_message_mapper.dart`. `chat_controller_sync.dart` applies before/after diffs to the `InMemoryChatController`. Custom message kinds and cards (tool calls, approval and clarify requests) live in `chat_message_kinds.dart` and `widgets/`. Tool calls follow assistant-ui: `tool.generating`, `tool.start` and `tool.complete` are matched by `tool_id` (name as fallback) into `ToolCall`s with args, result data, diff and timing; a run of calls is one `ToolCallGroup`; `widgets/tool_call_bodies.dart` gives terminal, web search, todo, diff and `memory` calls their own view, with `ToolCallCard`'s input and result as the fallback. The memory body (`widgets/memory_tool_body.dart`, outcome from `memory/memory_tool_outcome.dart`) reads `tool.complete`'s result as saved, staged (waiting for approval) or full; a full file is a `ToolCallStatus.warning`, not a failure. A staged card's Approve and Reject run `/memory approve|reject <id>` through `ChatTransport.runSlashCommand` on the chat's stored thread (`ChatController.memoryDecisionsIn`, `memory/memory_decisions.dart`; offered through `MemoryDecisionsScope`, so the catalog shows no buttons), and the Activity panel's background-review notes link to `MemoryDestination` for the chat's profile; an approval Hermes raises while a call runs is bound to it in `chat_reply.dart` and shown inside that call's card. The design for agent input requests is in `openspec/changes/archive/2026-09-19-agent-input-requests/`. Text Hermes writes before a tool call, or checkpoints mid-turn with a `message.interim` event, is sealed into `ChatMessage.sealedProse` (`chat_reply.dart`) instead of being folded into the trailing `content`, so the mapper can render it where it was actually written and `message.complete` never overwrites it.
- Agent activity outside the transcript is sorted into tiers (`activity/activity_tier.dart`: Needs you, Working, For reference; `openspec/changes/chat-activity-*`). The Activity panel (`activity/widgets/activity_panel.dart`, filled by `BoundActivityPanel`) lists Now (the Bot screen card first, see Bot Screen, then working items), Plan and This session; the header's Activity button (a toolbar button on a Mac, View > Inspector ⌥⌘I, routed to a key conversation window too) opens it as an inspector (`widgets/inspector_layout.dart`, shared with Kanban: docked from 760 pt, over the chat below) or, on a phone, a detent sheet. For reference items (usage, side answers, notices, the acknowledgement, idle billing, settled and connection-wide connector activity) live only there; the strip above the transcript keeps Working and Needs-you items, and an empty or unsupported state draws nothing. Breadcrumbs `chat.activity.opened` (`surface`, `source`) and `chat.activity.closed`.
- The composer is Hermes' own `ChatComposer` (`widgets/chat_composer.dart`), not flutter_chat_ui's `Composer`: a card with the field on top and attach, the model pill, the dictation microphone and send below it. `buildChatComposer` puts it in a `Positioned` that stays a direct child of the `Chat` stack and reports its height to the package's `ComposerHeightNotifier`, as the package's own composer does.
- The welcome view's starter prompts (`starter_prompts.dart`) come from the active profile's context: a failed cron job, a blocked or in-review Kanban task, the latest chat and the most-used skill, one each, padded with generic prompts. `StarterContextLoader` reads them in parallel, leaves out a source that fails or takes more than 5 s, and `ChatScreen` reloads it for another profile or after five minutes. Job, task and skill prompts go into the composer; a chat prompt opens that chat.
- The composer's model pill (`lib/src/models/widgets/composer_model_pill.dart`) picks a model and reasoning effort per chat from `GET /api/model/options` (`HermesModelsRepository`, loaded with each profile's threads, hidden when that fails). The pick lives on `ChatThread.modelChoice` and goes out with `ChatTransport.send`: as `session.create` overrides for a new chat, as session-scoped `config.set` (`model`, `reasoning`) on resume when it changed. Nothing is written to the profile's config; that is the Profiles screen's job, which sets a profile's default model (no effort, Hermes keeps none for the main model) with `POST /api/model/set?profile=<name>` (scope `main`; when Hermes answers `confirm_required` for an expensive model the screen asks with a confirm dialog and resends with `confirm_expensive_model`) through the same picker (`showModelPicker(withEffort: false)`). The Kanban create form opens the same picker from a Model value row with the plugin's own list (`GET /api/plugins/kanban/model-options`, no capabilities, so every model gets Minimal to Ultra) and the picker's default entry (`onUseDefault`); when the list is empty it falls back to a typed model name, like the dashboard. The task panel shows a task's override (`model_override`, `provider_override`, `reasoning_effort` on the task row) and applies the last pick once when the picker closes; bulk edit sets or clears only the effort.
- On macOS the sidebar is a source list (`lib/src/macos/mac_source_list.dart`): 28 pt destination rows (Kanban captioned "All profiles") and threads under recency sections (`thread_sections.dart`; Pinned, Today, Yesterday, Previous 7/30 days, Older) whose folded state `MacSidebarController.sections` keeps in shared preferences. `MacThreadRow` shows Archive and More on hover; More and a right-click open `macThreadMenuItems`, built on `AdaptiveMenuItem` (shortcut text, destructive) and `AdaptiveMenuController.open(at:)`. Copy Transcript copies Markdown and reads a thread's unloaded pages through `ThreadHousekeeping.history`.
- On macOS search and New Chat live in the toolbar (`widgets/mac_chat_toolbar.dart`, on the shared `MacToolbar`): `MacToolbarSearchField` (a button below a 1000 pt window), ⌘F from Edit > Find (`MacCommand.find`, offered by `ChatScreen`'s `MacCommandScope`), Escape to end. While `ThreadSearch.active` the sidebar shows `MacSearchResults` (Chats/Messages, recent searches) with a This profile / All profiles switch; `ChatController._searchAllProfiles` fans out one search per profile and skips a failing one. Below 760 pt (`isMacCompact`) `MacSplitView` opens the sidebar over the content (`MacSidebarController.toggle(compact: true)`, `closeOverlay`), and `ChatScreen`/`AppShell` keep the Mac split view at every width.
- The sidebar's search field (`widgets/thread_search_view.dart`) searches the active profile's sessions with `GET /api/sessions/search` (`HermesChatRepository.searchThreads`; FTS5 snippets mark matches with `>>>`/`<<<`). `ThreadSearch`, owned by `ChatController`, debounces typing by 300 ms, keeps only the latest query's answer and is cleared on a profile switch; while the field holds text the results replace the thread list. A result opens through `ChatController.open(fetchMissing: true)`, so a chat older than the loaded pages is fetched first.
- On macOS an attachment is a Finder item (`widgets/quick_look_target.dart`): a click selects it (the target owns a `FocusNode`, so a text field taking focus ends the selection and keeps its spaces), a double-click (the system's interval, press to press) opens it, Space toggles the system Quick Look panel and a secondary click offers Quick Look, Open and Save…. Its click recognizer never claims the arena and ignores a press that moved as far as a drag-out starts after, so `DragOut` and inner buttons are unaffected. `AttachmentCard`, `AttachmentThumbnail` and the Kanban attachment rows wrap themselves in it; elsewhere it is its child and a click still opens. Files are staged into `MediaStore` first (`stage`, `stageBytes`, `stageCopy`: the shared `hermes_media` cache, safe-name rule and sign-out `clear()`, which also closes the panel; a 24 h `sweep` runs at launch, after `wipeSecretCopies`, which deletes every copy staged under the `fs-secret:` key prefix, i.e. a Files-page copy of a secret-looking file that an app killed on the page never deleted), and `QuickLook` (`media/quick_look.dart`, channel `hermes_app/quick_look`, `macos/Runner/QuickLookPanel.swift`; a `QuickLookResponder` after each engine's Flutter view controller in the responder chain, main window and conversation windows alike, takes control of the panel, and Space or Escape close it while it is key) shows them. No menu chord is involved: Space and Enter are handled only while the target itself holds the focus.
- With no repository, `ChatScreen` falls back to `mock_chat_data.dart`. A canned reply is used when there is no transport.
- Known limit of `MediaStore.saveFile` (the Files page's Save): `PlatformMediaActions.saveFile` still reads the file into memory, because file_picker 13 saves from bytes on every platform, so it refuses a file above 32 MB (`kMaxSaveBytes`) with `SaveTooLargeException`, which `FilesController` shows as `FilesFailure.saveUnavailable` (no path or name in it). This deviates from the server-files spec ("SHALL NOT read it into memory"). A path-based save (`file_selector` on desktop, a document-export channel on mobile) is needed before the widget PR; until then a larger file can be opened with Open with… or shared.

## Agents of a chat

`ChatController.subagentsIn(thread)` gives a stored chat its `SubagentRoster` (`lib/src/chat/subagents/`): one row per delegated agent, merged from the chat's `subagent.*` frames (fed from the reply, follow-up and own-turn paths) and `subagent.list`. Rosters are keyed by the stored thread id, follow a rotated id (`_retargetBoundThread`), and are dropped with their thread, on a profile switch, when the owned session is retired, when the activity gate closes and on dispose. The roster reads the list only while something `watch()`es it, the app is in front (`ChatRosterEnvironment` follows the app lifecycle, the activity gate and App Lock), there is a connection and the session is attached on it; it never resumes a session, and a 4001 blocks reads until the connection changes or the session is attached here (`markAttached`, called when the owned binding is established). `SubagentDetailController` is the per-agent detail state (output tail, stop, notes) and works against the roster through `AgentDetailHost`. Goals, summaries, output and notes live in memory only; logs and spans carry fixed words. The detail, panel and widgets are not wired yet.
