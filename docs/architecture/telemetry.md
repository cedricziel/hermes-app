# Telemetry

**Telemetry** (`lib/src/telemetry/`). OpenTelemetry to SignalDB through the `flutter_otel` package and its `dart_otel_*` siblings from pub.dev (source: `cedricziel/flutter-otel`, ours — file upstream PRs there rather than working around gaps locally). It is off unless `OTEL_EXPORTER_OTLP_ENDPOINT` is passed via `--dart-define`. When off, no SDK exists and no `traceparent` header is added. Telemetry code must never break the app: every call into the logger or tracer from app code sits in a catch that swallows its own failure (`_quiet`/`_log` wrappers, or a `try` around the call), so a broken exporter changes nothing. Spans, request logs and `AuthController` events describe the Hermes server they belong to with `hermes.*` attributes (version, install ID, auth, gateway mode, profile count, health) read from its `/api/status` answer (`telemetry/hermes_server_attributes.dart`): `Telemetry.forConnection` builds an interceptor and event logger per connection, `AuthController` swaps them when a probe succeeds and drops them when a connect starts or on Change Server, so a request keeps the server it was sent to. They are never resource attributes, since one app can talk to several servers. A burst of requests failing with the same connection-level `error.type` (`connectionError`, a timeout, `unknown`; never `badResponse`) logs its first record and, 10 s later, one summary with `log.repeat_count` (`telemetry/burst_deduping_logger.dart`); every request keeps its span. `SuspensionMarkingTracer` (`telemetry/suspension_marking_tracer.dart`) marks an HTTP or gateway span that spans a pause of the app, or the return from one, with `app.suspended: true`, since Dart timers stop while the app is suspended and such a span measures the time away. The minute polls (`ScheduleWatcher`, `AgentMessageWatcher`, `SchedulesController`) and the chat's 5 s running-chats poll skip ticks after failures (`network/poll_backoff.dart`: `2^n - 1` ticks after `n` failures, capped); a return to the front or a restarted poll starts without the wait (the watchers also look at once). Breadcrumbs don't get them, except `server.connected` with the version. The connection's telemetry travels with `HermesRepositories` (`telemetry`, captured in `forAuth`): screens build a new gateway or Kanban tracer for each socket from it (`telemetry.gateway()`, `.kanban()`; a tracer links messages to the last upgrade it traced, so two sockets never share one), and the gateway transport, Kanban board, plugin and skills screens log through its `events`. The watch bridge and `TokenStore` keep the root logger. The gateway transport logs `gateway.reconnect`, `gateway.turn_settled`, `gateway.event_unmapped` (a frame type the app shows nothing for, once per type per connection) and `gateway.send_failed` (the step a send stopped at and the kind of error) through the `AppEventLogger`, never with message text. Uncaught Flutter and async errors are logged with full message, stack trace and recent breadcrumbs via `flutter_otel`'s `installCrashReporting`/`BreadcrumbTrail`, wired up in `Telemetry.logUncaughtErrors`/`Telemetry.events`: unlike the package's privacy-preserving `installUncaughtErrorLogging` (type only, for an arbitrary OTLP endpoint), the crash reporter keeps full detail because the endpoint here is always the operator's own self-hosted SignalDB. A recurring error is logged once and then summarized with a repeat count, and message and stack are trimmed to fit SignalDB's attribute size limit (details in `openspec/specs/telemetry/spec.md`). The crash record's breadcrumbs also say what the user was doing: `Breadcrumbs` (`telemetry/breadcrumbs.dart`, provided next to `AppEventLogger`; `Breadcrumbs.none` when telemetry is off or no provider is above) adds a crumb to the same trail without exporting a log record. `AppShell` records `nav.destination` and `app.lifecycle` (resumed, paused), `ChatController` records `chat.threads.loaded` (`switched`, `count`), `chat.thread.selected|new|closed`, `chat.open.requested|failed` and `chat.reply.started|ended` (`outcome`), and `ConversationWindows` records `window.opened|closed|key`; the gateway's `gateway.*` events are crumbs already, so they are not repeated. Crumbs hold fixed names, counts, flags and outcomes only: never text, titles, profile names, server addresses or ids. The trail keeps the last 40.

## Catching errors

`avoid_catches_without_on_clauses` is on, so a handler names a type, and `on Object` is the default for a boundary that must not let a failure through. The rule for new code, from the P.5 audit of the broad catches:

- **Catch what you expect.** Narrow to the type the call throws: `DioException` and the domain exception for a request, `FormatException` for parsing, `PlatformException` (and `MissingPluginException`) for a plugin or channel, `FileSystemException` for storage, `Exception` when any failed request will do. A bug (`Error`: `TypeError`, `RangeError`, `ArgumentError`, `AssertionError`, a `StateError` that is one) then reaches the zone and the crash reporter instead of being turned into a fallback.
- **A boundary that has to keep going keeps `on Object`** (a screen state that must leave its spinner, a background entry point, a plugin or telemetry call, lenient parsing of rows or third-party JSON, cleanup in `dispose`). Say what the failure becomes. In a UI or controller handler call `reportBug(error, stack, 'a fixed name')` (`telemetry/report_bug.dart`) before the fallback: it hands an `Error` to `FlutterError.reportError`, where the crash reporter listens, and ignores an `Exception`. The name is a fixed place, never text, ids, profile names or server addresses.
- **An empty handler needs a reason** in a comment when the surrounding code does not give one, and a failure the user would otherwise not notice is reported once by error type (`events('area.what_failed', {'error_type': '${error.runtimeType}'})`, de-duplicated per type until a success) or shown in the screen's error state. Never log `$error`: print `error.runtimeType`.
- **Do not throw an `Error` for an ordinary condition.** `reportBug` and a narrowed catch both read an `Error` as a bug. A missing session token, an unknown active profile, an unsupported server or a cancelled operation is an `Exception` of its own (`GatewayCredentialUnavailable`, `McpProfileUnknown`). Bot Mode, voice and the chat's epoch checks still use `StateError` for such refusals; until those become exceptions their handlers stay broad and do not call `reportBug`.
- **A test fake that stands in for a failed request throws an `Exception`** (`GatewayConnectionClosed`, `DioException`, `PlatformException`), not a `StateError`: a `StateError` is reported as a bug and fails the test. A test of a bug captures `FlutterError.onError`.

No further lint is proposed: `avoid_catches_without_on_clauses` and `only_throw_errors` are already on, and `empty_catches` (core lints) lets a commented empty handler through. The two things left, "a catch-all without `reportBug`" and "an `Error` thrown for an ordinary condition", are not expressible as a stock lint without flagging the several hundred correct boundaries; they stay a review rule.
