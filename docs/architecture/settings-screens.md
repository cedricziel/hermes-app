# Settings screens: plugins, MCP servers, helper models, model providers

**Settings pages** (`lib/src/widgets/settings_scaffold.dart`, `grouped_list.dart`, `settings_search_field.dart`). Skills, Messaging, Plugins, MCP servers and Helper models share one chrome. `SettingsScaffold` takes a title, a subtitle (profile · count), `SettingsBarAction`s (a button, or `.menu` with `AdaptiveMenuItem`s that act through `onTap`), optional tabs and a `SettingsSearch`, and draws the platform's bar: iOS a 44 pt bar with the title centered, macOS the `MacToolbar` with back, tabs (`MacToolbarTabs`), search and actions in it, Material a 56 pt bar with pill tabs (`PillSegmentedControl`, which `AdaptiveTabBar` now draws on Material). There is no floating button; adding is a bar action. Lists are `GroupedListView` of `GroupedSection`s (header, footer, inset separators) holding `GroupedRow`s (title, inline meta, a subtitle of one line unless `subtitleMaxLines` allows more, warning and error lines that wrap, a muted value of at most half the row and chevron, or a trailing widget; above the default text size a value that does not fit beside the title stacks under it, and only a row with `wrapWhenStacked` lets its title and subtitle wrap in full there, otherwise they keep `titleMaxLines` and `subtitleMaxLines`) and `GroupedSwitchRow`s; `GroupedMetrics.of(context)` has each platform's sizes.

**Shared widgets.** `AppBanner` (`lib/src/widgets/app_banner.dart`, tones `AppBannerTone`: success, warning, error, neutral) is the one tinted note box with an icon, title, optional detail and action. It is a polite live region, and status is told by its icon and the words of its title. In the wave 4 design records "Banner" and "the shared Banner" mean `AppBanner`; the class is not called `Banner` because Material already has one. `DestructiveTintButton` (`destructive_tint_button.dart`) is the destructive action drawn tinted in the error colour with an outline, never filled (44 pt on iOS, 48 dp on Material, 28 pt on a Mac; busy and disabled states), so a screen's one filled button stays the safe one. `LoadingSkeleton` and `CommandRow` (a copyable shell command) live here too; server care builds on them. `GroupedActionRow` (`grouped_action_row.dart`) is a tappable action row of a grouped section with an optional muted `subtitle` under the title and a status slot (working, done, failed, warning); `OutputLinesTile` (`output_lines_tile.dart`) is a closed-by-default disclosure of selectable monospace command output, its label passed in by the caller (`UpdateDetailsDisclosure` is a thin user of it).

**Dialogs and sheets** (`lib/src/theme/hermes_theme.dart`, `lib/src/widgets/adaptive_dialog.dart`, `adaptive_sheet.dart`, `grouped_dialog.dart`). Every Material dialog, bottom sheet and date or time picker takes its look from the theme, never from a per-call colour: in dark, `dialogTheme`, `bottomSheetTheme`, `datePickerTheme` and `timePickerTheme` give a zinc900 surface, a 1 px zinc500 edge (`hermesOverlayEdge`, also used by `GroupedDialog` and the Kanban sheets, whose shapes are their own) and, for dialogs and sheets, a 0.6 scrim, mirrored as `--h-overlay-surface`, `--h-overlay-edge` and `--h-scrim` in `design/web/src/styles/tokens.css`. The edge, not the surface, carries the boundary: surface and scrimmed backdrop are both near black, and only zinc500 stands 3:1 off that backdrop (4.2:1; zinc600 gives 2.7). Two traps. Zinc800 is `colorScheme.outline` and `surfaceContainerHighest`, so as a surface it hides the idle outline of `AppDialogTextField` and the unselected effort segments of `ModelPicker` (#1003 had to take that back). Zinc900 is `outlineVariant` in dark, so a hairline inside an overlay must use `outline`, not `outlineVariant`, or it vanishes (the model picker's effort divider and the platform hint sheet's box and rows do). A `GroupedSection` inside an overlay fills with `surface` (zinc950), a deliberate sunken well one step darker than the sheet, with its own zinc900 dividers. `showKanbanDetentSheet` gives `showModalBottomSheet` a plain shape because `KanbanDetentSheet` draws the one visible edge; the theme's shape would paint a second one round the transparent layer. `CupertinoAlertDialog` keeps the system look, but on macOS `showAppDialog` reads `DialogTheme.barrierColor`, so a dark Mac alert gets the 0.6 scrim; iOS keeps the system barrier. `test/dialog_edge_test.dart` pins the edge contrast, both controls, the hairlines and the single Kanban edge. Use cases: `widgetbook/dialogs_use_cases.dart`, "Overlay surface".

**Secret fields** (every screen that takes a key, token or password). Typed secrets are obscured by default and have a Show/Hide control (a 44 pt touch target on iOS and iPadOS, 48 dp on Android, a standard Mac button) labelled "Show key" / "Hide key". Under the field a muted line, announced to screen readers, reads "<N> characters entered"; the count is never stored. A shown value is hidden again when the lifecycle leaves `resumed` (`inactive` included), when a check or save starts, after any failed save, and when the form closes; the shown state is never persisted or restored. Going inactive or to the background only hides a shown value; the typed text stays. The typed text is cleared only when App Lock locks the app, when the form closes, and when the answer to a save is lost (the value may already be saved, so the field is cleared and the message asks to paste it again). After a plain failed save the typed value stays in the field, hidden, so it can be edited. A saved value is never revealed (no `POST /api/env/reveal`). The shared widget is `SecretFieldRow` (`lib/src/widgets/secret_field_row.dart`), built on `GroupedTextFieldRow` with autocorrect, suggestions, keyboard learning, smart dashes and quotes and autofill off, the visible-password keyboard on Android, one line and no `restorationId`; its Widgetbook use cases are hidden, shown, hidden again on going inactive, after a failed save, and after a lost answer (cleared). Model providers (`openspec/changes/provider-setup`) and toolsets use it; a new feature that takes a secret points here instead of restating the rule.

**Plugins** (`lib/src/plugins/`). The chat sidebar's Plugins row opens a screen with three tabs. Installed lists the dashboard's agent plugins (`GET /api/dashboard/plugins/hub`) and enables, disables, updates, removes and hides them; it does not list Kanban or Achievements, which the hub reports apart as dashboard-only extensions. Catalog (`GET /api/dashboard/plugins/catalog`, loaded when first opened) searches the curated catalog and installs from it, and installs from a Git URL behind an unreviewed-code warning; the typed URL can hold a token, so it is never logged or kept. Providers (the `providers` object of the same hub, loaded when first opened) picks the memory provider and context engine: only providers the server reports as ready can be picked, the rest list what they need on the server (the app runs nothing), and Save sends only the fields that changed to `PUT /api/dashboard/plugin-providers`. `PluginsController`, `CatalogController` and `ProvidersController` hold the state. Details are a bottom sheet below 900 px and a pane at 900 px or wider. The screen shows the chat's profile (or the one picked on the Mac Profiles page): `HermesPluginManagerRepository.forProfile` sends `profile` to the hub, visibility and provider routes, but install, enable, disable, update and remove take none, so Hermes runs them for the dashboard's own profile. The generated client puts a plugin's name into the path unencoded, so the repository encodes it. An install can outlast the client's 30 s timeout, so a timeout is reported as "still installing", not as a failure. `PluginsScreen.initialTab` (`PluginsTab`) picks the tab shown first; the Memory screen's provider row opens Providers, and the other tabs stay unrequested.

**MCP servers** (`lib/src/mcp/`). List, switch, test and remove the MCP servers of the active profile, opened from the chat sidebar. `HermesMcpRepository` wraps the generated MCP calls and parses leniently. `McpServersController` holds one visit's state (the profile learned first, the list, the test results), and `McpServersScreen` and `McpServerDetail` render it, side by side from 900 logical pixels. The bar's "+" (Add server) is a menu: "Browse the catalog" opens `McpCatalogScreen` (Hermes' approved catalog, searched and filtered on the device; `McpCatalogController`), where an entry that is not installed opens `McpInstallPanel` (a bottom sheet, or the right-hand pane from 900 logical pixels) and an installed one opens its server. `McpInstallController` sends the install and, for entries Hermes builds on the server, polls `GET /api/actions/{name}/status`. Credentials live only in the panel's text fields and go into the install request. `McpSignInScreen` waits while the user approves an OAuth sign-in in the browser (`McpServersController.startSignIn`, then polling `GET /api/mcp/oauth/flows/{id}`); Hermes keeps the token and the app never sees the code. "Add a custom server" opens `McpAddServerScreen` (remote or command server) and the overflow menu's "Edit as JSON" opens `McpJsonEditorScreen`, which loads the whole map from `GET /api/config` (the servers route is lossy) and saves it with `PUT /api/mcp/servers`. A command server makes the Hermes host run a program, so `McpServersController.addServer` and `replaceServers` take a required `McpReviewer` and send nothing until it confirms; the screens pass `showMcpCommandReview` (bottom sheet, dialog from 900 px). Bearer tokens, environment values and the editor's text stay in screen state and are cleared after the request.

**Helper models** (`lib/src/settings/helper_models_screen.dart`). The chat sidebar's "Helper models" row lists the chat profile's auxiliary task slots (`GET /api/model/auxiliary`) and opens the shared `showModelPicker` for one, with its "Use the profile's default" entry. The pick is saved once, when the picker closes, with `POST /api/model/set` (`scope: auxiliary`; the default entry sends `provider: auto`, empty model, which Hermes runs on the main model). Hermes may answer `confirm_required` for an expensive model; the screen asks and resends with `confirm_expensive_model`. Changes apply to new sessions only. Below the slots, a "Mixture of agents" section lists the default preset's advisors and aggregator (`GET /api/model/moa`, `MoaSetup`); a change sends the whole config back with `PUT /api/model/moa`, only that slot edited, and keeps the MoA rows closed until it answers. The section is left out when MoA cannot be read.

**Model providers** (`lib/src/providers/`; roadmap 4.1, `openspec/changes/provider-setup`). One screen per profile: `ProvidersScreen` (`providers_screen.dart`) over `ProviderSetupController`, which holds the state and every write; the screen words it, owns the dialogs and sheets and never builds a widget inline (the plain-model widgets are in `widgets/`, built from the controllers' state by `provider_view_mapper.dart`). `HermesRepositories.providers` builds the `ProvidersRepository`.
- Routes and profile scope. Opened from the chat's sidebar and compact drawer ("Model providers", before "Helper models", only while the chat's model options did not answer 404) for the chat's profile, and from the Mac Profiles page (`ProfileSection.providers`, "N connected") for the selected profile. Every request carries that profile (none on a server without profiles). The chat reads its model options again (`ChatController.refreshModelOptions`) whenever the controller's `changes` moves and when the screen closes. `ProvidersScreen.focus` (`ProvidersFocus.add()` or `.provider(id)`) says where it starts once its first read answered: "Add a provider" scrolled into view, or one provider (its detail when connected, the key form, sign-in or server command to connect it when not). Entry points record `providers.opened` with `source` (`sidebar`, `drawer`, `profiles`, and from the chat's first-run entry points `welcome`, `composer`, `reply`; see chat.md), starting a connect `providers.connect.started` with `method`, a confirmed removal `providers.remove.confirmed` with `kind`: fixed words only, never a provider, address, model or profile. "Use an account instead" on a key form records `method: server`, so one attempt can leave two `providers.connect.started` crumbs (`key`, then `server`).
- Layout. List beside detail from 900 pt (`isWideLayout`, so a full-screen iPad too; a Mac from `kMacSplitBreakpoint`), else a pushed `ProviderDetailPage`. Forms go through `showProviderSheet` (`provider_flow.dart`): a page sheet on iOS phones, a full-screen dialog on Android phones, a dialog on macOS and wide windows, never a bottom sheet on macOS (`showAdaptiveSheet` is used for all but the Android phone). Escape closes a form and Return does its primary action on desktop. Pull to refresh only on iOS and Android; a Mac has Command R.
- Secrets. Every key field follows the secret field rule above. The sheets own the `TextEditingController`s (`ProviderKeySheet`, `ProviderEndpointSheet`), clear them when App Lock locks (`SecretFieldsLock`), when the form saves and when it closes, and never persist or restore them. A saved key is never revealed (no `POST /api/env/reveal`): a row shows only its last four characters. Signing out or changing the server closes the screen and everything over it; the controller then stops following sign-ins without cancelling them.
- Sheets and steps. A sheet pops only while it is still the top route (`popIfCurrent`), so Cancel, Escape, Keep and Not now never close the screen under them. A default-model step that begins while something else is over the screen (the model picker, "Stop signing in?", a pushed detail) waits and opens once the screen is current again. App Lock locking clears typed keys; an endpoint save waiting on "Send the key unencrypted?" is dropped if the key was cleared meanwhile. In a Mac dialog the bar leads with "Cancel" (`SettingsScaffold.macCancel`); the Profiles page hides its Model providers row on a server whose model options answer 404.
- Links Hermes sends (key page, sign-in page) are opened only after `openableLink` (absolute `https`, or `http` to a local host); otherwise the button is not drawn. Endpoint ids and session ids are percent-encoded by the repository.
- Shared widgets changed with the forms: `GroupedTextFieldRow` stacks its label above the field at large text on Apple platforms and takes a `focusNode`; `CommandRow.copyBelowAtLargeText` puts Copy under the command at large text.

**Tools widgets** (`lib/src/tools/widgets/`, `lib/src/tools/toolset_copy.dart`). Plain-model pieces for the Tools screens, each with Widgetbook use cases in `widgetbook/tools_use_cases.dart`: `ToolsetRow` (`ToolsetRowView`; the text opens the details, the switch is its own control; saving, lost-answer, unconfirmed and error lines), `ToolsetHeader`, `RiskNote` (one semantics element), `StatusChip` (`ToolsStatus`: icon and words, never colour alone), `ToolsListFooter` and `ToolsSwitch` (the switch with its 44 pt / 48 dp / 28 pt target and the "<name>, on, saving" label). At a text scale of 2 or more the switch moves to its own line with "On" or "Off" before it. They build on `GroupedRow` (`details`, `titleWeight` and `trailingBelow`) and `GroupedSwitch`. `toolset_copy.dart` holds the per-toolset sentences, labels, risk titles and the confirm-question text as pure functions over `AppLocalizations`.

**Tools widgets** (`lib/src/tools/widgets/`, `lib/src/tools/toolset_copy.dart`). Plain-model pieces for the Tools screens, each with Widgetbook use cases in `widgetbook/tools_use_cases.dart`: `ToolsetRow` (`ToolsetRowView`; the text opens the details, the switch is its own control; saving, lost-answer, unconfirmed and error lines), `ToolsetHeader`, `RiskNote` (one semantics element), `StatusChip` (`ToolsStatus`: icon and words, never colour alone), `ToolsListFooter` and `ToolsSwitch` (the switch with its 44 pt / 48 dp / 28 pt target and the "<name>, on, saving" label). At a text scale of 2 or more the switch moves to its own line with "On" or "Off" before it. They build on `GroupedRow` (`details`, `titleWeight` and `trailingBelow`) and `GroupedSwitch`. `toolset_copy.dart` holds the per-toolset sentences, labels, risk titles and the confirm-question text as pure functions over `AppLocalizations`. The setup pieces (use cases in `widgetbook/tools_setup_use_cases.dart`): `ProviderRow` (radio row with the badge as an outlined tag, status chip and notes; Apple check mark in the link colour, Material leading radio; also for terminal backends) with `ToolsLoadingRow`, `ToolsFailureRow` and `ToolsNothingRow` for the set-up and backend states; `ToolsetKeyForm` (composed over `SecretFieldRow`, owns no secret field; the caller owns each field's controller and the phase, and Save is the screen's one filled button); `InstallProgress` and `ToolsInstallButton` (the running body, log lines and spinner are `lib/src/widgets/install_parts.dart`, shared with the Bot Screen install card; the button is filled exactly when the provider needs setup); `ReadinessRow`, `ReadinessSection` and `readinessItems` for Computer use; `ToolsetModelSheet`; `ToolsetConfirmDialog` with `showToolsetConfirmation` (the platform alert, Cancel first and default, the confirming action plain; Material shows two text buttons); and `ToolsDifferenceSheet`. Sheets open through `showAdaptiveSheet`, so a Mac and a wide window get a dialog, not an anchored popover. Buttons use `toolsButtonStyle` (44 pt, 48 dp, 28 pt on a Mac at standard density).

**Tools controllers** (`lib/src/tools/`, plain Dart, no text). `ToolsAvailability` reads the list on connect and resume for the chat's profile (`404`/`405` hide Tools; a failed read keeps the last answer; a gone profile is reported, not hidden; seeds only the profile it read). `ToolsetSetupController` also picks providers (a `needs_nous_auth` answer is a flag; `web` sends `capability` for search and extract) and models (`image_gen` and `video_gen` only; only an id the catalog lists is sent); one write at a time. `ToolsetInstalls` is the connection's one `tools-post-setup` follower: it is started only after the caller's confirmation (`startConfirmed`), follows the shared status log every 2 s, keeps the last six lines (never logged), treats a missing exit code, a replaced process or 22 minutes without an end as unknown, and ends in `requestReread`, never in "Installed" from the log. `TerminalBackendsController` sends nothing for `local` until `confirmLocal` says yes. `ComputerUseController` owns the `computer-use-grant` follow (separate slot, shared `ActionFollower`; leaving the screen drops it and the status read on return shows the result) and asks `confirmGrant` first. For every pick, a lost answer is checked by a re-read of at most 10 s and never sent again; spans (`tools.setup` with `step`, `tools.terminal_backend`, `tools.computer_use` with `action`) and the `tools.setup_outcome` and `tools.availability` events carry `step`, `action` and `outcome` only.

**Tools screen** (`lib/src/tools/tools_screen.dart`, `tools_row_mapping.dart`). `ToolsScreen` is on `SettingsScaffold` and `GroupedListView`, titled "Tools" with "<profile> · <N> on", sections Needs setup, On and Off (empty ones left out) and the `ToolsListFooter`. `toolsetRowView` and `toolsetDetailView` are pure mappers from a `Toolset` and its `ToolsRowState` to the widgets' plain values: the app's own name and sentence for a built-in, the server's label and description for a plugin's toolset (no risk line), the risk line at both levels of the risk table, the action count, the error text per kind (Hermes' own text for a refusal) and the Try again form of "Couldn't confirm" on a Mac or a wide window. A tap on a row's text opens the details, below 900 pt (`isWideLayout`) as a pushed page and from there up in a pane (420 pt list) beside the list with the selected row filled; the switch is its own control. The details are `ToolsetDetailBody` (header with the same switch phases, `RiskNote`, a slot for the setup sections that the next change fills, "Where it applies", a collapsed "What's inside (N)" with monospace names and the helper line). `ToolsController.requestSwitch` decides whether a question comes first; when `confirmation` appears the screen shows `showToolsetConfirmation` once and answers `confirm()` or `cancel()`, and App Lock covering the app (`AppLockController.covered`) cancels it and takes the dialog down. A successful change shows "Applies from your next chat. A chat that is already open keeps the tools it started with." (`changedSinceOpen`), or, when the switch started an installer, the banner "<name> is on." with Show (`postSetupStarted`; Show opens that toolset's details). Page-level problems are banners above the rows (couldn't load, offline; the rows stay) or, with nothing read yet, a `StateMessage`; an old server (a read answering 404 or 405, also while the screen is open) shows "This server doesn't offer tools settings." with Back, and a deleted profile shows "This profile no longer exists." and calls `onProfileGone` so the caller reads the profile list again. A toolset that left the server (`toolVanished`) shows a banner and the selection moves to the first row. Pull to refresh (not on a Mac) and Try again call `load()`. The screen seeds its controller with `ToolsAvailability.rowsFor(profile)` and still reads.

**Tools setup sections** (`tools_setup_registry.dart`, `toolset_setup_panel.dart`, `terminal_backends_panel.dart`, `computer_use_panel.dart`, `tools_panel_env.dart`, `tools_asker.dart`, widgets `ProviderChoiceSection`, `ToolsNote`, `ToolsDisclosure`, `ToolsetModelRow`). `ToolsScreen` fills `ToolsetDetailBody.setup` with panels that show the registry's controllers and own only their text fields; `ToolsSetupRegistry` (owned by the screen) holds the setup, backends and Computer use controllers, so a write belongs to its controller and not to the panel: opening another toolset mid-save drops the panel, the write goes on, the toolset's switch stays locked until it settles (the registry reports the lock to `ToolsController.setSetupBusy`, counted per toolset), and returning shows the waiting result (the area opens when a result waits; `acknowledge()` clears an ended result, a looked-at provider and Hermes' texts when the panel that showed it goes away, but not while a write still runs). There is one controller per toolset the user opened, freed with the screen. Typed keys go with the panel, App Lock, a profile change and sign-out; a profile change hands every controller to the new profile after the frame and closes the details pages and the model list. Install (and Try again) wait for every write, the switch's included; a locked `ProviderRow` is dimmed on every platform (its picked mark included), while a picked row with no action is not drawn disabled; Web's Advanced install step has its own "Install on server" header and is offered once the key is saved. `ToolsPanelEnv` is what they share (repository for the profile, the connection's `ToolsetInstalls`, the question asker, the link launcher, the refresh registry, the optional Bot Screen link, `onWritten` and `locked`: some write of the toolset is out, counted over its own switch, setup writes, backend picks and the grant, so every panel and install button waits for all of them). Setup: `ToolsetSetupPanel` reads `/config` when the details open (loading, "Couldn't load setup." with Try again, "Nothing to set up."; Terminal hides that line because it has its own section) and shows the area open under the header when the toolset needs setup, or behind a collapsed "Change setup" row (value: the active provider) when it is set up; it stays open when what the user does there sets the toolset up. A provider with an install step that has not run reads "Needs install". Picking sends only after Hermes is asked, the selection moves only when it accepted, a refusal shows Hermes' text, a lost answer is "May have changed. Checking…" then "Couldn't confirm" (Pull to refresh, or Try again where nothing pulls; the line says "Couldn't confirm." when a Try again action sits beside it) and nothing is sent twice. Web's "Use different providers for search and extract" sends `capability`; a ready provider's install step is "Run the install step again" in the same disclosure. After every landed write `onWritten` reads the list again, and while one is out `ToolsController.setSetupBusy` disables that toolset's switch (list row and header) and drops a request made behind it. **Secrets**: typed keys live in one `TextEditingController` per key (owned by the panel) and the setup controller's private map; the controller is the authority, so when it drops them (success, lost answer, provider or profile change, App Lock via `SecretFieldsLock`, closing the details) the fields are cleared; Save sends only typed fields; a failed save keeps the value hidden and raises `hideSignal`; Get a key opens http(s) addresses only, in the system browser. A test drives the real screen with the telemetry interceptor and checks that no span, log record, event or printed line contains a typed key. **Installs**: the button asks "Install on your server?" first (Cancel default, `ToolsAsker`, which App Lock covering the app takes down) and only then calls `ToolsetInstalls.startConfirmed`; progress is `InstallProgress` from the connection's state, so it survives leaving the screen; an install a switch started is followed from the switch's answer (`followSwitchStarted`) and the list banner's Show opens its section; an end reads the config and the list again and says "Checking…" before "Installed."; failed, unknown, follow failing ("Trying again…") and follow lost ("Check again") have their own copy. **Model**: `ToolsetModelRow` opens `ToolsetModelSheet` fed from the controller's catalog, so a refused pick does not show as chosen. **Terminal** and **Computer use** have their own routes and hide on 404 or 405 whatever the list says; Local asks first; Allow access asks first, follows `computer-use-grant` and reads the status again; "Open the bot's screen" shows only when `ChatScreen` gives the screen a `ToolsBotScreenLink` (it holds a Bot Screen controller whose status was read and is not unsupported) and opens the viewer with source `tools`. The driver's install button is the Set up area's (the one place), not a second one in Readiness. "Applies from your next chat." shows on a toolset's details only when that toolset's own switch changed (`ToolsController.changedToolset`); the list-level note stays after any change. In a row, "May have changed. Checking…" follows the action count.

**Tools entries and availability.** `HermesRepositories.tools` is the tools repository with no profile of its own: reach a profile through `tools.forProfile(name)`. `AppShell` owns one `ToolsAvailability` and one `ToolsetInstalls` per connection and provides both. It reads the chat profile's list once per profile (from `ChatProfiles.current`, else the server's default profile) and again on every resume; on sign-out or a server change (`_authorizedOwner` turning false) it clears both. `ChatScreen` takes `tools` and `toolsAvailability` (tests override them; otherwise `repositories.tools` and the provided availability) and shows the entry only while `ToolsAvailability.offered`: the sidebar's More section on iPad and desktop windows and the phone drawer, "Tools" with a wrench (`AppIcons.wrench`) after "MCP servers" and before "Helper models"; `_openTools` opens the screen for the chat's profile (the profile the list was read for when the chat names none) and reads the availability again when it closes. The Mac Profiles page has a `ProfileSection.tools` row, listed only while the server offers Tools, with a lazily read "5 of 12 on" and opening the screen for the selected profile; ⌘[ Back comes from the scaffold. A server without the routes shows no entry and no message anywhere. The Tools wording is in the `@@x-area-tools` block of both ARB files.
