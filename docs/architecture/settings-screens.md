# Settings screens: plugins, MCP servers, helper models, model providers

**Settings pages** (`lib/src/widgets/settings_scaffold.dart`, `grouped_list.dart`, `settings_search_field.dart`). Skills, Messaging, Plugins, MCP servers and Helper models share one chrome. `SettingsScaffold` takes a title, a subtitle (profile · count), `SettingsBarAction`s (a button, or `.menu` with `AdaptiveMenuItem`s that act through `onTap`), optional tabs and a `SettingsSearch`, and draws the platform's bar: iOS a 44 pt bar with the title centered, macOS the `MacToolbar` with back, tabs (`MacToolbarTabs`), search and actions in it, Material a 56 pt bar with pill tabs (`PillSegmentedControl`, which `AdaptiveTabBar` now draws on Material). `AdaptiveTabBar` sits in a bar of fixed height, so its labels stop growing at 1.3x text size (`MediaQuery.withClampedTextScaling`), as iOS bars do and leave larger text to the Large Content Viewer; this is a decision, not an oversight. Past the cap a label that still does not fit shrinks to 70% and then ends in an ellipsis (`ShrinkToFitText`, also in the iOS and Mac segmented control), so no tab label is cut mid-letter. There is no floating button; adding is a bar action. Lists are `GroupedListView` of `GroupedSection`s (header, footer, inset separators) holding `GroupedRow`s (title, inline meta, a subtitle of one line unless `subtitleMaxLines` allows more, warning and error lines that wrap, a muted value of at most half the row and chevron, or a trailing widget; above the default text size a value that does not fit beside the title stacks under it, and only a row with `wrapWhenStacked` lets its title and subtitle wrap in full there, otherwise they keep `titleMaxLines` and `subtitleMaxLines`; a bordered button at the end of a row, such as the Mac "Check for Updates" and the "Set up" button of a messaging platform, goes on a line of its own under the text once it no longer fits beside the title at the current text size (`trailingBelow`, decided by `trailingActionStacks`) and is its own accessibility control at every size) and `GroupedSwitchRow`s; `GroupedMetrics.of(context)` has each platform's sizes. Every `Switch.adaptive` (`GroupedSwitch` and the other switches) takes its colours from `_SwitchAdaptation` in `hermes_theme.dart`: on Material platforms (Android, Windows, Linux) an off switch has a `zinc500` outline and a `zinc400` (dark) or `zinc500` (light) thumb so it clears 3:1 against the row (`test/theme/switch_contrast_test.dart`); the iOS and macOS off track is below 3:1 and waits for the owner's choice, the test only stops it getting worse.

**Keyboard focus ring** (`lib/src/theme/focus_ring.dart`; design brief `docs/design-briefs/windows-linux-platform-fixes.md`, F7). A 2 px solid ring in `HermesChatColors.link` (never a raw colour; `colorScheme.primary` is near black and would vanish on a filled button), shown on keyboard focus only: `keyboardFocusShows` reads `FocusManager.instance.highlightMode`, so a pointer press never draws the ring (a button a pointer press focuses holds focus, and a text field does too, but neither shows it), and the hover tint is unchanged. Flutter's traditional mode stays on through a mouse click on a desktop (only touch and stylus switch it off), so the ring follows the last input itself: `_watchInput` (called on every style resolution and by every `FocusRing`, also when nothing is focused) adds a global pointer route (a pointer-down hides the ring), a `FocusManager` highlight-mode listener and an early key handler (a key-down shows it again). A change marks only the nearest `ButtonStyleButton` around the focused node dirty (nothing when the focus is elsewhere; a `FocusRing` listens on its own and rebuilds only when it is focused), so the ring goes with the pointer and returns with the keyboard without rebuilding the app. `markFocusRingKeyboardInput` lets the catalog show a preview as the keyboard would; app code never calls it (`arch.focus-ring-keyboard-override` fails on a call or tear-off under `lib/`). Two forms. `FocusRingBorder` / `focusRingShape` sit in the theme's text, filled, outlined and icon button styles (`hermes_theme.dart`): the ring is 2 px outside the control, the control's radius plus 2, painted past the bounds while the ink clip stays the button's own. A button style that sets its own `shape` replaces the theme's and the ring with it, so such a site writes `.copyWith(shape: focusRingShapeOf(context, shape))` (`arch.button-shape-without-focus-ring` fails on a `shape:` inside `styleFrom`, `ButtonStyle` or any `copyWith` that does not go through a real `focusRingShape(` or `focusRingShapeOf(` call (a name that only starts like one, such as `focusRingShapeOverride`, is flagged); a leading `const` is ignored, a variable is not ringed, and the exact name `buttonShape` is exempt in `hermes_theme.dart` only). `FocusRing` is for what a container clips: it paints the ring 2 px inside the child, with the row's own `radius` (`GroupedRow`: the section radius minus the inset), and an optional `fill` painted under the child. It wraps the grouped row's tap target (`GroupedRow` with `focusable` and `focusFill`; a row that draws its own mark is left alone), the segments of `PillSegmentedControl` (and so `AdaptiveTabBar` on Material, Windows and Linux), the popover choice row (`inset: 0`, the model picker's outline), and `FocusRingMenuItem`, the item `AdaptivePopupMenuButton` builds on Material, Windows and Linux, which also takes the hover fill while focused. Not covered: `ListTile` (7 sites) and chips (3 sites), which keep Material's own focus fill; hand-rolled `InkWell` controls and floating action buttons (the model pill, the schedule weekday toggles, `new_chat_fab`); `CheckedPopupMenuItem` (Material builds it, so it keeps the theme's focus fill only), the Android `SegmentedButton`, the Mac compact menu row (`MacMenuRow`, which inverts to the primary fill) and the iOS and Mac sliding segmented control (system-drawn); text fields keep their own focus border. Status is never carried by the ring: focus is also the fill and the platform's own highlight. Catalog: "Keyboard focus ring" (`widgetbook/focus_ring_use_cases.dart`) forces keyboard mode and focuses one control per use case; tests in `test/focus_ring_test.dart`.

**Shared widgets.** `AppBanner` (`lib/src/widgets/app_banner.dart`, tones `AppBannerTone`: success, warning, error, neutral) is the one tinted note box with an icon, title, optional detail and action. It is a polite live region, and status is told by its icon and the words of its title. The action sits beside the text; at a text size above 150% or in German it stacks below it, the text at full width and the action aligned to the text's leading edge (inner side padding cancelled). Whatever button the caller passes (also inside a wrapper widget), its target is at least 44 pt on iOS, 48 dp on Material and 28 pt on a Mac (`AppBanner._target`, a constraint around the button, so a compact density or the button's own smaller minimum cannot cut it); an action that is no button, such as a small spinner, is passed with `actionIsButton: false` and keeps its size. A stacked button that sets its own side padding through `style:` is moved toward the leading edge by that padding (in layout, so its whole target taps) so its label still lines up with the text; callers that cap an action's width while it sits beside the text lift the cap when `AppBanner.stacksAction(context)` is true. Since this change, for every banner with an action: in German at normal text size the action stacks under the text (it used to sit beside it); above 150% text size it is start-aligned under the text (it used to be end-aligned); and a plain `TextButton` action grew to the minimum (Android 40 to 48 dp high, Mac 20 to 28 pt, iOS unchanged at 44), while actions that already carry a platform-sized style (Files, workspaces, tools, context) did not change size. In the wave 4 design records "Banner" and "the shared Banner" mean `AppBanner`; the class is not called `Banner` because Material already has one. `DestructiveTintButton` (`destructive_tint_button.dart`) is the destructive action drawn tinted in the error colour with an outline, never filled (44 pt on iOS, 48 dp on Material, 28 pt on a Mac; busy and disabled states), so a screen's one filled button stays the safe one. `LoadingSkeleton` and `CommandRow` (a copyable shell command) live here too; server care builds on them. `GroupedActionRow` (`grouped_action_row.dart`) is a tappable action row of a grouped section with an optional muted `subtitle` under the title and a status slot (working, done, failed, warning); `OutputLinesTile` (`output_lines_tile.dart`) is a closed-by-default disclosure of selectable monospace command output, its label passed in by the caller (`UpdateDetailsDisclosure` is a thin user of it).

**Dialogs and sheets** (`lib/src/theme/hermes_theme.dart`, `lib/src/widgets/adaptive_dialog.dart`, `adaptive_sheet.dart`, `grouped_dialog.dart`). Every Material dialog, bottom sheet and date or time picker takes its look from the theme, never from a per-call colour: in dark, `dialogTheme`, `bottomSheetTheme`, `datePickerTheme` and `timePickerTheme` give a zinc900 surface, a 1 px zinc500 edge (`hermesOverlayEdge`, also used by `GroupedDialog` and the Kanban sheets, whose shapes are their own) and, for dialogs and sheets, a 0.6 scrim, mirrored as `--h-overlay-surface`, `--h-overlay-edge` and `--h-scrim` in `design/web/src/styles/tokens.css`. The edge, not the surface, carries the boundary: surface and scrimmed backdrop are both near black, and only zinc500 stands 3:1 off that backdrop (4.2:1; zinc600 gives 2.7). Two traps. Zinc800 is `colorScheme.outline` and `surfaceContainerHighest`, so as a surface it hides the idle outline of `AppDialogTextField` and the unselected effort segments of `ModelPicker` (#1003 had to take that back). Zinc900 is `outlineVariant` in dark, so a hairline inside an overlay must use `outline`, not `outlineVariant`, or it vanishes (the model picker's effort divider and the platform hint sheet's box and rows do). A `GroupedSection` inside an overlay fills with `surface` (zinc950), a deliberate sunken well one step darker than the sheet, with its own zinc900 dividers. `showKanbanDetentSheet` gives `showModalBottomSheet` a plain shape because `KanbanDetentSheet` draws the one visible edge; the theme's shape would paint a second one round the transparent layer. `CupertinoAlertDialog` keeps the system look: alert content follows the system alert's centred 13 pt message style, and data blocks (paths, lists, findings) opt into start alignment with `DefaultTextStyle.merge(textAlign: TextAlign.start)`. On macOS `showAppDialog` reads `DialogTheme.barrierColor`, so a dark Mac alert gets the 0.6 scrim; iOS keeps the system barrier. `test/dialog_edge_test.dart` pins the edge contrast, both controls, the hairlines and the single Kanban edge. Use cases: `widgetbook/dialogs_use_cases.dart`, "Overlay surface". `showAppDialog` takes an optional `barrierDismissible`: null keeps each platform's own default (a barrier tap closes a Material or macOS dialog, not an iOS one), false makes the barrier inert on every platform (`test/widgets/barrier_dismissible_test.dart`). Text-entry dialogs (the thread rename, Kanban `askKanbanText`) pass `barrierDismissible: false` on macOS only, so a stray click does not discard typed text; a barrier that is not dismissible also turns off Esc, so on macOS those two dialogs handle `DismissIntent` themselves (macOS only; iOS keeps Esc inert). On macOS Esc closes all nine dialogs that moved to `showAppDialog` (the Cupertino route did not), and a click outside closes all but those two (`test/widgets/mac_dialog_route_test.dart`). `showAppActionSheet` (`lib/src/widgets/app_action_sheet.dart`) is the one iOS action sheet: a one-line title, `AppActionSheetEntry` buttons (label, value, `destructive`) and a Cancel button read from `widgetsCancel`; it answers the tapped value or null (`RowActions` and `SwipeableThreadRow` use it). `showAdaptiveSheet` shows a dialog on macOS and wide layouts (up to `maxWidth`) and a bottom sheet elsewhere. `showDragHandle` puts Material's drag handle on the phone sheet (a dialog never has one). `maxSheetHeightFraction` caps the phone sheet at that share of the screen height; the sheet's own content must then scroll (the skill job sheet is one scrolling column). Passing a height constraint replaces the theme's, so the cap keeps the theme's `bottomSheetTheme.constraints` width, or Material 3's 640 pt when it has none: an Android sheet at 800 pt stays 640 wide (`test/adaptive_attach_and_skill_sheet_test.dart`). The `GroupedDialog` header on iOS and macOS is a small custom layout (`_TitleBar`) inside a column of its own (`_DialogColumn`): rows win. The header may grow (the title wraps; Done takes its own row when the title does not fit on one line beside it) up to 40% of the room the dialog really gets, and only while the rows keep at least the height they have on main (the resting 52 pt bar on iOS, 44 on macOS). The exception is a Done taller than main's bar: Done is never cut, so there the rows get that much less. When growing would take rows from main's height, the header stays in the one-line form (title centred in the bar like main, cut by an ellipsis before Done); the full title stays in the heading's semantics label and a long-press tooltip (`excludeFromSemantics`, so it is not announced twice). Past the 40% cap the title scrolls with a fade at its bottom edge. The title and Done carry sort keys so screen readers read title, Done, rows. The header measures the title with the style it is drawn in, never paints outside itself, and the column lays the rows out once under the one-line header and reads their laid-out content height from a probe (no intrinsics and no dry layout, which a `LayoutBuilder` row cannot answer the same in debug and release), so a relayout keeps their scroll offset. `test/widgets/grouped_dialog_sweep_test.dart` sweeps 10,080 cells against main's own dialog, frozen in `test/support/legacy_grouped_dialog.dart`. Done reads `widgetsDone`. Use cases: `widgetbook/grouped_dialog_use_cases.dart`, "Grouped dialog", with the 320 pt x2.0 and x3.1 states; `test/widgets/grouped_dialog_test.dart` pins that the title never meets Done.

**Secret fields** (every screen that takes a key, token or password). Typed secrets are obscured by default and have a Show/Hide control (a 44 pt touch target on iOS and iPadOS, 48 dp on Android, a standard Mac button) labelled "Show key" / "Hide key". Under the field a muted line, announced to screen readers, reads "<N> characters entered"; the count is never stored. A shown value is hidden again when the lifecycle leaves `resumed` (`inactive` included), when a check or save starts, after any failed save, and when the form closes; the shown state is never persisted or restored. Going inactive or to the background only hides a shown value; the typed text stays. The typed text is cleared only when App Lock locks the app, when the form closes, and when the answer to a save is lost (the value may already be saved, so the field is cleared and the message asks to paste it again). After a plain failed save the typed value stays in the field, hidden, so it can be edited. A saved value is never revealed (no `POST /api/env/reveal`). The shared widget is `SecretFieldRow` (`lib/src/widgets/secret_field_row.dart`), built on `GroupedTextFieldRow` with autocorrect, suggestions, keyboard learning, smart dashes and quotes and autofill off, the visible-password keyboard on Android, one line and no `restorationId`; its Widgetbook use cases are hidden, shown, hidden again on going inactive, after a failed save, and after a lost answer (cleared). Model providers (`openspec/changes/provider-setup`) and toolsets use it; a new feature that takes a secret points here instead of restating the rule.

**Plugins** (`lib/src/plugins/`). The chat sidebar's Plugins row opens a screen with three tabs. Installed lists the dashboard's agent plugins (`GET /api/dashboard/plugins/hub`) and enables, disables, updates, removes and hides them; it does not list Kanban or Achievements, which the hub reports apart as dashboard-only extensions. Catalog (`GET /api/dashboard/plugins/catalog`, loaded when first opened) searches the curated catalog and installs from it, and installs from a Git URL behind an unreviewed-code warning; the typed URL can hold a token, so it is never logged or kept. Providers (the `providers` object of the same hub, loaded when first opened) picks the memory provider and context engine: only providers the server reports as ready can be picked, the rest list what they need on the server (the app runs nothing), and Save sends only the fields that changed to `PUT /api/dashboard/plugin-providers`. `PluginsController`, `CatalogController` and `ProvidersController` hold the state. Details are a bottom sheet below 900 px and a pane at 900 px or wider. The screen shows the chat's profile (or the one picked on the Mac Profiles page): `HermesPluginManagerRepository.forProfile` sends `profile` to the hub, visibility and provider routes, but install, enable, disable, update and remove take none, so Hermes runs them for the dashboard's own profile. The generated client puts a plugin's name into the path unencoded, so the repository encodes it. An install can outlast the client's 30 s timeout, so a timeout is reported as "still installing", not as a failure. `PluginsScreen.initialTab` (`PluginsTab`) picks the tab shown first; the Memory screen's provider row opens Providers, and the other tabs stay unrequested.

**MCP servers** (`lib/src/mcp/`). List, switch, test and remove the MCP servers of the chat's profile, else the launch profile (`ProfileResolver`), opened from the chat sidebar. `HermesMcpRepository` wraps the generated MCP calls and parses leniently. `McpServersController` holds one visit's state (the profile learned first, the list, the test results), and `McpServersScreen` and `McpServerDetail` render it, side by side from 900 logical pixels. The bar's "+" (Add server) is a menu: "Browse the catalog" opens `McpCatalogScreen` (Hermes' approved catalog, searched and filtered on the device; `McpCatalogController`), where an entry that is not installed opens `McpInstallPanel` (a bottom sheet, or the right-hand pane from 900 logical pixels) and an installed one opens its server. `McpInstallController` sends the install and, for entries Hermes builds on the server, polls `GET /api/actions/{name}/status`. Credentials live only in the panel's text fields and go into the install request. `McpSignInScreen` waits while the user approves an OAuth sign-in in the browser (`McpServersController.startSignIn`, then polling `GET /api/mcp/oauth/flows/{id}`); Hermes keeps the token and the app never sees the code. "Add a custom server" opens `McpAddServerScreen` (remote or command server) and the overflow menu's "Edit as JSON" opens `McpJsonEditorScreen`, which loads the whole map from `GET /api/config` (the servers route is lossy) and saves it with `PUT /api/mcp/servers`. A command server makes the Hermes host run a program, so `McpServersController.addServer` and `replaceServers` take a required `McpReviewer` and send nothing until it confirms; the screens pass `showMcpCommandReview` (bottom sheet, dialog from 900 px). Bearer tokens, environment values and the editor's text stay in screen state and are cleared after the request.

**Helper models** (`lib/src/settings/helper_models_screen.dart`). The chat sidebar's "Helper models" row lists the chat profile's auxiliary task slots (`GET /api/model/auxiliary`) and opens the shared `showModelPicker` for one, with its "Use the profile's default" entry. The pick is saved once, when the picker closes, with `POST /api/model/set` (`scope: auxiliary`; the default entry sends `provider: auto`, empty model, which Hermes runs on the main model). Hermes may answer `confirm_required` for an expensive model; the screen asks and resends with `confirm_expensive_model`. Changes apply to new sessions only. Below the slots, a "Mixture of agents" section lists the default preset's advisors and aggregator (`GET /api/model/moa`, `MoaSetup`); a change sends the whole config back with `PUT /api/model/moa`, only that slot edited, and keeps the MoA rows closed until it answers. The section is left out when MoA cannot be read.

**Model providers** (`lib/src/providers/`; roadmap 4.1, `openspec/changes/provider-setup`). One screen per profile: `ProvidersScreen` (`providers_screen.dart`) over `ProviderSetupController`, which holds the state and every write; the screen words it, owns the dialogs and sheets and never builds a widget inline (the plain-model widgets are in `widgets/`, built from the controllers' state by `provider_view_mapper.dart`). `HermesRepositories.providers` builds the `ProvidersRepository`.
- Routes and profile scope. Opened from the chat's sidebar and compact drawer ("Model providers", before "Helper models", only while the chat's model options did not answer 404) for the chat's profile, and from the Mac Profiles page (`ProfileSection.providers`, "N connected") for the selected profile. Every request carries that profile (none on a server without profiles). The chat reads its model options again (`ChatController.refreshModelOptions`) whenever the controller's `changes` moves and when the screen closes. `ProvidersScreen.focus` (`ProvidersFocus.add()` or `.provider(id)`) says where it starts once its first read answered: "Add a provider" scrolled into view, or one provider (its detail when connected, the key form, sign-in or server command to connect it when not). Entry points record `providers.opened` with `source` (`sidebar`, `drawer`, `profiles`, and from the chat's first-run entry points `welcome`, `composer`, `reply`; see chat.md), starting a connect `providers.connect.started` with `method`, a confirmed removal `providers.remove.confirmed` with `kind`: fixed words only, never a provider, address, model or profile. "Use an account instead" on a key form records `method: server`, so one attempt can leave two `providers.connect.started` crumbs (`key`, then `server`).
- Layout. List beside detail from 900 pt (`isWideLayout`, so a full-screen iPad too; a Mac from `kMacSplitBreakpoint`), else a pushed `ProviderDetailPage`. Forms go through `showProviderSheet` (`provider_flow.dart`): a page sheet on iOS phones, a full-screen dialog on Android phones, a dialog on macOS and wide windows, never a bottom sheet on macOS (`showAdaptiveSheet` is used for all but the Android phone). Escape closes a form and Return does its primary action on desktop. Pull to refresh only on iOS and Android; a Mac has Command R.
- Secrets. Every key field follows the secret field rule above. The sheets own the `TextEditingController`s (`ProviderKeySheet`, `ProviderEndpointSheet`), clear them when App Lock locks (`SecretFieldsLock`), when the form saves and when it closes, and never persist or restore them. A saved key is never revealed (no `POST /api/env/reveal`): a row shows only its last four characters. Signing out or changing the server closes the screen and everything over it; the controller then stops following sign-ins without cancelling them.
- Sheets and steps. A sheet pops only while it is still the top route (`popIfCurrent`), so Cancel, Escape, Keep and Not now never close the screen under them. A default-model step that begins while something else is over the screen (the model picker, "Stop signing in?", a pushed detail) waits and opens once the screen is current again. App Lock locking clears typed keys; an endpoint save waiting on "Send the key unencrypted?" is dropped if the key was cleared meanwhile. In a Mac dialog the bar leads with "Cancel" (`SettingsScaffold.macCancel`); the Profiles page hides its Model providers row on a server whose model options answer 404.
- Links Hermes sends (key page, sign-in page) are opened only after `openableLink` (absolute `https`, or `http` to a local host); otherwise the button is not drawn. Endpoint ids and session ids are percent-encoded by the repository.
- Shared widgets changed with the forms: `GroupedTextFieldRow` stacks its label above the field at large text on Apple platforms and takes a `focusNode`; `CommandRow.copyBelowAtLargeText` puts Copy under the command at large text.

**Tools widgets** (`lib/src/tools/widgets/`, `lib/src/tools/toolset_copy.dart`). Plain-model pieces for the Tools screens, each with Widgetbook use cases in `widgetbook/tools_use_cases.dart`: `ToolsetRow` (`ToolsetRowView`; the text opens the details, the switch is its own control; saving, lost-answer, unconfirmed and error lines), `ToolsetHeader`, `RiskNote` (one semantics element), `StatusChip` (`ToolsStatus`: icon and words, never colour alone), `ToolsListFooter` and `ToolsSwitch` (the switch with its 44 pt / 48 dp / 28 pt target and the "<name>, on, saving" label). At a text scale of 2 or more the switch moves to its own line with "On" or "Off" before it. They build on `GroupedRow` (`details`, `titleWeight` and `trailingBelow`) and `GroupedSwitch`. `toolset_copy.dart` holds the per-toolset sentences, labels, risk titles and the confirm-question text as pure functions over `AppLocalizations`.

**Tools widgets** (`lib/src/tools/widgets/`, `lib/src/tools/toolset_copy.dart`). Plain-model pieces for the Tools screens, each with Widgetbook use cases in `widgetbook/tools_use_cases.dart`: `ToolsetRow` (`ToolsetRowView`; the text opens the details, the switch is its own control; saving, lost-answer, unconfirmed and error lines), `ToolsetHeader`, `RiskNote` (one semantics element), `StatusChip` (`ToolsStatus`: icon and words, never colour alone), `ToolsListFooter` and `ToolsSwitch` (the switch with its 44 pt / 48 dp / 28 pt target and the "<name>, on, saving" label). At a text scale of 2 or more the switch moves to its own line with "On" or "Off" before it. They build on `GroupedRow` (`details`, `titleWeight` and `trailingBelow`) and `GroupedSwitch`. `toolset_copy.dart` holds the per-toolset sentences, labels, risk titles and the confirm-question text as pure functions over `AppLocalizations`. The setup pieces (use cases in `widgetbook/tools_setup_use_cases.dart`): `ProviderRow` (radio row with the badge as an outlined tag, status chip and notes; Apple check mark in the link colour, Material leading radio; also for terminal backends) with `ToolsLoadingRow`, `ToolsFailureRow` and `ToolsNothingRow` for the set-up and backend states; `ToolsetKeyForm` (composed over `SecretFieldRow`, owns no secret field; the caller owns each field's controller and the phase, and Save is the screen's one filled button); `InstallProgress` and `ToolsInstallButton` (the running body, log lines and spinner are `lib/src/widgets/install_parts.dart`, shared with the Bot Screen install card; the button is filled exactly when the provider needs setup); `ReadinessRow`, `ReadinessSection` and `readinessItems` for Computer use; `ToolsetModelSheet`; `ToolsetConfirmDialog` with `showToolsetConfirmation` (the platform alert, Cancel first and default, the confirming action plain; Material shows two text buttons); and `ToolsDifferenceSheet`. Sheets open through `showAdaptiveSheet`, so a Mac and a wide window get a dialog, not an anchored popover. Buttons use `toolsButtonStyle` (44 pt, 48 dp, 28 pt on a Mac at standard density).

**Tools controllers** (`lib/src/tools/`, plain Dart, no text). `ToolsAvailability` reads the list on connect and resume for the chat's profile (`404`/`405` hide Tools; a failed read keeps the last answer; a gone profile is reported, not hidden; seeds only the profile it read). `ToolsetSetupController` also picks providers (a `needs_nous_auth` answer is a flag; `web` sends `capability` for search and extract) and models (`image_gen` and `video_gen` only; only an id the catalog lists is sent); one write at a time. `ToolsetInstalls` is the connection's one `tools-post-setup` follower: it is started only after the caller's confirmation (`startConfirmed`), follows the shared status log every 2 s, keeps the last six lines (never logged), treats a missing exit code, a replaced process or 22 minutes without an end as unknown, and ends in `requestReread`, never in "Installed" from the log. `TerminalBackendsController` sends nothing for `local` until `confirmLocal` says yes. `ComputerUseController` owns the `computer-use-grant` follow (separate slot, shared `ActionFollower`; leaving the screen drops it and the status read on return shows the result) and asks `confirmGrant` first. For every pick, a lost answer is checked by a re-read of at most 10 s and never sent again; spans (`tools.setup` with `step`, `tools.terminal_backend`, `tools.computer_use` with `action`) and the `tools.setup_outcome` and `tools.availability` events carry `step`, `action` and `outcome` only.

**Tools screen** (`lib/src/tools/tools_screen.dart`, `tools_row_mapping.dart`). `ToolsScreen` is on `SettingsScaffold` and `GroupedListView`, titled "Tools" with "<profile> · <N> on", sections Needs setup, On and Off (empty ones left out) and the `ToolsListFooter`. `toolsetRowView` and `toolsetDetailView` are pure mappers from a `Toolset` and its `ToolsRowState` to the widgets' plain values: the app's own name and sentence for a built-in, the server's label and description for a plugin's toolset (no risk line), the risk line at both levels of the risk table, the action count, the error text per kind (Hermes' own text for a refusal) and the Try again form of "Couldn't confirm" on a Mac or a wide window. A tap on a row's text opens the details, below 900 pt (`isWideLayout`) as a pushed page and from there up in a pane (420 pt list) beside the list with the selected row filled; the switch is its own control. The details are `ToolsetDetailBody` (header with the same switch phases, `RiskNote`, a slot for the setup sections that the next change fills, "Where it applies", a collapsed "What's inside (N)" with monospace names and the helper line). `ToolsController.requestSwitch` decides whether a question comes first; when `confirmation` appears the screen shows `showToolsetConfirmation` once and answers `confirm()` or `cancel()`, and App Lock covering the app (`AppLockController.covered`) cancels it and takes the dialog down. A successful change shows "Applies from your next chat. A chat that is already open keeps the tools it started with." (`changedSinceOpen`), or, when the switch started an installer, the banner "<name> is on." with Show (`postSetupStarted`; Show opens that toolset's details). Page-level problems are banners above the rows (couldn't load, offline; the rows stay) or, with nothing read yet, a `StateMessage`; an old server (a read answering 404 or 405, also while the screen is open) shows "This server doesn't offer tools settings." with Back, and a deleted profile shows "This profile no longer exists." and calls `onProfileGone` so the caller reads the profile list again. A toolset that left the server (`toolVanished`) shows a banner and the selection moves to the first row. Pull to refresh (not on a Mac) and Try again call `load()`. **Personality controller** (`lib/src/profiles/soul/soul_controller.dart`, `soul_telemetry.dart`; roadmap 4.8, `openspec/changes/profile-soul`). `SoulController` is plain Dart, bound to one profile name (explicit in the path, never the server's active profile) and one connection, and holds the baseline `(exists, content)` of the last read or save. Load states: `loading`, `loaded`, `notSet`, `failed`, `profileGone`, `unsupported` (calls `onUnsupported` once so the shell can hide the entries) and `offline`; the editor exists only for `loaded` and `notSet`, so a failed read never shows an empty one. Save sends nothing until the UI confirms: `requestSave()` returns the question (profile, empty text, `pendingSaveNote`), `confirmSave()` reads the file first (every read and the PUT give up after `kSoulAnswerTimeout`, 10 s; nothing is resent) and sends once only if the file still equals the baseline. A read equal to the text (file exists) is Saved without a PUT; a read that differs from the baseline is `changedOnServer` with `serverText` and `serverExists`, sends nothing, and offers `keepEditing()` or `replaceAnyway()` (one PUT); a failed or timed-out read is `saveCheckFailed` (Try again is `confirmSave()` again). A PUT with no answer, a timeout or a 200 without `ok` is `lostAnswer`: the text stays, `canCheck` is true and `check()` reads the file and compares it with the sent text (not the editor): equal and existing is `saved` (baseline = sent text, later edits stay dirty; a missing file never confirms, even for empty text), equal to the old baseline is `earlierText` (not a failure; the next question carries `pendingSaveNote`), anything else is `changedOnServer`. The editor is `readOnly` while the read, the PUT or a Check runs, and a second press while busy sends nothing. There is no length limit. `cover()` (App Lock) drops text, baseline and server text at once and keeps nothing; a request in flight finishes and its outcome is discarded; `uncover()` reads the server's text again. `clear()` (sign-out, server change, profile switch) and `dispose()` end it, and a late answer neither changes state nor notifies. A 401 on a read or write is a failed read or a refused write; the existing sign-in path handles the session. Telemetry (`SoulTelemetry`): spans `profile_soul.fetch` (`outcome`, `exists`) and `profile_soul.save` (`outcome`, `empty`, `length_bucket`), the log event `profile_soul.saved` (`outcome` of `saved`, `conflict_kept`, `conflict_replaced`, `failed`, `unconfirmed`, plus `empty`) and the crumbs `profile_soul.opened` (`source`, set by the controller's `openedFrom`) and `profile_soul.save.confirmed`; never the text, the profile name or a response body. **Skill curator data** (`lib/src/skills/curator/`, `lib/src/server_care/`). `HermesCuratorRepository` wraps `GET /api/curator`, `PUT /api/curator/paused`, `POST /api/curator/run` (generated client) and the `curator-run` action status (server care's `ServerCareRepository.actionStatus` with `CareAction.curatorRun` and the shared `ActionStatus`; always `lines=2000`). Every call names its profile and a blank one sends nothing. A call answers a `CuratorResult` (`CuratorOk`, `CuratorUnsupported`, `CuratorProfileGone`, `CuratorFailed(kind)`) and never throws: a failure is a `CuratorFailure` kind, so no `DioException` (its URL carries the profile) leaves the repository, and no server text either, except `CuratorFailed.detail` for the two failures the screen words itself with: a refused or failed pause (400 to 499 and 500, not 401, 403, "Curator unavailable" or a lost answer) and a spawn failure (the whole `Failed to run curator: ...` detail). **Skill curator controller** (`lib/src/skills/curator/curator_controller.dart`, `curator_telemetry.dart`, `curator_config.dart`). `CuratorController` is a plain `ChangeNotifier`, one per Skills screen State (the home shell builds the next State before the old one disposes, so `dispose` only cancels what that instance owns: its polling and its span). State is per profile and has three independent parts: the status read (`CuratorLoad`: loading, loaded, offline, unavailable, failed, profileGone, unsupported, which hides the section), the pause switch (`CuratorPause`; optimistic, and what is shown afterwards is the `paused` Hermes answered; no answer rolls back to the last known value and reads the status again; 404 `Profile '` keeps the switch, calls `onProfileGone`; 400 and 500 are `failed`) and the run (`CuratorRunPhase`). On open one read of the action status gives `running` and a baseline header; while it is true the phase is `elsewhere` and nothing is polled until Check status. `confirmRun` reads it once more before the POST, so the baseline is the log as it is then, not as it was on open: a pass running then is `elsewhere` and a read with no usable `running` is `unchecked`, and neither sends a POST; a profile switch, a dispose, or a status read that turned the curator off while that read was on its way also send none; status reads are numbered and one older than the last applied read or the last pause answer is dropped (the read is a GET and is the only extra request; the POST is still sent once and never resent). `beginRun` opens the confirmation at once with unknown wording and the `GET /api/config` read (`HermesCuratorRepository.config`, `CuratorConfig`: top-level `curator.consolidate` and `curator.prune_builtins`) refines it when it lands; only an open confirmation sends, so a second press from this controller sends nothing (another client can still start a pass: Hermes has no guard, and the read before the POST narrows that window without closing it), and the POST is never resent: a lost answer (including a dropped connection) is `lostAnswer`, never "offline", and only Check status settles it by reading. A followed pass is polled every 2 s, backing off to 5 s; 10 s of failed polling is `progressLost`; 15 minutes is `stillRunning` with Check status (one read; one that finds a run follows it again with a new 15 minutes). **"Finished" needs proof**: `running` false and a `=== curator-run started` header that differs from the baseline, the latest header read before the POST (the header time is the server's local time with no zone, so it is never compared with the device clock; Hermes writes the header while answering the POST, so the first read after the answer already holds this pass's header; two passes starting in the same second would look alike, which fails safe as `unconfirmed`). No proof leaves `unconfirmed`; a newer `last_run_at` alone only sets `startedAt` ("A pass started at"). Run now is enabled only in `idle`, `finished`, `failed`, `notStarted` and `checkedNothing`, so every unsure phase needs a read that shows `running` false. Hermes' own text is screen state in the output's lifetime: `pauseDetail` (the refused pause), `notStartedDetail` (a spawn failure) and `failureLine` (the last non-empty line of a failed pass), each through `curatorServerText` (white space collapsed to one line, `safePathText` so control and bidi characters show as `<U+XXXX>` and a lone surrogate as U+FFFD, at most 200 characters cut at a character boundary with an ellipsis, null when nothing readable is left). They are dropped by `lock()`, a profile switch and `dispose`; a new run also drops `notStartedDetail` and `failureLine`, and the next pause attempt drops `pauseDetail` (sign-out, a server change), never kept when the answer lands while locked, hidden while `blanked`, and never reach telemetry (`test/skills/curator_controller_test.dart` plants a sentinel in all three). `outputLineCount` keeps the "Show output · N lines" label's count while the lines are hidden. Output lines exist only for a proof-backed pass this app started, as display lines (`safeContentText`: control and bidi characters drawn as `<U+XXXX>`), the last 30, in memory only; `lock()` drops them, `setInactive` only hides them (`blanked`), and lines that arrive while locked are never kept. The result stays through `searching` (which hides the section) until the next run or a profile switch, which drops it and cancels polling. `onRunEnded` asks the owner to re-read the installed skills. Telemetry (`CuratorTelemetry`): span `skills_curator.run` from the POST to the first end (`outcome` done, failed, unknown, timed_out; `trigger_lost`; the connection's `hermes.*` attributes), event `skills_curator.run_finished` (`outcome`, `archived` from the `archived=N` line, absent when none), crumbs `skills_curator.run.confirmed` (logged just before the POST, after the read that precedes it and the re-check that Run now is still on, so it counts sends, not confirmations) and `skills_curator.paused` (`paused`); a later Check status that resolves a pass logs `done` or `failed` again, with `resolved_by_check: true`, so one pass can have two events. A `stopped` pass (a header, lines and no exit code, as after a dashboard restart) and a Check status that then reads `running` false end in `checkedNothing`, which keeps the earlier pass's output on screen (the section labels it as the earlier pass): Hermes loses its process handle on a restart, so `running` false does not prove that a detached child is gone. No profile, skill name, line or action id reaches any of them (`test/skills/curator_controller_test.dart` plants a marker in all of them).

## Measuring consistency

`tool/style_score.dart` counts the places in `lib/` that bypass the shared theme and widgets (raw colours, off-scale spacing and radii, literal font sizes, elevation, dialogs built outside `showAppDialog` and `showAdaptiveSheet`, non-adaptive controls, English literals in widgets), and `scripts/tap-report.sh` lists undersized tap targets across the Widgetbook catalog and the workflow screens. The tap report only measures. The categories, the provisional spacing scale and how to add an exception are in the `hill-climb-style` skill (`.claude/skills/hill-climb-style/SKILL.md`). The style counts are ratcheted by `test/architecture/style_ratchet_test.dart`, so a new hit fails CI and a fixed one must lower `test/architecture/baseline/style.yaml`.
