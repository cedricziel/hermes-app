# macOS: menu bar, windows, Dock, drag out, menu bar item

**macOS menu bar** (`lib/src/macos/mac_menu_bar.dart`, `mac_commands.dart`). In a Mac window the app sets its own `PlatformMenuBar` (Hermes, File, Edit, View, Chat, Window, Help), which replaces `MainMenu.xib`'s menu. A screen offers commands by wrapping its content in `MacCommandScope(commands: {MacCommand.x: MacCommandHandler(callback, title: ...)})`; an item is disabled while no visible scope offers its command (null callback also disables), the innermost or latest scope wins, and `priority` overrides that. Edit items send the text intents to the focused widget, and Delete… (⌘⌫) deletes to the line start while a text field has focus. Menu shortcuts reach the menu only when no Flutter widget handled the key, so don't add a `HardwareKeyboard`/`Shortcuts` handler for a chord the menu owns. File > New (`MacCommand.newChat`, ⌘N) follows the page in front: New Chat on Chat, New Task on Kanban, New Schedule on Schedules, each page retitling it through its scope. View > Back (⌘[) is offered by a pushed `SettingsScaffold` while its route is current (not under a dialog or sheet) and leaves that page. View > Show Files (`MacCommand.showFiles`, ⇧⌘F) is offered by `ChatScreen` while the server has `/api/fs` (disabled otherwise) and disabled while a conversation window is key: a window has no session of its own, so a Files page there could not close on App Lock or an expired session, and it provides no `HermesRepositories` (which would also make `MemoryDestination` work there). Tests answer `SystemChannels.menu` and set `MacWindow.enabled` (`test/macos/mac_menu_bar_test.dart`). The menus are described once in `menu_layout.dart` (`menuLayout`: sections, groups, `MenuEntry` with its chord and platforms); `macMenus` renders it for the Mac, and on iOS and iPadOS `IpadMenuBridge` (`ipad_menu_bridge.dart`, mounted by `MacMenuBar` with iOS chrome) sends it once plus each command's enabled flag and title over `hermes_app/menu` to `ios/Runner/KeyCommandMenu.swift`, which builds `UIKeyCommand`s in `buildMenu(with:)` and answers `canPerformAction` from that state. Flutter sees a key first; for an enabled item UIKit then runs the command once, for a disabled one the key stays with the app. The iPad has no Open in New Window, Close Window, sidebar or inspector items and no chord for Delete…; ⌘F is `MacCommand.find` on both (on iPad `ChatScreen` offers it from the layout while the sidebar is beside the chat and focuses its search field). Breadcrumb `menu.command`, log `ipad_menu.sync_failed`. Chat > Compress Conversation… (`MacCommand.compress`, Mac only, titled from `macosCompressConversation`) is offered by `ChatScreen` (`chat_screen_checkpoints.dart`): on only while the selected stored chat's `ContextController.canCompress` (idle, live session, connected, not locked, a server that compresses), and it opens `confirmCompressFlow`, the same confirmation the Context details page uses (a `CompressConversationEntry` can replace it, as a test does); the screen listens to the selected chat's context controller so the item follows it. While a conversation window is key, `ConversationWindowsMenu` turns it off: windows hold no checkpoint or context controllers.

**Conversation windows** (macOS, `lib/src/windows/`). A chat can open in a window of its own (double-click in the sidebar, the thread menu, File > Open in New Window ⌥⌘O). Each window is its own engine and isolate (`desktop_multi_window`; Flutter's own multi-window API is master-only), started through `main(["multi_window", id, args])` into `runConversationWindow`. A conversation window holds no session and never refreshes one: `WindowAuthInterceptor` asks the main window for each request's headers (`AuthController.windowAuthHeaders`, which refreshes only when the rejected token is the current one), and `MainFlutterWindow.swift` registers only a few plugins in its engine (no secure storage, notifications or macos_window_utils). Only the main engine sets the menu bar, telemetry and notifications. `ConversationWindows` (main isolate) tracks the open windows and the key one, persists them for the next launch (frames through `NSWindow` frame autosave), closes them on sign-out, and forwards "Show in Main Window" to the shell. Each engine keeps its own state: a window reloads its chat when it becomes key, and the main window reloads the chats that were open in a window when it becomes key (`ChatController.refreshThread`). The main window is hidden, not released, when closed, so its engine keeps serving the windows; ⌘0 or the Dock icon brings it back. `ConversationWindowsMenu` (in `HermesApp`'s builder) lists the windows in the Window menu and, while one is key, routes the menu bar's window and chat commands to it with a priority-1 `MacCommandScope`, which also disables View > Back so a settings page in the main window stays put. Handoff advertises the key conversation window's chat, and a handed-over chat that has a window opens there. The quick panel (`lib/src/quick_panel/`, change `mac-quick-panel`) is one more engine of this kind, started with `QuickPanelLaunch` (`kind: panel`): on its first `presentPanel` call `QuickPanel.swift` moves its view controller into a non-activating floating `NSPanel` and orders the plugin's window out, so the panel takes keys without bringing Hermes forward. A global shortcut opens it: the Swift package KeyboardShortcuts (Xcode SPM on the Runner, pinned in `Package.resolved`) registers the user's chord (none by default) in `QuickPanelShortcut.swift` and forwards presses over `hermes_app/quick_panel` to `GlobalShortcut`; `QuickPanelShortcut` (Dart) toggles the panel through `ConversationWindows.togglePanel` while signed in and shows the main window otherwise. Settings… records the chord with the package's native recorder (`AppKitView` `hermes_app/shortcut_recorder`). The panel is never saved or listed in the Window menu, closes on sign-out, and gets the dictation plugins conversation windows leave out. `QuickPanelScreen` holds one chat on the main window's current profile (`profile.current` on the main channel): before the first send the panel is just the composer and as tall as it, after it the chat's `ChatThreadView` (`welcome: false`) at a fixed height (`resizePanel`, capped at 60% of the screen natively). A show continues the chat when it was used within five minutes on the same profile (`QuickPanelSession`) and otherwise starts empty. Open in Hermes (⌘O) hides the panel, then asks the main window (`panel.showInWindow`) to open the chat, with the composer's draft, through `ConversationWindows.open`. Dictation there goes through `ComposerDictation` (`lib/src/voice/`), as in `ChatScreen`, and the chat view's callbacks, latest-reply tracking and model pill come from `lib/src/chat/chat_thread_bindings.dart`, shared by the chat screen, conversation windows and the panel.

**Dock menu** (macOS, `lib/src/macos/dock/`, `macos/Runner/DockMenu.swift`). AppKit asks for the Dock icon's menu synchronously, so Dart pushes what it shows (`DockMenuBridge.update`, method `dockMenu` on the `hermes_app/app` channel, `MacApp.setDockMenu`) and `AppDelegate.applicationDockMenu` builds it from the copy in memory: New Chat, up to five recent chats of the shown profile (remote, not Bot Chat registries, newest first, titles cut to 40 characters), Show Main Window (native only, so it works in every state). `DockMenuController` (provided in `main.dart` on a Mac) holds the state, which `DockMenuGate` sets from `AuthController` and `AppLockController` (`off` unless connected, `locked` while covered, else `ready`); only `ready` carries titles, and `ChatScreen` supplies them from `_changed` and clears them in `dispose`. A pick comes back as `dockNewChat` or `dockOpenChat`; `ChatScreen._showChat` (shared with Handoff) focuses the chat's conversation window or restores it in the main window. New Chat while locked waits for `AppLockController.unlock()` (which returns whether the app is unlocked and joins a prompt already open) and is dropped if the unlock fails, the app locks again, the user signs out or a newer pick replaced it. Breadcrumbs `dock.menu.action` and `dock.menu.deferred` and the event `dock.menu.open_failed` hold no titles, ids or profile names.

**Drag out** (macOS, `lib/src/drag_out/`, `macos/Runner/DragOut.swift`). Chat attachments and Kanban task attachments drag out of the app as files (file promises: the bytes are read only when the receiver asks). Widgets never touch the platform: they wrap their child in `DragOut(kind:, item:, child:)`, which asks the `DragOutSource?` provider (set in `main.dart`, `MacDragOutSource` on macOS, null elsewhere, so conversation windows and the catalog see none) to make it draggable. `MacDragOutSource` watches the pointer (a `Listener`, not the gesture arena, so taps, selection and scrolling are untouched) and after 6 px with the primary mouse button down calls `startDrag` on the `hermes_app/drag_out` channel. `DragOutController` (Swift, registered by one line in `MainFlutterWindow.awakeFromNib`) remembers the window's latest left-button `NSEvent`s with a local monitor, starts `beginDraggingSession` on the Flutter view from them, allows copy only outside the app (so `desktop_drop` cannot take the file back), and at the session end posts a synthetic `leftMouseUp` to the Flutter view (the session swallows the real one, which would leave Flutter's button state stuck). Files go out as `NSFilePromiseProvider`s: on demand Swift asks Dart (`readFile`), which answers with the path of a local file (`DragOutFile.localPath`, copied natively) or, when there is none, the bytes; a 60 s timeout fails the promise, and `fileWritten`, `readTimedOut` and `ended` report back; text goes out as an `NSPasteboardItem` with plain text and Markdown. `DragOutItem` is `DragOutFile(name:, read:)` or `DragOutText`; names go through `sanitizeDragFileName`. `DraggableAttachment` (`chat/attachments/`) wraps `AttachmentCard`/`AttachmentThumbnail` in `chat_builders.dart` and offers the picked path or the `MediaStore.file` cache copy as the local file, bytes only for an embedded attachment; `DraggableKanbanAttachment` wraps a task panel row and reads through `KanbanTaskController.readAttachment`. `DragOutTelemetry` records the `drag_out.started` breadcrumb, `drag_out.promise` span and `drag_out.completed` event (slugs only, never names or ids). The drop side stays `desktop_drop`; the controller registers no drag destination. Message text and chats drag out too: `MessageDragGrip` (`chat/widgets/`, wrapped around the bubble in `_buildText`; a gutter beside the message holds the grip on hover, so it never covers content; the gutter stays but the grip is off while a reply streams, and neither exists where there is no source) drags `DragOutText(message.text)` as plain text and Markdown; a Mac sidebar row (`ThreadSidebar._row`) drags `threadDragItem` (`chat/thread_export.dart`), a `<title>.md` promise of `# <title>` plus the Copy Transcript Markdown, read through `ThreadHousekeeping.history` only on the drop (`DragOutKind.thread`, failure `history`; a promise Swift times out is `timeout` and cancels the read between pages). A started drag cancels the pointer in the gesture binding, so releasing near where it began is not a click. Tests: `FakeDragOutSource`, a mocked channel for `MacDragOutSource`, `macos/RunnerTests/DragOutTests.swift` for the promises; the catalog uses `CatalogDragOutSource`.

**Staying alive and the menu bar item** (macOS, `lib/src/macos/menu_bar_extra/`, `lib/src/shell/app_presence.dart`, `lib/src/macos/mac_app.dart`). Closing the last window leaves the app running with its Dock icon (`applicationShouldTerminateAfterLastWindowClosed` is false, the activation policy never changes); Cmd-Q, Hermes > Quit and the menu bar item's Quit end it, the last through `MacApp.terminate` (channel `hermes_app/app`). `AppDelegate.refreshWindowless()` tells Dart when no window is on screen (`MacApp.windowlessChanges`) and holds a `beginActivity` against App Nap meanwhile. `AppPresence.foreground` counts `hidden` and `inactive` as running on macOS, so `ScheduleWatcher` keeps its minute timer; `AppPresence.focused` stays `resumed` only, so notifications still post with no window. The menu bar item is an `NSStatusItem` in the runner (`MenuBarStatusItem` at the end of `MainFlutterWindow.swift`, created by the main engine only, not `tray_manager`: 0.8.0 builds a C++ core for every platform). Dart sends it the icon state (SF Symbols `bubble.left`, `ellipsis.bubble`, `exclamationmark.bubble`, as template images) and the whole menu in one `update` call on `hermes_app/menu_bar_extra`, and hears `selected` (an item key) and `opened`. `MenuBarExtraModel.of(chat)` reads the replying threads and pending requests the `ChatController` already holds (no polling, no request on open; replies running only in a conversation window are not listed) and is compared with `==` so the menu is sent only when it changed. `buildMenuBarMenu` makes the rows: approvals are submenus with the card's own choices (`offeredApprovalChoices`, `approvalChoiceLabels`), other requests open their chat, and New Chat, Show Main Window and Quit end it. `MenuBarExtra` (plain Dart, over the `MenuBarTray` boundary) acts on a pick: approvals go through `ChatController.answerApproval` like the card, "Always allow" asks first (`confirmAlwaysAllow`), an answer that did not go through opens the chat, and a chat with a conversation window is focused instead of opened in the main one. `MenuBarExtraHost` (in `HermesApp`'s builder, so a signed-out app keeps its item) owns it and provides a `MenuBarExtraLink` that `ChatScreen` connects its controller to while it is on screen; `MenuBarExtraSettings` (`menuBarExtra.enabled`, on by default; the "Menu bar item" switch in Settings) hides the item without changing the stay-alive. While the app is locked (`AppLockController.covered`; the host sits above `AppLockGate`) the menu shows counts, "Unlock Hermes…" and the fixed entries only, with no title, command or choice. Row keys come from what a row does (`approve:<thread>:<request>:<choice>`), so a pick on a changed menu does nothing (crumb `menubar.stale_pick`); an approval is answered once (in flight from the pick, rechecked after the "always" question); the runner applies an update only when the open menu closes; the item stays hidden until `MenuBarExtraSettings.loaded`. Crumbs `menubar.opened`, `menubar.action` and `menubar.stale_pick` and the log `menubar.approval_answered` carry counts and fixed names only (`choice` is once, session, always, deny or other).
