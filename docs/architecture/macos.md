# macOS: menu bar, windows, Dock, drag out, menu bar item

**macOS menu bar** (`lib/src/macos/mac_menu_bar.dart`, `mac_commands.dart`). In a Mac window the app sets its own `PlatformMenuBar` (Hermes, File, Edit, View, Chat, Window, Help), which replaces `MainMenu.xib`'s menu. A screen offers commands by wrapping its content in `MacCommandScope(commands: {MacCommand.x: MacCommandHandler(callback, title: ...)})`; an item is disabled while no visible scope offers its command (null callback also disables), the innermost or latest scope wins, and `priority` overrides that. Edit items send the text intents to the focused widget and are on only where they apply (`EditMenuState`, `edit_menu_state.dart`, a `ValueNotifier<EditAvailability>` that `MacMenuBar` owns, provides to its subtree and rebuilds the menus from when it changes): with no text field focused all six are disabled (no `onSelected`), not merely grey; in a focused `EditableText` Cut and Copy need a selection (Cut off when read-only, both off for a password field), Paste needs text on the pasteboard (the field's own `clipboardStatus`) and a field that is not read-only, Select All is on for any field that allows selecting, Undo needs history and Redo an undone step (a field's `UndoHistoryController` when it was given one, else an estimate, since Flutter keeps the stack private: Undo while the text differs from what it was at focus, Redo after an undo made from the menu until the next edit). Selected chat text keeps Copy on: the message bubble is a `MenuSelectionArea` (`menu_selection_area.dart`, a `SelectionArea` that reports to `EditMenuState`), and only Copy turns on while a selection area that holds text has focus. Every selectable text in `lib/` uses `MenuSelectionArea`, never a raw `SelectionArea` (guard `arch.raw-selection-area`), so Copy stays on wherever text is selected. The Paste state is refreshed from the pasteboard each time a field gains focus and each time the Edit menu opens (`PlatformMenu.onOpen`; a field only reads it when created and after its own copy or cut, so a message's Copy button or Copy Transcript would otherwise leave Paste stale). The refresh lands after the menu has started opening and the engine then swaps in a new menu, so after an in-app copy made with focus unchanged Paste is right from the second open of the Edit menu, not the first (the copies are not routed through one helper: there are about sixteen `Clipboard.setData` sites), and a field rebuilt with another controller while focused is followed (a self-re-arming post-frame identity check that runs only while a field is bound). While a conversation window is key (`ConversationWindows.keyWindowId` set) or the quick panel is shown (`ConversationWindows.quickPanelKey`, set from the panel's `shown` and `hidden` reports, and cleared when the panel is dropped on sign-out or when its engine goes away; the native panel is made key when shown and reports no key changes), `ConversationWindowsMenu` sets `EditMenuState.suspended` and all six items are off: this engine's focus is the main window behind, not what the user is editing. One known gap: while the panel is held (dictation in its composer, `keepsFocusHere` in `QuickPanel.swift`) it does not hide when the main window is clicked, so the Edit items stay off until the hold ends. Delete… (⌘⌫) deletes to the line start while a text field has focus. Menu shortcuts reach the menu only when no Flutter widget handled the key, so don't add a `HardwareKeyboard`/`Shortcuts` handler for a chord the menu owns. File > New (`MacCommand.newChat`, ⌘N) follows the page in front: New Chat on Chat, New Task on Kanban, New Schedule on Schedules, each page retitling it through its scope. View > Back (⌘[) is offered by a pushed `SettingsScaffold` while its route is current (not under a dialog or sheet) and leaves that page. Chat > Change Folder… (`MacCommand.changeFolder`, no chord, Mac only) is offered by `ChatScreen` for the open chat, disabled while it replies and in a conversation window (see chat.md, Working directory). View > Show Files (`MacCommand.showFiles`, ⇧⌘F) is offered by `ChatScreen` while the server has `/api/fs` (disabled otherwise) and disabled while a conversation window is key: a window has no session of its own, so a Files page there could not close on App Lock or an expired session, and it provides no `HermesRepositories` (which would also make `MemoryDestination` work there). View leads with Reload (`MacCommand.reload`, ⌘R, its own group), then lists Back and Forward with Enclosing Folder (`MacCommand.enclosingFolder`, ⌘↑) and, Mac only, Previous Change and Next Change (`MacCommand.previousChange` and `nextChange`, ⌥↑ and ⌥↓, below Show Files). `FilesScreen` offers Reload and Enclosing Folder (the latter on only while `canGoUp`), `ProvidersScreen` offers Reload, and so do the Kanban board, Active workers, Plugins (it reloads the tab in front, with the same failure notice as pull to refresh through `refreshReporting`), the Checkpoints page (off while its list loads or is out of date), Schedules and Connection (`HomeScreen`), each only on the Mac and off while a reload the user started runs (a `_reloading` flag set around the refresh; Schedules' minute timer and change-feed reads never set it, so they show no spinner); each also has a 28 pt Refresh button in its Mac toolbar (`MacToolbarButton`, tooltip "Refresh ⌘R", `busy` swaps a spinner for the glyph while the reload runs and the button says "Refreshing" (`commonRefreshing`) to screen readers, not just "dimmed"; the Checkpoints page sits in the Activity panel's own bar, so there it is a `NamedIconButton` with `ActivityPageAction.busy`). The Mac has no pull to refresh: a screen wraps its scrolling list in `PlatformRefresh` (`lib/src/widgets/platform_refresh.dart`), which is a plain pass-through on macOS and `RefreshIndicator.adaptive` elsewhere, so a screen that gets it needs View > Reload and a toolbar Refresh. `showKanbanTask` opens a task as the form-sheet dialog on macOS at any window width, never the phone detent sheet. `FileChangePage` offers the change steps (each on only while there is a file before or after); each registers through its own `MacCommandScope` and binds no key of its own where the menu owns the chord, so a Mac key press reaches them through the menu and the item shows its enabled state. The Files and Providers screens never bound ⌘R or ⌘↑ off macOS, so nothing is kept there; `FileChangePage` keeps its ⌥↑ and ⌥↓ key bindings on every chrome except macOS, since Windows, Linux, iPad and Android have no menu item for them. ⌘↑ is a text caret key on iPad and ⌥↑ and ⌥↓ move by paragraph, so Enclosing Folder is in the iPad menu without a chord (`ipadShortcut: false`) and the change steps are not on iPad at all; Reload is on iPad too, with ⌘R (it keeps the default `ipadShortcut: true`). While a conversation window is key, `ConversationWindowsMenu` turns all four off: it has no such pages. Tests answer `SystemChannels.menu` and set `MacWindow.enabled` (`test/macos/mac_menu_bar_test.dart`). The menus are described once in `menu_layout.dart` (`menuLayout`: sections, groups, `MenuEntry` with its chord and platforms; labels are `(l10n) => l10n.macosMenu…` callbacks, read with `entry.label(l10n)`, so the Mac menu, the Edit and Window menus in `macMenus(registry, l10n)` and the iPad layout all follow the app's language; `MacMenuBar` rebuilds the menus and resends the iPad layout when the locale changes, German uses the system names Ablage, Bearbeiten, Darstellung, Fenster and Hilfe, and the screens that retitle a command through `MacCommandHandler(title:)` read their titles from the same `macos*` and `chatActivityInspector*` keys); `macMenus` renders it for the Mac, and on iOS and iPadOS `IpadMenuBridge` (`ipad_menu_bridge.dart`, mounted by `MacMenuBar` with iOS chrome) sends it once plus each command's enabled flag and title over `hermes_app/menu` to `ios/Runner/KeyCommandMenu.swift`, which builds `UIKeyCommand`s in `buildMenu(with:)` and answers `canPerformAction` from that state. Flutter sees a key first; for an enabled item UIKit then runs the command once, for a disabled one the key stays with the app. The iPad has no Open in New Window, Close Window, sidebar or inspector items and no chord for Delete…; ⌘F is `MacCommand.find` on both (on iPad `ChatScreen` offers it from the layout while the sidebar is beside the chat and focuses its search field). Breadcrumb `menu.command`, log `ipad_menu.sync_failed`. Chat > Export Chat as JSON… (`MacCommand.exportThread`, after Copy Transcript, no chord, Mac and iPad) is offered by `ChatScreen` for every chat and disabled for no chat, a local chat, a chat without a profile and while an export runs; `ConversationWindowsMenu` sends it to the key window (`ThreadAction.exportJson`) and disables it when that window has no profile. The window reports its export's busy state to the main window, which disables the item meanwhile. Chat > Compress Conversation… (`MacCommand.compress`, Mac only, titled from `macosCompressConversation`) is offered by `ChatScreen` (`chat_screen_checkpoints.dart`): on only while the selected stored chat's `ContextController.canCompress` (idle, live session, connected, not locked, a server that compresses), and it opens `confirmCompressFlow`, the same confirmation the Context details page uses (a `CompressConversationEntry` can replace it, as a test does); the screen listens to the selected chat's context controller so the item follows it. While a conversation window is key, `ConversationWindowsMenu` turns it off: windows hold no checkpoint or context controllers.

**Main window size** (macOS, `macos/Runner/Base.lproj/MainMenu.xib`, `MainFlutterWindow.swift`). The main window opens at 1100x760 (`kMacMainWindowDefaultSize`): the xib's content rect before the title bar merges in, so AppKit makes a 1100x788 frame and, with `enableFullSizeContentView`, the Flutter view is 1100x788. That is above `kWideLayoutBreakpoint`, so a fresh window gets the wide layouts. It cannot be resized below `MainFlutterWindow.minimumContentSize`, 640x480 (`kMacMainWindowMinSize`), but that is not a xib content rect: AppKit applies `contentMinSize` against the full-size style mask, so the minimum reads as a 640x480 frame and the Flutter view is 640x480 with the toolbar included. The exact effect of the minimum is unmeasured until the CI measurement of the window lands. `awakeFromNib` calls `setFrame` first and `center()` after it (`setFrame` restores the xib origin), so a fresh window opens centred. `test/macos/main_window_size_test.dart` reads the xib and the Swift file, compares them with the Dart constants, pins where and in which order they are decided, and lays the home shell and an open chat out at both sizes. The 1100x760 default is the size of a launch without saved state. The xib window is restorable (`applicationSupportsSecureRestorableState` is true) and has no frame autosave name, so AppKit's Saved Application State is the only thing that brings a frame back, after `awakeFromNib`. Under the default macOS setting "Close windows when quitting an application" the state is thrown away on Cmd-Q, so a normal relaunch starts at the default centred. The frame can come back after a kill (`scripts/dev-app.sh stop`, `flutter run`), a crash, Quit and Keep Windows (⌥⌘Q), a logout or restart with "Reopen windows when logging back in", or with that setting off. That is why dev runs never showed the xib size (an earlier "never reached the built app" note), and the xib size is not verified on a Mac. Remembering the frame between launches needs a frame autosave name, which #1168 adds. The minimum is not affected by restoration: nothing after `awakeFromNib` sets `contentMinSize` (macos_window_utils swaps the content view controller and re-applies the same frame), but a restored frame smaller than the minimum is not clamped and stays until the user resizes it. On a small screen AppKit constrains the window to fit (a 1366x768 display cannot hold 1100x760 plus the menu bar and title bar). Conversation windows have their own 480x420 frame minimum and frame autosave. The screenshot scripts resize the window through `setContentSize` (`store-screenshots` skill).

**Conversation windows** (macOS, `lib/src/windows/`). A chat can open in a window of its own (double-click in the sidebar, the thread menu, File > Open in New Window ⌥⌘O). Each window is its own engine and isolate (`desktop_multi_window`; Flutter's own multi-window API is master-only), started through `main(["multi_window", id, args])` into `runConversationWindow`. A conversation window holds no session and never refreshes one: `WindowAuthInterceptor` asks the main window for each request's headers (`AuthController.windowAuthHeaders`, which refreshes only when the rejected token is the current one), and `MainFlutterWindow.swift` registers only a few plugins in its engine (no secure storage, notifications or macos_window_utils). Only the main engine sets the menu bar, telemetry and notifications. `ConversationWindows` (main isolate) tracks the open windows and the key one, persists them for the next launch (frames through `NSWindow` frame autosave), closes them on sign-out, and forwards "Show in Main Window" to the shell. Each engine keeps its own state: a window reloads its chat when it becomes key, and the main window reloads the chats that were open in a window when it becomes key (`ChatController.refreshThread`). The main window is hidden, not released, when closed, so its engine keeps serving the windows; ⌘0 or the Dock icon brings it back. `ConversationWindowsMenu` (in `HermesApp`'s builder) lists the windows in the Window menu and, while one is key, routes the menu bar's window and chat commands to it with a priority-1 `MacCommandScope`, which also disables View > Back so a settings page in the main window stays put. Handoff advertises the key conversation window's chat, and a handed-over chat that has a window opens there. The quick panel (`lib/src/quick_panel/`, change `mac-quick-panel`) is one more engine of this kind, started with `QuickPanelLaunch` (`kind: panel`): on its first `presentPanel` call `QuickPanel.swift` moves its view controller into a non-activating floating `NSPanel` and orders the plugin's window out, so the panel takes keys without bringing Hermes forward. A global shortcut opens it: the Swift package KeyboardShortcuts (Xcode SPM on the Runner, pinned in `Package.resolved`) registers the user's chord (none by default) in `QuickPanelShortcut.swift` and forwards presses over `hermes_app/quick_panel` to `GlobalShortcut`; `QuickPanelShortcut` (Dart) toggles the panel through `ConversationWindows.togglePanel` while signed in and shows the main window otherwise. Settings… records the chord with the package's native recorder (`AppKitView` `hermes_app/shortcut_recorder`). The panel is never saved or listed in the Window menu, closes on sign-out, and gets the dictation plugins conversation windows leave out. `QuickPanelScreen` holds one chat on the main window's current profile (`profile.current` on the main channel): before the first send the panel is just the composer and as tall as it, after it the chat's `ChatThreadView` (`welcome: false`) at a fixed height (`resizePanel`, capped at 60% of the screen natively). A show continues the chat when it was used within five minutes on the same profile (`QuickPanelSession`) and otherwise starts empty. Open in Hermes (⌘O) hides the panel, then asks the main window (`panel.showInWindow`) to open the chat, with the composer's draft, through `ConversationWindows.open`. Dictation there goes through `ComposerDictation` (`lib/src/voice/`), as in `ChatScreen`, and the chat view's callbacks, latest-reply tracking and model pill come from `lib/src/chat/chat_thread_bindings.dart`, shared by the chat screen, conversation windows and the panel. A conversation window and the quick panel offer no voice call (the call lives in `ChatScreen`, which they do not use) and register neither `record` for calls nor `flutter_soloud`; the Mac toolbar carries the call button (`MacChatToolbar.callButton`, before New Chat), and the call opens as a 480 pt dialog at every Mac width (`showVoiceCall`, never a sheet). Neither a conversation window nor the quick panel shows the connect-a-model welcome card or a failed reply's "Check model providers": `ChatScreen` alone passes `welcomeCard` and `onCheckProviders` to `boundChatThreadView`, and they have no Model providers screen to open.

**Dock menu** (macOS, `lib/src/macos/dock/`, `macos/Runner/DockMenu.swift`). AppKit asks for the Dock icon's menu synchronously, so Dart pushes what it shows (`DockMenuBridge.update`, method `dockMenu` on the `hermes_app/app` channel, `MacApp.setDockMenu`) and `AppDelegate.applicationDockMenu` builds it from the copy in memory: New Chat, up to five recent chats of the shown profile (remote, not Bot Chat registries, newest first, titles cut to 40 characters), Show Main Window (native only, so it works in every state). `DockMenuController` (provided in `main.dart` on a Mac) holds the state, which `DockMenuGate` sets from `AuthController` and `AppLockController` (`off` unless connected, `locked` while covered, else `ready`); only `ready` carries titles, and `ChatScreen` supplies them from `_changed` and clears them in `dispose`. A pick comes back as `dockNewChat` or `dockOpenChat`; `ChatScreen._showChat` (shared with Handoff) focuses the chat's conversation window or restores it in the main window. New Chat while locked waits for `AppLockController.unlock()` (which returns whether the app is unlocked and joins a prompt already open) and is dropped if the unlock fails, the app locks again, the user signs out or a newer pick replaced it. Breadcrumbs `dock.menu.action` and `dock.menu.deferred` and the event `dock.menu.open_failed` hold no titles, ids or profile names.

**Drag out** (macOS, `lib/src/drag_out/`, `macos/Runner/DragOut.swift`). Chat attachments and Kanban task attachments drag out of the app as files (file promises: the bytes are read only when the receiver asks). Widgets never touch the platform: they wrap their child in `DragOut(kind:, item:, child:)`, which asks the `DragOutSource?` provider (set in `main.dart`, `MacDragOutSource` on macOS, null elsewhere, so conversation windows and the catalog see none) to make it draggable. `MacDragOutSource` watches the pointer (a `Listener`, not the gesture arena, so taps, selection and scrolling are untouched) and after 6 px with the primary mouse button down calls `startDrag` on the `hermes_app/drag_out` channel. `DragOutController` (Swift, registered by one line in `MainFlutterWindow.awakeFromNib`) remembers the window's latest left-button `NSEvent`s with a local monitor, starts `beginDraggingSession` on the Flutter view from them, allows copy only outside the app (so `desktop_drop` cannot take the file back), and at the session end posts a synthetic `leftMouseUp` to the Flutter view (the session swallows the real one, which would leave Flutter's button state stuck). Files go out as `NSFilePromiseProvider`s: on demand Swift asks Dart (`readFile`), which answers with the path of a local file (`DragOutFile.localPath`, copied natively) or, when there is none, the bytes; a 60 s timeout fails the promise, and `fileWritten`, `readTimedOut` and `ended` report back; text goes out as an `NSPasteboardItem` with plain text and Markdown. `DragOutItem` is `DragOutFile(name:, read:)` or `DragOutText`; names go through `sanitizeDragFileName`. `DraggableAttachment` (`chat/attachments/`) wraps `AttachmentCard`/`AttachmentThumbnail` in `chat_builders.dart` and offers the picked path or the `MediaStore.file` cache copy as the local file, bytes only for an embedded attachment; `DraggableKanbanAttachment` wraps a task panel row and reads through `KanbanTaskController.readAttachment`. `DragOutTelemetry` records the `drag_out.started` breadcrumb, `drag_out.promise` span and `drag_out.completed` event (slugs only, never names or ids). The drop side stays `desktop_drop`; the controller registers no drag destination. Message text and chats drag out too: `MessageDragGrip` (`chat/widgets/`, wrapped around the bubble in `_buildText`; a gutter beside the message holds the grip on hover, so it never covers content; the gutter stays but the grip is off while a reply streams, and neither exists where there is no source) drags `DragOutText(message.text)` as plain text and Markdown; a Mac sidebar row (`ThreadSidebar._row`) drags `threadDragItem` (`chat/thread_export.dart`), a `<title>.md` promise of `# <title>` plus the Copy Transcript Markdown, read through `ThreadHousekeeping.history` only on the drop (`DragOutKind.thread`, failure `history`; a promise Swift times out is `timeout` and cancels the read between pages). A started drag cancels the pointer in the gesture binding, so releasing near where it began is not a click. Tests: `FakeDragOutSource`, a mocked channel for `MacDragOutSource`, `macos/RunnerTests/DragOutTests.swift` for the promises; the catalog uses `CatalogDragOutSource`.

**Staying alive and the menu bar item** (macOS, `lib/src/macos/menu_bar_extra/`, `lib/src/shell/app_presence.dart`, `lib/src/macos/mac_app.dart`). Closing the last window leaves the app running with its Dock icon (`applicationShouldTerminateAfterLastWindowClosed` is false, the activation policy never changes); Cmd-Q, Hermes > Quit and the menu bar item's Quit end it, the last through `MacApp.terminate` (channel `hermes_app/app`). `AppDelegate.refreshWindowless()` tells Dart when no window is on screen (`MacApp.windowlessChanges`) and holds a `beginActivity` against App Nap meanwhile. `AppPresence.foreground` counts `hidden` and `inactive` as running on macOS, so `ScheduleWatcher` keeps its minute timer; `AppPresence.focused` stays `resumed` only, so notifications still post with no window. The menu bar item is an `NSStatusItem` in the runner (`MenuBarStatusItem` at the end of `MainFlutterWindow.swift`, created by the main engine only, not `tray_manager`: 0.8.0 builds a C++ core for every platform). Dart sends it the icon state (SF Symbols `bubble.left`, `ellipsis.bubble`, `exclamationmark.bubble`, as template images) and the whole menu in one `update` call on `hermes_app/menu_bar_extra`, and hears `selected` (an item key) and `opened`. `MenuBarExtraModel.of(chat)` reads the replying threads and pending requests the `ChatController` already holds (no polling, no request on open; replies running only in a conversation window are not listed) and is compared with `==` so the menu is sent only when it changed. `buildMenuBarMenu` makes the rows: approvals are submenus with the card's own choices (`offeredApprovalChoices`, `approvalChoiceLabels`), other requests open their chat, and New Chat, Show Main Window and Quit end it. `MenuBarExtra` (plain Dart, over the `MenuBarTray` boundary) acts on a pick: approvals go through `ChatController.answerApproval` like the card, "Always allow" asks first (`confirmAlwaysAllow`), an answer that did not go through opens the chat, and a chat with a conversation window is focused instead of opened in the main one. `MenuBarExtraHost` (in `HermesApp`'s builder, so a signed-out app keeps its item) owns it and provides a `MenuBarExtraLink` that `ChatScreen` connects its controller to while it is on screen; `MenuBarExtraSettings` (`menuBarExtra.enabled`, on by default; the "Menu bar item" switch in Settings) hides the item without changing the stay-alive. While the app is locked (`AppLockController.covered`; the host sits above `AppLockGate`) the menu shows counts, "Unlock Hermes…" and the fixed entries only, with no title, command or choice. Row keys come from what a row does (`approve:<thread>:<request>:<choice>`), so a pick on a changed menu does nothing (crumb `menubar.stale_pick`); an approval is answered once (in flight from the pick, rechecked after the "always" question); the runner applies an update only when the open menu closes; the item stays hidden until `MenuBarExtraSettings.loaded`. Crumbs `menubar.opened`, `menubar.action` and `menubar.stale_pick` and the log `menubar.approval_answered` carry counts and fixed names only (`choice` is once, session, always, deny or other).

**Pickers on desktop.** `showModelPicker` follows the platform before the width: on macOS, Windows and Linux the composer's model pill opens it as a popover on the pill (`lib/src/widgets/anchored_popover.dart`) and every other caller as the adaptive dialog, at any window width, so the default Mac window never gets a bottom sheet. Escape and the arrow keys are the route's; no menu chord is added. The popover is painted on the dialog's surface (`dialogTheme.backgroundColor`, else `surfaceContainerHigh`: zinc900 in dark, so it stands off the chat), pads its search field, list and effort block 20 pt, and marks the row the arrows reached with a 2 pt outline in the link colour (radius 10) instead of the grey fill and radio ring Settings rows get (`GroupedChoiceRow` with `rowFocusable: false`, which only the model popover passes). Its search field is the shared `MacToolbarSearchField` (26 pt, hint centred on the field).

**Mac button height** (`lib/src/theme/hermes_theme.dart`, test `test/theme/mac_button_height_test.dart`, decision in `docs/design-briefs/platform-controls.md`). On a Mac a plain FilledButton (also tonal), OutlinedButton and TextButton are 28 pt tall, the AppKit regular push button height and the app's Mac minimum target. ThemeData's desktop default density is compact, which takes 8 off a button's minimum size, so the Mac theme's `minimumSize` height is `_kMacButtonMinHeightBeforeDensity` (28 + 8) and renders 28. Density and padding are not set in the button themes, because a theme's density or padding reaches every button that styles only part of itself (AppBanner's flush action, `toolsButtonStyle`, `TextButton.icon`); the theme sets only `minimumSize`, which a button's own `minimumSize` replaces. A button that sets its own `minimumSize` and no density is still 8 pt shorter than that size on a Mac.

**Keyboard shortcuts on Windows and Linux** (`lib/src/macos/menu_layout.dart`, `lib/src/navigation/desktop_command_shortcuts.dart`, `keyboard_shortcuts.dart`). The commands of the menus have one declaration, `menuLayout`, and a `MenuEntry` holds its Mac chord (`shortcut`) and its Windows and Linux chords (`desktopShortcuts`, the first one is the one a tooltip and a menu show) side by side; `MenuPlatform.desktop` is the third platform the layout is read for, next to `mac` and `ipad`, and the `ipadShortcut` gate is unchanged. The chords are the Windows and Linux column of the "F1 command set" in `docs/design-briefs/windows-linux-platform-fixes.md`, not the Mac's with Ctrl for Cmd: Delete and Inspector have none (Ctrl+Backspace deletes a word), nothing uses Ctrl+Alt (AltGr) or Ctrl+[ and Ctrl+], no Ctrl chord is one text editing uses, and Previous and Next Change are F8 and Shift+F8 (Alt+Up and Alt+Down stay with the Mac, and with Android and iPad keyboards in `FileChangePage`). `DesktopCommandShortcuts`, inside `MacMenuBar` (so below the `MaterialApp` theme), binds every desktop chord with `Shortcuts` and an `Action` that runs the command through the same `MacCommandRegistry` the screens already register with (`MacCommandScope`), only where `bindsDesktopChords` holds (Windows and Linux). A chord whose command has no enabled handler is not taken, so the key reaches what has focus; the chords sit below Flutter's `DefaultTextEditingShortcuts` in the tree, which would let them win, so while an `EditableText` has primary focus a chord that those shortcuts also bind is not taken (Alt+Left, Alt+Right and Alt+Up move the caret in a field and run Back, Forward and Enclosing Folder anywhere else; the clash set is read from the framework, not listed by hand). `test/navigation/desktop_command_shortcuts_test.dart` presses every such chord in a focused field and checks the caret moves and nothing runs. Screens that offered a command only on the Mac (Reload on the Connection, Kanban, Schedules, Plugins and Active workers pages, Settings in `AppShell`, Previous and Next Change) now offer it on Windows and Linux too. Show or hide the sidebar (Ctrl+B) opens and closes the chat list's drawer in the narrow Windows and Linux layout while the list shows; the wide layout has no hidden state, so the command is not offered there. Key names on the page and in tooltips (Ctrl, Alt, Shift, arrows) come from `app_en.arb` and `app_de.arb` (`navigationKey*`), so a German keyboard reads Strg and Umschalt; from 1.3x text the page puts the key caps on a line under the command, where they wrap. F1 runs `MacCommand.keyboardShortcuts`, which `MacMenuBar` registers and which opens the Keyboard shortcuts page (`showKeyboardShortcuts`, not twice); the page is generated from `menuLayout` (`keyboardShortcutSections`), so a command is listed once, and Settings has a "Keyboard shortcuts" row on the Mac, Windows and Linux. Tooltips take the chord through `withChordHint` ("New chat (Ctrl+N)"); Mac buttons keep their own `shortcut:` text. The stock Material back button keeps its "Back" tooltip (it takes no custom text, and `BackButton` is what the navigation tests look for); Alt+Left still works. `arch.menu-chord-outside-menu-layout` fails a `SingleActivator` on one of those keys, or a `ctrlActivator`, outside `menu_layout.dart`.

**Menu bar on Windows and Linux** (`lib/src/navigation/desktop_menu_bar_host.dart`, `desktop_menu_models.dart`, `desktop_menu_bar_settings.dart`, `widgets/desktop_menu_bar.dart`). An optional Material `MenuBar`, 40 px high, with File, View, Chat and Help, behind the Settings switch "Show menu bar" (`DesktopMenuBarSettings`, preference `desktopMenuBar.enabled`, off by default; the row exists only where `bindsDesktopChords` holds, and the Mac menu bar item switch is a different setting). `DesktopMenuBarHost` sits inside `AppLockGate` and around the app's `Navigator`, so a locked app shows no bar, and is the app and nothing else on a Mac, iPhone, iPad and Android and while the switch is off. It wraps the bar and the app in an `Overlay` of its own, because the menus need one and the app's only overlay is inside the `Navigator`. `DesktopMenuBar` is a plain-model widget (`DesktopMenuModel`, `DesktopMenuItemModel`, callbacks only); `desktopMenus` builds the models from `menuLayout` on `MenuPlatform.desktop` and the `MacCommandRegistry`, so the bar, the Mac menus and the Keyboard shortcuts page share one declaration. An item is enabled while a screen offers an enabled handler for its command, takes its title from the handler (Pin becomes Unpin), runs `registry.invoke`, and shows the first desktop chord written by `desktopChordOf` after its label ("Ctrl+N", "Strg+N"). The bar binds no key: a `MenuItemButton` with a `shortcut` would register a second handler for a chord `DesktopCommandShortcuts` owns, so the chord is only text. The Hermes menu is the Mac's application menu: on this bar its Settings and Connection Details follow File's own items, Sign Out ends File after a divider and About ends Help (addendum in the brief). While a `PopupRoute` (dialog, sheet, popup) is open, which `ModalRouteObserver` on the app's `navigatorObservers` reports, every item is disabled, because the bar is above the `Navigator`; `DesktopCommandShortcuts` is unchanged. F1 and the Settings "Keyboard shortcuts" row stay; the bar adds no commands button. Superseding the canvas: the 32 px strip is 40, the app-bar "Commands" button is dropped, and the canvas command table is replaced by the "F1 command set" table in the brief. `test/navigation/desktop_menu_bar_test.dart` and `test/settings/settings_desktop_menu_bar_test.dart` cover presence per platform, dispatch, disabled items and the chord text.
