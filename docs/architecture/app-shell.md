# App shell, navigation and profiles

**State and routing.** `lib/main.dart` sets up telemetry and `provider` (`AuthController`, `ThemeController`, `NotificationSettings`, `ShareController`). `lib/src/app.dart` picks the screen purely from `AuthController.state` (`HermesConnectionState`): setup, login or `AppShell`. There are no named routes. `shell/app_shell.dart` navigates between Chat, Bots, Kanban and Schedules. Bots uses the shared gateway and explains when the dashboard lacks Bot Mode support. The Kanban tab (`lib/src/kanban/`) only exists while the server reports the Kanban plugin as on, and the Schedules tab (`lib/src/schedules/`, the server's cron jobs) only while `/api/cron/delivery-targets` answers. Both are re-checked on connect and on app resume. The board is shared by every profile, so Kanban requests (and the plugin check) send no `profile`; the job form asks for the delivery targets and blueprints of the job's profile. A page stays alive behind the others once opened; the board closes its event stream while it is not on screen (`KanbanBoardController.active`, set from `Visibility.of` and the app lifecycle) and resumes from its cursor. On macOS the board has the Mac toolbar (`widgets/kanban_mac_toolbar.dart`, on `macos/mac_toolbar.dart`) and opens a task in an inspector on the right (`KanbanInspector`, `widgets/kanban_inspector_layout.dart`: docked from 760 pt, over the board below that) instead of a sheet; View > Inspector (⌥⌘I) and File > New (⌘N, titled New Task) come from its `MacCommandScope`. Opening a run of a job goes through `ChatOpenRequests` to the chat screen. On macOS a task's attachment rows are Quick Look targets too (`KanbanTaskController.preview` and `open` stage the file through the same `MediaStore`). `AuthController` owns the whole connection lifecycle: server URL discovery, sign-in, token storage and refresh, and the authenticated `Dio` instance.

**Messenger navigation** (`lib/src/chat/chat_screen.dart`). Compact iOS and Android layouts start on Chats. A nested list/detail navigator keeps the existing chat owner alive while Back reveals the list; wide layouts retain their split view and macOS compact overlays. New message selects a profile locally and scopes history, model options, voice, and gateway sends explicitly. `ProfileAvatarRepository` reads `profiles.get_asset` with `name` and `asset: avatar`; `ProfileAvatar` uses authenticated image bytes or a deterministic monogram in rows, recipient controls, and headers. Dispose avatar reads and cached bytes when the account owner changes.

**Profile scope on macOS** (`lib/src/profiles/`). `ChatProfiles`, owned by `AppShell`, holds the server's profiles and the chat's local recipient; selecting one never changes the server active profile or CLI default; `ChatScreen` reports its profile with `showing` and attaches `loadThreads` as the switch handler. On macOS `AppShell` puts `MacProfileSwitcher` above the destinations and adds a Profiles destination (`MacProfilesPage`: the profiles beside the selected one's home with counts read lazily, each opening the existing screen for that profile). The Mac sidebar has no per-profile management rows and ends in `MacAccountFooter` (Settings… opens `showSettingsDialog`, which `AppShell` also registers as the menu bar's `MacCommand.settings`, next to `connectionDetails` and `signOut`; Sign Out asks first through `confirmSignOut`). The page reads Messaging and plugins per profile through `HermesMessagingRepository.forProfile` and `HermesPluginManagerRepository.forProfile`. Memory is per profile like Skills: a sidebar action right after Skills off the Mac (drawer and More section) and a Memory section after Skills on the Profiles page (count from `MemoryRepository.count`); both go through `openMemory` (`memory/memory_destination.dart`), which records `nav.memory` and opens `MemoryDestination` on that profile, never the server's active one. Settings has no Memory row. `AppShell` owns the `MacSidebarController` so a pick closes the compact overlay.

**App prompt hint** (`lib/src/platform_hint/`). Hermes has no prompt hint for the app's session source (`hermes_app`), so after sign-in and on each start `AppShell` checks every profile's saved config (`GET /api/config?include_defaults=false`) for `platform_hints.hermes_app`. When some profile lacks it, or still holds a text an earlier app wrote (`earlierAppPlatformHints`; add the old text there whenever `appPlatformHint` changes), `PlatformHintPrompt` asks first: a checklist of those profiles, the exact text on request, and Add / Not now / Don't ask again (per server, in shared preferences). Add sends only that key with `PUT /api/config?profile=`, which Hermes deep-merges; a hint someone else wrote is never touched. New sessions pick it up.

**Server care** (`lib/src/server_care/`; roadmap 4.7, `openspec/changes/server-care`). `ServerCareRepository` (on `HermesRepositories`) reads the server-care routes through the generated client and answers a `CareResult`, never throwing; parsers are lenient and a route the server lacks is `CareUnsupported`, so its part hides without an error. `ServerCareController`, one per `AppShell`, holds the status for the chat's profile (followed through `ChatProfiles`, never the server's active profile) and the `Attention` ranking behind `ServerAttentionMark`. It reads on open, on refresh, on a profile switch (an answer to the old profile is dropped) and when the app resumes at most every 5 minutes (Dart timers stop while iOS suspends the app, so resume is what catches up); under App Lock nothing is read, and the read missed is made up on unlock. A gateway restart or start in progress (`gatewayBusy`) hides the gateway rows of the headline. Its span `server_care.status.fetch` and the event `server_care.unsupported` (once per part and connection) carry fixed names only: never the profile, a log line, a model name or an address. **Pages that outlive the shell.** Server care pages are pushed on the root navigator, which stays when `AppShell` unmounts at sign-out, session expiry or server change. `ConnectionGuard` (`lib/src/server_care/connection_bound.dart`) watches `AuthController` and says when the connection a page was opened for ended: the state left `ready` (when it was ready at the start), protected requests closed, `ownerGeneration` changed or `baseUrl` changed. `ConnectionBound` wraps a page with it and removes the page's own route (`dismissRoute`, so never a dialog on top); `_carry` in `server_screen.dart` and `showUpdatePage` use it, so Server, Usage, Update and Logs all go. The Logs page also uses the guard itself to drop its lines at once. Any question or menu open above the Logs page is closed, and an answer to a stale question copies nothing, when the connection ends, the profile switches or App Lock covers (a counter, `_epoch`, compares). Covering also clears the typed search. The update run stays the shell's. **Logs** (`server_logs_page.dart`, `server_logs_controller.dart`): `ServerLogsController`, owned by the page, reads `/api/logs` for the chat's profile (default Errors, 200 lines, 500 after Show older, a search 400 ms after typing stops, only the latest answer kept) and keeps the lines, newest first, in memory only: dropped on page close, App Lock cover, sign-out, server change and profile switch, and read again after unlock. The page holds `SecureWindow` (`FLAG_SECURE` through the app's own `hermes_app/secure_window` channel on Android), wraps itself in `PrivateSurface` (a blank surface while the app is inactive or hidden on iOS and Android) and asks before Copy shown lines. Show logs opens it from the Logs row, from the headline for an unexpected restart (agent log) and offline channels (gateway log), and from a failed or slow gateway row (gateway log). Its span `server_care.logs.fetch` carries `file`, `level`, `filtered` (a flag, never the search), a `lines` bucket and `outcome`; the breadcrumb `server_care.logs.opened` carries `file`.

**Server care: updating Hermes** (`update_page.dart`, `update_actions.dart`, `update_banner.dart`, `widgets/update_*.dart`). `AppShell` owns one `HermesUpdateRun` per connection (provided next to `GatewayRestart`, resumed on launch, dropped on sign-out and server change when `AuthController.ownerGeneration` moves, `forgetText()` while App Lock covers the app). `UpdatePage` offers Update Hermes only for an available or rollback check; `runUpdate` counts the running replies (`RepliesInProgress`, attached by the main window's `ChatScreen`: remote threads that are replying) and the status's `active_agents`, asks through `UpdateConfirmDialog` (Cancel first and the default on Apple platforms, two text buttons on Material, nothing filled) and only then calls `start()`; Cancel sends nothing. `updateRunViewOf` turns a run into a plain `UpdateRunView` (the step list while it goes, `UpdateOutcomeCard` or the refused card after). The page, opened from the Server screen or from the banner (`showUpdatePage`), only shows the run: leaving never cancels, and Done, Try again (asks again), Check again, Keep waiting and Dismiss call the run. `UpdateBannerLayer` wraps the shell's main window only (never a conversation window or the quick panel): the restart banner while `showsBanner`, "Hermes <version> is ready" after a success it saw, which goes after 6 s or stays under reduced motion. It sits above each destination's own app bar, not under the toolbar: every destination (Chat, Bots, Kanban, Schedules, the Mac pages) draws its own bar, so a banner under "the toolbar" would have to be wired into each of them; one layer above them shows on all, and the page below loses the top inset it would have drawn (`MediaQuery.removePadding`). The banner paints through the window's top inset (status bar, notch or, on a Mac, the title bar that `MacWindowChrome` reports as top padding) and keeps its content below it; on a Mac that strip is a `MacWindowDragArea`. Tapping it opens the Update page unless one is already open. Pages the Server screen and the banner push sit above the shell's providers, so `_carry` and `showUpdatePage` take the care controller, the gateway and update runs and the reply counter along. After a finished or stale update the shell only re-checks Kanban and Schedules (`_detect`) and the care controller re-reads the status; it never calls `AuthController.connect`, which would replace the setup screen and the API client if it failed. `ServerCareController.updating` follows `busy`, so the Mac sidebar caption reads "Updating…" and the Updates row says so. When an update ends, a Server screen or page that owns its check controller asks again with `force`.
