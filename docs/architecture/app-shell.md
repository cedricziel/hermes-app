# App shell, navigation and profiles

**State and routing.** `lib/main.dart` sets up telemetry and `provider` (`AuthController`, `ThemeController`, `NotificationSettings`, `ShareController`). `lib/src/app.dart` picks the screen purely from `AuthController.state` (`HermesConnectionState`): setup, login or `AppShell`. There are no named routes. `shell/app_shell.dart` navigates between Chat, Bots, Kanban and Schedules. Bots uses the shared gateway and explains when the dashboard lacks Bot Mode support. The Kanban tab (`lib/src/kanban/`) only exists while the server reports the Kanban plugin as on, and the Schedules tab (`lib/src/schedules/`, the server's cron jobs) only while `/api/cron/delivery-targets` answers. Both are re-checked on connect and on app resume. The board is shared by every profile, so Kanban requests (and the plugin check) send no `profile`; the job form asks for the delivery targets and blueprints of the job's profile. A page stays alive behind the others once opened; the board closes its event stream while it is not on screen (`KanbanBoardController.active`, set from `Visibility.of` and the app lifecycle) and resumes from its cursor. On macOS the board has the Mac toolbar (`widgets/kanban_mac_toolbar.dart`, on `macos/mac_toolbar.dart`) and opens a task in an inspector on the right (`KanbanInspector`, `widgets/kanban_inspector_layout.dart`: docked from 760 pt, over the board below that) instead of a sheet; View > Inspector (⌥⌘I) and File > New (⌘N, titled New Task) come from its `MacCommandScope`. Opening a run of a job goes through `ChatOpenRequests` to the chat screen. On macOS a task's attachment rows are Quick Look targets too (`KanbanTaskController.preview` and `open` stage the file through the same `MediaStore`). `AuthController` owns the whole connection lifecycle: server URL discovery, sign-in, token storage and refresh, and the authenticated `Dio` instance.

**Messenger navigation** (`lib/src/chat/chat_screen.dart`). Compact iOS and Android layouts start on Chats. A nested list/detail navigator keeps the existing chat owner alive while Back reveals the list; wide layouts retain their split view and macOS compact overlays. The composer's recipient chip (`ProfileRecipientChip`) shows beside the model pill only while the recipient can still be chosen (no chat selected, or a new local chat with no messages); a chat that has messages or comes from the server shows the pill alone, since its profile is fixed and the header shows it. New message selects a profile locally and scopes history, model options, voice, and gateway sends explicitly. `ProfileAvatarRepository` reads `profiles.get_asset` with `name` and `asset: avatar`; `ProfileAvatar` uses authenticated image bytes or a deterministic monogram in rows, recipient controls, and headers. Dispose avatar reads and cached bytes when the account owner changes.

**Profile scope on macOS** (`lib/src/profiles/`). `ChatProfiles`, owned by `AppShell`, holds the server's profiles and the chat's local recipient; selecting one never changes the server active profile or CLI default; `ChatScreen` reports its profile with `showing` and attaches `loadThreads` as the switch handler. On macOS `AppShell` puts `MacProfileSwitcher` above the destinations and adds a Profiles destination (`MacProfilesPage`: the profiles beside the selected one's home with counts read lazily, each opening the existing screen for that profile). The Mac sidebar has no per-profile management rows and ends in `MacAccountFooter` (Settings… opens `showSettingsDialog`, which `AppShell` also registers as the menu bar's `MacCommand.settings`, next to `connectionDetails` and `signOut`; Sign Out asks first through `confirmSignOut`). The page reads Messaging and plugins per profile through `HermesMessagingRepository.forProfile` and `HermesPluginManagerRepository.forProfile`. Memory is per profile like Skills: a sidebar action right after Skills off the Mac (drawer and More section) and a Memory section after Skills on the Profiles page (count from `MemoryRepository.count`); both go through `openMemory` (`memory/memory_destination.dart`), which records `nav.memory` and opens `MemoryDestination` on that profile, never the server's active one. Settings has no Memory row. Personality (a profile's SOUL.md, `lib/src/profiles/soul/`) sits right after Memory in both places: a sidebar action off the Mac (drawer and More section, `AppIcons.personality`, the chat's profile, or `default` for a chat that names none) and a Personality section after Memory on the Profiles page (the selected profile; no preview of the text in the list, nothing is read for it); both go through `openSoul` (`soul/open_soul.dart`), which pushes `SoulScreen` on the root navigator bound to that name and records `profile_soul.opened` with `source` `sidebar` or `profiles_page`. The entries show until the server says it has no such route: `SoulAvailability` (provided per API client by `soulAvailabilityProvider` in `auth_providers.dart`, like `FilesAvailability` but with no probe) is marked by the controller's `onUnsupported` on the first 404 whose detail does not start `Profile '` or a 405, after which the row and the section are gone for the connection (`soulShown(context)` watches it; with no provider nothing is offered); a missing profile or a failed read never hides them. `AppShell` owns the `MacSidebarController` so a pick closes the compact overlay.

**App prompt hint** (`lib/src/platform_hint/`). Hermes has no prompt hint for the app's session source (`hermes_app`), so after sign-in and on each start `AppShell` checks every profile's saved config (`GET /api/config?include_defaults=false`) for `platform_hints.hermes_app`. When some profile lacks it, or still holds a text an earlier app wrote (`earlierAppPlatformHints`; add the old text there whenever `appPlatformHint` changes), `PlatformHintPrompt` asks first: a checklist of those profiles, the exact text on request, and Add / Not now / Don't ask again (per server, in shared preferences). Add sends only that key with `PUT /api/config?profile=`, which Hermes deep-merges; a hint someone else wrote is never touched. New sessions pick it up.

**Server care** (`lib/src/server_care/`; roadmap 4.7, `openspec/changes/server-care`). `ServerCareRepository` (on `HermesRepositories`) reads the server-care routes through the generated client and answers a `CareResult`, never throwing; parsers are lenient and a route the server lacks is `CareUnsupported`, so its part hides without an error. `ServerCareController`, one per `AppShell`, holds the status for the chat's profile (followed through `ChatProfiles`, never the server's active profile) and the `Attention` ranking behind `ServerAttentionMark`. It reads on open, on refresh, on a profile switch (an answer to the old profile is dropped) and when the app resumes at most every 5 minutes (Dart timers stop while iOS suspends the app, so resume is what catches up); under App Lock nothing is read, and the read missed is made up on unlock. A gateway restart or start in progress (`gatewayBusy`) hides the gateway rows of the headline. `GatewayRestart` and `HermesUpdateRun` sleep through `_sleep`, which `appResumed()` (from `AppShell.didChangeAppLifecycleState`) cuts short so a poll waiting for a timer the suspended app never ran reads at once; it only reads, a POST already sent is never repeated, and while App Lock covers the app nothing is woken (the wake is owed and made up by `appUnlocked()` from the shell's lock listener). Its span `server_care.status.fetch` (outcome and the `attention` slug from `Attention.slug`) and the event `server_care.unsupported` (once per part and connection) carry fixed names only: never the profile, a log line, a model name or an address. **Pages that outlive the shell.** Server care pages are pushed on the root navigator, which stays when `AppShell` unmounts at sign-out, session expiry or server change; `ConnectionPageCloser` (see Pages above the shell) removes them when the connection ends, so Server, Usage, Update, Check and Logs need no wrapper. `ConnectionGuard` (`lib/src/server_care/connection_guard.dart`) only tells a page, a frame earlier, that its connection ended (the state left `ready`, protected requests closed, `ownerGeneration` or `baseUrl` changed), so the Logs page drops its lines at once. A question or menu the Logs page opened is closed, and an answer to a stale question copies nothing, when the connection ends, the profile switches or App Lock covers: each marks itself with `ClosesWith` (a dialog from anywhere else is left alone), a counter (`_epoch`) compares, and the page's chrome sits in a `KeyedSubtree` keyed by the epoch, which also closes an iOS menu (an overlay inside the page). Covering also clears the typed search. The update run stays the shell's. **Logs** (`server_logs_page.dart`, `server_logs_controller.dart`): `ServerLogsController`, owned by the page, reads `/api/logs` for the chat's profile (default Errors, 200 lines, 500 after Show older, a search 400 ms after typing stops, only the latest answer kept) and keeps the lines, newest first, in memory only: dropped on page close, App Lock cover, sign-out, server change and profile switch, and read again after unlock. The page holds `SecureWindow` (`FLAG_SECURE` through the app's own `hermes_app/secure_window` channel on Android), wraps itself in `PrivateSurface` (a blank surface while the app is inactive or hidden on iOS and Android) and asks before Copy shown lines. Show logs opens it from the Logs row, from the headline for an unexpected restart (agent log) and offline channels (gateway log), and from a failed or slow gateway row (gateway log). Its span `server_care.logs.fetch` carries `file`, `level`, `filtered` (a flag, never the search), a `lines` bucket and `outcome`; the breadcrumb `server_care.logs.opened` carries `file`.

**Server care: wide layout.** On iPad (700 pt), wide Android, Windows and Linux (900 pt, `isWideLayout`, measured on the screen's own width) `ServerScreen` builds `ServerSplitView`: the overview (340 pt, with its own bar and Back, rows without a chevron and `selected` highlighted and announced) on the left, the selected page on the right; narrower it pushes pages as before. **macOS never splits**: its pages push inside the destination with the toolbar Back and ⌘[ at every width, as the design brief says. The pages are listed once, in `_ServerScreenState._destinations` (`usage`, `update`, `logs`, `check`, in the order the first one that may open by itself is the default): each says whether the server offers it, whether it may be the default (Logs and the Server check may not: both hold `SecureWindow`, Logs reads `/api/logs`) and builds the page, so a new page is one entry. A pick is a `_Request` (page; for Logs its file and profile; for Check a run number); the page in the pane is keyed by it, so a new pick disposes the old page, and Logs or Check then release `SecureWindow` and drop what they hold. The default is Usage, else Update, else the empty state, and Logs or Check open only when the person picks them (row, Show logs, Run a check); a pick the server stops offering falls back the same way. A "Run a check" button starts one check when the pane builds the page for that request, and a rebuilt page never starts a second. The pages stay the same widgets: `SettingsPane` marks the pane, so `SettingsScaffold` draws no Back and a page that used to pop its route (Usage, Logs and Check on a missing route) calls `SettingsPane.close` instead. Selecting leaves the route stack alone. **Lifetime.** A route pushed over the screen (Connection details, a dialog) keeps the pane page as it is, nothing is read again when it goes. The pane is torn down for real only when the window narrows or the screen is hidden behind another destination (`Visibility.of`, the Mac shell is not the only one that keeps destinations in an `IndexedStack`): a pane page is then disposed, so an open Update confirmation is lost and a typed Logs search is gone, and a Logs or Check pick is forgotten so that showing the pane again lands on the default and reads nothing for Logs or Check by itself (an Update pick is restored). A pick is also forgotten when the care profile changes from a known one to another (a profile that only becomes known keeps a pick made before); a Logs page in the pane leaves on such a switch instead of following it (`SettingsPane.close`, its lines dropped), so nothing is read for the new profile, while a pushed page still follows. Widening while a page is pushed puts the default page in the pane under it as well. Nothing new goes into breadcrumbs or spans; `server_care.usage.opened` also counts the default Usage page of a wide Server open, once per pick in the pane (a rebuilt pane page for the same pick records nothing); every pushed open, on the Mac and on a narrow window, records as before.

**Server care: updating Hermes** (`update_page.dart`, `update_actions.dart`, `update_banner.dart`, `widgets/update_*.dart`). `AppShell` owns one `HermesUpdateRun` per connection (provided next to `GatewayRestart`, resumed on launch, dropped on sign-out and server change when `AuthController.ownerGeneration` moves, `forgetText()` while App Lock covers the app). `UpdatePage` offers Update Hermes only for an available or rollback check; `runUpdate` counts the running replies (`RepliesInProgress`, attached by the main window's `ChatScreen`: remote threads that are replying) and the status's `active_agents`, asks through `UpdateConfirmDialog` (Cancel first and the default on Apple platforms, two text buttons on Material, nothing filled) and only then calls `start()`; Cancel sends nothing. `updateRunViewOf` turns a run into a plain `UpdateRunView` (the step list while it goes, `UpdateOutcomeCard` or the refused card after). The page, opened from the Server screen or from the banner (`showUpdatePage`), only shows the run: leaving never cancels, and Done, Try again (asks again), Check again, Keep waiting and Dismiss call the run. `UpdateBannerLayer` wraps the shell's main window only (never a conversation window or the quick panel): the restart banner while `showsBanner`, "Hermes <version> is ready" after a success it saw, which goes after 6 s or stays under reduced motion. It sits above each destination's own app bar, not under the toolbar: every destination (Chat, Bots, Kanban, Schedules, the Mac pages) draws its own bar, so a banner under "the toolbar" would have to be wired into each of them; one layer above them shows on all, and the page below loses the top inset it would have drawn (`MediaQuery.removePadding`). The banner paints through the window's top inset (status bar, notch or, on a Mac, the title bar that `MacWindowChrome` reports as top padding) and keeps its content below it; on a Mac that strip is a `MacWindowDragArea`. Tapping it opens the Update page unless one is already open. Pages the Server screen and the banner push sit above the shell's providers, so `_carry` and `showUpdatePage` take the care controller, the gateway and update runs and the reply counter along. After a finished or stale update the shell only re-checks Kanban and Schedules (`_detect`) and the care controller re-reads the status; it never calls `AuthController.connect`, which would replace the setup screen and the API client if it failed. `ServerCareController.updating` follows `busy`, so the Mac sidebar caption reads "Updating…" and the Updates row says so. When an update ends, a Server screen or page that owns its check controller asks again with `force`.

**Server care: server check** (`server_check_controller.dart`, `server_check_page.dart`, `widgets/server_check_body.dart`). `AppShell` owns one `ServerCheckController` per connection. It sends `POST /api/ops/doctor` (read-only, explicit profile) once per run, follows `/api/actions/doctor/status` every 1.5 s for at most 3 minutes and parses only the lines after the latest start header; a timeout sends no second run (Keep waiting reads the same one for another 3 minutes), and a lost answer to the POST is followed, never resent: after it only a running action or one with a header the log did not have before the run counts as this run. A doctor already running when a run starts (read first) is followed, not started again; a status or request that finds no route ends the run as unsupported and the controller reports it (`onUnsupported`) so the Tools row goes even with the page closed; a run that ends non-zero with no findings is "stopped", not a report; a clock set backwards counts as the window passed. Output is memory only; `drop()` (sign-out, server change, through `_resetUpdateOnDeparture`), `cover()` (App Lock) and `profileChanged` clear it, and nothing is resumed after the app is killed. The page holds `SecureWindow`, wraps itself in `PrivateSurface` and is removed with its connection like every pushed page (see Pages above the shell); the Tools row opens it, while the store-unreadable headline and the Usage page's Run a check open it with `runOnOpen`. Span `server_care.check` and log `server_care.check_finished` carry the outcome and problem, warning and unknown-line and duration buckets; breadcrumb `server_care.check.started` has no attributes.

**Hands-free strip** (`voice/hands_free_strip_layer.dart`, wired in `app.dart`'s builder). While a call's microphone is open, `HandsFreeStripLayer` puts the Hands-free strip under the platform bar (the window's top inset, which it then removes from the page below) on every page of the main window, pushed pages included, because it wraps the root navigator; the page keeps its state through a `GlobalKey` when the strip comes and goes. It reads `ActiveCallRegistry` and offers End while the call screen is closed. Under App Lock the cover is drawn over it and keeps its own mark. A conversation window and the quick panel are other engines and show none (the OS microphone indicator covers them). The home shell does not own the call: `ChatScreen` hands a call it disposes to `ActiveCallRegistry.release`, which acts only on that call, so the new shell's `initState` (before the old one's `dispose`) is never affected.

**Pages above the shell** (`navigation/connection_pages.dart`, wired in `app.dart`). `_RootRouter` only swaps `home`, so every page pushed on the root navigator (settings screens, and the dialogs, sheets and popup menus above them) would stay on top of the login or setup screen after the connection ends. `PushedRoutes`, a `NavigatorObserver` on the root navigator, keeps the routes above the first one; `ConnectionPageCloser` listens to `AuthController` and, when the connection ends, takes all of them out with `NavigatorState.removeRoute` (top first, no animation) before the frame that builds the new home. A removal is not a pop, so `PopScope(canPop: false)`, a dialog with `barrierDismissible: false`, a route mid-transition and a popup menu (a route on the root navigator) cannot keep a route. A route already popping is left to finish its exit (about 300 ms over the new home): it ignores touches. After the sweep a second one runs after the next frame, because the future of a removed route completes in a microtask before that frame, and code waiting on it may push a route or show a snackbar then. No screen has to opt in. The connection ends when `state` leaves `ready`, or while it is `ready` and `ownerGeneration` moves (sign-out, server change, another account on the same server; an ungated server stays `ready` after sign-out, so the generation is what catches it). The generation is the identity: it never moves on a token refresh (refreshes do not even notify), a retried refresh or a rejected access token, and the app only reconnects (`connect(automatic: true)`) from `connectionError`, where no page is open. The one path that notifies while ready and the account is the same, an expiry that another engine's newer stored pair rescues (`_finishExpiry`), closes nothing and is tested. An ordinary expiry goes through `needsLogin`, so its pages go when that lands. The owner does not move on expiry, so after signing back in as the same account the old `Dio` serves again; that is the same identity. The closer never signs out and never touches `AppShell`, whose update and restart runs end with the shell (`_resetUpdateOnDeparture`); the test with a running update only proves the closer does not touch them. It records only the breadcrumb `nav.connection_pages_closed` with a count. `HandoffNavigationObserver` and `DesktopNavigationHistory` handle `didRemove`. A late callback of a closed page is not stopped by `mounted` guards: the continuation of a removed route's future runs in a microtask while `context.mounted` is still true, and the page is only unmounted at the next frame. What stops a request is the authenticated `Dio` of the old owner, which rejects every request once `ownerGeneration` moved or `protectedRequestsAllowed` is false, and, from the next frame, the disposed controller; a new `Dio` is never reached because pages hold the repository they were given. The conversation windows and the quick panel are native windows that `ConversationWindows.closeAll` closes earlier and asynchronously over the method channel (when `protectedRequestsAllowed` turns false, which includes the start of an expiry), not on the same signals. The one navigator the shell owns besides the root, the compact messenger's list/detail navigator in `ChatScreen` (`_conversationNavigator`), goes with the shell when the state leaves `ready`. Dialogs use the root navigator and are closed. Only an ungated server's sign-out keeps the state `ready`: the shell is then replaced (see below) once the new API client is in place, which takes the nested navigator with it. Until then (the token-clear window, while `protectedRequestsAllowed` is false and the old `Dio` rejects every request) the conversation page and the sheets and menus opened with `useRootNavigator: false` (`showModalBottomSheet`, `showMenu`) on that nested navigator can outlive the closer's sweep; the UI cannot reach that sign-out (`thread_sidebar.dart` offers it only when the server needs auth, as does the Mac `signOut` command), and `connection_page_closer_test.dart` records the closer's own limit with a fake auth. `AppShell` fixes its `_ownerGeneration` at `initState` on purpose: after an owner change it is unauthorized for good, and `_RootRouter` replaces it. It keys the shell by the generation it saw while `protectedRequestsAllowed` was true (`_shellOwner`), so an ungated sign-out, which moves the generation while the state stays `ready`, builds a new shell (new controllers, update and restart runs, gateway and tools state, over the repositories of the new client) once the new client is in place. A key that followed the generation at once would build the shell over the old repositories, which are swapped a moment later (`test/app_shell_owner_test.dart` holds the token clear to cover that window). Because Flutter builds a keyed replacement before it disposes the old state, a dispose in the shell or `ChatScreen` must clear a shared object only if it still holds that state's own value: `ConversationWindows.currentProfile`, `HandoffController.unbind`/`withdraw`, `RepliesInProgress.detach`, `MenuBarExtraLink.disconnect` and `DockMenuController.release` do. An expiry does not move the generation and keeps its shell; the state leaving `ready` resets the key.

**Personality page and the shell** (`lib/src/profiles/soul/soul_screen.dart`; roadmap 4.8, `openspec/changes/profile-soul`). `SoulScreen` is pushed on the root navigator and outlives nothing of the shell: it owns its `SoulController`, reads the repositories once in `initState` and ends with the connection like every pushed page (`ConnectionPageCloser` removes it; `ConnectionGuard` only tells it a frame earlier, and the page then tells a real end from a pause: when the state left ready or the owner or server changed it calls `clear()` and drops its text at once; when only protected requests closed with the state still ready (an expired session another engine may rescue) it calls `pause()`, which keeps the text and baseline, makes the editor read-only, offers no Save or Revert and sends and reads nothing, while the page itself watches `AuthController` for the real end because the guard says it only once; `onRestored` calls `resume()`, which makes the editor editable again with the same text, never sending anything). While paused nothing is read or sent: an unlock or a Close Window Discard that lands then only marks the page stale, and `resume()` reads once for it (never over a newer edit; any read that runs clears the mark); a pause that lands while the read before a save is out sends no PUT and ends in "Couldn't check the server first" with the text kept; the page shows a fixed neutral "The connection is paused" banner, and it is the only banner while the pause lasts (a lost-answer or check banner would offer Check or Try again, which cannot run); that banner returns after the resume. Because the home shell is rebuilt per owner generation, a new shell's `initState` runs before the old one's `dispose`, so the page holds nothing of the shell's: its cleanups (`removeListener`, `dispose`) are for what this instance created. App Lock: it listens to `AppLockController` and `cover()`s the controller when `covered` (locked, or inactive on a phone) turns true, which drops the text, baseline and server text at once and closes any question or sheet the page opened (`popUntil` its own route, answering as Cancel or Keep editing); `uncover()` reads the file again. An unloaded lock counts as covering, so a page opened before the lock read its setting waits for it. The page is wrapped in `PrivateSurface` (a blank surface while the app is inactive or hidden on iOS and Android), and so is the changed-on-the-server sheet (`PrivateSurface(shrinkWrap: true)` inside `showSoulChangedSheet`: its content stays measured but unpainted, because the server's version may hold personality text); the Replace and Discard questions hold only the profile name, no personality text, and are not covered; the page does not hold `SecureWindow`. Leaving (the bar's back, the system back, View > Back) goes through a `PopScope` that asks "Discard changes?" while the text differs from the server's; Revert asks the same; the page offers File > Close Window (asking first, and dropping the text for good since the main window is hidden, not released) only while dirty and in front. The bar passes `shrinkTitle`, and on iOS at 150% text or more Save moves under the editor with Revert (as on a wide window), because the back label and a bar Save would otherwise leave the title no room. The page is bound to the profile it opened for: a switch of the chat's profile behind it changes nothing.
